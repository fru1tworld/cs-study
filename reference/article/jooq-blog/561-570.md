### jOOQ 3.2 출시

jOOQ 3.2 릴리스에서는 두 가지 중요한 서비스 제공자 인터페이스(SPI)가 도입되었습니다:

1. CRUD 작업 동작 주입 - 사전 및 사후 작업 훅을 허용하여 전역 ID 생성기 기능을 가능하게 합니다
2. SQL 렌더링 생명주기 주입 - 임의의 SQL 변환을 지원하며, 특히 공유 스키마 멀티테넌시 패턴 구현에 유용합니다

이번 릴리스에서 코드 생성기가 상당히 개선되었습니다. 전체 세부 사항은 공식 릴리스 노트에서 확인할 수 있습니다.

### jOOQ 라이선싱 및 지원 전략

Data Geekery GmbH는 오픈소스 원칙과 상용 소프트웨어의 이점을 균형 있게 조화시키는 듀얼 라이선싱 접근 방식을 발표했습니다. 이 전략은 무료 및 상용 제품 모두를 통한 창의적 역량 강화에 대한 회사의 철학을 반영합니다.

이 라이선싱 모델에 대한 자세한 설명은 함께 제공되는 블로그 게시물에서 확인할 수 있습니다.

### SQL2jOOQ 도구 개발

GUDU Soft는 Data Geekery와 협력하여 SQL2jOOQ라는 오픈소스 변환 유틸리티를 개발했습니다. GUDU Soft의 SQL 파서를 기반으로 구축된 이 도구는 텍스트 기반 SQL 문자열과 AST를 변환하면서 jOOQ를 출력 방언으로 지원합니다. 이 도구는 레거시 SQL 구현을 jOOQ 프레임워크로 변환하는 개발자들의 마이그레이션 문제를 해결합니다.

### NoSQL 시장 동향

MongoDB의 최근 1억 5천만 달러 벤처 펀딩 라운드는 업계에서 상당한 논의를 불러일으켰습니다. 이 발표는 194개의 추적 시스템 중 MongoDB가 선두적인 비관계형 데이터베이스 관리 시스템으로서의 위상을 강조했습니다.

이 기사는 Oracle과 SQL Server와 같은 기존 관계형 데이터베이스에 대한 경쟁이 비SQL 벤더에게서 오더라도 여전히 가치가 있다고 언급합니다.

## jOOQ 3.2 상용 라이선스 및 지원 제공

> 원문: https://blog.jooq.org/jooq-3-2-offering-commercial-licensing-and-support/

2013년 10월 9일 lukaseder 작성

4년 전, Java 데이터베이스 미들웨어 시장은 JPA를 구현하는 다양한 ORM들이 지배하고 있었습니다. 이 패러다임은 대안들에 의해 거의 도전받지 않았습니다. Java 언어 생태계에서 SQL을 일급 시민으로 만드는 API에 대한 공백이 있었고, jOOQ가 이 공백을 채우기 위해 등장했습니다. jOOQ를 통해 SQL 작성에 많이 관여하는 개발자들은 마침내 Java 언어에서 SQL을 거의 네이티브하게 표현할 수 있는 도구를 갖게 되었으며, Java 6+ 컴파일러의 기능을 활용하여 SQL 문의 구문과 타입 정확성을 검증할 수 있게 되었습니다. 지난 4년 동안 jOOQ는 점점 더 인기를 얻고 성숙해졌습니다. jOOQ는 대규모의 복잡한 데이터베이스에서 운영하는 많은 까다로운 고객들에 의해 사용되고 있습니다. 그 고객들로부터 받은 피드백은 만장일치로 긍정적이었지만, 한 가지 부족한 것이 있었습니다. 그 한 가지 부족한 것은 전문적인 지원, 보증, 그리고 따라서 상용 라이선스였습니다. 새로운 jOOQ 3.2에서는 훌륭한 새 기능들을 도입하는 것 외에도, 우리가 운영하는 방식에서 꽤 많은 것들을 변경하고 있습니다.

jOOQ 3.1 이후, 우리는 이제 jOOQ 3.2를 발표했습니다.

Data Geekery GmbH에서 우리는 오픈 소스를 믿습니다. 하지만 우리는 또한 상용 소프트웨어가 가능하게 하는 창조적인 힘도 믿습니다. 이것이 우리가 다음과 같은 듀얼 라이선스 전략을 구현하기로 선택한 이유입니다:

- 인기 있는 오픈 소스 데이터베이스와 함께 jOOQ를 사용하는 사용자들은 계속해서 Maven Central, GitHub, 또는 jOOQ 웹사이트에서 우리의 고품질, 통합 테스트된 Apache Software License 2.0 라이선스의 무료 오픈 소스 배포판을 얻을 수 있습니다. 동시에, 그들은 jOOQ User Group에서 영어로 제공되는 우리의 무료 커뮤니티 지원을 계속 이용할 수 있습니다.

- 상용 데이터베이스와 함께 jOOQ를 사용하는 사용자들은 우리의 경쟁력 있는 상용 jOOQ 구독 라이선스를 이용할 수 있으며, 이는 상용 데이터베이스 지원뿐만 아니라 영어, 독일어, 프랑스어로 제공되는 전문적인 지원, 릴리스 및 버그 수정에 대한 조기 액세스, 보증, 맞춤 엔지니어링 등을 포함합니다.

우리의 라이선스 모델에는 워크스테이션 라이선스와 상용 데이터베이스 지원 옵션이 포함됩니다.

물론, 오픈 소스 데이터베이스와 함께 jOOQ를 사용하는 고객들도 우리의 전문적인 지원과 서비스를 이용하고 싶다면 상용 라이선스 구독을 구매할 수 있습니다. 다음 FAQ에서 여러분이 가질 수 있는 몇 가지 질문에 답변하겠습니다:

### 왜 워크스테이션 라이선스를 제공하나요?

우리는 jOOQ의 주요 부가 가치가 고객의 개발 라이프사이클에 추가된다고 믿습니다. jOOQ는 개발자들이 JDBC나 다른 문자열 기반 접근 방식을 직접 사용했을 때 필요한 시간의 10%만에 SQL 코드를 작성할 수 있도록 도와줍니다. 동시에, jOOQ와 그 강력한 소스 코드 생성기는 개발 라이프사이클 초기에 코딩 실수를 방지하여 일반적인 SQL 실수의 90%를 예방합니다. 따라서 jOOQ는 개발 도구이며, 런타임에 가장 많은 가치를 추가하는 스토리지 도구인 데이터베이스와는 대조됩니다. 이것이 대부분의 데이터베이스가 서버 라이선스를 제공하는 것과 달리 jOOQ가 워크스테이션 라이선스를 제공하는 이유입니다.

### 왜 완전한 오픈 소스 라이브러리에 대한 지원만 제공하지 않나요?

우리는 모든 것을 오픈 소스로 제공하면서 비싼 지원 구독으로만 돈을 버는 벤더들을 알고 있습니다. 이것은 데이터베이스와 같은 서버 소프트웨어를 제공하는 벤더들에게는 실행 가능한 모델이며, 이 경우 24/7 지원이 매우 중요합니다. 또한 많은 추가적이고 비용이 많이 드는 컨설팅 노력이 필요한 매우 복잡한 소프트웨어를 제공하는 벤더들에게도 실행 가능한 모델입니다. jOOQ는 앞서 언급한 것들 중 어느 것도 아닙니다. 이것은 사용하기 매우 쉬운 미들웨어이며, SQL 자체 위에 거의 복잡성을 추가하지 않기 때문에 컨설팅 비즈니스를 생성하지 않을 것입니다. 우리는 다양한 기존 사용자 및 고객들과 함께 우리의 결정을 검토했으며, 종속적인 데이터베이스 라이선스 모델을 기반으로 하는 듀얼 라이선스 모델로 가장 많은 가치를 추가할 수 있다고 확고히 믿습니다. 결국, jOOQ 라이선스에 약간의 돈을 지출하면 DB2, Oracle, SQL Server, 또는 Sybase와 같은 강력한 데이터베이스를 사용하는 개발 라이프사이클에서 고객들에게 엄청난 양의 돈을 절약해 줄 것입니다.

### 왜 Apache License를 고수하나요?

Apache License는 지난 4년 동안 우리에게 잘 맞았습니다. 이것은 매우 자유로우면서도 동시에 우리의 상표를 보호합니다. 이것은 우리가 성장하고 많은 고품질 커뮤니티 피드백과 기여를 얻을 수 있게 해준 라이선스입니다. 우리는 *GPL 경로를 따르는 다른 듀얼 라이선스 회사들을 따르고 싶지 않습니다. 왜냐하면 우리는 듀얼 라이선스 *GPL 소프트웨어가 장기적으로 오픈 소스 소프트웨어의 정신에 진실하지 않다고 믿기 때문입니다. Apache License를 유지함으로써 우리는 오픈 소스에 대한 깊은 헌신을 표현하고자 합니다.

### 기여자 저작권은 어떻게 되나요?

우리는 저작권을 진지하게 다룹니다. 이것이 우리가 주요 기여자들에게 모든 저작권을 우리에게 양도하는 동의서에 서명하도록 한 이유입니다. 저작권을 정리해야 하지만, 우리는 여전히 코드나 문서를 공유해 준 기여자들에게 저작권을 공개적으로 귀속시키고자 합니다. 물론, 우리 커뮤니티의 모든 미래 기여도 환영합니다! 기여자로서 우리의 듀얼 라이선스에 의해 당신의 저작권이 도전받거나 침해받는다고 느끼신다면, 직접 저희에게 연락해 주세요.

### jOOQ Console은 어떻게 되었나요?

jOOQ Console 3.1은 Maven Central에서 jOOQ 3.2 사용자들에게 계속 제공되지만, jOOQ Console 개발은 현재 형태로 중단되었습니다. 이것은 Data Geekery가 가까운 미래에 개발할 새로운 상용 프로파일러 소프트웨어를 위한 자리를 만들 것입니다. 기대해 주세요.

### 왜 이것을 하나요?

우리는 jOOQ에 대한 헌신을 보여주고 싶기 때문입니다. jOOQ는 단순한 라이브러리 이상입니다. 이것은 더 나은 Java와 SQL 통합에 대한 비전입니다. 이것은 Java 생태계의 다양한 분야에서의 혁신입니다. 우리는 다음을 원합니다:

- Java와 SQL을 모두 사랑하지만 과거에 적절한 도구를 제공받지 못했던 사람들을 지원합니다.
- jOOQ와 같은 소프트웨어의 언어적 측면을 형식화함으로써 Java에서 내부 도메인 특화 언어의 통합을 더욱 발전시킵니다. jOOQ만을 위한 것이 아닙니다.
- 네이티브 Scala API - 그리고 가능하면 코어까지 - 제공함으로써 고품질 SQL 통합을 Scala 생태계로 확장합니다.
- 더 많은 고품질 개발 도구를 제공하기 위해 jOOQ Console을 더욱 개선합니다.
- 블로그와 소스 코드를 통해 고객들에게 우리의 SQL 지식을 제공합니다.

위의 계획들을 구현하기 위해, 우리는 jOOQ로부터 비즈니스를 만들어야 합니다. 그리고 우리는 이 비즈니스가 우리와 고객 모두에게 매우 흥미로울 것이라고 믿습니다. 함께, jOOQ 생태계로서, 우리는 더 나은 Java/SQL 세계를 만들 것입니다! jOOQ 3.2로 시작합시다!

## SQL 트릭: row_number()가 SELECT에 대한 것이면 dense_rank()는 SELECT DISTINCT에 대한 것이다

> 원문: https://blog.jooq.org/sql-trick-row_number-is-to-select-what-dense_rank-is-to-select-distinct/

2013년 10월 9일 lukaseder 작성

SQL:2003 표준 순위 함수들은 훌륭한 동반자이며 때때로 유용한 도구입니다. 거의 모든 데이터베이스에서 지원되는 함수들은 다음과 같습니다:

* ROW_NUMBER(): 파티션 내에서 중복 여부와 관계없이 모든 행에 대해 새로운 행 번호를 생성합니다.
* RANK(): 파티션 내에서 각각의 고유한 행에 대해 새로운 행 번호를 생성하며, 중복 그룹 사이에 간격을 남깁니다.
* DENSE_RANK(): 파티션 내에서 각각의 고유한 행에 대해 새로운 행 번호를 생성하며, 중복 그룹 사이에 간격을 남기지 않습니다.

항상 그렇듯이, 위의 내용은 예제를 통해 훨씬 이해하기 쉽습니다. 8개의 레코드가 있고 그 중 일부가 중복인 테이블을 포함하는 다음 PostgreSQL 스키마를 가정해 봅시다:

```sql
CREATE TABLE t AS
SELECT 'a' v UNION ALL
SELECT 'a'   UNION ALL
SELECT 'a'   UNION ALL
SELECT 'b'   UNION ALL
SELECT 'c'   UNION ALL
SELECT 'c'   UNION ALL
SELECT 'd'   UNION ALL
SELECT 'e'
```

이제 앞서 언급한 세 가지 순위 함수와 함께 각 값을 선택해 봅시다. 재미를 위해 SQL 표준 WINDOW 절을 사용해 보겠습니다! 야호, 반복적인 SQL 코드 15자를 절약했습니다. WINDOW 절은 PostgreSQL과 Sybase SQL Anywhere를 제외하고는 거의 구현되어 있지 않다는 점에 주의하세요...

```sql
SELECT
  v,
  ROW_NUMBER() OVER (window) row_number,
  RANK()       OVER (window) rank,
  DENSE_RANK() OVER (window) dense_rank
FROM t
WINDOW window AS (ORDER BY v)
ORDER BY v
```

위 쿼리의 결과는 다음과 같습니다:

```
+---+------------+------+------------+
| V | ROW_NUMBER | RANK | DENSE_RANK |
+---+------------+------+------------+
| a |          1 |    1 |          1 |
| a |          2 |    1 |          1 |
| a |          3 |    1 |          1 |
| b |          4 |    4 |          2 |
| c |          5 |    5 |          3 |
| c |          6 |    5 |          3 |
| d |          7 |    7 |          4 |
| e |          8 |    8 |          5 |
+---+------------+------+------------+
```

(이 SQLFiddle도 참고하세요)

#### SELECT DISTINCT를 작성할 때 DENSE_RANK()가 어떻게 도움이 될 수 있는가

의심할 여지 없이, `ROW_NUMBER()`는 위의 순위 함수들 중에서 가장 유용합니다. 특히 DB2, Oracle(11g 이하), Sybase SQL Anywhere(버전 12 이전), SQL Server(2008 이하)에서 LIMIT .. OFFSET 절을 에뮬레이션해야 할 때 그렇습니다. jOOQ가 다양한 SQL 방언에서 이 SQL 절을 어떻게 에뮬레이션하는지 더 읽어보세요.

하지만 `ROW_NUMBER()`를 `DISTINCT`나 `UNION`과 함께 사용할 때 미묘한 문제가 있습니다. `ROW_NUMBER`는 파티션 내에서 항상 고유한 값을 생성하기 때문에 데이터베이스가 중복을 제거하는 것을 방해합니다. 위의 예제에서 `T.V`에 대한 중복 값은 의도적으로 추가되었습니다. 어떻게 하면 먼저 중복을 제거하고 그 다음에만 행 번호를 매길 수 있을까요? 분명히, 더 이상 `ROW_NUMBER()`를 사용할 수 없습니다. 다음 쿼리는:

```sql
SELECT DISTINCT
  v,
  ROW_NUMBER() OVER (window) row_number
FROM t
WINDOW window AS (ORDER BY v)
ORDER BY v, row_number
```

... 다음을 출력합니다

```
+---+------------+
| V | ROW_NUMBER |
+---+------------+
| a |          1 |
| a |          2 |
| a |          3 |
| b |          4 |
| c |          5 |
| c |          6 |
| d |          7 |
| e |          8 |
+---+------------+
```

(이 SQLFiddle도 참고하세요)

하지만 대신 `DENSE_RANK()`를 사용할 수 있습니다! `DENSE_RANK()`를 사용하면 중복 레코드가 동일한 순위를 받는 방식으로 순위가 적용됩니다. 그리고 순위 사이에 간격이 없습니다. 따라서:

```sql
SELECT DISTINCT
  v,
  DENSE_RANK() OVER (window) row_number
FROM t
WINDOW window AS (ORDER BY v)
ORDER BY v, row_number
```

... 이것은 다음을 출력합니다:

```
+---+------------+
| V | ROW_NUMBER |
+---+------------+
| a |          1 |
| b |          2 |
| c |          3 |
| d |          4 |
| e |          5 |
+---+------------+
```

(이 SQLFiddle도 참고하세요)

#### 따라서 기억하세요...

> 따라서 기억하세요: `ROW_NUMBER()`가 `SELECT`에 대한 것이면 `DENSE_RANK()`는 `SELECT DISTINCT`에 대한 것입니다

#### 주의사항

위의 내용이 참이 되려면, `SELECT DISTINCT` 절의 모든 표현식이 `DENSE_RANK()`의 `OVER(ORDER BY ...)` 절에 사용되어야 합니다. 예를 들어:

```sql
SELECT DISTINCT
  v1,
  v2,
  v3,
  DENSE_RANK() OVER (window) row_number
FROM t
WINDOW window AS (ORDER BY v1, v2, v3)
```

`v1, v2, v3` 중 어느 것이라도 다른 순위 함수나 집계 함수, 또는 비결정적 표현식 등이라면, 위의 트릭은 작동하지 않습니다. 하지만 고유한 행에 행 번호가 필요한 드문 코너 케이스 쿼리를 위해 소매 속에 간직해 둘 만한 좋은 트릭입니다. 그리고 이 트릭에 대해 항상 생각하고 싶지 않다면, 우리는 이것을 jOOQ에 내장해 두었다는 점을 알아두세요. 왜냐하면 우리는 여러분이 SQL 표준화가 아닌 비즈니스 로직에 대해 걱정해야 한다고 생각하기 때문입니다.

## Java 자동 언박싱 함정. 조심하라!

> 원문: https://blog.jooq.org/java-auto-unboxing-gotcha-beware/

이 글은 자동 언박싱과 관련된 Java 삼항 연산자의 놀라운 동작을 살펴봅니다. 다음 코드를 작성하면:

```java
Object o = true ? new Integer(1) : new Double(2.0);
System.out.println(o);
```

출력 결과는 `1`이 아닌 `1.0`입니다. 이는 직관에 반하는 결과입니다.

### 근본 원인

Java 언어 명세(JLS) 15.25절에 따르면, "이진 숫자 승격(binary numeric promotion)은 암묵적으로 언박싱 변환을 수행할 수 있습니다." 삼항 연산자가 서로 다른 숫자 래퍼 타입의 분기를 평가할 때, 두 피연산자를 원시 타입 동등물로 언박싱하고, 승격된 타입으로 결과를 다시 박싱하는 숫자 승격 규칙을 적용합니다.

이 경우:
- `Integer(1)`은 `int`로 언박싱됩니다
- `Double(2.0)`은 `double`로 언박싱됩니다
- 이진 승격이 `int`를 `double`로 변환합니다
- 결과는 `Double(1.0)`이 됩니다

### 치명적인 위험: NullPointerException

이 글은 `null` 값이 관련될 때 이 동작이 숨겨진 위험을 만든다고 경고합니다:

```java
Integer i = new Integer(1);
if (i.equals(1))
    i = null;
Double d = new Double(2.0);
Object o = true ? i : d; // NullPointerException!
```

`null` 값에 대한 자동 언박싱 시도는 예외를 발생시킵니다.

### 권장 해결책

`Object`로 명시적 캐스팅하여 암묵적 숫자 승격을 방지하세요:

```java
Object o1 = true ? (Object) new Integer(1) : new Double(2.0);
System.out.println(o1); // 출력: 1
```

이렇게 하면 이진 숫자 승격을 트리거하지 않고 타입 일관성을 보장합니다.

### 핵심 요점

이 함정을 발견한 Paul Miner에게 감사를 표합니다. 이 글은 JPL의 코딩 표준(R40)을 참조하는데, 복잡한 승격 규칙 때문에 조건식에서 하나의 일관된 결과 타입을 사용할 것을 권장합니다.

## MongoDB의 성공에 대하여. 또는 냉소주의가 정신을 죽이지 않게 하라

> 원문: https://blog.jooq.org/on-mongodbs-success-or-do-not-let-cynicism-kill-your-spirit/

MongoDB가 1억 5천만 달러의 벤처 펀딩 라운드를 성공적으로 마쳤다. MongoDB는 성공했다!

그런데 Reddit에서 이 뉴스에 대한 냉소적인 댓글들을 보았다. 사람들은 10gen(MongoDB의 모회사)이 기술적으로 그다지 뛰어나지 않은 제품으로 돈을 벌고 있다고 비판했고, 창업자들이 단지 "부자가 되고 있을 뿐"이라고 암시했다.

이런 반응은 실망스럽다. 누군가가 두각을 나타내고 성공하면 질투하는 것일까?

이러한 냉소적인 논의에 빠져드는 것은 가치가 없다. MongoDB의 기업 가치는 진정한 시장 수요와 기대를 반영한다. 당시 DB-Engines.com 데이터에 따르면, MongoDB는 상위 DBMS 인기 순위에 등장한 유일한 NoSQL 데이터베이스 벤더였다.

나는 jOOQ로 비슷한 성공을 거두기를 희망하고 있다.

10gen이 이 이정표를 달성한 것을 축하한다. 플랫폼을 둘러싼 기술적 논쟁과 관계없이, 이것은 정당한 비즈니스 성과다.

냉소주의가 여러분의 기업가 정신을 죽이지 않게 하라. 성공은 종종 질투심 어린 비판이나 무시하는 비판을 끌어들이지만, 그러한 부정적인 반응이 야심찬 프로젝트를 낙담시켜서는 안 된다.

## SQL로의 조기 복귀

> 원문: https://blog.jooq.org/the-premature-return-to-sql/

게시일: 2013년 10월 2일
저자: Lukas Eder
블로그: Java, SQL and jOOQ

---

온라인 커뮤니티에서 NoSQL 주제는 (ORM 주제와 마찬가지로) 감정을 자극하는 것이 보장되어 있습니다. 많은 감정이 이념적 또는 마케팅적 이유로 양쪽 진영의 전도사들에 의해 자극됩니다. 다음은 열정적인 NoSQL 및 폴리글랏 퍼시스턴스 전도사인 Alex Popescu의 흥미로운 게시물입니다. 그는 최근 SQL로 복귀하는 트렌드가 시기상조라고 주장합니다:

- http://nosql.mypopescu.com/post/62403847766/the-premature-return-to-sql

이 게시물은 SQL Performance Explained의 저자인 Markus Winand의 똑같이 흥미로운 반응을 불러일으켰습니다:

- http://use-the-index-luke.com/blog/2013-10/mysql-is-to-sql-like-mongodb-to-nosql

사람들이 얼마나 자주 "트렌드"라는 관점에서 생각하는지는 정말 흥미롭습니다. 새로운 패러다임을 도입하여 우리가 이전에 가지고 있던 모든 것을 구식으로 만든다는 그런 트렌드 말입니다. 저는 이것들이 트렌드가 아니라 실험이라고 믿습니다. 저는 이전에 NoSQL 벤더들이 DBA를 끝장낸다고 약속할 때 경계해야 한다고 블로그에 쓴 적이 있습니다. 아주 소수의 "새로운" 솔루션이나 패러다임만이 그들의 선조를 완전히 대체하거나 치환한 적이 있습니다. 또는 아이작 뉴턴의 말을 빌리자면:

> "내가 더 멀리 볼 수 있었다면 그것은 거인의 어깨 위에 서 있었기 때문이다."

우리는 "SQL로 복귀"하는 것이 아니며, 그러한 복귀가 "시기상조"인 것도 아닙니다. 네, 늙은 코끼리에게 새로운 재주를 가르치는 혁신적인 사상가들이 있고, 그것은 좋은 일입니다. 그러한 혁신적인 사상가들이 케이크의 한 조각을 얻고 그들의 발명으로 돈을 버는 것도 좋은 일입니다.

대형 데이터베이스 벤더들이 그다지 혁신적이지 않다는 것도 사실입니다. 하지만 그들은 그럴 필요가 없습니다. 그들의 자산은 신뢰성, 예측 가능성, 안정성입니다. Oracle SQL은 15년 후에도 여전히 모든 오래된 레거시를 지원할 것이며, 이것이 은행과 보험 회사에 안전한 선택이 되는 이유입니다. NoSQL이나 NewSQL 기능이 혁신적이면서 신뢰할 수 있다고 입증되면, Oracle 등은 분명히 그것을 채택하여 SQL에 통합할 것입니다. 현명한 NoSQL 벤더들은 따라서 이미 그들의 출구를 준비하고 있습니다.

이것은 물론 데이터베이스 세계 밖에서도 일어납니다:

- Scala는 혁신적이며 Java에 기여합니다 (Java 5의 제네릭, Java 8의 람다).
- 오픈 소스 개발자들 (예: JAX-RS 개발자들)은 혁신적이며 JEE에 기여합니다.
- PostgreSQL은 혁신적이며 다른 SQL 방언과 궁극적으로 SQL 표준에 기여합니다.
- Instagram은 혁신적이었으며 Facebook에 기여했습니다.
- jOOQ는 혁신적이며 JDBC와 JPA에 기여합니다 (궁극적으로, 희망컨대).

SQL은 안전한 선택이며 여기에 계속 남아 있을 것입니다.

## 왜 RDBMS가 필요한가?

> 원문: https://blog.jooq.org/why-do-we-need-rdbms/

Quora에 이런 질문이 올라왔습니다: "왜 텍스트 파일을 사용하면 안 되나요? 단순한 텍스트 파일로는 할 수 없고 RDBMS만 할 수 있는 것이 무엇인가요? 또는, 여러 개의 텍스트 파일을 사용해서 서로 다른 테이블들을 표현하면 안 되나요?"

이에 대해 두 가지 방식으로 답변하겠습니다.

### 짧은 이야기 (유머러스한 비유)

어떤 사람들은 열쇠, 지갑, 화장품, 편지, 연필, 또 다른 화장품, 동전, 그리고 온갖 잡동사니들을 하나의 큰 가방에 쑤셔넣습니다. 그리고 기차를 잡으러 갈 때 물건을 찾느라 몇 시간을 허비합니다. 심지어 그 물건이 다른 가방에 있을 수도 있죠. 이것이 바로 텍스트 파일입니다.

저는 체계적인 정리를 선호합니다: "제 색인에 따르면: 지갑은 뒷주머니에, 열쇠는 오른쪽 앞주머니에, 휴대폰은 왼쪽 앞주머니에, 안경은 코 위에." 이러한 구조가 바로 RDBMS입니다.

### 긴 이야기 (역사적 맥락)

하나의 원동력이 RDBMS를 경쟁하는 다른 저장 모델들보다 앞서게 만들었습니다: 바로 관계 대수(relational algebra)입니다. 이것은 주로 에드거 F. 코드(Edgar F. Codd)에 의해 설계되었으며, 그는 당대의 뛰어난 컴퓨터 과학자였습니다.

RDBMS 구현체들은 데이터 관리, 데이터 구조, 물리적 모델, 트랜잭션, 쿼리 모델, 강력한 쿼리 언어(SQL, jOOQ, JPQL, LINQ to SQL 등), 참조 무결성, 제약 조건 관리를 "코드의 12가지 규칙(Codd's 12 rules)"에 기반하여 처리합니다.

관계형 데이터 모델은 거의 모든 비즈니스 규칙을 쉽게 모델링할 수 있습니다. 물론 커스텀 데이터 관리 시스템을 만드는 것도 가능하지만, 뛰어난 컴퓨터 과학자들이 고안한 확립된 규칙들을 따르는 검증된 RDBMS 시스템을 사용하는 것이 일반적으로 더 실용적입니다.
