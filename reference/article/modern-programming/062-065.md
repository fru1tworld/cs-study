### 7장 메모리 성능 도구

프로그램의 성능 특성, 캐시·메모리 사용을 이해하도록 돕는 도구는 다양하다. 최신 프로세서는 성능 모니터링 하드웨어를 제공하고, 정확히 측정하기 어려운 이벤트는 시뮬레이션으로 보완한다. 여기서는 리눅스에서 흔히 쓰이는 도구 몇 가지를 소개한다.

#### 7.1 메모리 연산 프로파일링

메모리 연산 프로파일링은 하드웨어의 협조가 필요하다. 소프트웨어만으로도 일부 정보를 모을 수 있지만 성기거나 시뮬레이션에 불과하다. 리눅스에서 성능 모니터링 하드웨어에 접근하는 대표 도구가 **oprofile**이다 — 시스템 전체를 대상으로 한 통계적 프로파일링을 쉬운 인터페이스로 제공한다(pfmon 같은 대안도 개발 중).

oprofile의 인터페이스는 단순하지만 상당히 저수준이다. 사용자는 프로세서가 기록할 수 있는 이벤트 중에서 골라야 하고, 이 이벤트들은 프로세서마다 다르며 해석에도 프로세서에 대한 상세한 지식이 필요하다. 절대값 하나만 봐서는 "얼마가 높은 수치인지" 판단하기 어렵다는 문제도 있다 — 그래서 흔히 두 카운터의 **비율**을 보는 방식을 쓴다(예: 클럭 사이클 대비 명령어 수).

**CPI(사이클/명령어) 측정**: `CPU_CLK_UNHALTED`(클럭 사이클)와 `INST_RETIRED`(완료된 명령어 수)의 비율을 랜덤 "Follow" 테스트의 작업 집합 크기별로 측정하면(그림 7.1), 리스트 원소당 사이클 측정과 비슷한 그림이 나온다 — 작은 작업 집합에서는 비율이 1.0 이하, L1d를 넘어서면 3.0 가까이, L2까지 넘어서면 20 이상으로 뛴다.

**캐시 미스 이벤트**: Core 2에서 주목할 이벤트는 `L1D_REPL`, `DTLB_MISSES`, `L2_LINES_IN`(하드웨어 프리페칭이 아닌 명령어에 의한 미스만 따로 셀 수도 있음)이다. 랜덤 Follow 테스트(그림 7.2)에서는 L1d 미스율이 32KB 부근에서 치솟기 시작하고(64KB까지는 하드웨어 프리페칭 덕에 1%로 유지되다가 그 이후 급증), L2 미스율은 L2 소진 시점(2^21바이트)부터 오르며, L2 디맨드 미스(하드웨어 프리페처가 못 채운 미스)가 0이 아니라는 점이 랜덤 접근에서 프리페칭이 완벽할 수 없음을 보여준다. 반면 순차 접근(그림 7.3)에서는 L2 디맨드 미스가 사실상 0이다 — 거의 모든 L2 미스가 프리페처에 의한 것이고, L1d·L2 미스율이 같다는 것은 L1d 미스가 지연 없이 L2에서 처리된다는, 사실상 이상적인 상황이다. 네 번째 지표인 DTLB 미스율은 랜덤 접근에서 상당한 지연 요인이 되지만(L2 미스보다 먼저 시작됨), 순차 접근에서는 거의 0이다.

6.2.1절의 행렬 곱셈 예제로 돌아가면, `SSE_HIT_PRE`, `SSE_PRE_MISS`, `LOAD_PRE_EXEC` 카운터로 소프트웨어 프리페칭의 효율을 볼 수 있다. 실제 측정에서 유효 NTA 프리페치 비율은 2.84%, 지연 NTA 프리페치 비율은 2.65%로 나왔는데 — 유효(제때 쓰인) 비율이 낮다는 것은 이미 로드되어 있던 캐시 라인에 불필요한 프리페치 명령을 실행해 디코딩·조회 시간만 낭비했다는 뜻이고, 지연 비율은 프리페치가 필요한 시점보다 늦게 도착했다는 뜻이다. 결국 5.5%만 유효했다는 것은 이 코드에 개선 여지(불필요한 프리페치 제거, 하드웨어 특성에 맞춘 프리페치 타이밍 조정)가 있음을 알려준다. `opannotate` 도구로 소스·어셈블리 코드에 이벤트가 어디서 발생했는지 표시할 수 있다(다만 oprofile은 확률적 샘플링이라 N번째 이벤트마다 기록하므로 일부 핫스팟이 누락될 수 있고, 비순차 실행 탓에 명령어 포인터가 정확하지 않을 수도 있다).

**페이지 폴트**: 하드웨어 지원 없이도 측정 가능한 이벤트다. OS가 페이지 폴트를 해결하며 집계하는데, **마이너 폴트**(익명 페이지, COW 페이지, 이미 메모리 어딘가에 있는 페이지)와 **메이저 폴트**(파일 백업이나 스왑에서 실제 디스크 접근이 필요)로 나뉜다. 둘 다 결코 저렴하지 않다(커널 진입, 새 페이지 확보, 초기화/데이터 채움, 페이지 테이블 수정, 필요시 다른 태스크와의 동기화가 필요). `time` 도구(셸 내장이 아닌 실제 `/usr/bin/time`)로 메이저·마이너 폴트 수를 바로 확인할 수 있고, 내부적으로는 `getrusage(2)`(`ru_minflt`, `ru_majflt`)를 쓰며 `/proc/<PID>/stat`의 10~14번째 필드로도 조회할 수 있다. 프로그램 시작 단계가 특히 페이지 폴트에 민감하다(사용하는 페이지마다 폴트가 발생하므로 GUI 앱의 체감 시작 시간에 큰 영향).

#### 7.2 CPU 캐시 시뮬레이션

프로그래머는 절대·상대 주소 값을 직접 다루지 않으므로, 실제 프로그램의 캐시 사용 양상을 감으로 파악하기 어렵다. oprofile 같은 CPU 레벨 프로파일러는 실제 하드웨어에 대응하는 데이터를 빠르게 모을 수 있지만, 세밀한 데이터가 필요하거나(스레드를 너무 자주 인터럽트해야 함) 여러 종류의 프로세서에서 동작을 봐야 할 때(그림 3.8의 24개 조합처럼 실제로 존재하지 않는 머신 구성도 포함)는 한계가 있다.

이런 경우를 위한 도구가 **cachegrind**다 — 원래 메모리 처리 문제를 점검하려고 만든 **valgrind** 프레임워크 위에서 프로그램 실행을 시뮬레이션하며 모든 메모리 주소 사용을 가로채, 주어진 크기·라인 크기·연관도의 L1i·L1d·L2 캐시 동작을 시뮬레이션한다.

```
valgrind --tool=cachegrind command arg
```

기본으로는 실행 중인 프로세서의 실제 캐시 구성을 시뮬레이션하며, 종료 시 표준 오류로 전체 명령어·메모리 참조 수, L1i/L1d/L2의 미스 수·미스율 등을 요약해 보여준다(그림 7.5 예시 출력). `--I1`, `--D1`, `--L2` 파라미터로 실제 프로세서와 무관한 임의의 캐시 구성(예: `--L2=8388608,8,64`로 8MB, 8-way, 64바이트 라인)을 시뮬레이션할 수도 있어, 다른 캐시 구성에서 프로그램이 어떻게 동작할지 실험해 볼 수 있다.

프로세스 종료 시 `cachegrind.out.XXXXX` 파일에 함수·소스 파일별 상세 캐시 사용 정보가 저장되고, `cg_annotate` 도구로 이를 볼 수 있다(디버그 정보가 있으면 함수 단위 매칭이 더 정확). 출력(그림 7.6)은 함수별 캐시 히트/미스 수를 보여줘 L2 미스가 큰 곳부터 L1i/L1d 미스 순으로 최적화 우선순위를 정하는 데 쓸 수 있고, 소스 파일명을 주면 줄 단위 주석까지 가능하다.

다만 cachegrind는 어디까지나 **시뮬레이터**임을 유의해야 한다 — 실제 프로세서의 캐시 구현과 다를 수 있다(예: cachegrind는 LRU 축출을 시뮬레이션하지만 실제로 높은 연관도 캐시에서는 LRU가 너무 비싸 다른 정책을 쓸 수 있음). 또한 컨텍스트 스위치·시스템 콜로 인한 L1i/L1d 플러시나 L2 오염을 반영하지 않으므로, 시뮬레이션된 전체 캐시 미스 수는 실제보다 낮게 나온다. 그럼에도 프로그램의 메모리 사용 패턴과 문제점을 배우기에 좋은 도구다.

#### 7.3 메모리 사용량 측정

프로그램이 얼마나 많은 메모리를 어디서 할당하는지 아는 것이 메모리 사용 최적화의 첫걸음이다. 재컴파일이나 코드 수정 없이도 쓸 수 있는 도구들이 있다.

**massif**(valgrind 기반)는 컴파일러가 자동 생성하는 디버그 정보만 있으면 시간에 따른 누적 메모리 사용 개요를 보여준다:

```
valgrind --tool=massif command arg
```

할당·해제 함수 호출을 인식해 호출 지점·타임스탬프와 함께 기록하고, 프로그램 전체와 호출 지점별 누적 크기에 반영한다. 종료 시 `massif.XXXXX.txt`(요약)와 `massif.XXXXX.ps`(호출 지점별 색으로 구분된 시간축 그래프, 그림 7.7)를 생성한다. 스택 사용량도 기록할 수 있지만(일부 상황에서는 스택 경계를 알 수 없어 부정확할 수 있어 `--stacks=no`로 끌 수 있음), 자체 메모리 할당기를 쓰거나 시스템 할당 함수를 감싸는 래퍼를 쓰는 프로그램은 `--alloc-fn=xmalloc` 같은 옵션으로 추가 할당 함수를 알려줘야 정확히 잡힌다.

그래프 해석: 같은 호출 지점에서 오랫동안 완만한 기울기로 계속 늘어나는 영역이 보인다면(원문 예시에서 800ms~1,800ms 구간) 상대적으로 작은 할당이 대량으로 일어난다는 뜻으로, GNU C 라이브러리의 **obstack**(큰 블록을 시스템 할당기에서 받아와 순차적으로 나눠주는 할당기, 완전한 malloc 대체는 아니고 해제 능력이 제한적) 같은 벌크 할당 기법을 검토할 후보다.

**memusage**(GNU C 라이브러리의 일부, massif보다 단순하지만 더 오래된 도구)는 힙(옵션으로 `mmap` 포함)과 스택의 총 메모리 사용만 기록하며, 실제 실행 코드에 직접 계측 코드를 심으므로(시뮬레이션이 아님) massif보다 훨씬 빠르다. `-p IMGFILE`로 PNG 그래프를 만들고, 할당 크기별 히스토그램도 표준 오류로 출력한다. `gcc`의 컴파일 단계처럼 드라이버 프로그램이 실행하는 서브프로세스를 관찰해야 할 때는 `-n NAME`으로 관찰 대상 프로그램 이름을 지정한다.

**메모리 레이아웃과 캐시의 관계**: 효율적인 동적 메모리 할당의 핵심은 **선형 할당**과 사용 영역의 **조밀함**이다 — 프리페칭 효율과 캐시 미스 감소로 직결되기 때문이다. 임의 크기 데이터를 처리하려고 연결 리스트로 하나씩 할당하면(단일 연결 리스트라면 오버헤드는 포인터 하나로 작더라도) 순차 할당이 메모리에서도 순차 배치된다는 보장이 없다(할당기 내부에서 뒤에서 앞으로 반환하거나, 청크가 소진돼 다른 영역에서 새로 시작하거나, 크기별로 다른 풀을 쓰거나, 멀티스레드 할당이 서로 뒤섞이는 등의 이유). 나중에 처리할 데이터를 미리 채워 넣어야 한다면 연결 리스트 방식은 피하고, 앞서 언급한 obstack 같은 별도 메모리 관리 계층을 써야 한다.

또한 malloc 구현이 만드는 관리용 헤더·패딩도 무시할 수 없다 — 예컨대 각 블록마다 최소 2워드 헤더(32비트 8바이트, 64비트 16바이트)가 붙고 블록 크기도 특정 배수로 반올림되므로, 작은 블록을 많이 할당하면 헤더·패딩이 실제 데이터 사이사이에 끼어들어 프로세서의 순차 프리페치 효율을 그만큼(예시에서는 최대 50%) 갉아먹을 수 있다. 이는 프로그래머가 할당을 직접 통제할 때만 피할 수 있는 비용이다.

#### 7.4 분기 예측 개선

6.2.2절에서 L1i 활용을 위한 두 기법(`__builtin_expect` 기반 정적 예측, PGO/블록 재배치)을 봤다. 여기서는 그 메모리 사용 측면의 개선을 다룬다.

`likely`/`unlikely` 매크로는 쓰기 간단하지만, 프로그래머가 실수로 반대로 표시하기 쉽고 oprofile로도 이런 오류를 잡아내기 어렵다는 문제가 있다. 부록 A.2에 소개된 기법은 이 매크로를 런타임에 실제로 예측이 맞았는지 능동적으로 계측하는 대안 정의로 바꿔, 프로그래머가 직접 검토·조정할 수 있게 해준다.

**PGO**(Profile-Guided Optimization)는 gcc에서 세 단계로 진행된다: (1) 모든 소스 파일을 `-fprofile-generate`로 컴파일해(더 크고 느리지만 분기 실행 여부를 기록하는) 바이너리를 만들고 대표 워크로드로 여러 번 실행해 `.gcda` 파일들을 누적시킨다, (2) 이 데이터를 바탕으로 `-fprofile-use`로 재컴파일한다(소스 파일 위치를 옮기면 안 되고, 공백·주석 외의 변경은 데이터 무효화로 이어짐). 대표 테스트 워크로드 선정이 관건이다 — 실사용 패턴과 다르면 최적화가 오히려 역효과를 낼 수 있어, 사용 시나리오가 다양한 라이브러리에는 PGO보다 정적 `__builtin_expect`가 대체로 더 적합하다. `.gcno`/`.gcda`는 `gcov`(커버리지 분석 도구, 파일 포맷은 PGO와 동일)로도 조회할 수 있다.

#### 7.5 페이지 폴트 최적화

리눅스처럼 데맨드 페이징을 지원하는 OS에서 `mmap` 호출은 페이지 테이블만 수정할 뿐 실제 메모리 할당은 첫 접근(읽기·쓰기·실행) 시 페이지 폴트를 통해 이뤄진다. 이 해결 과정은 절대 저렴하지 않고, 프로세스가 쓰는 모든 페이지마다 한 번씩 발생한다.

저자가 valgrind 기반으로 만든 **pagein** 도구는 페이지 폴트가 *왜*, 어떤 순서로 일어나는지 `pagein.<PID>` 파일에 기록한다(주소, 코드/데이터 구분, 첫 폴트 이후 경과 사이클, 가능하면 심볼명). 이 정보로 프로그램의 어떤 코드 시퀀스를 같은 페이지에 인접 배치해야 폴트를 줄이거나 늦출 수 있는지 파악할 수 있다. 정확한 최적 레이아웃을 찾는 것은 시행착오가 필요한 번거로운 과정이지만, 오브젝트 파일 단위의 호출 관계 분석이나 gcc의 `-finstrument-functions`(`__cyg_profile_func_enter`/`exit` 훅)를 이용한 실행 추적으로 근사할 수 있다 — 실제로 함수 재배치만으로 시작 비용을 5% 줄인 사례가 보고된 바 있다(TLB 미스 감소 효과도 있어, 가상화 환경에서는 TLB 미스 비용이 더 크므로 더욱 중요해진다).

리눅스 커널이 제공하는 두 가지 추가 메커니즘:

- **`MAP_POPULATE`** 플래그를 `mmap`에 주면 페이지 테이블 수정뿐 아니라 매핑된 영역 전체를 미리 폴트시킨다. 매핑 즉시 전부 쓰인다면 유리하지만, 매핑한 페이지 상당수가 당분간(또는 영원히) 쓰이지 않는다면 낭비다. 세분성이 너무 거칠다는 한계도 있다.
- **`posix_madvise`의 `POSIX_MADV_WILLNEED`** 힌트는 더 세밀하게(개별 페이지·페이지 범위 단위) 미리 폴트시킬 것을 커널에 제안한다(커널이 무시해도 됨) — 실제로는 쓰이지 않는 데이터가 많은 메모리 매핑 파일에서 `MAP_POPULATE`보다 유리할 수 있다.

**대용량 페이지(huge page)**: 페이지 크기를 키우면(대부분 아키텍처의 기본은 4KB, IA-64·PPC64는 64KB도 흔함) 같은 메모리를 커버하는 데 필요한 페이지 수, 따라서 페이지 폴트 수도 줄어든다. 원문 실험(그림 7.9, NPAD=0 랜덤 Follow, 4KB vs 2MB 페이지)에서 작업 집합 2^20바이트일 때 2MB 페이지 버전이 57% 빠르고, 512MB에서도 38% 빠르다 — 2MB 페이지용 TLB 항목 64개가 2^27바이트를 커버하는 지점까지는 평탄 구간이 유지된다. 이는 대용량 작업 집합에서 비용의 상당 부분이 TLB 미스에서 온다는 것을 보여준다.

대용량 페이지를 쓰려면 물리적으로 연속된 메모리가 필요한데, 시스템이 한동안 돌며 파편화되면 나중에 확보하기 어렵다 — 그래서 리눅스는 부팅 시점에 `/proc/sys/vm/nr_hugepages`로 미리 예약해야 하는 전용 `hugetlbfs` 파일시스템을 쓴다(가상화 환경에서는 VMM이 이를 지원해야 하는 추가 제약이 있음). 프로그램에서 대용량 페이지를 요청하는 방법은 두 가지: System V 공유 메모리의 `SHM_HUGETLB` 플래그, 또는 `hugetlbfs`를 마운트하고 그 안에 파일을 만들어 `mmap`하는 방식(후자가 키(key) 충돌 우려가 없어 더 권장됨). 파일 기반 매핑에는 아직 대용량 페이지를 자동으로 적용하는 방법이 없다(투명한 지원은 `mprotect` 등으로 매핑 일부의 보호 속성이 바뀔 때 발생하는 문제 때문에 구현이 까다로움).

### 8장 다가올 기술

멀티프로세서 처리를 다룬 앞 절들에서 CPU·코어 수가 늘수록 심각한 성능 문제가 생길 수 있음을 봤다. 하지만 바로 이 확장(코어 수 증가)이 앞으로 계속될 방향이다 — 단일 코어 성능이 예전만큼 빠르게 오르지 않으므로 프로그램은 갈수록 더 병렬화되어야 한다.

#### 8.1 원자 연산의 문제

공유 자료구조 접근 동기화는 전통적으로 상호 배제(뮤텍스)나 **락-프리 자료구조**로 이뤄진다. 락-프리 자료구조의 문제는 프로세서가 제공하는 원자 연산 프리미티브가 제한적이라는 것 — 대부분의 아키텍처는 워드 단위 원자적 읽기·쓰기 정도만 지원하며(CAS 또는 LL/SC로 구현), x86/x86-64는 이례적으로 더 풍부한 원자 연산 집합, 특히 **DCAS**(double-word CAS)까지 지원한다.

원문은 배열 기반 락-프리 LIFO(스택) 구현을 세 단계로 발전시키며 문제를 짚는다:

1. **원자 연산 없는 버전**: 당연히 스레드 안전하지 않다 — 원소가 사라지거나 이미 제거된 원소가 되살아날 수 있다.
2. **단순 CAS 버전**(`push`/`pop`에서 top 포인터를 CAS로 갱신): 얼핏 동작할 것 같지만 **ABA 문제**에 취약하다 — 스레드 A가 pop을 시작한 사이 다른 스레드가 `pop → push(새 원소) → push(A가 읽었던 원소)` 순서로 조작하면, top 값 자체는 A가 봤던 값으로 되돌아와 A의 CAS는 성공하지만 실제로는 리스트의 두 번째 원소가 바뀌어 있어 새로 push된 원소가 유실된다.
3. **DCAS + 세대 카운터 버전**: top 포인터 옆에 매 연산마다 증가하는 세대 카운터를 함께 두고 이를 DCAS로 원자적으로 갱신하면, 값이 같아 보여도 세대 카운터가 다르므로 ABA 문제를 피할 수 있다.

다만 이 세 번째 해법도 만능은 아니다. `pop`에서 `old.top == NULL` 검사 이후 스레드가 인터럽트되고, 그사이 다른 스레드가 같은 원소를 pop해 메모리를 해제해 버리면, 첫 스레드가 재개될 때 이미 해제된 메모리를 역참조하다가 크래시할 수 있다 — 이를 막으려면 메모리를 절대 해제하지 않거나 참조 여부를 검증해야 하는데, 이는 락-프리 자료구조가 노리는 성능 이점을 상당 부분 상쇄한다(가비지 컬렉션이 있는 언어라면 이 문제를 해결할 수 있지만 그 나름의 비용이 있음). 더 복잡한 자료구조(예: FIFO)일수록 문제는 더 심해지고, 애초에 x86/x86-64의 CAS는 메모리에서 연속된 두 워드에만 적용되므로 이중 연결 리스트의 임의 위치 삽입·삭제 같은 흔한 상황에는 아예 도움이 안 된다. 근본 문제는 여러 메모리 주소가 동시에 관련되고, 그 값들이 동시에 바뀌지 않아야만 연산 전체가 성공하는 상황 — 데이터베이스에서 익숙한 개념이며, 실제로 가장 유망한 해법도 여기서 나온다.

#### 8.2 트랜잭셔널 메모리

Herlihy와 Moss는 1993년 논문에서 메모리 연산의 트랜잭션을 소프트웨어만으로는 효율적으로 다룰 수 없으므로 **하드웨어에 구현**하자고 제안했다(당시 DEC가 수십 개 프로세서급 하이엔드 하드웨어에서 이미 비슷한 확장성 문제를 겪고 있었다). 원리는 데이터베이스 트랜잭션과 같다 — 트랜잭션의 결과는 한꺼번에 반영되거나, 실패하면 모든 값이 그대로 유지된다.

일부 프로세서의 LL/SC 명령어 쌍은 사실상 이미 작은 트랜잭션이다 — LL로 값을 읽어 L1d에 적재하고, 그사이 다른 프로세서가 그 메모리 위치를 바꾸면(MESI 프로토콜로 감지) SC가 실패한다. **트랜잭셔널 메모리**는 이 개념을 단순 쌍이 아니라 여러 개의 로드·스토어가 참여하는 트랜잭션으로 확장한 것이다.

**연산 종류**: 일반 읽기(LT), 나중에 쓸 것을 전제로 한 배타적 읽기(LTX), 쓰기(ST), 그리고 트랜잭션 상태를 확인하는 VALIDATE, 트랜잭션을 완료하는 COMMIT이 필요하다. MESI 관점에서 일반 읽기는 'E'·'S' 상태 라인으로 충족되지만, LTX는 'E' 상태 라인을 요구한다.

**예제 코드**(가상의 트랜잭셔널 메모리 프리미티브로 짠 락-프리 LIFO):

```c
struct elem *top;
void push(struct elem *n) {
  while (1) {
    n->c = LTX(top);
    ST(&top, n);
    if (COMMIT()) return;
    ... delay ...
  }
}
struct elem *pop(void) {
  while (1) {
    struct elem *res = LTX(top);
    if (VALIDATE()) {
      if (res != NULL) ST(&top, res->c);
      if (COMMIT()) return res;
    }
    ... delay ...
  }
}
```

이 코드는 스레드 안전하지 않은 원본 코드와 구조가 거의 같다는 점이 큰 이점이다. `pop`에서 `res`가 유효한지 역참조 전에 `VALIDATE()`로 확인하는 부분이, 원자 연산 버전에서 풀지 못했던 "해제된 메모리 역참조" 문제를 해결해 준다 — 트랜잭션이 이미 실패했다면 `VALIDATE`가 그 사실을 알려주고 역참조 자체가 일어나지 않기 때문이다.

**버스 프로토콜과 트랜잭션 캐시**: 트랜잭셔널 메모리는 별도 메모리가 아니라 L1d와 나란히 있는 전용 "트랜잭션 캐시"로 구현되는 것이 유력하다(L1d 자체에 넣는 것은 좋은 생각이 아니라고 원 논문은 지적한다). 이 캐시는 L1d보다 훨씬 작고(트랜잭션이 담을 수 있는 연산 수로 크기가 정해짐, 완전 연관일 가능성이 큼), L1d와 **배타적** 관계를 갖는다. 각 슬롯은 MESI 상태에 더해 EMPTY/NORMAL/XABORT/XCOMMIT라는 트랜잭션 상태를 갖는다 — XABORT는 트랜잭션 실패 시 버릴 데이터, XCOMMIT는 커밋 시 버릴(즉 롤백용 옛 값을 담은) 데이터다. 새 트랜잭션 읽기(T_READ)·배타적 읽기(T_RFO) 버스 요청은 일반 READ/RFO와 비슷하지만, 다른 프로세서가 같은 라인으로 활성 트랜잭션을 진행 중이면 그냥 실패 처리된다(값은 undefined로 취급되며, 이후 반드시 VALIDATE/COMMIT으로 확인해야 함).

이 설계의 핵심 이점은, **VALIDATE·COMMIT 자체가 버스 연산을 유발하지 않는다**는 것이다 — 원자 연산은 동시성을 보장하려고 결국 메인 메모리에 값을 써야 하지만(비용이 크다는 것은 이 문서 전체가 보여준 바), 트랜잭셔널 메모리는 새 트랜잭션을 시작할 때, 그리고 아직 트랜잭션 캐시에 없는 새 캐시 라인을 (성공 중인) 트랜잭션에 추가할 때만 버스 연산을 일으킨다. 실패한 트랜잭션 내부의 연산은 버스 연산을 일으키지 않으므로, 같은 메모리를 두고 여러 스레드가 경쟁해도 캐시 라인이 핑퐁하며 왔다 갔다 하는 일이 없다.

**기타 고려사항**: 6.4.2절에서 본 x86/x86-64의 `lock` 접두사 스킵 트릭은 동시에 도는 스레드가 실제로는 같은 메모리를 두고 경합하지 않는 경우에도 원자 연산을 강제한다는 한계가 있는데, 트랜잭셔널 메모리는 이 문제 자체가 사라진다 — RFO에 준하는 비싼 버스 메시지가 정말 필요한 경우(동시/연속으로 다른 CPU에서 그 메모리를 쓸 때)에만 발생한다. 트랜잭션 캐시가 캐시 라인 단위로 동작하는 배타적 캐시라는 점 때문에, 트랜잭션 데이터와 비트랜잭션 데이터를 같은 캐시 라인에 두면(트랜잭션 도중 그 라인에 대한 일반 접근이 발생해 트랜잭션이 중단될 수 있음) 문제가 된다 — 데이터 정렬이 성능뿐 아니라 정확성 문제로도 이어질 수 있다는 뜻이다.

#### 8.3 지연 시간 증가

미래 메모리 기술에서 거의 확실한 한 가지는 **지연 시간이 계속 늘어난다**는 것이다. 2.2.4절에서 봤듯 당시 예정된 DDR3는 DDR2보다 지연이 늘고, FB-DRAM도(특히 데이지 체인 구성일 때) 지연이 늘 수 있다.

두 번째 지연 요인은 **NUMA의 확산**이다 — AMD Opteron은 프로세서가 두 개 이상이면 NUMA 머신이고, 인텔의 CSI도 거의 같은 접근을 쓴다. 프로세서당 대역폭 제약과(예: 10Gb/s 이더넷 카드 여러 장 처리 같은) 서비스 요구 때문에, 소켓당 코어 수가 늘어도 멀티소켓 메인보드 자체는 사라지지 않을 전망이다.

세 번째 요인은 **코프로세서의 부활**이다. 1990년대 초 범용 프로세서에서 수학 코프로세서가 필요 없어진 뒤 사라졌다고 여겨졌지만, 인텔의 Geneseo와 AMD의 Torrenza 같은 플랫폼 확장은 제3자 하드웨어 개발자가 자사 제품을 PCIe 카드가 아니라 CPU에 훨씬 가까운(더 많은 대역폭을 갖는) 위치에 통합할 수 있게 한다. IBM은 다른 방향으로 접근했는데, Cell CPU는 PowerPC 코어 외에 부동소수점 연산에 특화된 8개의 SPU(Synergistic Processing Unit)를 갖는다. 이런 코프로세서·SPU의 공통점은 대체로 진짜 프로세서보다도 메모리 처리 로직이 단순(그래서 더 느림)하다는 것이다 — 캐시 일관성까지 고려한 캐시 처리·프리페칭은 복잡하기 때문이다. Cell CPU의 이론적 최대 성능은 210 GFLOPS로 당시 하이엔드 CPU의 50~60 GFLOPS를 압도했고, GPU는 이미 500 GFLOPS를 넘어서고 있었다 — 고성능 프로그램일수록 코프로세서 의존도가 커질 전망이었다.

이 모든 흐름이 프로그래머에게 주는 결론은 하나다: **프리페칭의 중요성이 갈수록 커진다**. 코프로세서에서는 절대적으로 중요하고, CPU에서도(코어 수가 늘수록) 요청을 몰아서 던지는 대신 FSB를 항상 바쁘게 유지해야 하며, 이를 위해서는 프리페치 명령어를 효율적으로 활용해 CPU에 미래 트래픽에 대한 통찰을 최대한 많이 줘야 한다.

#### 8.4 벡터 연산

오늘날 주류 프로세서의 멀티미디어 확장은 벡터 연산을 제한적으로만 구현한다. 벡터 명령어는 한 명령어로 대량의 연산을 수행한다는 특징이 있지만(SIMD), Cray-1이나 IBM 3090의 벡터 유닛에 비하면 훨씬 소박하다(한 명령어당 float 4개 또는 double 2개 수준). 이 제한을 메우려고 주변 루프를 더 자주 반복해야 한다(A.1절 행렬 곱셈 예제에서 캐시 라인 하나당 SM번 반복이 필요했던 것과 같은 맥락).

벡터 레지스터·연산이 넓어지면 루프 반복 횟수가 줄고, 프로세서가 애플리케이션의 메모리 사용 양상을 개별 명령어 동작에서 짜맞추지 않고도 더 잘 파악할 수 있게 된다. 캐시에 영향을 주지 않는 로드/스토어 명령어의 유용성도 커진다 — SSE 레지스터의 16바이트 로드처럼 좁은 단위에서는 캐시 없는 로드가 오히려 손해지만(캐시 미스 시 같은 라인을 다시 메모리에서 읽어야 함), 벡터 레지스터가 캐시 라인 하나 이상을 담을 만큼 넓다면 캐시 없는 로드/스토어가 불리하지 않고 캐시에 못 들어가는 큰 데이터셋 처리도 더 실용적이 된다. 큰 벡터 레지스터라고 반드시 명령어 지연 시간이 늘어나는 것도 아니다 — 벡터 유닛이 코드 흐름을 인식할 수 있다면 데이터 일부만 준비돼도 연산을 시작할 수 있기 때문이다. 다만 실제로는 멀티프로세스·멀티스레드 OS에서 컨텍스트 스위치 비용(레지스터 저장/복원) 때문에 벡터 레지스터 크기에 현실적 제약이 걸린다.

옛 벡터 유닛은 스트라이딩(벡터 원소 간 일정한 간격을 지정해, 예컨대 행렬의 열을 한 번에 벡터 레지스터로 읽는 것)과 인디렉션(로드/스토어 명령어가 실제 주소·오프셋 배열을 가리키는 포인터를 받아 임의 접근 패턴을 구현하는 것)으로 오늘날의 멀티미디어 명령어보다 훨씬 유연한 메모리 접근 패턴을 지원했다. 진짜 벡터 연산이 주류 프로세서에서 부활할지, 아니면 코프로세서 쪽으로 넘어갈지는 이 시점에서 불분명하지만, 만약 벡터 연산에 접근할 수 있게 된다면 코드를 자기완결적이고 교체 가능하게, 그리고 행/열/개별 원소 단위가 아니라 행렬 전체를 다루는 것처럼 충분히 일반적인 인터페이스로 짜는 것이 그만큼 더 중요해진다 — 다루는 빌딩 블록이 클수록 벡터 연산을 활용할 기회도 커지기 때문이다. 다만 큰 레지스터 집합에 따르는 컨텍스트 스위치 비용, 인터럽트 도중 긴 벡터 연산을 중단·재개해야 하는 어려움, RISC 계열 프로세서의 엄격한 정렬 요구 등은 여전히 실현을 가로막는 현실적 장벽으로 남아 있다.

### 부록 개요

원문 부록은 A~G로 구성된다. 상세 재현 대신 각 부록이 다루는 내용과 핵심 요지만 간단히 정리한다.

- **부록 A. 예제·벤치마크 프로그램**: A.1은 6.2.1절 행렬 곱셈의 완전한 벤치마크 코드(SSE2 인트린식, `_MM_HINT_NTA` 프리페치, 64바이트 정렬 활용). A.2는 7.4절에서 언급한, `likely`/`unlikely` 매크로를 런타임에 실제로 계측하는 디버그 버전 구현 — GNU 어셈블러·링커의 커스텀 섹션과 `__start_*`/`__stop_*` 심볼을 이용해 예측 성공/실패 횟수를 소스 위치별로 모아 프로그램 종료 시 출력한다(원자 연산 없이 카운터를 증가시키므로 완벽히 정확하지는 않지만 충분히 실용적). A.3은 6.4.1절 거짓 공유(false sharing) 실험에 쓰인 벤치마크 코드 — 스레드를 `pthread_setaffinity_np`로 특정 CPU에 고정하고, 같은 캐시 라인/다른 캐시 라인에 위치한 변수를 원자적·비원자적으로 증가시켜 오버헤드를 측정한다.

- **부록 B. OProfile 팁**: oprofile은 수집(커널, MSR 접근 권한 필요)과 분석 두 단계로 동작하며, 이벤트마다 오버런 값(몇 번째 이벤트마다 기록할지)·유저/커널 카운트 여부·유닛 마스크를 `opcontrol`로 지정한다. 오버런 값이 작을수록 해상도는 높아지지만 시스템 부하도 커진다. `opreport`로 리포트를, `opannotate`로 소스·명령어 단위 주석을 볼 수 있다. 절대 이벤트 수보다는 **두 이벤트의 비율**이 더 유의미하다는 점을 강조하며, 인텔 최적화 매뉴얼이 제시하는 메모리 관련 비율 지표들(명령어 페치 스톨, ITLB/L1i/L2 미스율, 로드율, 스토어 순서 블록, NTA 프리페치 유효율 등)의 의미와 해석 기준을 표로 정리한다.

- **부록 C. 메모리 타입**: "**레지스터드(registered/buffered)**" DRAM은 모듈에 버퍼 칩을 하나 더 두어 메모리 컨트롤러의 전기적 부담을 줄이고 더 많은 모듈·뱅크를 구동할 수 있게 하지만, 버퍼링 자체가 지연을 늘리고 비용·전력도 더 든다. **ECC(Error Correction Code)** DRAM은 데이터 8비트당 보통 1비트 정도의 오차 정정 비트를 추가로 저장해(해밍 코드 기반, SEC 또는 SEC/DED) 우주선(cosmic ray)이나 알파 붕괴 등으로 인한 셀 오류를 자동 정정한다 — 실제 계산(오차 정정 비트 수 E와 데이터 비트 수 W의 관계식, 행렬을 이용한 해밍 코드 인코딩/디코딩 예시 등)을 통해 W=64, E=8이 실용적인 선택이 되는 이유를 보여준다. 두 기술 모두 비용·지연이라는 트레이드오프 때문에 범용 시스템의 기본값은 아니며, 서버·대용량 메모리 환경에서 주로 쓰인다.

- **부록 D. libNUMA 소개**: 당시 리눅스의 `libnuma`(numactl 패키지)가 NUMA 프로그래밍에 필요한 기능을 충분히 제공하지 못한다는 문제의식에서, 저자가 제안한(당시 미완성·미검증 상태였던) 새 라이브러리의 인터페이스 초안을 소개한다. `/sys` 파일시스템 노출 정보에 크게 의존하며, 메모리 노드 집합을 다루는 `memnode_set_t`와 관련 매크로들을 정의한다. NUMA뿐 아니라 캐시 계층 문제와도 겹치므로 비NUMA 멀티코어 시스템에서도 유용하다고 언급된다.

- **부록 E~G**: 색인(주요 용어의 등장 위치), 참고문헌 목록(AMD·인텔 문서, Herlihy&Moss의 트랜잭셔널 메모리 논문 등 학술 자료), 개정 이력(2007년 6월 내부 초안부터 같은 해 11월 21일 Version 1.0 발행까지의 편집 경과)으로 구성된다.

---

이것으로 Ulrich Drepper의 "What Every Programmer Should Know About Memory" 5부작 정리를 마친다. 전체 흐름을 요약하면: DRAM은 근본적으로 느리고(2장), 이를 CPU 캐시로 가린다(3장). 가상 메모리·NUMA는 여기에 또 다른 계층의 비용과 복잡성을 더하며(4~5장), 결국 프로그래머가 지역성을 살리는 코드·자료구조를 설계하고 프리페칭·정렬·스레드 배치를 신경 써야만 하드웨어의 잠재력을 실제로 끌어낼 수 있다(6장). 측정 도구(7장)로 이를 검증하고, 코어 수 증가와 트랜잭셔널 메모리 같은 다가올 변화(8장)에 대비하는 것이 이 문서 전체가 남기는 실무적 메시지다.

## USE 메서드

> 저자: Brendan Gregg | 정리일: 2026-07-10
>
> 원문 사이트에 별도의 허용적 라이선스가 없어, 원문의 섹션 구조를 빠짐없이 따라가는 상세 정리 노트로 작성했다. 수치·표·용어는 원문 그대로다.

![Boeing 707 Emergency Checklist (1969)](https://www.brendangregg.com/USEmethod/B707_emergency01_crop0.jpg)

USE(Utilization, Saturation, Errors) 메서드는 어떤 시스템이든 성능을 분석할 수 있는 방법론이다. 체크리스트를 만들도록 이끌며, 서버 분석에서는 이 체크리스트로 리소스 병목이나 에러를 빠르게 찾아낼 수 있다. 주어진 지표(부분적인 답)에서 출발해 거꾸로 추적하는 대신, 먼저 질문을 던지고 그 답을 찾아 나간다.

원문 사이트에는 운영체제별 USE 체크리스트가 정리되어 있다: [Linux](https://www.brendangregg.com/USEmethod/use-linux.html), [Solaris](https://www.brendangregg.com/USEmethod/use-solaris.html), [Mac OS X](https://www.brendangregg.com/USEmethod/use-macosx.html), [FreeBSD](https://www.brendangregg.com/USEmethod/use-freebsd.html), [Unix 7th](https://www.brendangregg.com/USEmethod/use-unix7th.html), [SmartOS](https://www.brendangregg.com/USEmethod/use-smartos.html). 이들에서 자동 생성한 [Rosetta Stone of Performance Checklists](https://www.brendangregg.com/USEmethod/use-rosetta.html)도 있다. 자기 환경에 맞게 도구를 추가해 커스터마이즈하면 된다.

### 도입

심각한 성능 문제가 터졌고 서버가 원인으로 의심된다. 무엇부터 확인해야 할까?

시작이 가장 어렵다. Gregg는 중요한 영역을 빠뜨리지 않으면서 흔한 성능 문제를 빠르게 해결하는 법을 가르치려고 USE 메서드를 만들었다. 비행 매뉴얼의 비상 체크리스트처럼 단순하고, 직관적이고, 완전하고, 빠르게 쓸 수 있도록 설계했다. 기업 환경, 강의(학습 도구), 그리고 클라우드 컴퓨팅 환경에서 수없이 성공적으로 쓰였다.

USE 메서드는 세 가지 지표 유형과 복잡한 시스템에 접근하는 전략으로 이루어진다. 저자의 경험으로는 서버 문제의 약 80%를 5%의 노력으로 해결하며, 서버가 아닌 시스템에도 적용할 수 있다. 다만 이것은 더 큰 방법론 도구 상자의 도구 하나로 보아야 한다. 해결하지 못하는 문제 유형도 많으며, 그런 문제에는 다른 방법과 더 긴 시간이 필요하다.

### 요약

USE 메서드는 한 문장으로 요약된다.

**모든 리소스의 사용률(utilization), 포화도(saturation), 에러(errors)를 확인한다.**

성능 조사 초기에 시스템 전반의 병목을 찾는 용도로 쓴다.

용어 정의:

- **리소스(resource)**: 서버의 모든 물리적 기능 구성 요소(CPU, 디스크, 버스, ...) [1]
- **사용률(utilization)**: 리소스가 작업을 처리하느라 바빴던 평균 시간 [2]
- **포화도(saturation)**: 리소스가 처리하지 못해 대기(주로 큐잉)하는 추가 작업의 정도
- **에러(errors)**: 에러 이벤트의 횟수

[1] 일부 소프트웨어 리소스나 소프트웨어가 부과한 제한(리소스 컨트롤)도 함께 고려하면 유용할 수 있다.

[2] 사용률에는 "사용 중인 리소스의 비율"이라는 다른 정의도 있다. 그 정의에서는 100% 사용률이 "더 이상 작업을 받을 수 없음"을 뜻하는데, 위의 "바쁨(busy)" 정의와는 다르다.

지표는 보통 다음과 같이 표현한다.

- 사용률: 시간 구간 대비 백분율. 예: "디스크 하나가 90% 사용률로 돌고 있다."
- 포화도: 큐 길이. 예: "CPU들의 평균 실행 큐(run queue) 길이가 4다."
- 에러: 스칼라 카운트. 예: "이 네트워크 인터페이스에서 late collision이 50번 발생했다."

에러는 성능을 저하시킬 수 있고, 실패가 복구 가능한 유형이면 즉시 눈에 띄지 않을 수 있으므로 반드시 조사해야 한다. 실패 후 재시도되는 연산, 이중화 풀에서 고장 난 장치가 여기에 해당한다.

### 사용률이 낮으면 포화가 없다는 뜻일까?

짧은 순간의 높은 사용률 버스트가 포화와 성능 문제를 일으킬 수 있다. 긴 구간으로 평균 낸 사용률이 *낮더라도* 그렇다. 직관에 어긋날 수 있는 지점이다.

저자가 겪은 사례: 모니터링 도구상 CPU 사용률이 80%를 넘은 적이 없는데도 고객이 CPU 포화(지연)로 고생하고 있었다. 도구는 5분 평균을 보고하고 있었고, 그 사이 CPU 사용률은 몇 초씩 100%를 찍고 있었다.

### 리소스 목록

먼저 순회할 리소스 목록이 필요하다. 서버용 일반 목록:

- CPU: 소켓, 코어, 하드웨어 스레드(가상 CPU)
- 메모리: 용량
- 네트워크 인터페이스
- 스토리지 장치: I/O, 용량
- 컨트롤러: 스토리지, 네트워크 카드
- 인터커넥트: CPU, 메모리, I/O

일부 구성 요소는 두 종류의 리소스다. 예를 들어 스토리지 장치는 서비스 요청 리소스(I/O)이면서 용량 리소스(수용량)이기도 하며, 두 유형 모두 시스템 병목이 될 수 있다. 요청 리소스는 요청을 큐에 넣었다가 처리하는 *큐잉 시스템*으로 정의할 수 있다.

하드웨어 캐시(MMU TLB/TSB, CPU 캐시 등)처럼 목록에서 뺀 물리 구성 요소도 있다. USE 메서드는 높은 사용률이나 포화에서 성능이 저하되어 병목이 되는 리소스에 가장 효과적인데, 캐시는 사용률이 높을수록 오히려 성능을 *개선*한다. 캐시 히트율 등은 USE 메서드 이후, 즉 시스템 전반의 병목을 배제한 다음 확인하면 된다. 어떤 리소스를 포함할지 애매하면 일단 포함하고 지표가 얼마나 잘 동작하는지 보라.

### 기능 블록 다이어그램

리소스를 순회하는 또 다른 방법은 시스템의 [기능 블록 다이어그램(Functional Block Diagram)](http://en.wikipedia.org/wiki/Function_block_diagram)을 찾거나 직접 그리는 것이다. 구성 요소 간 관계도 보여주므로 데이터 흐름의 병목을 찾을 때 매우 유용하다. [Sun Fire V480 Guide](http://docs.oracle.com/cd/E19095-01/sfv480.srvr/816-0904-10/816-0904-10.pdf) 82쪽의 예:

![Sun Fire V480 기능 블록 다이어그램](https://www.brendangregg.com/USEmethod/v480.png)

이런 다이어그램은 구하기 어려울 수 있다. 실제로 하드웨어를 만드는 하드웨어 엔지니어가 최고의 자료원이고, 아니면 직접 그려도 된다.

여러 버스의 사용률을 파악하는 과정에서 기능 다이어그램의 각 버스에 최대 대역폭을 표기해 두면, 측정을 한 번도 하기 전에 시스템 병목 후보를 식별할 수 있는 다이어그램이 된다. (물리 구성 요소를 바꿀 수 있는 하드웨어 제품 설계 단계에서 유용한 연습이다.)

### 인터커넥트

CPU·메모리·I/O 인터커넥트는 자주 간과된다. 다행히 시스템 병목이 되는 일은 흔치 않다. 불행히도 병목이 되면 손쓰기 어렵다(메인보드를 업그레이드하거나 부하를 줄이는 정도 — 예: "zero copy" 프로젝트는 메모리 버스 부하를 줄인다). USE 메서드를 쓰면 최소한 그동안 고려하지 않던 것, 즉 인터커넥트 성능을 인식하게 된다. 저자가 USE 메서드로 인터커넥트 문제를 찾아낸 사례는 [Analyzing the HyperTransport](http://www.brendangregg.com/blog/2009-09-22/analyzing-the-hypertransport.html)를 보라.

### 지표

리소스 목록이 있으면 지표 유형(사용률, 포화도, 에러)을 각각 대입한다. 원문에서는 아래 표의 지표 칸을 마우스 오버로 가려 두고 독자가 먼저 채워 보게 한다. 일반적인 Unix/Linux 용어 기준의 답:

| 리소스 | 유형 | 지표 |
|---|---|---|
| CPU | 사용률 | CPU 사용률(CPU별 또는 시스템 전체 평균) |
| CPU | 포화도 | 실행 큐(run-queue) 길이 또는 스케줄러 지연 |
| 메모리 용량 | 사용률 | 가용 여유 메모리(시스템 전체) |
| 메모리 용량 | 포화도 | 익명 페이징(anonymous paging) 또는 스레드 스와핑("페이지 스캐닝"도 포함 가능) |
| 네트워크 인터페이스 | 사용률 | RX/TX 처리량 / 최대 대역폭 |
| 스토리지 장치 I/O | 사용률 | 장치 busy 백분율 |
| 스토리지 장치 I/O | 포화도 | 대기 큐 길이 |
| 스토리지 장치 I/O | 에러 | 장치 에러("soft", "hard", ...) |

시간 요소는 생략했다. 이 지표들은 구간별 평균이거나 카운트다. 수집 방법도 생략했는데, 자기만의 체크리스트에는 어떤 OS 도구나 모니터링 소프트웨어를 쓰고 어떤 통계를 읽을지를 포함하라. 구할 수 없는 지표에는 "?"를 적어라. 그러면 따라가기 쉽고 빠르면서 시스템에 대해 가능한 한 완전한 체크리스트가 만들어진다.

### 더 어려운 지표

더 어려운 조합들(역시 먼저 스스로 생각해 볼 것):

| 리소스 | 유형 | 지표 |
|---|---|---|
| CPU | 에러 | 예: 정정 가능한 CPU 캐시 ECC 이벤트, 고장(faulted) CPU (OS+하드웨어가 지원하는 경우) |
| 메모리 용량 | 에러 | 예: 실패한 malloc() (보통 물리 메모리가 아니라 가상 메모리 고갈 때문이긴 하다) |
| 네트워크 | 포화도 | 포화 관련 NIC/OS 이벤트. 예: "dropped", "overruns" |
| 스토리지 컨트롤러 | 사용률 | 컨트롤러에 따라 다름. 최대 IOPS나 처리량이 있으면 현재 활동과 비교 |
| CPU 인터커넥트 | 사용률 | 포트별 처리량 / 최대 대역폭 (CPU 성능 카운터) |
| 메모리 인터커넥트 | 포화도 | 메모리 스톨 사이클, 높은 CPI (CPU 성능 카운터) |
| I/O 인터커넥트 | 사용률 | 버스 처리량 / 최대 대역폭 (하드웨어에 성능 카운터가 있을 수 있음. 예: Intel "uncore" 이벤트) |

이런 지표는 OS에 따라 측정이 더 어려워지고, 저자는 직접 소프트웨어를 짜야 할 때가 많았다(예: [Analyzing the HyperTransport](http://www.brendangregg.com/blog/2009-09-22/analyzing-the-hypertransport.html)의 "amd64htcpu" 스크립트).

모든 조합을 반복하고 각 지표의 수집 방법을 적으면 약 30개의 지표 목록이 나온다. 일부는 측정할 수 없고 일부는 측정이 까다롭다. 다행히 가장 흔한 문제는 대개 쉬운 지표(CPU 포화, 메모리 용량 포화, 네트워크 인터페이스 사용률, 디스크 사용률)에서 발견되므로 이것들을 먼저 확인하면 된다.

### 실전에서

OS의 모든 조합에서 지표를 읽는 것은 시간이 많이 든다. 특히 버스와 인터커넥트 지표까지 가면 더 그렇다. 부분 집합(CPU, 메모리 용량, 스토리지 용량, 스토리지 장치 I/O, 네트워크 인터페이스)만 확인할 시간밖에 없을 수도 있는데, 이것도 생각보다 낫다. USE 메서드 덕분에 무엇을 확인하지 않았는지 인식하게 되었기 때문이다. 한때 unknown-unknown이던 것이 이제 known-unknown이 되었다. 회사 차원에서 성능 문제의 근본 원인을 반드시 찾아야 하는 순간이 오면, 더 철저한 분석을 위한 추가 작업의 할 일 목록을 이미 갖고 있는 셈이다.

OS에 지표가 계속 추가되면서 쉽게 확인할 수 있는 지표의 범위가 넓어지기를, 그리고 성능 모니터링 소프트웨어가 USE 메서드 마법사를 추가해 이 작업을 대신해 주기를 저자는 기대한다.

### 소프트웨어 리소스

일부 소프트웨어 리소스도 비슷하게 볼 수 있다. 보통 애플리케이션 전체가 아니라 소프트웨어의 작은 구성 요소에 적용된다.

- **뮤텍스 잠금**: 사용률은 잠금이 유지된 시간, 포화도는 잠금을 기다리며 큐잉된 스레드로 정의할 수 있다.
- **스레드 풀**: 사용률은 스레드가 작업을 처리하느라 바빴던 시간, 포화도는 스레드 풀의 처리를 기다리는 요청 수.
- **프로세스/스레드 용량**: 시스템의 프로세스·스레드 수 제한 대비 현재 사용량이 사용률, 할당 대기가 포화, 할당 실패(예: "cannot fork")가 에러.
- **파일 디스크립터 용량**: 위와 같되 파일 디스크립터 대상.

이 유형에 너무 매달리지 마라. 지표가 잘 동작하면 쓰고, 아니면 소프트웨어는 다른 방법론(예: 지연 시간 기반)에 맡겨라.

### 해석 가이드

USE 메서드는 어떤 지표를 쓸지 알려준다. OS에서 읽는 법을 익힌 다음 과제는 현재 값의 해석이다. 어떤 것은 해석이 명확하고 문서화도 잘 되어 있지만, 어떤 것은 그렇지 않고 워크로드 요구사항이나 기대치에 따라 달라진다.

지표 유형별 일반 해석 지침:

- **사용률**: 100% 사용률은 대개 병목의 신호다(포화도와 그 영향을 확인해 검증하라). 높은 사용률(예: 70% 초과)도 두 가지 이유로 문제가 되기 시작할 수 있다.
  - 비교적 긴 구간(수 초~수 분)으로 측정한 사용률에서는, 이를테면 70%라는 총 사용률이 짧은 100% 버스트를 가릴 수 있다.
  - 하드 디스크 같은 일부 시스템 리소스는 작업 도중에 더 높은 우선순위의 작업을 위해서라도 중단될 수 없다. 사용률이 70%를 넘으면 큐잉 지연이 더 잦고 뚜렷해질 수 있다. 거의 언제든 중단("선점")될 수 있는 CPU와 대비된다.
- **포화도**: 0이 아닌 어떤 수준의 포화도든 문제일 수 있다. 대기 큐의 길이나 큐에서 기다린 시간으로 측정한다.
- **에러**: 0이 아닌 에러 카운터는 조사할 가치가 있다. 특히 성능이 나쁜 상태에서 계속 증가하고 있다면 더 그렇다.

부정 사례(낮은 사용률, 포화 없음, 에러 없음)의 해석은 쉽다. 그리고 이는 생각보다 유용하다 — 조사 범위를 좁히면 문제 영역에 빠르게 집중할 수 있다.

### 클라우드 컴퓨팅

클라우드 컴퓨팅 환경에서는 하나의 시스템을 공유하는 테넌트를 제한·조절(throttle)하는 소프트웨어 리소스 컨트롤이 있을 수 있다. 메모리·CPU·네트워크·스토리지 I/O에 대한 하이퍼바이저 또는 컨테이너(cgroup) 제한이 그 예다. 네트워크 처리량처럼 외부 하드웨어가 제한을 가할 수도 있다. 이런 리소스 제한 각각도 물리 리소스처럼 USE 메서드로 검토할 수 있다.

예를 들어 저자의 환경에서 "메모리 용량 사용률"은 테넌트의 메모리 사용량 대 메모리 상한(cap)이 될 수 있다. "메모리 용량 포화"는 전통적인 Unix 페이지 스캐너가 놀고 있어도 익명 페이징 활동으로 관측할 수 있다.

### 전략

USE 메서드의 흐름도. 에러는 보통 더 빠르고 해석하기 쉬우므로 약간의 최적화로서 사용률·포화도보다 먼저 확인해도 된다.

![USE 메서드 흐름도](https://www.brendangregg.com/USEmethod/usemethod_flow.png)

USE 메서드는 시스템 병목일 가능성이 높은 문제를 찾아낸다. 다만 시스템은 성능 문제를 동시에 여러 개 겪을 수 있어, 처음 찾은 것이 *하나의* 문제일지언정 *바로 그* 문제가 아닐 수 있다. 발견할 때마다 다른 방법론으로 조사한 뒤, 필요하면 USE 메서드로 돌아와 나머지 리소스를 계속 순회한다.

후속 분석 전략으로는 워크로드 특성화(workload characterization)와 드릴다운 분석이 있다. 이를 마치면 시정 조치가 "가해지는 부하 조정"인지 "리소스 자체 튜닝"인지에 대한 근거가 생긴다.

### 아폴로

USE 메서드는 서버 너머에도 적용할 수 있다. 재미있는 예로 저자는 자신이 전혀 전문성이 없고 어디서 시작할지도 모르는 시스템, 아폴로 달 착륙선(LM)의 유도 시스템을 골랐다.

첫 단계는 리소스 목록, 더 좋게는 기능 블록 다이어그램을 찾는 것이다. "Lunar Module - LM10 Through LM14 Familiarization Manual"(1969)에서 찾은 다이어그램:

![아폴로 LM 유도 시스템 블록 다이어그램](https://www.brendangregg.com/USEmethod/apollo_LM_guidance.png)

일부 구성 요소는 사용률·포화 특성이 없을 수 있다. 한 번 순회한 뒤 관련 구성 요소만 남겨 다시 그리면 된다. (저자라면 메모리의 "erasable storage" 구역, "core set area"와 "vac area" 레지스터도 추가하겠다고 한다.)

아폴로 유도 컴퓨터(AGC) 자체부터 보면, 각 지표에 대해 LM 문서들을 뒤져 본 결과:

- **AGC 사용률**: 작업(job)을 수행한 CPU 사이클 수("DUMMY JOB" 제외)를 클럭 속도(2.048 MHz)로 나눈 값으로 정의할 수 있다. 당시에도 잘 이해되던 지표로 보인다.
- **AGC 포화도**: 프로그램 상태를 저장하는 7세트의 레지스터인 "core set area"의 작업 수로 정의할 수 있다. 이는 더 높은 우선순위 작업의 인터럽트가 오면 "EXECUTIVE" 프로그램(요즘으로 치면 "커널")이 작업을 중단시킬 수 있게 해 준다. 소진되면 포화 상태에서 에러 상태로 넘어가 AGC가 1202 "EXECUTIVE OVERFLOW-NO CORE SETS" 알람을 보고한다.
- **AGC 에러**: 알람이 다수 정의되어 있다. 1202 외에 1203 "WAITLIST OVERFLOW-TOO MANY TASKS" 알람도 있는데, 이는 다른 유형의 성능 문제다. 정상적인 작업 스케줄링으로 돌아가기 전에 처리되는 시한(timed) 태스크가 너무 많은 것이다. 1202처럼 WAITLIST 길이를 포화 지표로 정의해 두면 오버플로와 에러가 나기 전에 포화를 측정할 수 있다.

우주 애호가라면 익숙할 내용: 1201("NO VAC AREAS")과 1202 알람은 [아폴로 11호 하강](http://en.wikipedia.org/wiki/Apollo_Guidance_Computer#PGNCS_trouble) 중에 실제로 발생한 것으로 유명하다. ("VAC"은 "[vector accumulator](https://www.brendangregg.com/USEmethod/AGC_core_and_vac.png)"의 줄임말로, 벡터 값을 다루는 작업용 추가 저장 공간이다. 위키백과의 "vacant"라는 설명은 틀렸을 것이라고 저자는 본다.)

아폴로 11호의 1201 알람이 있으니 워크로드 특성화 같은 다른 방법론으로 분석을 이어갈 수 있다. 워크로드는 대부분 인터럽트로 가해지며, 그중 다수가 기능 다이어그램에 보인다. LM이 하강 중인데도 사령선(CM) 추적용 랑데부 레이더가 AGC에 인터럽트로 작업을 밀어 넣고 있었다. 불필요한 작업(또는 저우선순위 작업 — 필요시 LM AGC가 즉시 중단 궤도와 CM 랑데부를 계산할 수 있도록 레이더 업데이트 일부는 바람직했을 수 있다)을 찾아낸 사례다.

더 어려운 예로 랑데부 레이더 자체를 리소스로 보면, 에러가 가장 [식별하기 쉽다](https://www.brendangregg.com/USEmethod/apollo_LM_radarsignalflow.png). "DATA NO GOOD", "NO TRACK", "SHAFT- AND TRUNNION-AXIS ERROR" 신호의 세 유형이 있다. 사용률은 더 어려운데, 하나는 구동 모터의 사용률 — 각도 명령에 응답하느라 바빴던 시간(기능 다이어그램의 "COUPLING DATA UNIT" 경유) — 로 정의할 수 있다. 구동 모터나 반환되는 레이더 데이터에 포화 특성이 있는지는 LM 문서를 더 읽어야 한다.

이 방법론 덕분에 짧은 시간 안에, 어디서 시작할지 전혀 모르는 상태에서 찾아보고 조사할 구체적인 지표가 있는 상태가 되었다.

### 다른 방법론

USE 메서드가 서버 문제의 80%를 찾는다면, 지연 시간 기반 방법론(예: [Method R](http://carymillsap.blogspot.com/2009/11/why-we-made-method-r.html))은 전체 문제의 100%에 다가갈 수 있다. 그러나 소프트웨어 내부에 익숙하지 않으면 시간이 훨씬 오래 걸릴 수 있다. 이런 방법론은 이미 그런 지식을 갖춘 데이터베이스 관리자나 애플리케이션 개발자에게 더 맞을 수 있다. USE 메서드는 OS와 하드웨어가 책임 범위이자 전문 분야인 주니어·시니어 시스템 관리자에게 더 적합하며, 다른 직군도 시스템 상태를 빠르게 점검하고 싶을 때 쓸 수 있다.

### 도구 기반 방법(Tools Method)

USE 메서드와 비교하기 위해 도구 기반 접근("Tools Method")을 기술하면:

1. 사용 가능한 성능 도구를 나열한다(필요하면 설치·구매).
2. 각 도구의 유용한 지표를 나열한다.
3. 각 지표의 가능한 해석 규칙을 나열한다.

결과는 어떤 도구를 돌리고 어떤 지표를 읽고 어떻게 해석할지 알려주는 처방적 체크리스트다. 꽤 효과적일 수 있지만, 문제는 오로지 사용 가능한(또는 알려진) 도구에만 의존한다는 점이다. 그런 도구는 시스템의 불완전한 그림만 제공할 수 있고, 사용자는 자신의 시야가 불완전하다는 것조차 모른다 — 그래서 문제는 남는다.

반면 USE 메서드는 시스템 리소스를 순회하며 물어야 할 질문의 완전한 목록을 먼저 만들고, 그 다음에 답해 줄 도구를 찾는다. 더 완전한 그림이 만들어지고, 알 수 없는 영역은 문서화되어 그 존재가 인지된다("known unknowns"). USE에 기반해 어떤 도구를 돌리고(있다면) 어떤 지표를 읽고 어떻게 해석할지의 체크리스트를 비슷하게 만들 수 있다.

또 다른 문제는 수많은 도구를 순회하는 일이 목표 — 병목 찾기 — 에서 주의를 빼앗을 수 있다는 점이다. USE 메서드는 도구와 지표가 감당 못 할 만큼 많아도 병목과 에러를 효율적으로 찾는 전략을 제공한다.

### 결론

USE 메서드는 시스템 상태를 완전하게 점검해 흔한 병목과 에러를 찾아내는 단순한 전략이다. 조사 초기에 투입해 문제 영역을 빠르게 식별하고, 필요하면 다른 방법론으로 더 깊이 파고들 수 있다. USE의 강점은 속도와 가시성이다. 모든 리소스를 고려하므로 문제를 놓칠 가능성이 낮다. 다만 특정 유형의 문제 — 병목과 에러 — 만 찾으므로 더 큰 도구 상자의 도구 하나로 보아야 한다.

스레드 기반의 상보적 방법론인 [TSA Method](https://www.brendangregg.com/tsamethod.html)도 참고하라.

## 플레임 그래프(Flame Graphs)

> 원문: [Flame Graphs](https://www.brendangregg.com/flamegraphs.html)
> 저자: Brendan Gregg | 정리일: 2026-07-10
>
> 원문 사이트에 별도의 허용적 라이선스가 없어, 원문의 섹션 구조를 빠짐없이 따라가는 상세 정리 노트로 작성했다. 수치·링크·용어는 원문 그대로다.

![CPU Flame Graph 예시](https://www.brendangregg.com/FlameGraphs/cpu-mysql-crop-500.png)

플레임 그래프는 계층적 데이터를 시각화하는 방법으로, Brendan Gregg가 프로파일링된 소프트웨어의 스택 트레이스를 시각화해 가장 빈번한 코드 경로를 빠르고 정확하게 식별하기 위해 만들었다. 이 페이지는 플레임 그래프의 공식 사이트다. [github.com/brendangregg/FlameGraph](https://github.com/brendangregg/FlameGraph)의 오픈소스 프로그램으로 인터랙티브 SVG를 생성할 수 있다. 지금은 100개가 넘는 다른 구현체가 있으며 그중 다수가 오픈소스이고(아래 "업데이트" 절 참고), 대부분의 상용 프로파일러에서도 지원한다. Netflix 성능 엔지니어링 팀의 동료 Martin Spier는 더 인터랙티브한 d3 버전인 [d3-flame-graph](https://github.com/spiermar/d3-flame-graph)를 만들었으며 이 역시 널리 쓰인다.

원문 사이트는 플레임 그래프의 여러 종류를 각각 별도 페이지(또는 포스트)로 소개한다.

- [CPU](https://www.brendangregg.com/FlameGraphs/cpuflamegraphs.html)
- [AI/GPU](https://www.brendangregg.com/blog/2024-10-29/ai-flame-graphs.html)
- [Memory](https://www.brendangregg.com/FlameGraphs/memoryflamegraphs.html)
- [Off-CPU](https://www.brendangregg.com/FlameGraphs/offcpuflamegraphs.html)
- [Hot/Cold](https://www.brendangregg.com/FlameGraphs/hotcoldflamegraphs.html)
- [Differential](https://www.brendangregg.com/blog/2014-11-09/differential-flame-graphs.html)

위 예시 이미지는 CPU 플레임 그래프의 일부로, MySQL의 어떤 코드 경로가 얼마나 많은 CPU 사이클을 소비하는지 보여준다.

플레임 그래프는 계층 구조를 가진 데이터라면 무엇에든 쓸 수 있다. 예를 들어 파일 시스템 콘텐츠도 가능하다([방법](https://www.brendangregg.com/blog/2017-02-05/file-system-flame-graph.html), [트리맵·선버스트와의 비교](https://www.brendangregg.com/blog/2017-02-06/flamegraphs-vs-treemaps-vs-sunburst.html)). 변동·교란·주기적 활동을 연구하기 위해 커스텀 시간 범위별로 플레임 그래프를 생성하려면 [FlameScope](https://www.brendangregg.com/flamescope.html)를 참고하라.

### 요약

x축은 스택 프로파일 표본의 모집단을 알파벳순으로 정렬해 보여준다(시간의 흐름이 아니다). y축은 스택 깊이를 아래에서 0부터 세어 나타낸다. 각 사각형은 하나의 스택 프레임을 나타내며, 프레임이 넓을수록 스택에 더 자주 등장했다는 뜻이다. 맨 위 가장자리는 현재 CPU에서 실행 중인 것을 보여주고, 그 아래는 그 프레임의 조상(호출자) 체인이다. 원조 플레임 그래프는 인접한 프레임을 시각적으로 구분하기 쉽도록 무작위 색을 쓴다. y축을 뒤집는 변형("icicle graph"), 코드 종류를 나타내도록 색조를 바꾸는 변형, 추가 차원을 전달하기 위해 색 스펙트럼을 쓰는 변형 등이 있다.

플레임 그래프는 정적 시각화이자 동적 시각화다. 정적 시각화로서는 이미지로 저장해 인쇄물(책)에 실을 수 있으며, 가장 빈번한 프레임만 라벨을 붙일 만큼 넓기 때문에 이미지만으로도 "큰 그림"이 전달된다. 동적 시각화로서는 탐색과 이해를 돕는 인터랙티브 기능을 제공한다.

- 마우스를 올리면 상태 바에 프레임의 추가 정보가 표시된다.
- 마우스로 클릭하면 시각화가 수평으로 확대(zoom)되어, 가려져 있던 함수 이름이 드러난다.
- 검색하면 주어진 검색어와 일치하는 프레임을 강조하고, 검색어를 포함한 스택의 "누적 백분율"을 보여준다.

이 시각화는 저자의 ACMQ 아티클 [The Flame Graph](http://queue.acm.org/detail.cfm?id=2927301)에서 자세히 설명한다. 이 글은 [Communications of the ACM, Vol. 59 No. 6](http://cacm.acm.org/magazines/2016/6/202665-the-flame-graph/abstract)에도 게재되었다.

[CPU Flame Graphs](https://www.brendangregg.com/FlameGraphs/cpuflamegraphs.html) 페이지와 아래 "발표" 절도 참고하라.

### 발표

저자는 USENIX ATC 2017에서 플레임 그래프를 설명하는 갱신된 발표 [Visualizing Performance with Flame Graphs](https://www.usenix.org/conference/atc17/program/presentation/gregg-flame)를 했다. 이 발표는 [유튜브](https://www.youtube.com/watch?v=D53T1Ejig1Q)와 [슬라이드셰어](https://www.slideshare.net/brendangregg/usenix-atc-2017-visualizing-performance-with-flame-graphs)([PDF](https://www.brendangregg.com/Slides/USENIX_ATC2017_flamegraphs.pdf))에서 볼 수 있다.

플레임 그래프에 관한 첫 발표는 [USENIX LISA 2013](https://www.usenix.org/conference/lisa13/technical-sessions/plenary/gregg)이었고, 결국 본회의(plenary) 발표가 되었다([유튜브](http://www.youtube.com/watch?v=nZfNehCzGdw), [슬라이드셰어](http://www.slideshare.net/brendangregg/blazing-performance-with-flame-graphs), [PDF](https://www.brendangregg.com/Slides/LISA13_Flame_Graphs.pdf)).

### 운영체제

이제 일부 OS 프로파일러는 플레임 그래프를 내장 지원한다.

- Linux: perf (`perf script report flamegraph`)
- Windows: WPA, PerfView

스택 트레이스가 담긴 프로파일 데이터라면 어디서든 플레임 그래프를 생성할 수 있다. 다음 프로파일링 도구가 그 예다.

- Linux: perf, eBPF, SystemTap, ktap
- FreeBSD: DTrace
- Mac OS X: Instruments
- Windows: Xperf.exe

의미 있는 스택을 생성할 수 있는 프로파일러만 있으면 이를 플레임 그래프로 변환하는 것은 보통 쉬운 단계다.

플레임 그래프를 지원하는 프로파일링 제품과 회사도 이제 많다. 자세한 내용은 아래 "업데이트" 절을 참고하라.

### 변형

**Icicle chart**는 플레임 그래프를 위아래로 뒤집은 것이다. 이 방식을 선호하는 사람도 있다. 저자의 `flamegraph.pl`은 `--inverted` 옵션으로 이를 생성한다. 저자는 y축이 아래쪽 0부터 위로 스택 깊이를 세는 표준 "flame" 레이아웃을 선호하며, 위에서 아래로 훑으며 평평한 영역(plateau)을 찾는 데 익숙하다. 다만 매우 깊은 스택에서는 (맨 위부터 시작하는 GUI에서) 플레임 그래프 레이아웃의 초기 화면이 대부분 비어 있을 수 있어(가느다란 인터럽트 스택 몇 개뿐), 개발자가 프로파일의 대부분을 보려면 아래로 스크롤해야 하는 문제가 있다. root-to-leaf 순으로 읽는 것을 선호하는 개발자에게는 icicle 레이아웃이 스크롤 없이 항상 시작점을 화면에 보여준다는 장점이 있다. 이런 이유로 많은 플레임 그래프 구현체가 기본값으로 icicle 레이아웃을 쓴다. 다른 구현체는 flame 레이아웃을 쓰되 루트 프레임이 화면에 보이도록 아래쪽부터 표시하기 시작한다. 저자는 이에 대해 강한 의견은 없으며, 선호하는 쪽을 쓰면 된다고 말한다. 가능하면 최종 사용자가 원하는 레이아웃을 고를 수 있는 토글을 포함하는 것이 좋다.

**Flame chart**는 구글 크롬의 WebKit Web Inspector가 처음 추가했다([버그 트래커](https://bugs.webkit.org/show_bug.cgi?id=111162)). 플레임 그래프에서 영감을 받았지만, flame chart는 x축에 알파벳 대신 시간의 흐름을 놓는다. 이 덕분에 시간 기반 패턴을 연구할 수 있다. 플레임 그래프는 x축 샘플을 알파벳순으로 재정렬해 프레임 병합을 최대화하고, 프로파일의 큰 그림을 더 잘 보여준다. 멀티스레드 애플리케이션은 단일 flame chart로는 제대로 표시할 수 없지만 플레임 그래프로는 가능하다(flame chart는 원래 단일 스레드 자바스크립트 분석용으로 쓰였기에 이 문제를 다룰 필요가 없었다). 두 시각화 모두 유용하며, 가능하면 도구가 둘 다 제공해야 한다(예: TraceCompass는 실제로 둘 다 지원한다). 일부 분석 도구는 flame chart를 구현해 놓고 플레임 그래프라고 잘못 부르기도 한다.

**Sunburst 레이아웃**은 x축에 방사형(radial) 좌표를 써서 플레임 그래프를 계층적 파이 차트로 바꾼 것이다. 구글 Web Inspector 팀이 이를 [프로토타입](https://bugs.chromium.org/p/chromium/issues/detail?id=452624)으로 만들었다. 저자도 플레임 그래프와의 비교를 [별도 포스트](https://www.brendangregg.com/blog/2017-02-06/flamegraphs-vs-treemaps-vs-sunburst.html)에서 다뤘다.

### 기원

저자는 MySQL 성능 문제를 다루다가 CPU 사용량을 빠르고 깊이 있게 파악해야 했을 때 플레임 그래프를 발명했다. 기존 프로파일러/트레이서는 텍스트 벽만 만들어 냈기에 시각화를 탐색하기 시작했다. 처음에는 CPU 함수 호출을 트레이싱한 뒤 Neelakanth Nadgir의 콜스택 시간순 시각화 기법으로 그렸는데, 이 기법 자체는 Roch Bourbonnais의 CallStackAnalyzer와 Jan Boerhout의 vftrace에서 영감을 받은 것이었다. 이들은 플레임 그래프와 비슷해 보이지만 x축에 시간의 흐름을 둔다. 여기에는 두 가지 문제가 있었다. 함수 트레이싱의 오버헤드가 너무 커서 대상 시스템을 교란시켰고, 여러 초에 걸친 데이터를 표시하면 최종 시각화가 너무 밀도가 높아 읽기 어려웠다.

저자는 오버헤드 문제를 해결하기 위해 타임드 샘플링(프로파일링)으로 전환했다. 다만 샘플링은 사이에 공백이 있어 함수 흐름을 더 이상 알 수 없으므로, x축에서 시간을 버리고 프레임 병합을 최대화하도록 샘플을 재정렬했다. 이 방법이 통했고 최종 시각화는 훨씬 읽기 쉬워졌다. Neelakanth와 Roch의 시각화는 프레임을 구분하기 위해 완전히 무작위인 색을 썼다. 저자는 색 팔레트를 좁히는 편이 더 보기 좋다고 생각했고, 처음에는 CPU가 왜 "뜨거운(hot, 즉 바쁜)" 상태인지 설명하기 위해 따뜻한(warm) 색만 골랐다. 불꽃을 닮았다는 이유로 빠르게 "플레임 그래프"로 알려지게 되었다.

저자는 플레임 그래프로 이어진 원래 성능 문제를 위의 ACMQ/CACM 아티클에서 더 자세히 설명한다. 플레임 그래프 시각화는 사실 프로파일링된 스택 트레이스를 시각화하기 위해 저자가 사용한, 뒤집힌 icicle 레이아웃을 가진 인접(adjacency) 다이어그램이다.

### 업데이트

플레임 그래프는 2011년 12월에 공개되었다. 원문은 그 이후 있었던 소식을 연도별로 정리해 나열한다. 주요 흐름은 다음과 같다.

- **초기(2012년경)**: Alan Coopersmith가 X server의 플레임 그래프를 생성했고, Dave Pacheco가 node.js 함수용으로 만들었으며(이후 npm 패키지 stackvis로 발전), Max Bruning이 IP 스케일링 문제 해결에 활용했다. Zoltan Farkas는 플레임 그래프에서 영감을 받아 Java용 Spf4j를 만들었다.
- **2013년**: Linux perf/SystemTap 기반 커널 플레임 그래프 문서화, Mac OS X Instruments용 플레임 그래프(Mark Probst), Ruby MiniProfiler의 플레임 그래프(Sam Saffron), Windows Xperf 요약(Bruce Dawson), 구글 크롬의 Flame Charts 도입, Perl Devel::NYTProf에 플레임 그래프 통합(Tim Bunce) 등이 이어졌다.
- **2013년 하반기**: 메모리 누수/증가용 플레임 그래프 문서화(저자, 초록색으로 구분), Off-CPU Time 플레임 그래프(Yichun Zhang)로 블로킹 시간 문제 해결, node.js 대상 작성법 정리(Igor Soarez), V8 Flame Charts 데모(Paul Irish, Umar Hansa, Addy Osmani).
- **2014년**: USENIX/LISA13 본회의 발표 "Blazing Performance with Flame Graphs", Off-CPU 플레임 그래프와 Hot/Cold 플레임 그래프 문서화, Java lightweight-java-profiler 활용법, Erlang용 eflame(Vladimir Kirillov), Linux Node.js 플레임 그래프 생성법(Trevor Norris), Oracle 데이터베이스용 예시(Luca Canali), FreeBSD TCP 스택 락 경합 분석(Julien Charbon) 등.
- **2014년 말**: Facebook Strobelight의 뒤집힌 플레임 그래프 활용, 원본 FlameGraph 소프트웨어에 Click to Zoom 기능 추가(Adrien Mahieux), Differential 플레임 그래프 발표(저자), 이를 응용한 CPI 플레임 그래프(메모리 스톨 사이클 강조), FreeBSD 개발자 서밋에서의 발표, Node.js 플레임 그래프 문서화, Netflix의 "Node.js in Flames" 사례(Yunong Xiao).
- **2015년**: Erlang, GHC(Haskell), ODI(Oracle Data Integrator) 등 다양한 언어·도구로 확장. Google Chrome과 Firefox에 플레임 그래프/차트 토글 기능 요청 제출. mixed-mode Java 플레임 그래프 프리뷰(저자, `-XX:+PreserveFramePointer` 옵션으로 이어짐, JDK9와 JDK8u60에 반영). FlameGraphdiff(Cor-Paul Bezemer)로 A-B 차이 시각화. SpeedScope(Jamie Wong)가 time-order·left-heavy·sandwich 세 가지 뷰를 한 GUI에서 지원.
- **2016년**: Netflix Java in Flames(저자와 Martin Spier), 다양한 언어(Go, Python, GHC 등)의 플레임 그래프 도구 확산, ACMQ 아티클 "The Flame Graph" 발표(정의·기원·해석법·향후 발전 방향 정리), 0x(David Mark Clements)로 Node.js 인터랙티브 프로파일러 등장, Qt Creator 4.0.0에 통합.
- **2016년 하반기~2017년**: Go GC 지연 분석, eBay의 원클릭 프로덕션 플레임 그래프, Spark/Cassandra/PowerDNS 등 실제 성능 개선 사례 다수, ETW 플레임 그래프(Windows Performance Analyzer 지원), Linux 4.9의 효율적인 BPF 기반 프로파일러 소개.
- **2017년**: USENIX ATC 2017 발표 갱신, "Coloring Flame Graphs: Code Hues" 포스트, Oracle Developer Studio Performance Analyzer에 통합, LinkedIn의 Common Issue Detection for CPU Profiling, 파일 시스템용 플레임 그래프와 트리맵/선버스트 비교 포스트, Java Package Flame Graph 소개.
- **2017년 말~2018년**: FlameScope 공개(저자와 Martin Spier, Netflix, GitHub 오픈소스), Java Heap Allocation Flamegraphs, Windows PerfView·pprof 웹 UI에 병합, async-profiler로 Clojure 지원.
- **2019년**: SAP HANA, AMD uProf, YourKit, IntelliJ IDE, Percona(MySQL) 등 상용·오픈소스 도구에 폭넓게 통합.
- **2020년**: AWS CodeGuru Profiler, Google Cloud Profiler(largest-frame-left 정렬 기본값 사용)에 플레임 그래프 도입.
- **2021년**: Intel vTune에 플레임 그래프 추가.

저자는 이 페이지 마지막에 "플레임 그래프에 대해 글을 쓰고, 더 발전시키고, 결과를 공유해 준 모든 사람에게 감사하며, 앞으로도 이 페이지를 새 소식으로 계속 갱신하겠다"고 적었다.

## Napkin Math

> 원문: [sirupsen/napkin-math](https://github.com/sirupsen/napkin-math) (README.md)
> 저자: Simon Eskildsen (sirupsen) | 번역일: 2026-07-10
>
> 이 저장소는 MIT 라이선스로 배포된다. 아래는 README 전체 완역이다(표의 수치는 원문 그대로).

이 프로젝트의 목표는 시스템의 예상 성능을 원리로부터(first-principles) 빠르게 추정하는 데 쓰이는 소프트웨어, 수치, 기법을 모으는 것이다. 예를 들어 1GB의 메모리를 얼마나 빨리 읽을 수 있을까? 이런 자료를 조합하면 "초당 10만 요청(RPS)을 처리하는 애플리케이션의 로깅에 어느 정도의 스토리지 비용을 예상해야 하는가" 같은 흥미로운 질문에 답할 수 있다.

이 기술을 가장 잘 소개하는 자료는 [저자의 SRECON 발표](https://www.youtube.com/watch?v=IxkSlnrRFqc)다.

컴퓨터라는 거대한 영역에서 냅킨 수학(napkin math)을 연습하는 가장 좋은 방법은 자기 자신의 문제를 직접 풀어보는 것이다. 차선책은 **[이 뉴스레터](http://sirupsen.com/napkin)를 구독해 몇 주마다 연습할 문제를 받는 것**이다. 이 기법에 익숙해질수록 문제 하나를 푸는 데 몇 분밖에 걸리지 않을 것이다.

연습용 문제 아카이브는 [여기](https://sirupsen.com/napkin/)에 있다. 풀이는 그다음 뉴스레터에 실린다.

### 수치

아래 수치는 암기하기 좋게 반올림한 값이며, 가짜 정밀도(faux precision)를 나타내지 않는다.
이 저장소가 현재 단일 호스트에서 재측정할 수 있는 행들은 2026년 3월 8일 새로 만든 GCP `c4-standard-48-lssd` 인스턴스(Intel Xeon 6985P-C, 48 vCPU / 물리 코어 24개, RAM 180GB, Ubuntu 22.04.5 LTS)에서 재측정·재검증했다.

활성화된 Criterion 벤치마크 스위트를 돌리려면 `./run --bench napkin_math`를 실행해 올바른 최적화 수준과 Linux 튜닝을 적용하라. 디버그 모드로 컴파일하면 올바른 수치를 얻을 수 없다. 이 래퍼는 내부적으로 이미 `sudo`를 사용한다. 잠긴(locked-down) 클라우드 이미지에서는 실행 전 `sudo sysctl -w kernel.perf_event_paranoid=-1`을 한 번 실행하라. 새 스위트를 추가하고 빈칸을 채워 이 프로젝트에 기여할 수 있다.

**참고:** 현재 활성 벤치마크 경로는 `benches/`의 Criterion.rs다. `src/main.rs`는 여전히 예전 방식의 임시(ad hoc) 하네스이며, 아직 완전히 마이그레이션·재검증되지 않은 벤치마크에 대해서는 여전히 정본(source of truth)이다. 현재 Criterion 스위트에는 `blob_storage`, `memory_read`, `memory_random`, `hash`, `syscall`, `sort`, `serialization`, `compression`, `compressed_memory_read`가 포함된다. 현재 SSD 관련 행들은 `NAPKIN_BENCH_FILE`을 RAID0 로컬 SSD 마운트로 지정한 예전 하네스로 재측정한 값이다. `compressed_memory_read` Criterion 벤치마크는 BitPacker 정수 언팩 마이크로벤치마크이며, 위의 범용 `[11]` 압축/압축 해제 행을 다시 쓰는 데 쓰면 안 된다. 새로운 `serialization`과 `compression` Criterion 그룹은 워크로드에 특화되어 있으며, 아직 위의 범용 README 행에 연결되어 있지 않다.

새로운 `blob_storage` Criterion 그룹은 옵트인(opt-in)이고 자격 증명이 필요하다. `NAPKIN_GCS_BUCKET` 그리고/또는 `NAPKIN_S3_BUCKET`을 설정하라. GCS와 S3 경로 모두 이제 AWS S3 SDK를 사용한다. GCS 쪽은 GCS XML 상호운용 엔드포인트와 통신하며 `NAPKIN_GCS_ACCESS_KEY`와 `NAPKIN_GCS_SECRET_KEY`가 필요하다. S3 쪽은 `NAPKIN_S3_PROFILE`(기본값 `tpuf-test`)의 로컬 AWS 프로파일과 `NAPKIN_S3_REGION`(기본값 `us-west-2`)을 사용한다.

병렬(concurrent) `get_offsets`와 `put_multipart` 경로는 멀티스레드 Tokio 런타임으로 명시적으로 팬아웃(fan out)하므로, 범위(range) 수나 오브젝트 수가 충분히 많으면 호스트 NIC 한계에 근접할 수 있다. 2026년 3월 9일 기준, 동일 리전 `1 GiB` 단일 스트림 GET은 S3(`us-west-2a`의 `m6id.12xlarge`)에서 약 `95 MiB/s`, GCS XML(`us-central1-c`의 `c4-standard-48-lssd`)에서 약 `190-200 MiB/s`를 기록했다. 같은 머신에서 명시적 병렬 range GET은 S3에서 약 `2.0 GiB/s`, GCS에서 약 `4.9 GiB/s`에 도달했고, 멀티파트 PUT은 S3에서 약 `1.8-1.9 GiB/s`, GCS에서 약 `3.3 GiB/s`에 도달했다. AWS 자체의 S3 가이드는 `10 Gbps` 인스턴스를 포화시킬 때 병렬 요청당 약 `85-90 MB/s`를 잡으라고 제안하는데, 이는 측정한 S3 단일 스트림 결과와 거의 일치했다. 기존의 `500 MiB/s` 단일 스트림 blob GET 행은 두 클라우드 제공자 어디서도 재현되지 않아, 보수적인 범용 값 `100 MiB/s`로 하향 수정했다. 현재의 blob 스토리지 작업은 첫 바이트 지연 시간보다는 처리량을 훨씬 더 많이 재검증했다. 위의 `50 ms` / `150 ms` 지연 시간 셀은 소형 객체/첫 바이트 도달 시간(time-to-first-byte) 전용 측정이 추가되기 전까지는 여전히 대략적인 어림값으로 보아야 한다.

이제 `src/bin/s3_latency.rs`에 전용 소형 객체 지연 측정 도구가 있다. `./script/blob-latency s3` 또는 `./script/blob-latency gcs`를 실행하면 기본 `8 KiB .. 8 MiB` 크기 사다리를 따라 `get`, `put`, `if_none_match`, `put_if_match`를 훑는다. 단 `if_none_match`는 작은 크기 범위에서 지연 시간이 사실상 평탄했기 때문에 이제 기본값으로 `128 KiB` 행 하나만 측정한다. 더 작거나 클라우드 제공자에 특화된 실행을 원하면 `NAPKIN_BLOB_LATENCY_OPS`, `NAPKIN_BLOB_LATENCY_SIZES`, `NAPKIN_BLOB_LATENCY_IF_NONE_MATCH_SIZES`를 재정의하라. 이 지연 시간 측정 도구는 이제 행당 기본 `300`초의 실측 시간(wall-clock) 예산을 쓰며, 그 시간 안에 들어가는 만큼 샘플을 수집한다. `NAPKIN_BLOB_LATENCY_ROW_SECONDS`로 이를 조정하고, 개수 제한 방식의 짧은 실험을 원하면 `NAPKIN_BLOB_LATENCY_SAMPLE_CAP`(또는 예전 별칭 `NAPKIN_BLOB_LATENCY_SAMPLES`)로 상한을 둘 수 있다.

`list` 연산은 이제 기본으로 더 큰 네임스페이스(`10만` 키)를 시딩하고, 동일한 작은 고정 프리픽스를 반복 스캔하는 대신 `start_after`를 통해 샘플마다 무작위 `1000`키 페이지 하나를 측정한다. `NAPKIN_BLOB_LATENCY_LIST_NAMESPACE_KEYS`, `NAPKIN_BLOB_LATENCY_LIST_KEYS`, `NAPKIN_BLOB_LATENCY_LIST_SEED_CONCURRENCY`로 이 형태를 조정할 수 있다. 예전처럼 네임스페이스 전체를 훑고 싶다면 `NAPKIN_BLOB_LATENCY_OPS`에 `list_full_scan`을 추가하라.

정렬된(aligned) range-read 지연 시간의 경우, `./script/blob-random-range-latency`는 `128 KiB` 정렬 형태를 측정하고 `./script/blob-random-range-latency-8m`은 동일한 `128 x 1 GiB` 오브젝트 풀에 대해 `8 MiB` 정렬 형태를 측정한다. `./script/blob-random-range-latency-8m-multipart`는 `8 MiB` 파트로 멀티파트 업로드를 통해 그 `1 GiB` 소스 오브젝트들을 시딩한 뒤, 그 멀티파트 경계에 맞춰 `8 MiB` 정렬 읽기를 측정한다.

`memory_read`는 이제 Criterion에서 명시적으로 `No SIMD`와 `SIMD` 변형을 내보내지만, README는 암기하기 쉽도록 의도적으로 이를 단일 스레드 행 하나와 멀티스레드 행 하나로 합쳐 보여준다.

저자는 이 스위트에 일부 비효율이 있음을 알고 있다. 실제 운영 환경에서 짜낼 수 있는 성능의 상한(upper-bound)에 가까운 수치가 되도록 이 영역의 실력을 계속 키울 생각이다. 대부분의 사용자에게는 문제가 되지 않을 정도로, 이 수치들이 2~3배 이상 벗어날 가능성은 매우 낮다고 본다.

### 기법

- **과도하게 복잡하게 만들지 마라.** 계산의 근거가 되는 가정이 6개를 넘어간다면, 필요 이상으로 어렵게 만들고 있을 가능성이 크다.
- **단위를 유지하라.** 단위는 좋은 검산(checksum) 수단이다. KiB를 TiB로 바꾸는 등의 변환이 필요하면 [Wolframalpha](https://wolframalpha.com)가 훌륭한 도움을 준다.
- **지수로 계산하라.** 어림 계산 대부분은 계수와 지수만으로 이루어진다. 예를 들면 `c * 10^e` 형태다. 목표는 자릿수(order of magnitude), 즉 `e`만 맞추는 것이다. `c`는 훨씬 덜 중요하다. 한 자리 계수와 지수만 신경 쓰면 냅킨 위에서 계산하기가 훨씬 쉬워진다(0을 잔뜩 적을 필요도 없다).
- **페르미 분해(Fermi decomposition)를 수행하라.** 답을 어렴풋이 짐작할 수 있을 때까지, 추측 가능한 요소들을 적어 내려가라. 로깅용 스토리지 비용을 알고 싶다면 로그 한 줄의 크기, 초당 로그 줄 수, 그 비용 등을 순서대로 알아야 할 것이다.

- [Top-Down 성능 분석 방법론](https://easyperf.net/blog/2019/02/09/Top-Down-performance-analysis-methodology). `toplev`로 병목을 찾는 유용한 글. 이 저장소의 벤치마크 스위트가 올바르게 작성되었는지 확인하는 데 특히 유용하다(아직 이 스위트에 적용하지는 않았지만 계획 중이다).
- [Godbolt의 컴파일러 익스플로러](https://gcc.godbolt.org/#). Rust와 Clang/GCC의 C 어셈블리를 비교하는 데 훌륭한 자료.
- [cargo-show-asm](https://github.com/pacak/cargo-show-asm). 함수를 역어셈블할 수 있게 해 주는 Cargo 확장. 다만 클로저 지원이 다소 부족해 일부 리팩터링이 필요하다.
- [Agner의 어셈블리 가이드](https://www.agner.org/optimize/optimizing_assembly.pdf). 최적의 어셈블리를 작성하는 훌륭한 자료로, 이 스위트의 여러 함수에서 비효율을 찾아보는 데 유용하다.
- [Agner의 명령어 표](https://www.agner.org/optimize/instruction_tables.pdf). 다양한 명령어의 예상 처리량을 다루는 상세한 자료로, 어셈블리를 살펴볼 때 도움이 된다.
- [halobates.de](http://halobates.de/). `toplev` 저자가 쓴 저수준 성능 관련 유용한 자료.
- [Systems Performance (책)](https://www.amazon.com/Systems-Performance-Enterprise-Brendan-Gregg/dp/0133390098/ref=sr_1_1?keywords=systems+performance&qid=1580733419&sr=8-1). 시스템 성능 분석, 병목 찾기, 운영체제 이해를 다룬 훌륭한 책.
- [io_uring](https://lwn.net/Articles/776703/). 가장 좋은 요약이며 여러 자료로 연결된다.
- [컨텍스트 스위치에 걸리는 시간](https://blog.tsunanet.net/2010/11/how-long-does-it-take-to-make-context.html)
- [정수 압축 비교](https://github.com/powturbo/TurboPFor-Integer-Compression)
- [파일은 어렵다(Files are hard)](https://danluu.com/file-consistency/)
