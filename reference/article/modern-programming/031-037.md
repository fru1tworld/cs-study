# 모던 프로그래밍 031-037

## 메모리 배리어는 소스 컨트롤 작업과 같다

> 원문: [Memory Barriers Are Like Source Control Operations](https://preshing.com/20120710/memory-barriers-are-like-source-control-operations/)
> 저자: Jeff Preshing | 번역일: 2026-07-10

소스 컨트롤을 쓰고 있다면, 당신은 이미 메모리 순서(memory ordering)를 이해하는 길에 들어선 셈이다. 메모리 순서는 C, C++ 및 다른 언어로 락프리 코드를 작성할 때 중요하게 고려해야 할 사항이다.

지난 글에서는 메모리 순서 퍼즐의 절반에 해당하는 [컴파일 시점의 메모리 순서](http://preshing.com/20120625/memory-ordering-at-compile-time)를 다뤘다. 이번 글은 나머지 절반, 즉 런타임에 프로세서 자체에서 일어나는 메모리 순서에 관한 것이다. 컴파일러 재배열과 마찬가지로, 프로세서 재배열은 단일 스레드 프로그램에서는 보이지 않는다. [락프리 기법](http://preshing.com/20120612/an-introduction-to-lock-free-programming)을 쓸 때 — 즉 스레드 간 상호 배제 없이 공유 메모리를 조작할 때 — 비로소 드러난다. 다만 컴파일러 재배열과 달리 프로세서 재배열의 효과는 [멀티코어와 멀티프로세서 시스템에서만 보인다](http://preshing.com/20120515/memory-reordering-caught-in-the-act).

**메모리 배리어(memory barrier)** 역할을 하는 명령어를 발행하면 프로세서에서 올바른 메모리 순서를 강제할 수 있다. 어떤 면에서는 이것이 알아야 할 유일한 기법이다. 그런 명령어를 쓰면 컴파일러 순서는 자동으로 처리되기 때문이다. 메모리 배리어 역할을 하는 명령어의 예로는 다음이 있다(이게 전부는 아니다):

- GCC의 특정 인라인 어셈블리 지시문, 예: PowerPC 전용 `asm volatile("lwsync" ::: "memory")`
- 모든 [Win32 Interlocked 연산](http://msdn.microsoft.com/en-us/library/windows/desktop/ms684122.aspx) (Xbox 360 제외)
- [C++11 원자적 타입](http://en.cppreference.com/w/cpp/atomic/atomic)의 많은 연산, 예: `load(std::memory_order_acquire)`
- POSIX 뮤텍스 연산, 예: [`pthread_mutex_lock`](http://linux.die.net/man/3/pthread_mutex_lock)

메모리 배리어 역할을 하는 명령어가 많은 것처럼, 알아야 할 메모리 배리어의 종류도 많다. 실제로 위 명령어들이 전부 같은 종류의 메모리 배리어를 만드는 것은 아니다 — 락프리 코드를 작성할 때 혼란을 일으킬 수 있는 또 하나의 지점이다. 이를 어느 정도 정리해 보고자, 가능한 메모리 배리어 유형의 대다수(전부는 아니다)를 이해하는 데 도움이 됐던 비유 하나를 제시하려 한다.

먼저 전형적인 멀티코어 시스템의 아키텍처를 생각해 보자. 코어가 두 개인 장치가 있고, 각 코어는 32 KiB의 전용 L1 데이터 캐시를 갖는다. 두 코어가 공유하는 1 MiB의 L2 캐시가 있고, 512 MiB의 메인 메모리가 있다.

![](https://preshing.com/images/cpu-diagram.png)

멀티코어 시스템은 기묘한 소스 컨트롤 전략을 쓰며 한 프로젝트에서 협업하는 프로그래머 집단과 약간 비슷하다. 예를 들어 위의 듀얼코어 시스템은 프로그래머가 딱 두 명인 시나리오에 대응한다. 이름을 Larry와 Sergey라고 하자.

![](https://preshing.com/images/source-control-analogy.png)

오른쪽에는 공유되는 중앙 저장소가 있다. 이것은 메인 메모리와 공유 L2 캐시를 합친 것을 나타낸다. Larry는 자기 로컬 머신에 저장소의 완전한 작업 사본(working copy)을 갖고 있고, Sergey도 마찬가지다. 이것들은 (사실상) 각 CPU 코어에 붙어 있는 L1 캐시를 나타낸다. 각 머신에는 레지스터나 지역 변수를 개인적으로 관리하는 스크래치 영역도 있다. 두 프로그래머는 거기 앉아 작업 사본과 스크래치 영역을 정신없이 편집하면서, 눈에 보이는 데이터를 근거로 다음에 뭘 할지 결정한다 — 그 코어에서 돌아가는 실행 스레드와 똑 닮았다.

이제 소스 컨트롤 전략 차례다. 이 비유에서 소스 컨트롤 전략은 정말이지 아주 이상하다. Larry와 Sergey가 저장소의 작업 사본을 수정하면, 그 수정 사항이 백그라운드에서 완전히 무작위한 시점에 중앙 저장소로, 그리고 중앙 저장소로부터 끊임없이 **새어 나간다(leaking)**. Larry가 파일 X를 편집하면 그 변경은 중앙 저장소로 새어 나가겠지만, 언제 그럴지는 아무 보장이 없다. 즉시일 수도 있고, 한참, 아주 한참 뒤일 수도 있다. 그가 이어서 다른 파일 Y와 Z를 편집하면, 그 수정들이 X보다 *먼저* 저장소로 새어 들어갈 수도 있다. 이런 식으로 store는 저장소로 가는 길에 사실상 재배열된다.

마찬가지로 Sergey의 머신에서도, 그 변경들이 저장소에서 *그의* 작업 사본으로 새어 *돌아오는* 시점이나 순서에 아무 보장이 없다. 이런 식으로 load는 저장소에서 나오는 길에 사실상 재배열된다.

자, 두 프로그래머가 저장소의 완전히 다른 부분에서 작업한다면, 어느 쪽도 이런 백그라운드 누출이 일어나고 있다는 것도, 심지어 상대 프로그래머의 존재조차도 알아차리지 못할 것이다. 이는 독립된 단일 스레드 프로세스 두 개를 실행하는 것에 해당한다. 이 경우 [메모리 순서의 제1 규칙](http://preshing.com/20120625/memory-ordering-at-compile-time)은 지켜진다.

이 비유는 두 프로그래머가 저장소의 같은 부분에서 작업하기 시작할 때 더 쓸모 있어진다. [이전 글](http://preshing.com/20120515/memory-reordering-caught-in-the-act)에서 들었던 예를 다시 보자. X와 Y는 전역 변수이고 둘 다 처음에는 0이다:

![](https://preshing.com/images/marked-example2-2.png)

X와 Y를 Larry의 작업 사본, Sergey의 작업 사본, 그리고 중앙 저장소 자체에 존재하는 파일이라고 생각하라. Larry가 자기 작업 사본의 X에 1을 쓰고, 거의 같은 시각에 Sergey가 자기 작업 사본의 Y에 1을 쓴다. 각 프로그래머가 자기 작업 사본에서 *상대편* 파일을 확인하기 전에 어느 수정도 저장소로 새어 나갔다가 돌아올 시간이 없었다면, 결과는 r1 = 0이면서 r2 = 0이 된다. 처음에는 직관에 어긋나 보였을 이 결과가, 소스 컨트롤 비유에서는 오히려 꽤 당연해진다.

![](https://preshing.com/images/iriw-state.png)

### 메모리 배리어의 종류

다행히 Larry와 Sergey가 백그라운드에서 일어나는 이 무작위하고 예측 불가능한 누출에 전적으로 휘둘리기만 하는 것은 아니다. 그들에게는 펜스(fence) 명령어라 불리는 특수 명령어를 발행할 능력이 있고, 이 명령어들이 메모리 배리어 역할을 한다. 이 비유에서는 네 가지 유형의 메모리 배리어, 즉 네 가지 펜스 명령어를 정의하면 충분하다. 각 메모리 배리어 유형의 이름은 그것이 막도록 설계된 메모리 재배열의 유형에서 따왔다. 예를 들어 `#StoreLoad`는 store 뒤에 오는 load의 재배열을 막도록 설계되었다.

![](https://preshing.com/images/barrier-types.png)

[Doug Lea가 지적하듯](http://g.oswego.edu/dl/jmm/cookbook.html), 이 네 범주는 실제 CPU의 특정 명령어들과 꽤 잘 대응한다 — 정확히 일치하지는 않지만. 대부분의 경우 실제 CPU 명령어는 위 배리어 유형들의 어떤 조합으로 동작하며, 다른 효과가 더해지기도 한다. 어쨌든 소스 컨트롤 비유 안에서 이 네 가지 메모리 배리어를 이해하고 나면, 실제 CPU의 수많은 명령어뿐 아니라 여러 고수준 프로그래밍 언어 구성 요소도 이해할 좋은 위치에 서게 된다.

#### #LoadLoad

LoadLoad 배리어는 배리어 앞에서 수행된 load와 배리어 뒤에서 수행된 load의 재배열을 사실상 막는다.

우리 비유에서 `#LoadLoad` 펜스 명령어는 기본적으로 중앙 저장소로부터의 **pull**에 해당한다. `git pull`, `hg pull`, `p4 sync`, `svn update`, `cvs update`를 떠올리되, 전부 저장소 전체에 작용한다고 생각하라. 로컬 변경과 병합 충돌이 나면, 뭐, 무작위로 해결된다고 해두자.

![](https://preshing.com/images/loadload.png)

한 가지 유의할 점: `#LoadLoad`가 저장소 전체의 최신(head) 리비전을 pull한다는 보장은 없다! head보다 오래된 리비전을 pull할 수도 있다. 단, 그 리비전이 *중앙 저장소에서 자신의 로컬 머신으로 새어 들어온 가장 새로운 값 이상으로 새것*이기만 하면 된다.

약한 보장처럼 들릴 수 있지만, 오래된(stale) 데이터를 보는 것을 막는 데는 여전히 더할 나위 없이 좋은 방법이다. 고전적인 예를 보자. Sergey가 Larry가 어떤 데이터를 게시했는지 공유 플래그로 확인한다. 플래그가 참이면, 게시된 값을 읽기 전에 `#LoadLoad` 배리어를 발행한다:

```cpp
if (IsPublished)                   // 공유 플래그를 load하여 확인
{
    LOADLOAD_FENCE();              // load의 재배열을 방지
    return Value;                  // 게시된 값을 load
}
```

물론 이 예는 `IsPublished` 플래그가 저절로 Sergey의 작업 사본으로 새어 들어오는 것에 의존한다. 그게 정확히 언제 일어나는지는 중요하지 않다. 새어 들어온 플래그가 관찰되고 나면, 그는 `#LoadLoad` 펜스를 발행해 플래그 자체보다 오래된 `Value`의 값을 읽는 것을 막는다.

#### #StoreStore

StoreStore 배리어는 배리어 앞에서 수행된 store와 배리어 뒤에서 수행된 store의 재배열을 사실상 막는다.

우리 비유에서 `#StoreStore` 펜스 명령어는 중앙 저장소로의 **push**에 해당한다. `git push`, `hg push`, `p4 submit`, `svn commit`, `cvs commit`을 떠올리되, 전부 저장소 전체에 작용한다고 생각하라.

![](https://preshing.com/images/storestore.png)

한 가지 반전을 더하자면, `#StoreStore` 명령어는 **즉각적이지 않다**고 가정하자. 지연된, 비동기적인 방식으로 수행된다. 그래서 Larry가 `#StoreStore`를 실행하더라도, 그의 이전 store들이 마침내 중앙 저장소에서 보이게 되는 시점에 대해서는 아무것도 가정할 수 없다.

이 역시 약한 보장처럼 들릴 수 있지만, 다시 말하건대 Sergey가 Larry가 게시한 오래된 데이터를 보는 것을 막는 데는 완벽히 충분하다. 위와 같은 예로 돌아가면, Larry는 공유 메모리에 데이터를 게시하고, `#StoreStore` 배리어를 발행한 뒤, 공유 플래그를 참으로 설정하기만 하면 된다:

```cpp
Value = x;                         // 데이터를 게시
STORESTORE_FENCE();
IsPublished = 1;                   // 데이터가 준비됐음을 알리는 공유 플래그 설정
```

여기서도 우리는 `IsPublished`의 값이 저절로 Larry의 작업 사본에서 Sergey의 작업 사본으로 새어 가기를 기대하고 있다. Sergey가 그것을 감지하면, 그는 올바른 `Value` 값을 보게 되리라 확신할 수 있다. 흥미로운 점은, 이 패턴이 동작하기 위해 `Value`가 원자적 타입일 필요조차 없다는 것이다. 원소가 잔뜩 든 거대한 구조체여도 상관없다.

#### #LoadStore

![](https://preshing.com/images/get-back-to-later.png)`#LoadLoad`나 `#StoreStore`와 달리, `#LoadStore`에는 소스 컨트롤 작업으로 표현할 기발한 은유가 없다. `#LoadStore` 배리어를 이해하는 가장 좋은 방법은, 아주 단순하게, 명령어 재배열의 관점에서 보는 것이다.

Larry에게 따라야 할 명령어 목록이 있다고 상상하자. 어떤 명령어는 그의 개인 작업 사본에서 레지스터로 데이터를 load하게 하고, 어떤 명령어는 레지스터의 데이터를 작업 사본으로 store하게 한다. Larry는 명령어를 뒤섞을 수 있는데, 특정한 경우에만 가능하다. load를 만나면 그 뒤에 오는 store들을 미리 살펴본다. 그 store들이 현재 load와 *완전히 무관*하다면, 먼저 건너뛰어 store들을 처리하고 나서 돌아와 load를 마무리하는 것이 허용된다. 이런 경우에도 메모리 순서의 제1 규칙 — 단일 스레드 프로그램의 동작을 절대 바꾸지 않는다 — 은 여전히 지켜진다.

실제 CPU에서는, 이를테면 load에서 캐시 미스가 나고 뒤이은 store에서 캐시 히트가 나는 경우 일부 프로세서에서 이런 명령어 재배열이 일어날 수 있다. 하지만 비유를 이해하는 데 그런 하드웨어 세부 사항은 별로 중요하지 않다. 그냥 Larry의 일이 지루한데, 이때가 그에게 창의력 발휘가 허락되는 몇 안 되는 순간이라고 해두자. 그가 그렇게 할지 말지는 전혀 예측할 수 없다. 다행히 이것은 막는 비용이 비교적 저렴한 유형의 재배열이다. Larry는 `#LoadStore` 배리어를 만나면 그 배리어 주위에서 이런 재배열을 삼가기만 하면 된다.

우리 비유에서는 load와 store 사이에 `#LoadLoad`나 `#StoreStore` 배리어가 있어도 Larry가 이런 LoadStore 재배열을 수행하는 것이 유효하다. 하지만 실제 CPU에서 `#LoadStore` 배리어 역할을 하는 명령어는 보통 그 두 배리어 유형 중 적어도 하나의 역할도 겸한다.

#### #StoreLoad

StoreLoad 배리어는 배리어 앞에서 수행된 모든 store가 다른 프로세서들에게 보이게 하고, 배리어 뒤에서 수행된 모든 load가 배리어 시점에 보이는 최신 값을 받도록 보장한다. 다시 말해, [순차 일관성](http://preshing.com/20120612/an-introduction-to-lock-free-programming#sequential-consistency)을 갖춘 멀티프로세서가 그 연산들을 수행하는 방식을 존중하면서, 배리어 앞의 모든 store와 배리어 뒤의 모든 load 사이의 재배열을 사실상 막는다.

`#StoreLoad`는 유일무이하다. [Memory Reordering Caught in the Act](http://preshing.com/20120515/memory-reordering-caught-in-the-act)의 예제 — 이 글 앞부분에서 반복한 바로 그 예제 — 에서 r1 = r2 = 0이라는 결과를 막을 수 있는 유일한 유형의 메모리 배리어다.

여기까지 잘 따라왔다면 궁금할 것이다. `#StoreLoad`는 `#StoreStore` 뒤에 `#LoadLoad`를 붙인 것과 뭐가 다른가? 어쨌든 `#StoreStore`는 변경을 중앙 저장소로 push하고 `#LoadLoad`는 원격 변경을 pull해 오지 않는가. 하지만 그 두 배리어 유형만으로는 불충분하다. 기억하라, push 연산은 임의 개수의 명령어만큼 지연될 수 있고, pull 연산은 head 리비전을 pull하지 않을 수 있다. 이것이 PowerPC의 `lwsync` 명령어 — `#LoadLoad`, `#LoadStore`, `#StoreStore` 세 가지 배리어 역할은 전부 하지만 `#StoreLoad`는 아닌 — 가 그 예제에서 r1 = r2 = 0을 막기에 불충분한 이유를 시사한다.

비유의 관점에서 `#StoreLoad` 배리어는, 모든 로컬 변경을 중앙 저장소에 push하고, 그 작업이 완료되기를 기다린 다음, 저장소의 절대적으로 최신인 head 리비전을 pull하는 것으로 달성할 수 있다. 대부분의 프로세서에서 `#StoreLoad` 배리어 역할을 하는 명령어는 다른 배리어 유형 역할을 하는 명령어보다 비싼 경향이 있다.

![](https://preshing.com/images/storeload.png)

여기에 `#LoadStore` 배리어를 하나 더 얹으면 — 별로 대단한 일도 아니다 — 우리가 얻는 것은 전체 메모리 펜스(full memory fence), 즉 네 가지 배리어 유형 모두를 한꺼번에 수행하는 것이다. [역시 Doug Lea가 지적하듯](http://g.oswego.edu/dl/jmm/cookbook.html), 공교롭게도 현존하는 모든 프로세서에서 `#StoreLoad` 배리어 역할을 하는 명령어는 전부 전체 메모리 펜스 역할도 한다.

### 이 비유는 어디까지 통할까?

앞서 언급했듯, 메모리 순서에 관해서는 [프로세서마다 습성이 다르다](http://preshing.com/20120612/an-introduction-to-lock-free-programming#different-processors-have). 특히 x86/64 계열은 강한 메모리 모델을 갖는다. 메모리 재배열을 최소한으로 유지하는 것으로 알려져 있다. PowerPC와 ARM은 더 약한 메모리 모델을 갖고, Alpha는 독보적인 존재로 유명하다. 다행히 이 글에서 제시한 비유는 [약한 메모리 모델](http://preshing.com/20120930/weak-vs-strong-memory-models)에 대응한다. 이 비유를 머릿속에 담아두고 여기서 소개한 펜스 명령어로 올바른 메모리 순서를 강제할 수 있다면, 대부분의 CPU를 다룰 수 있을 것이다.

이 비유는 C++11(예전 이름 C++0x)과 C11이 대상으로 삼는 추상 기계와도 꽤 잘 대응한다. 따라서 이 비유를 염두에 두고 그 언어들의 표준 라이브러리로 락프리 코드를 작성하면, 어떤 플랫폼에서든 올바르게 동작할 가능성이 더 높다.

이 비유에서 나는 각 프로그래머가 별도의 코어에서 실행되는 단일 실행 스레드를 나타낸다고 말했다. 실제 운영체제에서 스레드는 살아 있는 동안 여러 코어 사이를 옮겨 다니는 경향이 있지만, 비유는 여전히 유효하다. 또 기계어 예제와 C/C++ 예제를 번갈아 사용했다. 당연히 우리는 C/C++이나 다른 고수준 언어를 쓰는 편을 선호할 것이다. 이것이 가능한 이유는, 다시 말하지만, 메모리 배리어 역할을 하는 모든 연산은 [컴파일러 재배열](http://preshing.com/20120625/memory-ordering-at-compile-time)도 막기 때문이다.

모든 종류의 메모리 배리어를 다 다룬 것은 아니다. 예를 들어 [데이터 의존성 배리어](http://www.mjmwired.net/kernel/Documentation/memory-barriers.txt#305)도 있다. 이후 글에서 더 설명하겠다. 그래도 여기서 소개한 네 가지가 큰 축이다.

CPU가 내부에서 어떻게 동작하는지 — 스토어 버퍼, 캐시 일관성 프로토콜 같은 하드웨어 구현 세부 사항 — 그리고 애초에 왜 메모리 재배열을 수행하는지 궁금하다면, Paul McKenney와 David Howells의 [훌륭한](http://www.rdrop.com/users/paulmck/scalability/paper/whymb.2010.07.23a.pdf) [작업물](http://www.kernel.org/doc/Documentation/memory-barriers.txt)을 추천한다. 실제로 락프리 코드를 성공적으로 작성해 본 프로그래머라면 대부분 그런 하드웨어 세부 사항에 최소한 스치듯이라도 익숙하리라 짐작한다.

## 젊은 피를 위한 분산 시스템 노트

> 원문: [Notes on Distributed Systems for Young Bloods](https://www.somethingsimilar.com/2013/01/14/notes-on-distributed-systems-for-young-bloods/)
> 저자: Jeff Hodges | 번역일: 2026-07-10

분산 시스템 엔지니어가 실무에서 배우는 교훈을 곰곰이 생각해 봤다. 우리가 받는 가르침의 상당 부분은 프로덕션 트래픽에서 저지른 실수가 남긴 흉터다. 이 흉터가 유용한 경고판인 것은 맞지만, 손가락을 다 온전히 가진 엔지니어가 더 많아지는 편이 낫지 않겠는가.

새로 온 시스템 엔지니어는 독학 과정에서 [분산 컴퓨팅의 오류들(Fallacies of Distributed Computing)](http://en.wikipedia.org/wiki/Fallacies_of_Distributed_Computing)과 [CAP 정리](http://codahale.com/you-cant-sacrifice-partition-tolerance/)를 접하게 된다. 하지만 이것들은 추상적인 내용이라, 경험 없는 엔지니어가 첫발을 떼는 데 필요한 직접적이고 실행 가능한 조언이 아니다[^1]. 새로 온 엔지니어가 일을 시작할 때 주어지는 맥락이 얼마나 적은지 놀라울 정도다.

아래는 내가 분산 시스템 엔지니어로 일하며 배운 것 중, 신입 엔지니어에게 들려줄 가치가 있는 교훈의 목록이다. 미묘한 것도 있고 놀라운 것도 있지만, 논쟁의 여지가 있는 것은 없다. 이 목록은 새로 분산 시스템에 뛰어드는 엔지니어가 이 분야를 어떻게 생각해야 할지 이끌어 주기 위한 것이다. 망라적이지는 않지만 좋은 출발점이 될 것이다.

이 목록의 가장 큰 결점은 기술적 문제에 집중하느라 엔지니어가 마주칠 사회적 문제는 거의 다루지 않는다는 것이다. 분산 시스템은 더 많은 머신과 자본을 필요로 하기 때문에, 그 엔지니어들은 더 많은 팀, 더 큰 조직과 함께 일하는 경향이 있다. 소프트웨어 개발자의 일에서 가장 어려운 부분은 대개 사람에 관한 것이고, 분산 시스템 개발에서는 특히 더 그럴 것이다.

우리의 배경, 교육, 경험은 사회적 해법이 더 효율적이고 더 만족스러운 상황에서조차 기술적 해법 쪽으로 우리를 기울게 한다. 그 편향을 바로잡으려 노력하자. 사람은 컴퓨터보다 덜 까다롭다. 인터페이스가 조금 덜 표준화되어 있을 뿐이다.

자, 시작하자.

**분산 시스템이 다른 이유는 자주 실패하기 때문이다.** 분산 시스템이 다른 소프트웨어 엔지니어링 분야와 무엇이 다르냐고 물으면, 신입 엔지니어는 흔히 지연 시간(latency)을 꼽으며 그것이 분산 계산을 어렵게 만든다고 믿는다.

하지만 틀렸다. 분산 시스템 엔지니어링을 구별 짓는 것은 실패의 확률, 그리고 더 나쁘게는 부분 실패(partial failure)의 확률이다. 올바르게 작성된 뮤텍스 해제가 에러와 함께 실패하면 프로세스가 불안정하다고 판단하고 크래시시키면 된다. 하지만 분산 뮤텍스의 해제 실패는 락 프로토콜 안에 처리 방법이 설계되어 있어야 한다.

분산 계산을 해 보지 않은 시스템 엔지니어는 "그냥 두 머신 모두에 쓰기를 보내면 되지" 또는 "성공할 때까지 쓰기를 재시도하면 되지" 같은 아이디어를 내놓는다. 이런 엔지니어들은 네트워크로 연결된 시스템이 단일 머신 위의 시스템보다 더 자주 실패하며 그 실패가 전체가 아니라 부분적인 경향이 있다는 사실을, 머리로는 대개 인정하면서도, 완전히 받아들이지는 못한 것이다. 두 쓰기 중 하나는 성공하고 다른 하나는 실패할 수 있다. 그러면 이제 데이터의 일관된 뷰를 어떻게 얻을 것인가? 이런 부분 실패는 추론하기가 훨씬 어렵다.

스위치가 죽고, 가비지 컬렉션 일시 정지가 리더를 "사라지게" 만들고, 소켓 쓰기는 성공한 것처럼 보이지만 실제로는 상대 머신에서 실패했고, 한 머신의 느린 디스크 드라이브가 클러스터 전체의 통신 프로토콜을 기어가게 만들고, 등등. 로컬 메모리에서 읽는 것이 스위치 몇 개 너머에서 읽는 것보다 그냥 더 안정적이다.

실패를 위해 설계하라.

**견고한 분산 시스템을 작성하는 데는 견고한 단일 머신 시스템을 작성하는 것보다 더 큰 비용이 든다.** 견고한 분산 해법을 만드는 데 단일 머신 해법보다 더 많은 돈이 드는 이유는 여러 머신에서만 발생하는 실패들이 있기 때문이다. 가상 머신과 클라우드 기술 덕분에 분산 시스템 엔지니어링이 저렴해지긴 했지만, 이미 소유한 컴퓨터에서 설계·구현·테스트할 수 있는 것만큼 저렴하지는 않다. 그리고 단일 머신에서 재현하기 어려운 실패 조건들이 있다. 공유 머신에 담을 수 있는 것보다 훨씬 큰 데이터셋 크기에서만 발생하기 때문이든, 데이터센터에서나 볼 수 있는 네트워크 조건에서만 발생하기 때문이든, 분산 시스템의 버그를 몰아내려면 시뮬레이션이 아닌 실제 분산 환경이 필요한 경향이 있다. 물론 시뮬레이션도 매우 유용하다.

**견고한 오픈 소스 분산 시스템은 견고한 단일 머신 시스템보다 훨씬 드물다.** 많은 머신을 오래 돌리는 비용은 오픈 소스 커뮤니티에 부담이다. 취미로 하는 사람들과 아마추어들이 오픈 소스 소프트웨어의 엔진인데, 이들에게는 분산 시스템이 겪을 문제들을 탐구하거나 고치는 데 쓸 재정적 자원이 없다. 취미 개발자는 여가 시간에 이미 가진 머신으로 재미 삼아 오픈 소스 코드를 작성한다. 여러 대의 머신을 띄우고, 유지하고, 비용을 지불할 의향이 있는 오픈 소스 개발자를 찾기는 훨씬 어렵다.

이 공백의 일부는 기업에 소속된 엔지니어들이 메워 왔다. 하지만 그들 조직의 우선순위가 당신 조직의 우선순위와 일치하지 않을 수 있다.

오픈 소스 커뮤니티의 일부는 이 문제를 인지하고 있지만, 아직 해결되지 않았다. 어려운 문제다.

**조율(coordination)은 매우 어렵다.** 가능한 한 머신 간 조율을 피하라. 이것은 흔히 "수평 확장성(horizontal scalability)"이라 불린다. 수평 확장성의 진짜 비결은 독립성이다. 즉, 머신 간의 통신과 합의를 최소로 유지하도록 데이터를 머신에 배치할 수 있어야 한다. 두 머신이 무언가에 합의해야 할 때마다 서비스는 구현하기 더 어려워진다. 정보가 이동할 수 있는 속도에는 상한이 있고, 네트워크 통신은 생각보다 더 잘 끊기며, 합의가 무엇인지에 대한 당신의 관념은 아마 틀렸을 것이다. [두 장군 문제](http://en.wikipedia.org/wiki/Two_Generals%27_Problem)와 [비잔틴 장군 문제](http://en.wikipedia.org/wiki/Byzantine_Generals%27_Problem)를 공부해 두면 도움이 된다. (아, 그리고 Paxos는 정말로 [구현하기 매우 어렵다](http://research.google.com/pubs/pub33002.html). 성질 고약한 늙은 엔지니어들이 잘난 척하는 게 아니다.)

**문제를 메모리에 담을 수 있다면 아마 사소한 문제다.** 분산 시스템 엔지니어에게 한 머신 안에 국한된 문제는 쉬운 문제다. 데이터가 포인터 역참조 몇 번 거리가 아니라 스위치 몇 개 너머에 있을 때, 데이터를 빠르게 처리하는 방법을 알아내는 일은 더 어려워진다. 분산 시스템에서는 컴퓨터 과학 초창기부터 문서화되어 온 검증된 효율화 기법들이 더 이상 통하지 않는다. 단일 머신에서 도는 알고리즘에 대한 문헌과 구현은 풍부하다. 대부분의 계산이 조율 없는 단일 머신에서 이루어져 왔기 때문이다. 분산 시스템용은 그보다 현저히 적다.

**"느려요"는 당신이 디버깅하게 될 가장 어려운 문제다.** "느려요"는 사용자 요청을 수행하는 데 관여하는 여러 시스템 중 하나 이상이 느리다는 뜻일 수 있다. 여러 머신에 걸친 변환 파이프라인의 부분 중 하나 이상이 느리다는 뜻일 수도 있다. "느려요"가 어려운 이유 중 하나는 문제 진술이 결함의 위치에 대한 단서를 거의 주지 않기 때문이다. 평소 보는 그래프에 나타나지 않는 부분 실패가 어두운 구석에 도사리고 있다. 그리고 성능 저하가 아주 명백해지기 전까지는 이를 해결할 자원(시간, 돈, 도구)을 충분히 받지 못할 것이다. [Dapper](http://research.google.com/pubs/pub36356.html)와 [Zipkin](http://engineering.twitter.com/2012/06/distributed-systems-tracing-with-zipkin.html)이 괜히 만들어진 게 아니다.

**시스템 전체에 백프레셔(backpressure)를 구현하라.** 백프레셔란 서비스를 제공하는 시스템이 요청하는 시스템에 실패를 알리는 신호, 그리고 요청하는 시스템이 자신과 상대 시스템의 과부하를 막기 위해 그 실패를 처리하는 방식을 말한다. 백프레셔를 고려해 설계한다는 것은 과부하 시와 시스템 실패 시의 자원 사용량에 한계를 두는 것을 의미한다. 이는 견고한 분산 시스템을 만드는 기본 구성 요소 중 하나다.

백프레셔의 구현은 보통 자원이 한계에 이르거나 실패가 발생할 때 새 메시지를 버리거나 사용자에게 에러를 돌려보내는 것으로 이루어진다(두 경우 모두 지표를 증가시킨다). 다른 시스템으로의 연결과 요청에 대한 타임아웃과 지수 백오프도 필수다.

백프레셔 메커니즘이 없으면 연쇄 실패(cascading failure)나 의도치 않은 메시지 유실이 일어나기 쉽다. 어떤 시스템이 다른 시스템의 실패를 감당하지 못하면, 자신에게 의존하는 또 다른 시스템에 실패를 내보내는 경향이 있다.

**부분적으로 가용할 방법을 찾아라.** 부분 가용성(partial availability)이란 시스템의 일부가 실패하고 있을 때도 일부 결과를 반환할 수 있는 것이다.

검색은 이를 탐구하기에 이상적인 사례다. 검색 시스템은 결과의 품질과 사용자를 기다리게 하는 시간 사이에서 트레이드오프를 한다. 전형적인 검색 시스템은 문서를 검색하는 시간에 제한을 두고, 모든 문서를 검색하기 전에 제한 시간이 만료되면 그때까지 모은 결과를 반환한다. 이 덕분에 간헐적인 지연과 에러가 발생해도 검색을 확장하기가 더 쉬워진다. 그런 실패들이 모든 문서를 검색하지 못한 것과 똑같이 취급되기 때문이다. 시스템이 부분 결과를 사용자에게 반환할 수 있게 되면서 회복탄력성이 높아진다.

이번에는 웹 애플리케이션의 개인 메시지 기능을 생각해 보자. 어느 시점이 되면, 무슨 수를 쓰든, 개인 메시지용 스토리지 머신이 동시에 충분히 많이 죽어서 사용자들이 알아차리게 된다. 그렇다면 이 시스템에서는 어떤 종류의 부분 실패를 원해야 할까?

이건 고민이 필요하다. 사람들은 대체로, 모든 사용자의 메시지 일부가 사라지는 것보다는 자신(그리고 다른 몇몇 사용자)의 개인 메시지가 아예 안 되는 쪽을 더 잘 받아들인다. 서비스가 과부하되거나 머신 하나가 죽었을 때, 소수의 사용자만 실패 처리하는 것이 더 많은 사용자의 데이터를 잃는 것보다 낫다. 게다가 그 선택 위에, 개인 메시지에 문제가 있다는 이유로 공개 이미지 업로드 같은 무관한 기능까지 영향을 받는 것은 원치 않을 것이다. 그 실패 도메인들을 분리해 두기 위해 우리는 얼마나 많은 일을 감수할 것인가?

부분 가용성에서 이런 종류의 트레이드오프를 알아보는 능력은 도구 상자에 넣어 둘 만하다.

**지표(metrics)는 일을 해내는 유일한 방법이다.** 지표(지연 시간 백분위수, 특정 동작에 대한 증가 카운터, 변화율 등)를 노출하는 것은 시스템이 프로덕션에서 무엇을 한다고 믿는지와 실제로 무엇을 하고 있는지 사이의 간극을 건너는 유일한 방법이다. 20일째의 시스템 동작이 15일째의 동작과 어떻게 다른지 아는 것이 성공적인 엔지니어링과 실패한 주술의 차이다. 물론 지표는 문제와 동작을 이해하는 데 필요조건이지만, 다음에 무엇을 해야 할지 알기에 충분조건은 아니다.

로깅에 대한 여담 하나. 로그 파일은 있으면 좋지만, 거짓말하는 경향이 있다. 예를 들어 소수의 에러 클래스에 대한 로깅이 로그 파일 공간의 큰 부분을 차지하지만 실제로는 매우 낮은 비율의 요청에서만 발생하는 일이 아주 흔하다. 성공을 로깅하는 것은 대부분 불필요하고(대부분의 경우 디스크를 터뜨릴 것이다), 엔지니어들은 어떤 에러 클래스를 보는 게 유용할지 자주 잘못 짚기 때문에, 로그 파일은 온갖 잡동사니로 채워진다. 코드를 본 적 없는 사람이 로그를 읽는다고 생각하고 로깅하라.

로그에서 본 이상한 것을 지표와 대조해 보지도 않고 과대 해석한 다른 엔지니어(또는 나 자신) 때문에 장애가 길어지는 것을 여러 번 봤다. 로그 몇 줄에서 셜록 홈즈처럼 실패 동작 전체를 추리해 내는 다른 엔지니어(또는 나 자신)도 봤다. 하지만 유의하라. a) 그런 성공을 기억하는 이유는 그것이 극히 드물기 때문이고, b) 지표나 실험이 그 이야기를 뒷받침하지 않는 한 당신은 셜록이 아니다.

**평균이 아니라 백분위수를 쓰라.** 백분위수(50번째, 99번째, 99.9번째, 99.99번째)가 분산 시스템 대다수에서 평균보다 더 정확하고 더 많은 정보를 준다. 평균을 쓴다는 것은 평가 대상 지표가 종형 곡선(bell curve)을 따른다고 가정하는 것인데, 실제로 엔지니어가 신경 쓰는 지표 중 이에 해당하는 것은 거의 없다. "평균 지연 시간"은 흔히 보고되는 지표지만, 나는 지연 시간이 종형 곡선을 따르는 분산 시스템을 단 한 번도 본 적이 없다. 지표가 종형 곡선을 따르지 않으면 평균은 무의미하고, 잘못된 결정과 이해로 이어진다. 백분위수로 이야기함으로써 이 함정을 피하라. 기본을 백분위수로 삼으면 사용자가 시스템을 실제로 어떻게 겪는지 더 잘 이해하게 될 것이다.

**용량 추정을 배워라.** 이 덕분에 하루가 몇 초인지 알게 될 것이다. 작업을 수행하는 데 몇 대의 머신이 필요한지 아는 것이 오래가는 시스템과 3개월 만에 교체해야 하는 시스템의 차이다. 더 나쁘게는, 프로덕션화를 끝내기도 전에 교체해야 하는 시스템이 될 수도 있다.

트윗을 생각해 보자. 흔한 머신 한 대의 메모리에 트윗 id를 몇 개나 담을 수 있을까? 2012년 말 기준 전형적인 머신은 24GB 메모리를 갖고 있고, OS 오버헤드로 4~5GB가 필요하며, 요청 처리에 최소 몇 GB가 더 필요하고, 트윗 id는 8바이트다. 이런 종류의 어림 계산(back of the envelope calculation)을 스스로 하고 있는 자신을 발견하게 될 것이다. Jeff Dean의 [모두가 알아야 할 숫자들(Numbers Everyone Should Know)](http://www.cs.cornell.edu/projects/ladis2009/talks/dean-keynote-ladis2009.pdf) 슬라이드가 기대치를 잡는 데 좋다.

**피처 플래그는 인프라를 배포하는 방법이다.** "피처 플래그"는 제품 엔지니어가 시스템에 새 기능을 배포하는 흔한 방법이다. 피처 플래그는 보통 새 디자인이나 기능을 사용자층 일부에게만 보여 주는 프론트엔드 A/B 테스트와 연관 짓곤 한다. 하지만 인프라를 교체하는 강력한 방법이기도 하다.

"빅 컷오버(big cutover)" 또는 연속된 "빅 컷오버"를 감행했다가 너무 늦게 발견된 버그 때문에 롤백을 강요당하며 실패한 프로젝트가 너무 많다. 대신 피처 플래그를 사용하면 프로젝트에 대한 확신을 얻고 실패 비용을 줄일 수 있다.

단일 데이터베이스에서, 새 스토리지 솔루션의 세부 사항을 숨기는 서비스로 옮겨 간다고 하자. 피처 플래그를 사용하면 기존 데이터베이스로의 쓰기와 병행해 새 서비스로의 쓰기를 서서히 늘려 가면서, 쓰기 경로가 올바르고 충분히 빠른지 확인할 수 있다. 쓰기 경로가 100%에 도달하고 서비스의 데이터스토어로 백필(backfill)이 완료되면, 별도의 피처 플래그로 서비스에서 읽기를 시작하되 그 데이터를 사용자 응답에는 쓰지 않으면서 성능 문제를 점검할 수 있다. 또 다른 피처 플래그로는 기존 시스템과 새 시스템에서 읽은 데이터를 비교 검증할 수 있다. 그리고 마지막 플래그 하나로 새 시스템에서의 "진짜" 읽기를 서서히 늘릴 수 있다.

배포를 여러 단계로 쪼개고 피처 플래그로 빠르고 부분적인 대응 수단을 확보해 두면, 버그와 성능 문제를 "빅뱅" 릴리스 시점이 아니라 점진적 확대 도중 발생하는 대로 찾기가 쉬워진다. 문제가 생기면 피처 플래그 설정을 즉시 더 낮은(어쩌면 0인) 값으로 되돌리면 된다. 비율을 조정할 수 있으면, 어떤 문제를 만나더라도 총체적 재앙은 아니라는 것을 알면서 다양한 트래픽 양에서 디버깅하고 실험할 수 있다. 피처 플래그가 있으면 사용자 단위로 요청을 옮기는 것처럼 새 시스템에 대한 더 나은 통찰을 주는 다른 마이그레이션 전략도 선택할 수 있다. 그리고 새 서비스가 아직 프로토타입 단계일 때는 플래그를 낮은 값으로 설정해 새 시스템이 자원을 덜 소비하게 할 수 있다.

물론 고전적인 교육을 받은 개발자나 선의의 훈련을 받은 신입 엔지니어에게 피처 플래그는 조건문의 끔찍한 난장판처럼 들린다. 그리고 피처 플래그를 쓴다는 것은 인프라와 데이터의 여러 버전이 공존하는 것이 예외가 아니라 표준임을 받아들인다는 뜻이다. 이것은 깊은 교훈이다. 단일 머신 시스템에서 잘 통하는 것이 분산 문제 앞에서는 흔들리기도 한다.

피처 플래그는 트레이드오프로 이해하는 것이 가장 좋다. 국소적 복잡성(코드 안, 한 시스템 안)을 내주고 전역적 단순성과 회복탄력성을 얻는 것이다.

**id 공간을 현명하게 선택하라.** 시스템에 어떤 id 공간을 선택하느냐가 시스템의 모양을 결정한다.

데이터 한 조각에 도달하는 데 필요한 id가 많을수록 데이터를 파티셔닝할 때 선택지가 많아진다. 데이터 한 조각에 필요한 id가 적을수록 시스템의 출력을 소비하기가 쉬워진다.

트위터 API 버전 1을 생각해 보자. 트윗을 조회, 생성, 삭제하는 모든 작업은 트윗별 숫자 id 하나를 기준으로 이루어졌다. 트윗 id는 다른 어떤 데이터와도 연결되지 않은 단순한 64비트 숫자다. 트윗 수가 늘어나면서, 같은 사용자의 트윗들이 모두 같은 머신에 저장된다면 사용자 트윗 타임라인과 다른 사용자 구독 타임라인을 효율적으로 구성할 수 있으리라는 것이 분명해진다.

하지만 공개 API는 모든 트윗이 트윗 id만으로 접근 가능해야 한다고 요구한다. 트윗을 사용자별로 파티셔닝하려면 어떤 사용자가 어떤 트윗 id를 소유하는지 아는 조회 서비스를 만들어야 한다. 필요하다면 가능은 하지만, 무시할 수 없는 비용이 든다.

대안적인 API라면 모든 트윗 조회에 사용자 id를 요구하고, 초기에는 사용자별 파티셔닝 스토리지가 준비될 때까지 그냥 트윗 id를 스토리지에 사용할 수 있었을 것이다. 또 다른 대안은 트윗 id가 더 이상 k-정렬 가능하고 숫자형이지 못하게 되는 비용을 치르고, 사용자 id를 트윗 id 안에 포함시키는 것이었을 것이다.

id에 명시적으로든 암묵적으로든 어떤 정보를 인코딩하는지 조심하라. 클라이언트는 id 구조를 이용해 비공개 데이터의 익명성을 벗기거나, 예상치 못한 방식으로 시스템을 크롤링하거나(자동 증가 id가 전형적인 골칫거리다), [그 밖의 온갖 공격](https://www.owasp.org/index.php/Top_10_2010-A4-Insecure_Direct_Object_References)을 수행할 수 있다.

**데이터 지역성(data-locality)을 활용하라.** 데이터의 처리와 캐싱이 그 데이터의 영속 스토리지에 가까이 있을수록 처리는 더 효율적이고, 캐시를 일관되고 빠르게 유지하기도 더 쉽다. 네트워크는 포인터 역참조와 `fread(3)`보다 실패도 많고 지연 시간도 크다.

물론 데이터 지역성은 공간적으로 가깝다는 뜻이지만, 시간적으로 가깝다는 뜻이기도 하다. 여러 사용자가 거의 동시에 같은 비싼 요청을 하고 있다면, 그 요청들을 하나로 합칠 수 있을지도 모른다. 같은 종류의 데이터에 대한 요청 여러 건이 서로 가까운 시점에 발생한다면, 더 큰 요청 하나로 합칠 수 있다. 그렇게 하면 통신 오버헤드가 낮아지고 장애 관리가 쉬워지는 경우가 많다.

**캐시된 데이터를 영속 스토리지에 되쓰는 것은 나쁘다.** 이런 일은 생각보다 많은 시스템에서 일어난다. 특히 분산 시스템 경험이 적은 사람이 처음 설계한 시스템에서 그렇다. 당신이 물려받을 많은 시스템에 이 결함이 있을 것이다. 구현자들이 "러시아 인형 캐싱(Russian-doll caching)"을 이야기한다면, 아주 눈에 잘 띄는 버그를 만날 확률이 높다. 이 항목은 목록에서 뺄 수도 있었지만, 내 마음속에 이것을 향한 특별한 증오가 있다. 이 결함의 흔한 증상은 사용자 정보(예: 사용자명, 이메일, 해시된 비밀번호)가 이전 값으로 불가사의하게 되돌아가는 것이다.

**컴퓨터는 당신 생각보다 많은 일을 할 수 있다.** 오늘날 현장에는, 경험이 그리 많지 않은 실무자들이 퍼뜨린, 머신 한 대가 무엇을 할 수 있는지에 대한 잘못된 정보가 넘쳐난다.

2012년 말 기준으로 가벼운 웹 서버 한 대는 프로세서 6개 이상, 메모리 24GB, 그리고 다 쓰지 못할 만큼의 디스크 공간을 갖추고 있었다. 현대적 언어 런타임 위의 비교적 복잡한 [CRUD](http://en.wikipedia.org/wiki/Create,_read,_update_and_delete) 애플리케이션은 단일 머신에서 수백 밀리초 안에 초당 수천 건의 요청을 너끈히 처리할 수 있다. 그리고 그것도 넉넉히 낮게 잡은 하한이다. 운영 능력 관점에서 머신당 초당 수백 건의 요청은 대부분의 경우 자랑할 일이 아니다.

더 높은 성능을 얻는 것은 어렵지 않다. 애플리케이션을 프로파일링하고 측정에 근거해 효율화를 도입할 의향만 있다면 특히 그렇다.

**CAP 정리는 시스템을 비평하는 데 쓰라.** CAP 정리는 그것으로 시스템을 지어 올릴 수 있는 무언가가 아니다. 제1원리로 삼아 동작하는 시스템을 도출해 낼 수 있는 정리가 아니다. 적용 범위가 너무 일반적이고, 가능한 해법의 공간이 너무 넓다.

하지만 분산 시스템 설계를 비평하고 어떤 트레이드오프가 필요한지 이해하는 데는 아주 적합하다. 시스템 설계를 놓고 CAP가 그 하위 시스템들에 부과하는 제약을 하나씩 짚어 나가면, 끝에는 더 나은 설계가 남을 것이다. 숙제로, 러시아 인형 캐싱의 실제 구현에 CAP 정리의 제약을 적용해 보라.

마지막으로 한 가지. C, A, P 중에서 [CA는 선택할 수 없다](http://codahale.com/you-cant-sacrifice-partition-tolerance/).

**서비스를 추출하라.** 여기서 "서비스"란 "스토리지 시스템보다 높은 수준의 로직을 담고 있으며 보통 요청-응답 스타일의 API를 가진 분산 시스템"을 뜻한다. 코드가 당신 시스템 안이 아니라 별도의 서비스에 있었다면 더 쉬웠을 코드 변경이 없는지 눈여겨보라.

추출된 서비스는 보통 라이브러리 생성에서 연상되는 캡슐화의 이점을 제공한다. 하지만 서비스 추출은 클라이언트 시스템의 라이브러리를 업그레이드하는 것보다 변경을 더 빠르고 쉽게 배포할 수 있게 해 준다는 점에서 라이브러리 생성보다 낫다. (물론 추출된 서비스가 배포하기 어렵다면, 배포하기 쉬워지는 쪽은 클라이언트 시스템들이다.) 이 용이함은 더 작게 추출된 서비스의 코드 의존성과 운영 의존성이 더 적다는 데서 오고, 서비스가 만드는 엄격한 경계는 라이브러리가 허용하는 "지름길"을 택하기 어렵게 만든다. 그런 지름길은 거의 항상 내부 구현이나 클라이언트 시스템을 새 버전으로 마이그레이션하기 어렵게 만든다.

클라이언트 시스템이 여럿일 때 서비스를 쓰는 조율 비용도 공유 라이브러리보다 훨씬 낮다. 라이브러리를 업그레이드하려면, API 변경이 전혀 없더라도, 각 클라이언트 시스템의 배포를 조율해야 한다. 배포가 순서를 벗어나 수행될 때 데이터 손상이 가능하다면(그리고 그것이 일어날지 예측하기가 더 어렵다면) 이 일은 더 어려워진다. 클라이언트 시스템들의 유지 보수자가 서로 다르면, 라이브러리 업그레이드는 서비스 배포보다 사회적 조율 비용도 더 크다. 다른 사람들이 업그레이드를 인지하고 기꺼이 하도록 만드는 것은 의외로 어렵다. 그들의 우선순위가 당신의 것과 일치하지 않을 수 있기 때문이다.

서비스의 정석적인 사용 사례는 변경이 진행될 스토리지 계층을 숨기는 것이다. 추출된 서비스는 그 앞을 막아선 스토리지 계층에 비해 더 편리하고 표면적이 줄어든 API를 가진다. 서비스를 추출하면 클라이언트 시스템들은 새 스토리지 시스템이나 포맷으로의 느린 마이그레이션의 복잡성을 알 필요가 없고, 새 스토리지 레이아웃에서 반드시 발견될 버그를 점검해야 하는 대상은 새 서비스뿐이다.

이를 수행할 때 고려할 운영적·사회적 문제가 아주 많다. 여기서 다 다룰 수는 없다. 다른 글을 써야 할 것이다.

### 들어가며

Jay Kreps는 LinkedIn에 합류한 이후 회사가 단일 중앙 집중형 데이터베이스에서 여러 종류의 분산 시스템(그래프 데이터베이스, 검색 백엔드, Hadoop, 1세대·2세대 키-값 저장소 등)으로 옮겨가는 과정을 직접 겪었다. 이 과정에서 그가 배운 가장 중요한 사실 하나는, 이렇게 서로 달라 보이는 시스템들의 밑바닥에 놓인 개념이 사실 아주 단순한 하나의 자료구조, 즉 **로그**(log)라는 것이었다. write-ahead log, commit log, transaction log 등으로도 불리는 이 개념은 컴퓨터의 역사만큼이나 오래되었으며, 수많은 분산 데이터 시스템과 실시간 애플리케이션 아키텍처의 핵심에 자리 잡고 있다.

데이터베이스, NoSQL, 키-값 저장소, 복제, Paxos, Hadoop, 버전 관리 시스템 등을 제대로 이해하려면 로그를 이해해야 하는데도, 정작 많은 소프트웨어 엔지니어는 로그 개념에 익숙하지 않다. 이 글은 그 간극을 메우기 위해 쓰였고, 로그가 무엇인지부터 시작해 데이터 통합, 실시간 처리, 시스템 구축이라는 세 가지 실용적 응용까지를 다룬다.

### Part One: 로그란 무엇인가

로그는 아마도 가장 단순한 저장 추상화일 것이다. 시간 순으로 완전히 정렬되고 오직 끝에만 추가되는(append-only) 레코드의 나열이 로그다.

![로그 구조 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/log.png)

레코드는 항상 로그의 끝에 덧붙여지고, 읽을 때는 왼쪽에서 오른쪽으로 진행한다. 각 항목에는 고유하고 순차적인 로그 엔트리 번호가 매겨진다. 이 순서는 곧 "시간"의 개념을 만들어낸다. 왼쪽에 있는 항목이 오른쪽 항목보다 먼저 일어난 것으로 정의되기 때문이다. 로그 엔트리 번호는 그 항목의 "타임스탬프"라고 볼 수 있다. 시간이라는 개념을 이런 식으로 정의하는 것이 처음에는 낯설게 느껴질 수 있지만, 이 방식은 물리적인 시계와 완전히 분리되어 있다는 편리한 성질을 갖는다. 이 성질은 분산 시스템으로 넘어가면 본질적으로 중요해진다.

레코드 자체의 내용이나 포맷은 이 논의에서 중요하지 않다. 또한 로그에 레코드를 무한정 추가할 수는 없으므로 언젠가는 공간이 부족해지는데, 이 문제는 뒤에서 다시 다룬다.

이렇게 보면 로그는 파일이나 테이블과 크게 다르지 않다. 파일은 바이트의 배열이고, 테이블은 레코드의 배열이며, 로그는 결국 레코드가 시간 순으로 정렬되어 있는 파일 혹은 테이블의 한 종류일 뿐이다.

그렇다면 이렇게 단순한 것을 왜 굳이 논의할 가치가 있을까? 그 답은, 로그가 "무엇이 언제 일어났는가"를 기록한다는 아주 구체적인 목적을 갖기 때문이다. 분산 데이터 시스템에서는 여러 면에서 이것이 문제의 본질 그 자체다.

여기서 흔한 혼동 하나를 짚고 넘어갈 필요가 있다. 프로그래머 대부분은 "로깅"이라고 하면 syslog나 log4j로 로컬 파일에 남기는 비정형 에러 메시지나 추적 정보를 떠올린다. 이 글에서는 이를 "애플리케이션 로깅"이라 부르며, 이는 이 글이 말하는 로그 개념의 퇴화된 형태에 가깝다. 가장 큰 차이는 텍스트 로그가 기본적으로 사람이 읽기 위한 것인 반면, 이 글에서 말하는 "저널" 또는 "데이터 로그"는 프로그램이 처리하도록 만들어졌다는 점이다. 실제로 여러 대의 서버에 흩어진 로그를 사람이 일일이 눈으로 훑어보는 방식은 서비스와 서버 수가 늘어나는 순간 곧 감당할 수 없게 되며, 로그의 진짜 쓸모는 여러 머신에 걸친 동작을 이해하기 위한 질의와 그래프의 입력으로 옮겨간다.

#### 데이터베이스 속의 로그

로그 개념이 어디서 처음 나왔는지는 확실치 않지만, 이진 탐색처럼 너무 단순해서 발명자조차 이것을 "발명"이라고 자각하지 못했을 법한 개념 중 하나로 보인다. 이미 IBM의 System R에서부터 등장한다. 데이터베이스에서 로그의 용도는, 장애가 발생해도 여러 자료구조와 인덱스를 서로 일관된 상태로 유지하는 것이다. 원자성과 지속성을 보장하기 위해 데이터베이스는 실제로 여러 자료구조를 변경하기 전에, 어떤 레코드를 어떻게 바꿀지에 대한 정보를 먼저 로그에 기록한다. 로그는 "무슨 일이 일어났는가"의 기록이고, 각 테이블이나 인덱스는 이 히스토리를 특정한 자료구조나 인덱스로 투영한 결과물이다. 로그는 즉시 영속화되므로, 장애 발생 시 다른 모든 영속 자료구조를 복구하는 데 있어 가장 신뢰할 수 있는 근거(authoritative source)로 쓰인다.

시간이 지나면서 로그의 쓰임새는 단순히 ACID를 구현하기 위한 내부 디테일에서, 데이터베이스 간 복제를 위한 방법으로 확장되었다. 데이터베이스에서 일어난 변경의 순서 자체가 원격 복제본을 동기화하는 데 정확히 필요한 정보였기 때문이다. Oracle, MySQL, PostgreSQL은 로그의 일부를 복제 데이터베이스(슬레이브)로 전송하는 로그 시핑(log shipping) 프로토콜을 갖추고 있다. Oracle은 XStreams와 GoldenGate 같은 제품으로 이 로그를 Oracle 외부의 구독자에게도 열어주는 범용 데이터 구독 메커니즘으로 상품화했고, MySQL과 PostgreSQL에도 이에 상응하는 기능이 여러 데이터 아키텍처의 핵심 요소로 쓰이고 있다.

이런 기원 때문에 기계가 읽을 수 있는 로그라는 개념은 오랫동안 데이터베이스 내부 구현에 갇혀 있었고, 데이터 구독 메커니즘으로서 로그를 쓰는 발상은 거의 우연히 생겨난 것처럼 보인다. 하지만 이 추상화 자체는 메시징, 데이터 흐름, 실시간 데이터 처리 전반을 뒷받침하기에 이상적이다.

#### 분산 시스템 속의 로그

로그가 풀어내는 두 가지 문제 — 변경의 순서를 정하는 것과 데이터를 배포하는 것 — 는 분산 데이터 시스템에서 훨씬 더 중요해진다. 업데이트의 순서에 합의하는 것(혹은 합의하지 않기로 합의하고 그 부작용을 감당하는 것)은 이런 시스템 설계의 핵심 문제 중 하나다.

로그 중심의 분산 시스템 접근법은 필자가 **상태 기계 복제 원칙**(State Machine Replication Principle)이라 부르는 단순한 관찰에서 출발한다. 요지는 이렇다.

> "두 개의 동일하고 결정적인(deterministic) 프로세스가 같은 상태에서 시작해 같은 순서로 같은 입력을 받는다면, 둘은 같은 출력을 내고 같은 상태로 끝난다."

여기서 "결정적"이란, 처리 결과가 스레드 실행 순서나 `gettimeofday` 호출처럼 타이밍에 의존하거나 "대역 외(out of band)"의 다른 입력에 영향을 받지 않는다는 뜻이다. "상태"는 처리가 끝난 시점에 메모리든 디스크든 그 프로세스에 남아 있는 데이터 전체를 말한다. 그리고 "같은 순서로 같은 입력을 받는다"는 부분이 바로 로그가 담당하는 몫이다. 두 개의 결정적인 코드에 동일한 입력 로그를 먹이면 동일한 출력이 나온다는, 직관적으로 당연한 이야기다.

이를 분산 컴퓨팅에 적용하면, 여러 대의 머신이 모두 같은 일을 하도록 만드는 문제를, 이 프로세스들에 입력을 공급하는 분산적이면서 일관된 로그를 구현하는 문제로 환원할 수 있다. 즉 로그의 역할은 입력 스트림에서 비결정성을 최대한 짜내어, 이 입력을 처리하는 각 복제본이 서로 어긋나지 않도록 만드는 데 있다.

이 원칙 자체는 이해하고 나면 "결정적인 처리는 결정적이다"라는 동어반복에 가까울 만큼 단순하지만, 그럼에도 분산 시스템 설계에서 가장 범용적인 도구 중 하나라고 필자는 평가한다. 이 접근의 아름다운 점 하나는, 로그를 색인하는 타임스탬프가 복제본들의 상태에 대한 "시계" 역할을 한다는 것이다. 각 복제본은 그 복제본이 처리한 최대 로그 엔트리의 타임스탬프라는 단 하나의 숫자로 요약해서 설명할 수 있고, 이 타임스탬프와 로그를 합치면 복제본의 전체 상태를 고유하게 포착할 수 있다.

이 원칙을 시스템에 적용하는 방식은 로그에 무엇을 기록하느냐에 따라 다양하다. 예를 들어 서비스로 들어오는 요청 자체를 기록할 수도 있고, 요청에 따라 서비스가 겪는 상태 변화를 기록할 수도 있으며, 서비스가 실행하는 변환 명령을 기록할 수도 있다. 이론적으로는 각 복제본이 실행할 일련의 머신 명령어나, 각 복제본에서 호출할 메서드 이름과 인자를 로그로 남길 수도 있다. 이 입력을 각 프로세스가 동일한 방식으로 처리하기만 하면 복제본들은 계속 일관된 상태를 유지한다.

이런 개념을 부르는 용어는 분야마다 조금씩 다르다. 데이터베이스 쪽에서는 **물리적 로깅**(physical logging)과 **논리적 로깅**(logical logging)을 구분한다. 물리적 로깅은 변경된 각 행의 내용 자체를 기록하는 것이고, 논리적 로깅은 변경된 행이 아니라 그 변경을 일으킨 SQL 명령(INSERT, UPDATE, DELETE)을 기록하는 것이다.

분산 시스템 문헌에서는 처리와 복제에 관해 크게 두 가지 접근법을 구분한다. **상태 기계 모델**(state machine model)은 보통 액티브-액티브 방식을 가리키는데, 들어오는 요청의 로그를 유지하고 각 복제본이 각 요청을 처리하는 방식이다. 이를 살짝 변형한 **주-백업 모델**(primary-backup model)은 복제본 중 하나를 리더로 선출해 이 리더가 요청을 도착 순서대로 처리하고 그 처리 결과로 발생한 상태 변화를 로그로 남기는 방식이다. 나머지 복제본들은 리더가 만든 상태 변화를 순서대로 적용해서 리더와 동기화 상태를 유지하고, 리더가 실패했을 때 언제든 그 자리를 이어받을 준비를 한다.

![액티브-패시브 아키텍처 비교 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/active_and_passive_arch.png)

이 두 접근의 차이를 이해하기 위해 간단한 예를 하나 생각해보자. 단일 숫자(초기값 0)를 상태로 유지하며 덧셈과 곱셈을 적용하는 복제된 "산술 서비스"가 있다고 하자. 액티브-액티브 방식이라면 "+1", "*2" 같은 변환 자체를 로그에 남기고 각 복제본이 이 변환들을 차례로 적용해 같은 값들을 거쳐 간다. 반대로 액티브-패시브 방식이라면 단일 마스터가 변환을 실행하고 그 결과값, 즉 "1", "3", "6" 같은 수치를 로그에 남긴다. 이 예시는 왜 순서가 복제본 간 일관성에 결정적인지도 잘 보여준다. 덧셈과 곱셈의 순서를 바꾸면 결과값 자체가 달라지기 때문이다.

![Paxos 관련 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/paxos_postcard.jpg)

분산 로그는 합의(consensus) 문제를 모델링하는 자료구조로도 볼 수 있다. 로그란 결국 "다음에 추가할 값"에 대한 일련의 결정들의 집합이기 때문이다. Paxos 계열 알고리즘에서 로그의 모습을 알아보려면 약간의 상상력이 필요하지만, 로그를 구축하는 것이야말로 Paxos의 가장 흔한 실용적 응용이다. Paxos에서는 흔히 "multi-paxos"라 불리는 확장을 사용하는데, 이는 로그를 로그 안의 각 슬롯마다 하나씩 벌어지는 일련의 합의 문제로 모델링한다. ZAB, RAFT, Viewstamped Replication 같은 다른 프로토콜들은 분산적이고 일관된 로그를 유지하는 문제를 훨씬 더 직접적으로 모델링한다는 점에서 로그의 존재감이 더 두드러진다.

필자는 우리가 이 분야를 바라보는 관점이 역사적 경로에 조금 편향되어 있다고 본다. 분산 컴퓨팅 이론이 실무 응용을 앞질렀던 수십 년의 시간 때문일 것이다. 실제로 합의 문제는 다소 지나치게 단순하다. 컴퓨터 시스템이 단 하나의 값을 결정해야 하는 경우는 드물고, 거의 항상 일련의 요청들을 다뤄야 한다. 그래서 단일 값을 다루는 레지스터보다는 로그가 더 자연스러운 추상화다.

나아가, 알고리즘 자체에만 초점을 맞추다 보면 시스템이 정말로 필요로 하는 것은 로그라는 밑바탕의 추상화라는 사실이 가려진다. 필자는 결국 우리가 해시 테이블을 이야기할 때 그것이 murmur hash에 linear probing을 쓴 것인지 아닌지를 굳이 따지지 않듯이, 로그도 구체적인 구현과 무관하게 상품화된 빌딩 블록으로 취급하는 방향으로 나아갈 것이라 본다. 로그는 여러 알고리즘과 구현체가 최적의 성능과 보장을 놓고 경쟁하는, 일종의 상품화된 인터페이스가 될 것이다.

#### Changelog 101: 테이블과 이벤트는 쌍대(dual) 관계다

다시 데이터베이스 이야기로 돌아가 보자. 변경 로그와 테이블 사이에는 흥미로운 쌍대 관계가 있다. 로그는 은행의 모든 입출금 내역 목록과 비슷하고, 테이블은 현재의 계좌 잔액 전체와 비슷하다. 변경의 로그가 있다면 이를 순서대로 적용해서 현재 상태를 담은 테이블을 만들어낼 수 있다. 이 테이블은 (특정 로그 시점 기준으로) 각 키의 최신 상태를 기록한다. 어떤 의미에서는 로그가 더 근본적인 자료구조다. 원래의 테이블을 만들어내는 것 외에도, 이를 변형해 온갖 파생 테이블을 만들어낼 수 있기 때문이다.

![음양(yin-yang) 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/yin-yang.jpg)

이 과정은 거꾸로도 성립한다. 업데이트를 받는 테이블이 있다면, 이 변경들을 기록해서 테이블 상태에 대한 모든 업데이트를 담은 "변경 로그(changelog)"를 발행할 수 있다. 이 변경 로그는 근실시간(near-real-time) 복제본을 지원하는 데 정확히 필요한 것이다. 즉 테이블은 "정지 상태의 데이터"를 담당하고 로그는 "변화"를 포착한다는 점에서 둘은 쌍대 관계다. 로그의 마법은, 만약 그것이 변경의 완전한 기록이라면 테이블의 최종 버전 내용뿐 아니라 그 테이블이 과거에 거쳐온 모든 버전을 재구성할 수 있게 해준다는 데 있다. 사실상 테이블의 모든 과거 상태에 대한 일종의 백업인 셈이다.

이는 소스 코드 버전 관리를 떠올리게 한다. 버전 관리와 데이터베이스는 밀접하게 연관되어 있다. 버전 관리 시스템은 분산된 상태 변경 관리라는, 분산 데이터 시스템이 풀어야 하는 문제와 매우 비슷한 문제를 다룬다. 버전 관리 시스템은 보통 패치들의 순서를 모델링하는데, 이는 사실상 로그다. 사용자는 테이블에 해당하는 "체크아웃된 스냅샷"과 직접 상호작용한다. 버전 관리 시스템에서도 다른 분산 상태 시스템과 마찬가지로 복제는 로그를 통해 이루어진다는 점에 주목할 만하다. 업데이트를 받을 때 실제로 받아오는 것은 패치들뿐이고, 이를 현재 스냅샷에 적용하는 방식으로 동작한다.

로그 중심 데이터베이스를 표방하는 Datomic이라는 회사가 이런 아이디어를 최근 다시 조명하기도 했다. 다만 이 개념 자체는 분산 시스템과 데이터베이스 문헌에서 십 년 넘게 다뤄져 온 것으로, 이 시스템만의 독창적인 발상은 아니다.

#### 다음으로 다룰 내용

여기까지는 다소 이론적으로 느껴질 수 있다. 이어지는 글에서는 로그가 분산 컴퓨팅 내부 구현이나 추상적인 이론 모델을 넘어 실제로 어디에 쓸모가 있는지를 다룬다. 다음 세 가지가 그 축이다.

- **데이터 통합** — 조직이 가진 모든 데이터를 저장·처리 시스템 어디에서든 손쉽게 쓸 수 있게 만드는 것
- **실시간 데이터 처리** — 파생 데이터 스트림을 계산해내는 것
- **분산 시스템 설계** — 로그 중심 설계로 실제 시스템을 어떻게 단순화할 수 있는지

이 세 가지 응용은 모두 "독립된 서비스로서의 로그"라는 하나의 아이디어로 수렴한다. 각각의 경우에서 로그의 유용함은 결국 하나의 단순한 기능, 즉 **영속적이고 재생 가능한 히스토리 기록을 만들어낸다**는 데서 나온다. 놀랍게도 이 문제들의 핵심에는, 여러 머신이 저마다의 속도로 이 히스토리를 결정적으로 재생(playback)할 수 있게 하는 능력이 자리 잡고 있다.

### Part Two: 데이터 통합

먼저 "데이터 통합"이 무엇을 뜻하는지, 왜 중요한지를 짚고 나서 로그와의 관계로 넘어간다. 여기서 말하는 데이터 통합이란 **조직이 가진 모든 데이터를 조직의 모든 서비스와 시스템에서 쓸 수 있도록 만드는 것**이다.

"데이터 통합"이라는 표현 자체가 널리 쓰이는 용어는 아니지만 이보다 더 적절한 표현을 찾기 어렵다. 좀 더 익숙한 용어인 ETL은 보통 관계형 데이터 웨어하우스를 채우는, 데이터 통합의 아주 제한된 일부만을 가리킨다. 이 글에서 다루는 것은 사실 ETL을 실시간 시스템과 처리 흐름까지 아우르도록 일반화한 개념에 가깝다.

![케이블 배선 사진](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/cabling.jpg)

빅데이터를 둘러싼 온갖 화려한 관심과 열기 속에서 데이터 통합이라는 화제는 거의 언급되지 않지만, 필자는 오히려 이 다소 평범해 보이는 "데이터를 쓸 수 있게 만드는" 문제야말로 조직이 집중할 수 있는 가장 값진 일 가운데 하나라고 본다.

데이터를 효과적으로 활용하는 과정은 일종의 매슬로우의 욕구 단계와 비슷한 구조를 갖는다. 피라미드의 가장 아래층은 관련된 데이터를 모두 포착해서, 이를 적용 가능한 처리 환경(화려한 실시간 질의 시스템이든, 그냥 텍스트 파일과 파이썬 스크립트든)에 함께 모아 놓는 일이다. 이 데이터는 읽고 처리하기 쉽도록 일관된 방식으로 모델링되어야 한다. 데이터를 일관되게 포착한다는 기초적인 필요가 충족된 뒤에야, MapReduce나 실시간 질의 시스템 같은 인프라로 이 데이터를 다양하게 가공하는 작업으로 넘어갈 수 있다.

당연한 얘기지만, 신뢰할 수 있고 완전한 데이터 흐름이 갖춰지지 않은 Hadoop 클러스터는 비싸고 조립하기 까다로운 공간 히터에 지나지 않는다. 데이터와 처리 인프라가 갖춰진 다음에야 좋은 데이터 모델과 잘 정의된 일관된 의미론이라는, 좀 더 정제된 문제로 관심을 옮길 수 있고, 그다음에야 더 정교한 시각화·리포팅·알고리즘 처리와 예측으로 나아갈 수 있다.

필자의 경험상 대부분의 조직은 이 피라미드의 기반부에 커다란 구멍을 갖고 있다 — 즉 신뢰할 수 있고 완전한 데이터 흐름이 없다 — 그러면서도 곧바로 고급 데이터 모델링 기법으로 건너뛰고 싶어 한다. 이는 순서가 완전히 뒤바뀐 접근이다.

그렇다면 질문은, 조직 내 모든 데이터 시스템에 걸쳐 신뢰할 수 있는 데이터 흐름을 어떻게 만들 것인가다.

#### 데이터 통합을 어렵게 만드는 두 가지 흐름

이 문제를 더 어렵게 만드는 두 가지 트렌드가 있다.

**첫째, 이벤트 데이터의 폭증.** 이벤트 데이터는 "지금 무슨 상태인가"가 아니라 "무슨 일이 일어났는가"를 기록한다. 웹 시스템에서는 사용자 행동 로깅이 대표적이지만, 데이터센터 전체의 머신들을 안정적으로 운영·모니터링하는 데 필요한 머신 수준의 이벤트와 통계도 여기 포함된다. 사람들은 흔히 이를 "로그 데이터"라 부르는데, 애플리케이션 로그 파일에 자주 기록되기 때문이다. 하지만 이는 형식과 기능을 혼동하는 표현이다. 이런 데이터는 현대 웹 산업의 핵심이다. 구글의 부(富)는 결국 클릭과 노출, 즉 이벤트를 바탕으로 만들어진 연관성 파이프라인에서 나온다.

이런 흐름이 웹 기업에만 국한되는 것도 아니다. 웹 기업들이 먼저 이런 흐름을 겪는 이유는 그들이 이미 완전히 디지털화되어 있어 계측(instrumentation)이 쉽기 때문일 뿐이다. 금융 데이터는 오래전부터 이벤트 중심이었고, RFID는 물리적 사물에도 이런 추적 방식을 더한다. 전통적인 비즈니스와 활동들이 디지털화되면서 이 흐름은 계속될 것으로 보인다.

이런 이벤트 데이터는 전통적인 데이터베이스 용도의 데이터보다 몇 자릿수는 더 큰 규모를 이루는 경향이 있고, 이는 처리에 상당한 부담을 준다.

**둘째, 전문화된 데이터 시스템의 폭증.** 지난 5년 사이 OLAP, 검색, 단순 온라인 저장, 배치 처리, 그래프 분석 등 특정 용도에 특화된 시스템들이 인기를 끌고 흔히 무료로도 이용 가능해졌다.

더 다양한 종류의 더 많은 데이터를, 더 많은 시스템으로 밀어 넣고 싶다는 욕구가 합쳐지면서 거대한 데이터 통합 문제가 생겨난다.

#### 로그 구조 데이터 흐름

이 문제를 다루는 데 있어 로그는 시스템 간 데이터 흐름을 위한 자연스러운 자료구조다. 처방은 아주 단순하다. **조직의 모든 데이터를 실시간 구독이 가능한 중앙 로그에 담는 것.**

각 논리적인 데이터 소스는 각자의 로그로 모델링될 수 있다. 데이터 소스는 클릭이나 페이지뷰 같은 이벤트를 남기는 애플리케이션일 수도 있고, 변경을 받아들이는 데이터베이스 테이블일 수도 있다. 각 구독 시스템은 이 로그를 가능한 한 빠르게 읽어서, 새 레코드를 자신의 저장소에 적용하고 로그 상의 자기 위치를 갱신해 나간다. 구독자는 캐시, Hadoop, 다른 사이트의 또 다른 데이터베이스, 검색 시스템 등 어떤 종류의 데이터 시스템이든 될 수 있다.

![로그 구독 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/log_subscription.png)

예컨대 로그 개념은 각 변경마다 하나의 논리적 시계를 제공하는데, 이를 기준으로 모든 구독자의 위치를 잴 수 있다. 각 구독자 시스템이 서로 대비해 어디까지 읽었는지를 "특정 시점"으로 나타낼 수 있으므로, 서로 다른 구독 시스템들의 상태를 추론하는 일이 훨씬 단순해진다.

좀 더 구체적으로 살펴보자. 데이터베이스 하나와 여러 대의 캐시 서버가 있는 단순한 상황을 가정하면, 로그는 이 시스템들 전체의 업데이트를 동기화하고 각 시스템이 어느 시점에 도달했는지를 추론하는 방법을 제공한다. 로그 엔트리 X번으로 어떤 레코드를 기록한 뒤 캐시에서 읽어야 한다고 하자. 만약 오래된(stale) 데이터를 보지 않도록 보장하고 싶다면, X까지 복제가 끝나지 않은 캐시로부터는 읽지 않도록만 하면 된다.

또한 로그는 데이터 생산과 데이터 소비를 비동기적으로 분리해주는 버퍼 역할도 한다. 이는 특히 서로 다른 속도로 소비하는 여러 구독자가 존재할 때 중요하다. 구독 시스템은 다운되거나 유지보수에 들어가더라도 복귀했을 때 자신이 감당할 수 있는 속도로 따라잡을 수 있다. Hadoop이나 데이터 웨어하우스 같은 배치 시스템은 시간 단위, 일 단위로만 소비해도 되지만, 실시간 질의 시스템은 초 단위로 최신 상태를 따라잡아야 할 수도 있다. 원본 데이터 소스도, 로그 자체도 다양한 목적지 시스템들에 대해 전혀 알 필요가 없으므로, 파이프라인을 전혀 바꾸지 않고도 소비자 시스템을 추가하거나 제거할 수 있다.

이 대목에서 필자는 톨스토이의 『안나 카레니나』 도입부 문장을 빗대어, "잘 동작하는 데이터 파이프라인은 모두 로그처럼 설계되어 있고, 고장 난 파이프라인은 저마다의 방식으로 고장 난다"는 취지의 농담을 남긴다.

![톨스토이 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/tolstoy.jpg)

특히 중요한 점은, 목적지 시스템이 오직 로그만 알면 되고 원본 시스템의 세부 사항은 전혀 몰라도 된다는 것이다. 소비 시스템은 데이터가 RDBMS에서 왔는지, 최신 유행의 키-값 저장소에서 왔는지, 아니면 어떤 실시간 질의 시스템도 거치지 않고 만들어졌는지 신경 쓸 필요가 없다. 사소해 보이지만 실제로는 결정적으로 중요한 지점이다.

필자는 여기서 "메시징 시스템"이나 "pub/sub" 대신 굳이 "로그"라는 표현을 쓰는데, 그 이유는 로그가 의미론에서 훨씬 더 구체적이고, 데이터 복제를 실제로 지원하는 데 필요한 실용적 구현에 훨씬 가까운 표현이기 때문이다. "발행-구독"이라는 표현은 사실상 메시지의 간접 주소 지정 이상을 함의하지 않으며, 발행-구독을 표방하는 두 메시징 시스템을 비교해보면 보장하는 내용이 서로 완전히 다른 경우가 많아 이 도메인에서는 별로 쓸모가 없다는 것이 필자의 경험이다. 로그는 지속성 보장과 강한 순서 보장을 갖춘 일종의 메시징 시스템으로 볼 수 있으며, 분산 시스템 문헌에서는 이런 통신 모델을 (다소 투박한 이름으로) atomic broadcast라 부르기도 한다.

여기서 짚어둘 점은, 로그는 어디까지나 인프라일 뿐이라는 것이다. 로그만으로 데이터 흐름을 완전히 정복했다고 할 수는 없다. 나머지 이야기는 메타데이터, 스키마, 호환성, 데이터 구조와 그 진화를 다루는 온갖 세부 사항들에 관한 것이다. 하지만 데이터 흐름의 메커니즘을 신뢰성 있고 일반적인 방식으로 다루는 방법이 갖춰지기 전까지는, 의미론적 세부 사항은 부차적인 문제다.

#### LinkedIn에서의 경험

필자는 LinkedIn이 중앙 집중형 관계형 데이터베이스에서 여러 분산 시스템의 집합으로 옮겨가는 과정에서 이 데이터 통합 문제가 빠르게 부상하는 것을 직접 목격했다. 당시 LinkedIn의 주요 데이터 시스템으로는 검색, 소셜 그래프, Voldemort(키-값 저장소), Espresso(문서 저장소), 추천 엔진, OLAP 질의 엔진, Hadoop, Teradata, Ingraphs(모니터링 그래프·메트릭 서비스) 등이 있었다. 이들 각각은 자기 분야에서 고급 기능을 제공하는 특화된 분산 시스템이었다.

![LinkedIn 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/linkedin.png)

데이터 흐름에 로그를 쓴다는 아이디어 자체는 필자가 합류하기 전부터 LinkedIn 내부에 이미 있었다. 초기 인프라 중 하나로 Oracle 테이블 위에 로그 캐싱 추상화를 얹어 데이터베이스 변경 구독을 확장할 수 있게 해주는 Databus라는 서비스가 있었는데, 이는 소셜 그래프와 검색 색인에 데이터를 공급하기 위한 것이었다.

필자 개인의 관여는 2008년 무렵 키-값 저장소 개발을 마친 뒤 시작되었다. 다음 과제는 실제로 동작하는 Hadoop 환경을 구축해서 일부 추천 처리를 그리로 옮기는 것이었다. 이 분야 경험이 부족했던 팀은 데이터를 들여오고 내보내는 데는 몇 주 정도, 나머지 시간은 정교한 예측 알고리즘 구현에 쓰겠다고 순진하게 예상했다. 그렇게 길고 힘든 여정이 시작됐다.

처음에는 기존 Oracle 데이터 웨어하우스에서 데이터를 긁어오는 방식을 계획했다. 그러나 곧 Oracle에서 데이터를 빠르게 뽑아내는 것 자체가 상당한 비기(秘技)라는 것을 깨달았다. 설상가상으로 데이터 웨어하우스의 처리 방식은 Hadoop에서 계획한 프로덕션 배치 처리와 맞지 않았다 — 대부분의 처리가 되돌릴 수 없고 특정 리포팅 용도에 특화되어 있었기 때문이다. 결국 데이터 웨어하우스를 우회해 원본 데이터베이스와 로그 파일로 직접 접근하는 방식을 택했고, 마지막으로 처리 결과를 서빙용 키-값 저장소로 다시 적재하는 또 하나의 파이프라인을 구현했다.

이런 평범한 데이터 복사 작업이 결국 초기 개발 기간의 상당 부분을 차지하는 항목이 되어버렸다. 더 나쁜 것은, 어느 파이프라인에든 문제가 생기면 Hadoop 시스템 전체가 거의 무용지물이 됐다는 점이다. 나쁜 데이터에 정교한 알고리즘을 돌려봐야 더 나쁜 데이터만 만들어질 뿐이었다.

비교적 범용적으로 구축했음에도, 새로운 데이터 소스가 추가될 때마다 별도의 커스텀 설정이 필요했고, 이는 곧 수많은 오류와 장애의 원인이 되었다. Hadoop 위에 구현한 사이트 기능들이 인기를 끌면서 관심 있는 엔지니어들의 대기 목록이 길어졌고, 각 사용자는 연동하고 싶은 시스템 목록과 원하는 새 데이터 피드 목록을 저마다 갖고 있었다.

![시시포스 이미지: 고대 그리스의 ETL, 별로 달라진 게 없다](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/sisyphus.jpg)

이 과정에서 몇 가지가 서서히 분명해졌다.

첫째, 다소 지저분하긴 했지만 이미 구축된 파이프라인들은 실제로 대단히 값진 것이었다. 새로운 처리 시스템(Hadoop)에 데이터를 쓸 수 있게 만드는 과정 자체가 이전에는 어려웠던 여러 계산을 가능하게 만들었고, 이전에는 여러 전문 시스템에 갇혀 있던 데이터 조각들을 한데 모으는 것만으로도 새로운 제품과 분석이 나올 수 있었다.

둘째, 신뢰할 수 있는 데이터 적재를 위해서는 파이프라인 자체가 이를 깊이 지원해야 한다는 것이 분명해졌다. 필요한 구조를 처음부터 제대로 포착해두면, Hadoop으로의 데이터 적재를 완전히 자동화할 수 있다. 새로운 데이터 소스를 추가하거나 스키마가 바뀔 때마다 사람이 손댈 필요 없이, 데이터는 자동으로 HDFS에 나타나고 Hive 테이블은 적절한 컬럼으로 자동 생성되어야 한다는 것이다.

셋째, 여전히 데이터 커버리지가 매우 낮았다. LinkedIn이 가진 전체 데이터 중 Hadoop에서 실제로 이용 가능한 비율을 따져보면 여전히 매우 불완전했고, 새 데이터 소스 하나를 운영 가능한 상태로 만드는 데 드는 노력을 생각하면 완전한 커버리지에 도달하는 것은 결코 쉬운 일이 아니었다.

당시 방식 — 각 데이터 소스와 목적지 쌍마다 커스텀 데이터 적재를 따로 구축하는 방식 — 은 명백히 불가능한 접근이었다. 수십 개의 데이터 시스템과 저장소가 있었는데, 이들 모두를 서로 연결하려면 각 시스템 쌍 사이에 커스텀 파이프를 놓아야 했다.

![복잡하게 얽힌 파이프라인 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/datapipeline_complex.png)

여기서 유의할 점은, 데이터베이스나 Hadoop처럼 많은 시스템이 데이터의 소스인 동시에 목적지이기도 해서 데이터가 흔히 양방향으로 흐른다는 것이다. 즉 시스템당 사실상 두 개의 파이프라인 — 데이터를 들여오는 것과 내보내는 것 — 을 만들어야 했다. 이런 식으로는 완전한 연결에 다가갈수록 파이프라인 수가 대략 시스템 수의 제곱(O(N²))에 가깝게 늘어나므로, 이를 유지하려면 어마어마한 인력이 필요했고 애초에 운영 가능한 구조가 아니었다.

대신 필요했던 것은 이런 형태의 좀 더 범용적인 구조였다.

![단순화된 파이프라인 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/datapipeline_simple.png)

가능한 한, 각 소비자를 데이터 소스로부터 격리시켜야 했다. 이상적으로는 모든 것에 접근할 수 있게 해주는 단 하나의 데이터 저장소만 연동하면 충분해야 한다. 즉 새로운 데이터 시스템(소스든 목적지든)을 추가할 때 필요한 통합 작업이 각 소비자마다가 아니라 단 하나의 중앙 파이프라인에 연결하는 것으로 끝나야 한다는 아이디어다.

이 경험이 필자로 하여금 Kafka를 만드는 데 집중하게 했다. Kafka는 메시징 시스템에서 봐온 것과 데이터베이스·분산 시스템 내부에서 널리 쓰이던 로그 개념을 결합한 것이다. 목표는 모든 활동 데이터를 위한 중앙 파이프라인이자, 나아가 Hadoop에서 나오는 데이터 배포, 모니터링 데이터 등 다양한 용도로 쓸 수 있는 무언가를 만드는 것이었다.

오랫동안 Kafka는 인프라 제품으로서 다소 독특한(어떤 이는 이상하다고 할 만한) 존재였다. 데이터베이스도 아니고, 로그 파일 수집 시스템도 아니고, 전통적인 메시징 시스템도 아니었기 때문이다. 그런데 최근 Amazon이 Kinesis라는, Kafka와 매우 흡사한 서비스를 내놓았다. 파티셔닝을 다루는 방식, 데이터 보존 방식, 그리고 Kafka API에서 상위/하위 레벨 컨슈머를 나누는 다소 특이한 구조까지 유사성이 이어졌다. 필자는 이를 반가운 신호로 받아들였다. 좋은 인프라 추상화를 만들었다는 증거 중 하나는 AWS가 그것을 서비스로 제공한다는 것이기 때문이다. Amazon의 비전 역시 DynamoDB, RedShift, S3 등 자사의 여러 분산 시스템을 잇는 배관이자, EC2를 이용한 분산 스트림 처리의 기반이라는, 이 글이 말하는 것과 거의 동일한 그림으로 보인다.

#### ETL과 데이터 웨어하우스와의 관계

데이터 웨어하우징에 대해서도 잠깐 짚고 넘어갈 만하다. 데이터 웨어하우스는 분석을 지원하기 위해 구조화된, 깨끗하고 통합된 데이터의 저장소가 되는 것을 목표로 한다. 훌륭한 아이디어다. 데이터 웨어하우징 방법론에 익숙하지 않은 이들을 위해 설명하면, 원본 데이터베이스에서 주기적으로 데이터를 추출하고, 이를 이해 가능한 형태로 다듬은 뒤, 중앙 데이터 웨어하우스에 적재하는 과정을 말한다. 모든 데이터의 깨끗한 사본을 담은 이 중앙 저장소를 갖는 것은 데이터 집약적인 분석과 처리에서 엄청나게 값진 자산이다. 이 방법론 자체는 Oracle이나 Teradata 같은 전통적 웨어하우스를 쓰든 Hadoop을 쓰든 크게 다르지 않다. 적재와 가공의 순서만 달라질 뿐이다.

깨끗하고 통합된 데이터를 담은 데이터 웨어하우스는 굉장한 자산이지만, 그것을 만들어내는 메커니즘 자체는 다소 시대에 뒤떨어져 있다.

![Oracle 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/oracle.jpg)

데이터 중심 조직이 마주하는 핵심 문제는, 깨끗하게 통합된 데이터가 데이터 웨어하우스라는 하나의 시스템에 결합(coupling)되어 있다는 점이다. 데이터 웨어하우스는 단순 카운팅, 집계, 필터링이 중심인 여러 종류의 리포팅과 애드혹 분석에 잘 맞는 배치 질의 인프라다. 하지만 깨끗하고 완전한 데이터의 유일한 저장소가 배치 시스템이라면, 실시간 처리·검색 색인·모니터링 시스템처럼 실시간 피드가 필요한 시스템에는 그 데이터를 쓸 수 없다는 문제가 생긴다.

필자가 보기에 ETL은 사실 두 가지 서로 다른 일을 하나로 뭉뚱그린 것이다. 첫째는 추출과 데이터 정제 과정 — 조직 곳곳의 시스템에 갇혀 있던 데이터를 해방시키고 시스템 특유의 잡음을 제거하는 일이다. 둘째는 그 데이터를 데이터 웨어하우스 질의에 맞게 재구성하는 일, 즉 관계형 DB의 타입 체계에 맞추거나 star/snowflake 스키마에 강제로 끼워 맞추거나 고성능 컬럼 포맷으로 쪼개는 일이다. 이 두 가지를 뭉뚱그리는 것이 문제다. 깨끗하고 통합된 데이터 저장소는 저지연 처리나 다른 실시간 저장 시스템의 색인 작업에도 실시간으로 이용 가능해야 한다.

이렇게 나누면 데이터 웨어하우징 ETL을 조직적으로 훨씬 더 확장 가능하게 만드는 부수적 이점도 생긴다. 데이터 웨어하우스 팀의 고질적인 문제는, 조직 내 다른 모든 팀이 생성한 데이터를 수집하고 정제하는 책임을 떠안는다는 것이다. 인센티브가 서로 어긋나 있다 — 데이터를 생산하는 쪽은 그 데이터가 웨어하우스에서 어떻게 쓰이는지 잘 모르는 경우가 많아서, 추출하기 어렵거나 사용 가능한 형태로 바꾸는 데 무겁고 확장하기 힘든 변환이 필요한 데이터를 만들어내곤 한다. 물론 중앙 팀은 조직의 성장 속도를 결코 따라잡지 못하니, 데이터 커버리지는 늘 듬성듬성하고 데이터 흐름은 취약하며 변경은 느리기만 하다.

더 나은 방식은 데이터를 추가하기 위한 명확한 API를 갖춘 중앙 파이프라인, 즉 로그를 두는 것이다. 이 파이프라인에 연동하고 깨끗하고 잘 구조화된 데이터 피드를 제공할 책임은 그 데이터를 생산하는 쪽에 있다. 즉 시스템을 설계하고 구현할 때부터 데이터를 어떻게 내보내고 중앙 파이프라인에 맞는 잘 구조화된 형태로 만들지를 함께 고민해야 한다는 뜻이다. 새로운 저장 시스템이 추가되어도 데이터 웨어하우스 팀에는 아무 영향이 없다. 이들에게는 이미 통합을 위한 단 하나의 지점이 있기 때문이다. 데이터 웨어하우스 팀은 이제 중앙 로그에서 구조화된 피드를 적재하고, 자신들의 시스템에 특화된 변환만 수행하면 되는, 훨씬 단순한 문제만 다루면 된다.

![파이프라인 소유권 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/pipeline_ownership.png)

이런 조직적 확장성 문제는 전통적인 데이터 웨어하우스를 넘어 추가적인 데이터 시스템을 도입하려 할 때 더욱 중요해진다. 예컨대 조직 전체 데이터셋에 대한 검색 기능을 제공하고 싶다거나, 실시간 트렌드 그래프와 알림 기능을 갖춘 초 단위 미만 모니터링을 제공하고 싶다고 하자. 이런 경우 전통적인 데이터 웨어하우스나 심지어 Hadoop 클러스터의 인프라조차 적합하지 않다. 설상가상으로, 데이터베이스 적재를 지원하기 위해 만들어진 ETL 파이프라인은 이런 다른 시스템들에 데이터를 공급하는 데 별 쓸모가 없는 경우가 많아서, 이런 인프라를 처음부터 구축하는 부담이 데이터 웨어하우스를 도입하는 것만큼이나 커져버린다. 이는 현실적으로 감당하기 어려운 일이고, 대부분의 조직이 모든 데이터에 대해 이런 역량을 쉽게 갖추지 못하는 이유를 설명해준다. 반대로 조직이 이미 균일하고 잘 구조화된 데이터 피드를 갖춰 두었다면, 어떤 새 시스템이든 전체 데이터에 완전히 접근하게 만드는 데 필요한 것은 그 파이프라인에 붙일 단 하나의 연동 작업뿐이다.

이런 아키텍처는 또한 정제나 변환 작업을 어디서 수행할지에 관해 몇 가지 선택지를 제시한다.

- 데이터 생산자가 회사 전체 로그에 데이터를 추가하기 전에 수행할 수 있다.
- 로그 위에서의 실시간 변환으로 수행할 수 있다(이 경우 새로운, 변환된 로그가 만들어진다).
- 특정 목적지 데이터 시스템으로의 적재 과정 일부로 수행할 수 있다.

가장 좋은 모델은 데이터를 발행하는 쪽이 로그에 발행하기 전에 정제를 마치는 것이다. 즉 데이터가 그것을 만든 특정 코드나 그것이 유지되던 저장 시스템의 흔적을 남기지 않는, 표준적인(canonical) 형태를 갖추도록 하는 것이다. 이런 세부 사항은 자신의 데이터를 가장 잘 아는 팀이 처리하는 것이 최선이며, 이 단계에서 적용되는 어떤 로직이든 무손실이고 되돌릴 수 있어야 한다.

실시간으로 수행 가능한 부가가치 변환은 원본 로그 피드에 대한 후처리로 수행하는 것이 좋다. 예컨대 이벤트 데이터의 세션화(sessionization)나, 일반적으로 유용한 다른 파생 필드를 추가하는 일이 여기 해당한다. 원본 로그는 여전히 그대로 남아 있고, 이 실시간 처리는 보강된 데이터를 담은 파생 로그를 만들어낸다.

마지막으로, 목적지 시스템에만 특화된 집계는 적재 과정의 일부로 수행되어야 한다. 예컨대 데이터 웨어하우스에서 분석과 리포팅을 위한 특정 star/snowflake 스키마로 데이터를 변환하는 작업이 여기 해당한다. 전통적인 ETL 과정에 가장 가깝게 대응하는 이 단계는, 이제 훨씬 더 깨끗하고 균일한 스트림들을 대상으로 이루어지므로 훨씬 단순해진다.

#### 로그 파일과 이벤트

이 아키텍처의 부수적인 이점 하나는 결합이 느슨한(decoupled), 이벤트 기반 시스템을 가능하게 한다는 것이다.

웹 업계에서 흔한 활동 데이터 처리 방식은 텍스트 파일에 로그로 남긴 뒤 이를 긁어서 데이터 웨어하우스나 Hadoop으로 옮겨 집계·질의하는 것이다. 이 방식의 문제는 다른 모든 배치 ETL의 문제와 같다 — 데이터 흐름이 데이터 웨어하우스의 처리 능력과 스케줄에 결합되어 버린다는 것.

LinkedIn은 이벤트 데이터 처리를 로그 중심 방식으로 구축했다. 중앙의, 다중 구독자를 지원하는 이벤트 로그로 Kafka를 쓰며, 특정 종류의 행동이 갖는 고유한 속성을 포착하는 수백 종의 이벤트 타입을 정의해 두었다. 페이지뷰, 광고 노출, 검색부터 서비스 호출, 애플리케이션 예외까지 모두 이 범주에 들어간다.

이 방식의 장점을 이해하기 위해 간단한 이벤트 하나를 생각해보자 — 채용공고 페이지에 공고 하나를 보여주는 것. 채용공고 페이지는 원래 공고를 보여주는 데 필요한 로직만 가지면 된다. 그런데 상당히 동적인 사이트에서는 이 페이지가 공고를 보여주는 것과 무관한 로직으로 금세 뒤덮이기 쉽다. 예를 들어 다음과 같은 시스템들과 연동해야 한다고 하자.

- 오프라인 처리를 위해 이 데이터를 Hadoop과 데이터 웨어하우스로 보내야 한다.
- 콘텐츠 스크래핑 같은 시도를 탐지하기 위해 조회수를 세야 한다.
- 채용 담당자의 분석 페이지에 표시하기 위해 이 조회를 집계해야 한다.
- 같은 추천을 반복해서 보여주지 않도록 사용자별 노출 상한(impression cap)을 관리하려면 이 조회를 기록해야 한다.
- 추천 시스템이 해당 공고의 인기도를 정확히 추적하기 위해 이 조회를 기록해야 할 수도 있다.
- 그 외에도 여러 가지.

이렇게 되면 공고 하나를 보여주는 단순한 동작이 순식간에 상당히 복잡해진다. 게다가 공고가 노출되는 지점(모바일 앱 등)이 늘어날수록 이 로직을 그대로 이식해야 하고 복잡도는 계속 커진다. 더 나쁜 것은, 이렇게 연동해야 하는 시스템들이 서로 얽혀버려서 공고 표시 화면을 담당하는 사람이 다른 여러 시스템과 기능을 알아야 하고 이들이 제대로 연동되는지 신경 써야 한다는 점이다. 이는 아주 단순화된 예시일 뿐이고, 실제 애플리케이션은 이보다 훨씬 더 복잡할 수밖에 없다.

"이벤트 기반" 스타일은 이 문제를 단순화하는 접근법을 제공한다. 공고 표시 페이지는 이제 공고를 보여주고, 공고가 표시되었다는 사실과 공고·조회자·기타 유용한 속성들을 기록하기만 하면 된다. 추천 시스템, 보안 시스템, 채용 담당자 분석 시스템, 데이터 웨어하우스 같은 다른 관심 있는 시스템들은 모두 이 피드를 구독해서 각자의 처리를 수행한다. 화면을 표시하는 코드는 이런 다른 시스템들의 존재를 알 필요가 없고, 새로운 데이터 소비자가 추가되어도 바뀔 필요가 없다.

#### 확장 가능한 로그 구축하기

발행자와 구독자를 분리하는 것 자체는 새로운 아이디어가 아니다. 하지만 소비자 규모의 웹사이트에서 벌어지는 모든 일을 다중 구독자용 실시간 저널로 담는 commit log를 유지하고 싶다면, 확장성이 핵심 과제가 된다. 로그를 범용 통합 메커니즘으로 쓴다는 발상은, 빠르고 저렴하며 실제 규모에서 실용적으로 동작할 만큼 확장 가능한 로그를 만들어낼 수 없다면 그저 우아한 공상에 그칠 뿐이다.

시스템 엔지니어들은 흔히 분산 로그를 느리고 무거운 추상화로 여기고(그래서 Zookeeper가 다루는 것 같은 "메타데이터" 용도에나 어울린다고 생각하는 경우가 많다), 그러나 대용량 데이터 스트림을 저널링하는 데 초점을 맞춰 신중하게 구현하면 꼭 그럴 필요는 없다. LinkedIn은 이 글을 쓰는 시점 기준으로 하루 600억 건이 넘는 고유 메시지를 Kafka로 처리하고 있으며(데이터센터 간 미러링에서 발생하는 쓰기까지 더하면 수천억 건에 달한다), 이는 로그가 결코 느린 추상화일 필요가 없다는 방증이다.

이런 규모를 지원하기 위해 Kafka는 몇 가지 기법을 사용한다.

- 로그를 파티셔닝한다.
- 읽기와 쓰기를 배칭(batching)해서 처리량을 최적화한다.
- 불필요한 데이터 복사를 피한다.

수평 확장을 가능하게 하기 위해 로그를 여러 파티션으로 쪼갠다.

![파티셔닝된 로그 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/partitioned_log.png)

각 파티션은 완전히 순서가 정해진 로그이지만, 파티션들 사이에는 전역적인 순서가 없다(메시지에 굳이 포함시킨 벽시계 시간이 있다면 모를까). 어떤 메시지를 어느 파티션에 넣을지는 쓰는 쪽에서 제어할 수 있으며, 대부분의 사용자는 사용자 ID 같은 키를 기준으로 파티셔닝한다. 파티셔닝 덕분에 샤드 간 조정 없이도 로그에 append할 수 있고, 시스템의 처리량은 Kafka 클러스터 크기에 비례해 선형적으로 늘어난다.

각 파티션은 설정 가능한 수만큼 복제되며, 각 복제본은 해당 파티션의 로그를 동일하게 갖고 있다. 언제든 그중 하나가 리더 역할을 맡고, 리더가 실패하면 다른 복제본 중 하나가 리더 역할을 이어받는다.

파티션 간 전역 순서가 없다는 것은 하나의 제약이지만, 실제로 큰 문제가 되지는 않았다. 실제로 로그와의 상호작용은 보통 수백, 수천 개의 서로 다른 프로세스에서 이루어지므로, 이들의 행동 전체에 대한 전역 순서를 논하는 것 자체가 별로 의미가 없다. 대신 Kafka가 보장하는 것은 각 파티션 내부의 순서가 유지된다는 것과, 단일 발신자가 특정 파티션에 append한 메시지들은 보낸 순서대로 전달된다는 것이다.

로그는 파일 시스템처럼 선형적인 읽기·쓰기 패턴에 최적화하기 좋다. 작은 규모의 읽기·쓰기를 더 크고 처리량 높은 연산으로 묶어낼 수 있는데, Kafka는 이 최적화를 적극적으로 추구한다. 배칭은 클라이언트에서 서버로 데이터를 보낼 때, 디스크에 쓸 때, 서버 간 복제 시, 컨슈머로의 데이터 전송 시, 커밋된 데이터를 확인응답할 때 등 여러 단계에서 이루어진다.

또한 Kafka는 인메모리 로그, 디스크 상의 로그, 네트워크 전송 사이에 동일하게 유지되는 단순한 바이너리 포맷을 쓴다. 이는 zero-copy 데이터 전송을 비롯한 다양한 최적화를 가능하게 한다.

이런 최적화들이 누적된 효과로, 메모리 용량을 훨씬 초과하는 데이터셋을 다루면서도 대체로 디스크나 네트워크가 지원하는 속도만큼 데이터를 읽고 쓸 수 있게 된다.

이 글의 주된 목적이 Kafka 자체를 설명하는 것은 아니므로 세부 사항은 여기까지만 다룬다. LinkedIn의 접근 방식과 Kafka의 설계에 대한 더 자세한 내용은 원문이 링크하는 별도의 자료들에서 확인할 수 있다.

### Part Three: 로그와 실시간 스트림 처리

지금까지는 결국 데이터를 이곳저곳으로 옮기는 다소 고급스러운 복사 방법을 설명한 셈이다. 하지만 저장 시스템 사이에서 바이트를 실어 나르는 것이 이야기의 끝은 아니다. "로그"는 사실 "스트림"의 다른 이름이며, 로그는 스트림 처리의 핵심에 자리 잡고 있다.

그런데 스트림 처리란 정확히 무엇인가? 1990년대 말·2000년대 초의 데이터베이스 문헌이나 그 시절 다소 성공적이었던 데이터 인프라 제품에 익숙한 사람이라면, 스트림 처리라고 하면 이벤트 기반 처리를 위한 SQL 엔진이나 "박스와 화살표" 형태의 인터페이스를 만들려는 시도를 떠올릴 것이다. 반대로 오픈소스 데이터 시스템의 폭발적 증가를 지켜본 사람이라면 Storm, Akka, S4, Samza 같은 시스템들을 떠올릴 텐데, 대부분의 사람은 이런 시스템을 클러스터를 인식하는 RPC 계층과 크게 다르지 않은 일종의 비동기 메시지 처리 시스템 정도로 본다(실제로 그런 성격이 강한 것도 일부 있긴 하다).

두 관점 모두 다소 협소하다. 스트림 처리는 SQL과 아무 관련이 없으며, 실시간 처리에 국한되지도 않는다. 어제나 한 달 전의 데이터 스트림을 다양한 언어로 처리하지 못할 근본적인 이유는 없다.

![인구 조사 이미지](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/census.jpg)

필자는 스트림 처리를 훨씬 더 넓은 개념 — **연속적인 데이터 처리를 위한 인프라** — 로 본다. 이 계산 모델은 MapReduce 같은 다른 분산 처리 프레임워크만큼이나 일반적일 수 있으면서도, 저지연 결과를 낼 수 있는 능력을 갖춘다.

어떤 처리 모델을 택할지를 실제로 좌우하는 것은 데이터를 어떻게 수집하느냐다. 배치로 수집된 데이터는 자연스럽게 배치로 처리되고, 연속적으로 수집된 데이터는 자연스럽게 연속적으로 처리된다.

미국 인구 조사(census)는 배치 데이터 수집의 좋은 예다. 인구 조사는 주기적으로 시작되어, 사람들이 집집마다 돌아다니며 시민을 무차별적으로 찾아내고 세는 방식으로 이루어진다. 1790년 최초의 인구 조사가 시작될 당시에는 이런 방식이 상당히 합리적이었다. 그 시절의 데이터 수집이란 본질적으로 배치였다 — 말을 타고 돌아다니며 종이에 기록을 남기고, 이 기록 뭉치를 중앙의 한 장소로 옮겨 사람이 직접 집계하는 식이었으니 말이다. 오늘날 이런 인구 조사 과정을 설명하면, 왜 출생과 사망을 계속 기록해서 원하는 단위로 언제든 연속적으로 인구수를 산출하지 않는지 의문이 들 정도다.

이는 다소 극단적인 예시지만, 여전히 많은 데이터 전송 과정이 주기적인 덤프와 대량 전송·통합에 의존하고 있다. 대량 덤프를 처리하는 자연스러운 방법은 배치 처리뿐이다. 그러나 이런 과정들이 점차 연속적인 피드로 대체되면서, 처리에 필요한 자원을 매끄럽게 유지하고 지연을 줄이기 위해 자연스럽게 연속 처리 쪽으로 옮겨가게 된다.

예를 들어 LinkedIn은 배치 데이터 수집이 거의 없다. LinkedIn 데이터 대부분은 활동 데이터이거나 데이터베이스 변경이며, 둘 다 연속적으로 발생한다. 사실 어떤 비즈니스를 떠올려 봐도 그 밑바탕의 메커니즘은 거의 항상 연속적인 과정이다 — 이벤트는 실시간으로 일어나기 때문이다. 데이터가 배치로 수집된다면 그것은 거의 항상 어떤 수작업 단계나 디지털화 부재, 혹은 비디지털 프로세스가 자동화되면서 남은 역사적 유물에 가깝다. 우편과 사람이 처리를 담당하던 시절에는 데이터를 전달하고 그에 반응하는 일 자체가 매우 느렸고, 자동화의 첫 시도는 대체로 원래 프로세스의 형태를 그대로 유지하는 경향이 있어 이런 잔재가 오래 남곤 한다.

매일 실행되는 "배치" 프로덕션 처리 작업들도 사실은 하루라는 윈도우 크기를 가진 일종의 연속 계산을 흉내 내고 있는 셈이다. 밑바탕의 데이터는 물론 끊임없이 변하고 있다. LinkedIn에서는 이런 일간 배치 작업이 실제로 매우 흔했고(Hadoop에서 이를 제대로 동작시키는 메커니즘도 꽤 까다로웠다), 그래서 증분(incremental) Hadoop 워크플로를 관리하기 위한 프레임워크를 통째로 구축하기도 했다.

이런 관점에서 보면 스트림 처리를 다르게 바라볼 수 있다. 그것은 그저 처리 대상 데이터에 시간이라는 개념이 내재해 있고, 데이터의 정적인 스냅샷을 요구하지 않으며, 데이터셋의 "끝"에 도달하기를 기다리는 대신 사용자가 제어하는 빈도로 결과를 낼 수 있는 처리일 뿐이다. 이런 의미에서 스트림 처리는 배치 처리를 일반화한 것이며, 실시간 데이터가 널리 퍼진 오늘날 이는 매우 중요한 일반화다.

그렇다면 스트림 처리는 왜 오랫동안 그저 틈새 응용 분야로만 여겨져 왔을까? 필자는 그 가장 큰 이유가 실시간 데이터 수집의 부재로 인해 연속 처리 자체가 다소 학술적인 관심사에 머물렀기 때문이라고 본다. 상업용 스트림 처리 시스템들이 몰락한 것도 실시간 데이터 수집의 결여 때문이었을 가능성이 크다. 그들의 고객은 여전히 ETL과 데이터 통합을 위해 파일 기반의 일간 배치 처리를 하고 있었다. 스트림 처리 회사들은 실시간 데이터 스트림에 붙일 처리 엔진을 제공하는 데 초점을 맞췄지만, 정작 당시에는 실제로 실시간 데이터 스트림을 갖춘 곳이 거의 없었다. 필자가 LinkedIn 경력 초창기에 겪은 일화로, 어떤 회사가 매우 멋진 스트림 처리 시스템을 팔러 왔는데, 당시 모든 데이터가 시간 단위 파일로 수집되고 있었던 탓에 이 시스템을 활용할 가장 그럴듯한 방법이 그 시간 단위 파일을 정각에 스트림 시스템으로 흘려보내는 것뿐이었다는 웃지 못할 사례가 있었다. 그 회사도 이것이 꽤 흔한 문제라고 인정했다. 이 예외 사례가 오히려 규칙을 증명해주는 셈인데, 스트림 처리가 어느 정도 성공을 거둔 유일한 영역인 금융이야말로 실시간 데이터 스트림이 이미 표준이었고 처리 자체가 병목이었던 영역이기 때문이다.

건강한 배치 처리 생태계가 있는 지금도, 인프라 스타일로서 스트림 처리가 실제로 적용될 수 있는 범위는 상당히 넓다고 필자는 본다. 이는 실시간 요청/응답 서비스와 오프라인 배치 처리 사이의 인프라 공백을 메워준다. 현대 인터넷 기업이라면 코드의 약 25% 정도가 이 범주에 들어간다는 것이 필자의 추정이다.

결국 로그가 스트림 처리의 여러 핵심적인 기술 문제를 풀어주는데, 그중에서도 가장 큰 기여는 데이터를 실시간 다중 구독자 피드로 이용 가능하게 만든다는 점이다. 더 자세한 내용에 관심 있는 독자를 위해, LinkedIn은 이런 아이디어들 위에 명시적으로 구축한 스트림 처리 시스템 Samza를 오픈소스로 공개했다.

#### 데이터 흐름 그래프

![DAG 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/dag.png)

스트림 처리에서 가장 흥미로운 지점은 스트림 처리 시스템 내부 구현이 아니라, 앞서 데이터 통합에서 다룬 "데이터 피드"라는 개념을 어떻게 확장하느냐에 있다. 앞에서는 주로 원본 데이터 — 여러 애플리케이션이 실행되며 만들어내는 이벤트와 행(row) 데이터 — 의 피드나 로그를 다뤘다. 하지만 스트림 처리는 다른 피드로부터 계산되는 파생 피드까지 포함할 수 있게 해준다. 이 파생 피드는 이를 소비하는 쪽에서 보면 원본 데이터의 피드와 조금도 다르지 않으며, 임의의 복잡도를 얼마든지 캡슐화할 수 있다.

좀 더 파고들어 보자. 이 글의 맥락에서 스트림 처리 작업이란, 로그로부터 읽어 다른 로그나 시스템으로 출력을 쓰는 무엇이든을 가리킨다. 이런 작업들이 입출력에 사용하는 로그가 이 프로세스들을 하나의 처리 단계 그래프로 엮어준다. 실제로 이런 식으로 중앙화된 로그를 활용하면, 조직의 모든 데이터 포착·변환·흐름을 그저 로그들과 거기에 쓰고 읽는 프로세스들의 연속으로 바라볼 수 있게 된다.

스트림 처리기가 반드시 대단한 프레임워크일 필요는 없다. 로그로부터 읽고 로그에 쓰는 프로세스(들의 집합)라면 무엇이든 스트림 처리기가 될 수 있으며, 다만 처리 코드를 관리하는 데 도움이 될 추가적인 인프라와 지원을 얹을 수 있을 뿐이다.

이 통합 구조에서 로그가 하는 역할은 두 가지다.

첫째, 로그는 각 데이터셋을 다중 구독자가 가능하고 순서가 보장되는 형태로 만들어준다. 앞서 다룬 "상태 복제" 원칙을 떠올리면 순서가 왜 중요한지 알 수 있다. 좀 더 구체적으로 말해, 데이터베이스에서 나오는 업데이트 스트림을 생각해보면, 같은 레코드에 대한 두 업데이트의 순서가 처리 과정에서 뒤바뀔 경우 잘못된 최종 결과가 나올 수 있다. 이 순서 보장은 TCP 같은 것이 제공하는 순서 보장보다 훨씬 더 영속적인데, 단일한 지점 대 지점(point-to-point) 연결에 국한되지 않고 프로세스 실패와 재연결을 넘어서도 유지되기 때문이다.

둘째, 로그는 프로세스들에 버퍼링을 제공한다. 이는 매우 근본적인 성질이다. 처리 과정이 동기화되지 않은 상태로 진행되면, 상류(upstream)의 데이터 생산 작업이 하류(downstream)의 작업이 소비할 수 있는 속도보다 더 빠르게 데이터를 만들어내는 상황이 흔히 벌어진다. 이런 경우 처리는 블록되거나, 버퍼링되거나, 데이터를 버려야 한다. 데이터를 버리는 것은 대체로 선택지가 아니고, 블로킹은 처리 그래프 전체를 멈춰 세울 위험이 있다. 로그는 아주 커다란 버퍼처럼 동작해서, 프로세스가 재시작되거나 실패해도 처리 그래프의 다른 부분들의 속도를 늦추지 않게 해준다. 이런 격리는 이 데이터 흐름을 더 큰 조직으로 확장할 때 특히 중요해진다. 서로 다른 팀들이 만든 여러 작업들이 함께 처리를 담당하는 상황에서, 어느 한 작업의 결함이 전체 처리 흐름을 멈추는 역압(back-pressure)을 만들어서는 안 되기 때문이다.

Storm과 Samza 모두 이런 방식으로 구축되어 있으며, 로그로 Kafka나 이와 유사한 시스템을 활용할 수 있다.

#### 상태를 가진 실시간 처리

일부 실시간 스트림 처리는 레코드 하나하나를 상태 없이(stateless) 변환하는 정도에 그치지만, 많은 경우 스트림 위의 윈도우에 걸친 좀 더 정교한 카운트, 집계, 조인이 필요하다. 예를 들어 클릭 이벤트 스트림을, 그 클릭을 발생시킨 사용자 계정 정보로 보강(enrich)하고 싶을 수 있다 — 사실상 클릭 스트림을 사용자 계정 데이터베이스와 조인하는 것이다. 이런 처리는 예외 없이 처리기가 어떤 형태로든 상태를 유지해야 하는 상황으로 이어진다. 가령 카운트를 계산한다면 지금까지의 누적 카운트를 어딘가에 유지해야 한다. 그렇다면 처리기 자체가 실패할 수 있는 상황에서 이런 상태를 어떻게 올바르게 유지할 수 있을까?

가장 단순한 방법은 상태를 메모리에 두는 것이지만, 프로세스가 죽으면 중간 상태를 잃어버리게 된다. 상태가 특정 윈도우에 대해서만 유지되는 것이라면, 윈도우가 시작된 지점의 로그로 되돌아가 다시 처리하면 되지만, 한 시간 단위의 카운트라면 이마저 현실적이지 않을 수 있다.

또 다른 방법은 모든 상태를 원격 저장 시스템에 저장하고 네트워크를 거쳐 그 저장소와 조인하는 것이다. 문제는 데이터 지역성(locality)이 사라지고 네트워크 왕복이 잦아진다는 점이다.

그렇다면 처리와 함께 파티셔닝되는 일종의 "테이블"을 어떻게 지원할 수 있을까? 여기서 앞서 다룬 테이블과 로그의 쌍대성이 정확히 필요한 도구가 되어준다. 스트림을 처리와 같은 위치에 놓인(co-located) 테이블로 변환하는 방법, 그리고 이 테이블들의 장애 대응을 처리하는 메커니즘까지 제공해주기 때문이다.

스트림 처리기는 자신의 상태를 bdb, leveldb, 혹은 Lucene이나 fastbit 색인 같은 좀 더 특이한 형태를 포함한 로컬 "테이블" 또는 "인덱스"에 보관할 수 있다. 이 저장소의 내용은 (필요하면 임의의 변환을 먼저 거친) 입력 스트림으로부터 채워진다. 처리기는 자신이 유지하는 이 로컬 인덱스에 대한 변경 로그(changelog)를 저널로 남겨서, 프로세스가 죽었을 때 상태를 복원할 수 있게 만든다. 이 메커니즘은 들어오는 스트림 데이터와 함께 파티셔닝된 상태를, 어떤 종류의 인덱스 형태든 상관없이 유지할 수 있는 범용적인 방법을 제공한다.

프로세스가 실패하면 이 변경 로그로부터 자신의 인덱스를 복원한다. 로그는 로컬 상태를 일종의 시간 순 증분 백업 형태로 변환한 것이라 볼 수 있다.

이런 상태 관리 방식이 가진 우아한 성질은, 처리기의 상태 역시 하나의 로그로서 유지된다는 것이다. 이 로그는 데이터베이스 테이블에 대한 변경 로그와 똑같은 방식으로 생각할 수 있다. 실제로 이 처리기들은 함께 파티셔닝된 테이블에 매우 가까운 것을 유지하는 셈이며, 이 상태 자체가 로그이므로 다른 처리기들이 이를 구독할 수도 있다. 이는 처리의 목표가 최종 상태를 갱신하는 것이고 그 상태 자체가 처리의 자연스러운 산출물일 때 특히 유용하다.

이를 데이터 통합 목적으로 데이터베이스에서 뽑아낸 로그와 결합하면, 로그와 테이블의 쌍대성이 갖는 힘이 분명해진다. 데이터베이스에서 추출한 변경 로그를 다양한 스트림 처리기들이 각기 다른 형태로 색인하여 이벤트 스트림과 조인할 수 있게 되는 것이다.

#### 로그 컴팩션

![로그 컴팩션 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/log_compaction_0.png)

물론 모든 시간 동안의 모든 상태 변경을 담은 완전한 로그를 영원히 유지할 수는 없다. 무한한 공간을 쓰지 않는 한, 로그는 어떻게든 정리되어야 한다. Kafka에서의 구현을 조금 구체적으로 살펴보자. Kafka에서 정리 방식은 데이터가 키 기반 업데이트인지, 이벤트 데이터인지에 따라 두 가지로 나뉜다. 이벤트 데이터의 경우 Kafka는 일정한 데이터 윈도우만 보관하는 방식을 지원하는데, 보통 며칠 정도로 설정하며 시간이나 용량 기준으로 정의할 수 있다. 반면 키 기반 데이터의 경우, 완전한 로그가 지닌 좋은 성질 하나는 이를 재생(replay)해서 원본 시스템의 상태를 (필요하다면 다른 시스템에서도) 다시 만들어낼 수 있다는 것이다.

다만 완전한 로그를 계속 유지하면 시간이 지날수록 공간을 점점 더 많이 쓰게 되고, 재생에도 점점 더 오랜 시간이 걸린다. 그래서 Kafka는 다른 방식의 보존 정책을 지원한다. 오래된 로그를 그냥 버리는 대신, 더 최신 업데이트가 존재하는 오래된 레코드, 즉 이미 최신 값으로 덮어써진 레코드만 골라 제거한다. 이렇게 하면 로그가 여전히 원본 시스템의 완전한 백업이라는 보장은 유지하면서도, 더 이상 원본 시스템의 과거 모든 시점을 재현할 수는 없고 비교적 최신 상태들만 재현할 수 있게 된다. 이 기능을 **로그 컴팩션**(log compaction)이라 부른다.

### Part Four: 시스템 구축

마지막으로 다룰 주제는 온라인 데이터 시스템 설계에서 로그가 맡는 역할이다. 분산 데이터베이스 내부에서 로그가 데이터 흐름을 담당하는 역할과, 더 큰 조직에서 데이터 통합을 위해 로그가 담당하는 역할 사이에는 유사성이 있다. 두 경우 모두 로그는 데이터 흐름, 일관성, 복구를 책임진다. 조직이라는 것도 결국 아주 복잡한 분산 데이터 시스템이 아니면 무엇이겠는가.

#### 언번들링(Unbundling)?

조금 눈을 가늘게 뜨고 보면, 조직의 모든 시스템과 데이터 흐름 전체를 하나의 거대한 분산 데이터베이스로 볼 수 있다. Redis, SOLR, Hive 테이블 같은 개별 질의 지향 시스템들은 그저 데이터에 대한 특정한 인덱스로 볼 수 있고, Storm이나 Samza 같은 스트림 처리 시스템은 잘 발전된 트리거이자 뷰 구체화(view materialization) 메커니즘으로 볼 수 있다. 전통적인 데이터베이스 전문가들이 이런 관점을 특히 좋아하는데, 사람들이 왜 이렇게 다양한 데이터 시스템을 쓰고 있는지가 마침내 설명되기 때문이다 — 그것들은 그저 서로 다른 인덱스 타입일 뿐이라는 것이다.

물론 지금은 데이터 시스템의 종류가 폭발적으로 늘어난 것이 분명하지만, 사실 이런 복잡성은 예전부터 늘 존재했다. 관계형 데이터베이스의 전성기에도 조직들은 이미 수많은 관계형 데이터베이스를 갖고 있었다. 어쩌면 진정한 의미의 데이터 통합이라는 것은 모든 데이터가 정말로 한곳에 있었던 메인프레임 시절 이후로는 존재한 적이 없었을지도 모른다. 데이터를 여러 시스템으로 나누는 데는 여러 이유가 있다 — 규모, 지리적 위치, 보안, 성능 격리가 가장 흔한 이유다. 하지만 좋은 시스템이라면 이런 문제들을 해결할 수 있다. 예컨대 한 조직이 모든 데이터를 담고 다양하고 방대한 사용자층에 서비스를 제공하는 단 하나의 거대한 Hadoop 클러스터를 갖는 것도 충분히 가능하다.

그래서 분산 시스템으로 옮겨가는 과정에서 이미 가능해진 한 가지 단순화가 있다. 바로 각 시스템의 작은 인스턴스 여럿을 몇 개의 큰 클러스터로 통합하는 것이다. 아직 많은 시스템이 이를 허용할 만큼 충분히 성숙하지 않았다 — 보안이 부족하거나, 성능 격리를 보장하지 못하거나, 확장성이 충분치 않은 경우가 많다. 하지만 이런 문제들은 모두 해결 가능한 성질의 것들이다.

필자가 보기에 서로 다른 시스템들이 이렇게 폭발적으로 늘어난 원인은 분산 데이터 시스템을 만드는 일 자체가 어렵다는 데 있다. 하나의 질의 유형이나 사용 사례로 범위를 좁힘으로써 각 시스템은 실현 가능한 수준으로 자신의 범위를 줄일 수 있었다. 하지만 이 모든 시스템을 함께 운영하는 것은 지나친 복잡도를 낳는다.

필자는 앞으로 세 가지 방향이 가능하다고 본다.

첫째, 현재 상태가 상당 기간 그대로 이어지는 것이다. 분산 시스템을 만드는 어려움을 극복하기 힘들거나, 이런 전문화가 각 시스템에 새로운 수준의 편의성과 성능을 가져다주기 때문일 수 있다. 이 상태가 이어지는 한, 데이터 통합 문제는 데이터를 성공적으로 활용하는 데 있어 가장 핵심적인 과제 중 하나로 남을 것이고, 이 경우 데이터를 통합하는 외부 로그가 매우 중요해진다.

둘째, 충분히 범용적인 단일 시스템으로의 재통합이 일어나서, 여러 기능이 하나의 거대한 통합 시스템으로 다시 합쳐지는 것이다. 이 통합 시스템은 겉보기에는 관계형 데이터베이스와 비슷할 수도 있지만, 조직에서 쓰이는 방식은 크게 다를 것이다 — 자잘한 여러 시스템 대신 하나의 커다란 시스템만 있으면 되기 때문이다. 이 세계에서는 이 시스템 내부에서 해결되는 것을 제외하면 별도의 데이터 통합 문제가 사실상 존재하지 않는다. 다만 필자는 이런 시스템을 실제로 구축하는 일의 현실적 어려움 때문에 이 시나리오는 가능성이 낮다고 본다.

셋째, 필자가 엔지니어로서 개인적으로 매력을 느끼는 시나리오다. 새로운 세대의 데이터 시스템들은 거의 대부분 오픈소스라는 흥미로운 특징을 갖고 있다. 오픈소스라는 조건은 또 다른 가능성을 열어준다 — 데이터 인프라가 여러 서비스와 애플리케이션 대상 시스템 API들의 집합으로 "언번들링(unbundling)"될 수 있다는 것이다. 이는 이미 자바 진영에서 어느 정도 일어나고 있는 현상이다.

- Zookeeper가 시스템 조정(coordination)의 상당 부분을 담당한다(Helix나 Curator 같은 상위 추상화의 도움을 받기도 한다).
- Mesos와 YARN이 프로세스 가상화와 자원 관리를 담당한다.
- Lucene, LevelDB 같은 임베디드 라이브러리가 인덱싱을 담당한다.
- Netty, Jetty, 그리고 Finagle, rest.li 같은 상위 래퍼들이 원격 통신을 담당한다.
- Avro, Protocol Buffers, Thrift 등 수많은 라이브러리들이 직렬화를 담당한다.
- Kafka와 BookKeeper가 백엔드 로그를 제공한다.

이런 것들을 한데 쌓아놓고 눈을 가늘게 뜨고 보면, 마치 분산 데이터 시스템 엔지니어링을 위한 레고 조각들처럼 보이기 시작한다. 이 재료들을 조합해서 방대한 범위의 시스템을 만들어낼 수 있는 것이다. 물론 API보다는 구현 방식에 관심이 있는 최종 사용자에게 곧바로 와닿는 이야기는 아니지만, 계속 진화하는 더 다양하고 모듈화된 세계 속에서도 단일 시스템이 주는 단순함을 얻을 수 있는 길이 될 수도 있다. 신뢰할 수 있고 유연한 빌딩 블록들이 등장해서 분산 시스템을 구현하는 데 걸리는 시간이 몇 년에서 몇 주로 줄어든다면, 하나의 거대한 단일 시스템으로 합쳐야 한다는 압력 자체가 사라질 것이다.

#### 시스템 아키텍처 속 로그의 위치

외부 로그의 존재를 전제로 하는 시스템은 개별 시스템 자체가 짊어져야 할 복잡성의 상당 부분을 내려놓고 공유된 로그에 의존할 수 있다. 필자가 보기에 로그가 해줄 수 있는 일은 다음과 같다.

- (즉시적이든 최종적이든) 노드에 대한 동시 업데이트의 순서를 정함으로써 데이터 일관성을 다룬다.
- 노드 간 데이터 복제를 제공한다.
- 쓰기 요청자에게 "커밋" 의미론을 제공한다(즉 쓰기가 유실되지 않는다고 보장될 때만 확인응답한다).
- 시스템으로부터의 외부 데이터 구독 피드를 제공한다.
- 데이터를 잃은 복제본을 복구하거나 새 복제본을 부트스트랩하는 능력을 제공한다.
- 노드 사이의 데이터 재분배(rebalancing)를 처리한다.

이는 사실 분산 데이터 시스템이 하는 일의 상당 부분에 해당한다. 실제로 이를 제외하고 남는 부분은 대체로 최종 클라이언트를 향한 질의 API와 인덱싱 전략에 관한 것뿐이다. 그리고 이 부분이야말로 시스템마다 달라져야 하는 지점이다. 예를 들어 전문(full-text) 검색 질의는 모든 파티션을 뒤져야 할 수 있지만, 기본 키로의 질의는 그 키의 데이터를 담당하는 단일 노드만 조회하면 될 수도 있다.

이 구조는 이렇게 동작한다. 시스템은 논리적으로 로그와 서빙 계층(serving layer)이라는 두 부분으로 나뉜다. 로그는 상태 변화를 순차적으로 포착한다. 서빙 노드들은 질의에 필요한 인덱스를 저장한다(예컨대 키-값 저장소라면 btree나 sstable 같은 것을, 검색 시스템이라면 역색인을 가질 것이다). 쓰기는 로그로 직접 갈 수도 있고, 서빙 계층을 거쳐 프록시될 수도 있다. 로그에 쓰는 것은 논리적인 타임스탬프(로그 상의 인덱스라 할 수 있다)를 만들어낸다. 시스템이 파티셔닝되어 있다면(대체로 그렇다고 가정한다), 로그와 서빙 노드는 같은 수의 파티션을 갖지만, 각 파티션을 감당하는 머신의 수는 서로 크게 다를 수 있다.

![로그와 서빙 계층 아키텍처 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/system.png)

서빙 노드들은 로그를 구독하고, 로그에 저장된 순서대로 최대한 빠르게 쓰기를 자신의 로컬 인덱스에 적용한다. 클라이언트는 질의에 자신이 방금 수행한 쓰기의 타임스탬프를 함께 실어 보냄으로써, 어떤 노드에서든 자신이 쓴 내용을 곧바로 읽을 수 있는(read-your-write) 의미론을 얻을 수 있다. 이런 질의를 받은 서빙 노드는 원하는 타임스탬프와 자신이 색인을 마친 지점을 비교해서, 필요하면 그 시점까지 색인이 끝날 때까지 요청을 지연시켜 오래된 데이터를 서빙하지 않도록 한다.

서빙 노드들은 "마스터" 지위나 "리더 선출" 같은 개념을 아예 가질 필요가 없을 수도 있다. 많은 단순한 사용 사례에서는 서빙 노드에 리더가 전혀 없어도 되는데, 로그 자체가 진실의 원천(source of truth)이기 때문이다.

분산 시스템이 다뤄야 하는 까다로운 일 중 하나가 실패한 노드를 복구하거나 파티션을 노드 간에 옮기는 것이다. 전형적인 접근은 로그가 고정된 윈도우의 데이터만 유지하도록 하고, 이를 해당 파티션에 저장된 데이터의 스냅샷과 결합하는 것이다. 로그가 데이터의 완전한 사본을 유지하면서 로그 자체를 가비지 컬렉션하는 것도 마찬가지로 가능하다. 이렇게 하면 상당한 복잡도가 시스템마다 특화된 서빙 계층에서 벗어나, 범용적으로 만들 수 있는 로그 쪽으로 옮겨간다.

이런 로그 시스템을 갖춤으로써, 다른 시스템으로의 ETL을 공급하는, 완전히 발전된 데이터 저장소 콘텐츠에 대한 구독 API를 얻게 된다. 실제로 여러 시스템이 서로 다른 인덱스를 제공하면서도 동일한 로그를 함께 쓸 수 있다.

![여러 시스템이 하나의 로그를 공유하는 전체 스택 다이어그램](https://web.archive.org/web/20240105095933im_/https://content.linkedin.com/content/dam/engineering/en-us/blog/migrated/full-stack.png)

이렇게 로그 중심으로 만들어진 시스템은 그 자체로 곧바로 다른 시스템에서의 처리와 적재를 위한 데이터 스트림의 공급자가 된다는 점에 주목할 만하다. 마찬가지로 하나의 스트림 처리기가 여러 입력 스트림을 소비한 뒤, 그 결과를 색인하는 또 다른 시스템을 통해 서빙할 수도 있다.

필자는 시스템을 로그와 질의 API로 나누어 보는 이런 관점이 매우 유용하다고 생각한다. 이렇게 보면 시스템의 질의 특성과, 가용성·일관성 측면을 분리해서 볼 수 있기 때문이다. 실제로 이런 식으로 설계되지 않은 시스템이라도, 이 틀에 맞춰 머릿속으로 나누어 이해하는 것이 도움이 될 정도다.

여기서 짚어둘 점은, Kafka와 BookKeeper가 (강)일관된 로그이긴 하지만 이것이 필수 조건은 아니라는 것이다. Dynamo 같은 데이터베이스도 최종적 일관성을 갖는 AP 로그와 키-값 서빙 계층으로 얼마든지 나눌 수 있다. 다만 이런 로그는 오래된 메시지를 다시 전달할 수 있고 이를 구독자가 처리해야 한다는 점에서(Dynamo 자체와 비슷하게) 다루기가 다소 까다롭다.

로그에 (특히 완전한 사본이라면) 데이터의 별도 복사본을 두는 것이 낭비처럼 느껴질 수 있다. 하지만 실제로는 이를 크게 문제 삼지 않게 만드는 몇 가지 요인이 있다. 첫째, 로그는 특히 효율적인 저장 메커니즘이 될 수 있다. LinkedIn은 프로덕션 Kafka 서버의 데이터센터당 저장량이 75TB를 넘는다. 반면 많은 서빙 시스템은 데이터를 효율적으로 서빙하기 위해 훨씬 더 많은 메모리를 필요로 한다(예컨대 텍스트 검색은 흔히 전부 메모리에 올려둔다). 서빙 시스템은 또한 최적화된 하드웨어를 쓰기도 한다. 예컨대 LinkedIn의 라이브 데이터 시스템 대부분은 메모리에서 서빙하거나 SSD를 쓴다. 반면 로그 시스템은 오직 선형적인 읽기·쓰기만 하기 때문에 수 테라바이트 규모의 저렴한 하드 드라이브를 써도 충분히 만족스럽다. 마지막으로, 앞서 그림에서 본 것처럼 데이터가 여러 시스템에서 서빙되는 경우 로그의 비용은 여러 인덱스에 걸쳐 분산(amortize)된다. 이런 요인들이 합쳐지면 외부 로그를 두는 비용은 상당히 미미해진다.

바로 이것이 LinkedIn이 자체 실시간 질의 시스템 여러 개를 구축하는 데 써온 패턴이다. 이 시스템들은 (로그 추상화로 Databus를 쓰거나 Kafka의 전용 로그를 써서) 데이터베이스로부터 데이터를 받아, 그 데이터 스트림 위에 특정한 파티셔닝, 인덱싱, 질의 기능을 제공한다. LinkedIn의 검색, 소셜 그래프, OLAP 질의 시스템이 모두 이런 방식으로 구현되었다. 실제로 (라이브 피드든 Hadoop에서 나온 파생 피드든) 하나의 데이터 피드가 여러 서빙 시스템에 복제되어 라이브 서빙에 쓰이는 것은 매우 흔한 패턴이며, 이는 엄청난 단순화 효과를 가져왔다. 이런 시스템들 중 어느 것도 외부에 노출되는 쓰기 API를 따로 가질 필요가 없다 — Kafka와 데이터베이스가 진실의 원천 역할을 하고, 변경 사항은 그 로그를 통해 적절한 질의 시스템들로 흘러간다. 쓰기는 해당 파티션을 담당하는 노드가 로컬에서 처리하는데, 이 노드들은 그저 로그가 제공하는 피드를 자신의 저장소로 그대로 옮겨 적을 뿐이다. 실패한 노드는 상류의 로그를 재생함으로써 복구할 수 있다.

이런 시스템들이 로그에 의존하는 정도는 시스템마다 다르다. 완전히 로그에 의존하는 시스템이라면, 데이터 파티셔닝, 노드 복구, 재분배, 그리고 일관성과 데이터 전파의 모든 측면에 로그를 활용할 수 있다. 이런 구성에서는 실제 서빙 계층이 사실상 특정 종류의 처리를 가능하게 하도록 구조화된 일종의 "캐시"에 지나지 않으며, 쓰기는 곧바로 로그로 향한다.

### 맺음말

원문의 마지막 절 "The End"는 별도의 논지를 펼치기보다, 상태 기계 복제와 주-백업(primary-backup) 복제에 관한 개괄 자료, Paxos 원 논문과 그 성립 배경을 다룬 Leslie Lamport의 회고, ZAB·RAFT·Viewstamped Replication 같은 Paxos 대안 프로토콜, Google Spanner처럼 물리적 시간을 다루는 방식이 다른 시스템, PNUTS·HBase·Bigtable·LinkedIn 자체의 Espresso처럼 실제 분산 데이터베이스에서 로그가 어떻게 쓰이는지를 보여주는 사례, 그리고 스트림 처리 초기 연구를 정리한 문헌 등 방대한 참고 자료 목록으로 마무리된다. 필자는 이 글에서 다룬 로그 개념이 데이터베이스 문헌, 분산 시스템 문헌, 엔터프라이즈 소프트웨어 진영, 오픈소스 커뮤니티에서 저마다 다른 용어로 불려온 탓에 서로 연결 짓기가 쉽지 않다는 점을 인정하면서, 이 참고 문헌들이 그 연결 고리를 찾는 데 도움이 되길 바란다는 말로 글을 맺는다.

## 분산 트랜잭션 너머의 삶

> 원문: [Life Beyond Distributed Transactions](https://queue.acm.org/detail.cfm?id=3025012)
> 저자: Pat Helland (ACM Queue) | 번역일: 2026-07-10

### 어느 배교자의 견해

*이 글은 2007년 CIDR(Conference on Innovative Database Research)에 처음 발표된 같은 제목의 논문을 갱신하고 축약한 버전이다.*

트랜잭션은 놀랍도록 강력한 메커니즘이며, 나는 거의 40년에 이르는 경력의 대부분을 트랜잭션 작업에 쏟았다. 1982년 나는 Tandem NonStop System에서 트랜잭션을 제공하는 일을 처음 맡았다. 이 시스템은 평균 무고장 시간(MTBF)이 연 단위로 측정되었고(참고문헌 4), 지리적으로 분산된 2단계 커밋을 갖추어 강한 일관성 트랜잭션에 대해 탁월한 가용성을 제공했다.

Google의 Spanner(참고문헌 2)를 비롯한 새로운 혁신들은 극도로 큰 규모에서 강한 일관성의 트랜잭션 환경을 탁월한 가용성과 함께 제공한다. 고가용성 애플리케이션을 지원하는 분산 트랜잭션을 만드는 일은 훌륭한 혁신과 뛰어난 기술을 낳은 대단한 도전이다. 안타깝게도 이것은 애플리케이션 개발자에게 널리 제공되고 있지 않다.

대부분의 분산 트랜잭션 시스템에서는 노드 하나의 실패가 트랜잭션 커밋을 멈추게 한다. 그러면 애플리케이션도 꼼짝 못 하게 된다. 이런 시스템에서는 규모가 커질수록 시스템이 다운되어 있을 가능성도 커진다. 모든 엔진이 작동해야만 하는 비행기라면, 엔진을 추가하는 것은 비행기의 가용성을 떨어뜨린다. 장애를 견디는 특별한 메커니즘 없이 수천 노드 위에서 분산 트랜잭션 시스템을 운영하는 것은 비현실적이다. 애플리케이션 개발자가 고가용성이 아닌 분산 트랜잭션으로 시스템을 만들면, 그 해법은 취약해서 결국 버려진다. 자연 선택이 작동하는 것이다...

*대신, 애플리케이션은 트랜잭션 보장을 제공하지 않지만 그래도 비즈니스의 요구를 충족하는 기법들로 만들어진다.*

이 글은 분산 트랜잭션을 거부하는 세계에서 대규모 미션 크리티컬 애플리케이션을 구현할 때 사용되는 실용적 접근법 몇 가지를 탐구하고 이름을 붙인다. 애플리케이션이 성장하면서 시간이 지남에 따라 재파티셔닝될 수 있는, 세밀한 단위의 애플리케이션 데이터를 관리하는 방법을 다룬다. 이렇게 재파티셔닝 가능한 데이터 조각들 사이에 메시지를 보내는 것을 디자인 패턴들이 뒷받침한다.

여기서의 목표는 초대형 확장 가능 애플리케이션을 손수 만드는 사람들이 마주하는 어려움을 줄이는 것이다. 또 이런 디자인 패턴을 관찰함으로써, 업계가 확장 가능한 애플리케이션을 더 쉽게 개발하게 해 주는 플랫폼의 창출로 나아갈 수 있을지도 모른다. 마지막으로, 이 글은 확장 가능한 동종(homogeneous) 애플리케이션을 대상으로 하지만, 이 기법들은 모바일 기기 지원 같은 확장 가능한 이종(heterogeneous) 애플리케이션을 지원하는 데도 매우 유용하다.

#### 목표

이 글은 로컬 데이터베이스나 로컬 트랜잭션 시스템밖에 쓸 수 없는 애플리케이션 개발자가 어떻게 성공적인 확장 가능 엔터프라이즈 애플리케이션을 만들 수 있는지에 집중한다. 가용성은 다루지 않고, 오직 규모와 정확성만 다룬다.

##### 확장 가능한 애플리케이션을 논의하기

확장 가능한 애플리케이션의 설계자 대부분은 비즈니스 요구 사항을 이해하고 있다. 문제는 트랜잭션과 확장 가능한 시스템의 상호작용에 관한 쟁점, 개념, 추상화에 이름이 없고 명료하게 이해되고 있지 않다는 것이다. 이것들은 일관성 없이 적용되고, 때로는 설계자의 발목을 잡는다. 이 글의 목표 중 하나는 이런 개념들에 대한 인식을 높이는 논의를 시작하여, 공통의 용어와 확장 가능한 프로그램에 대한 합의된 접근법으로 나아가는 것이다.

##### 애플리케이션의 거의 무한한 확장을 생각하기

이 글은 거의 무한한 확장(almost-infinite scaling)이 미치는 영향에 대한 비형식적 사고 실험을 제시한다. 고객, 구매 가능한 품목, 주문, 배송, 의료 환자, 납세자, 은행 계좌, 그 밖에 앱이 다루는 모든 비즈니스 개념의 수가 시간이 지나며 크게 늘어난다고 가정하자. 보통 개별 항목 하나가 훨씬 커지지는 않는다. 단지 그 수가 점점 많아질 뿐이다. CPU, DRAM, 스토리지, 아니면 다른 어떤 자원이 먼저 포화되는지는 사실 중요하지 않다. 어느 시점에 이르면 수요 증가 때문에, 한 머신에서 돌던 것을 더 많은 머신 위로 펼치게 된다. 이 사고 실험은 우리로 하여금 수만에서 수십만 대의 머신을 고려하게 만든다.

거의 무한한 확장이란, 어떤 것이 한 머신에 들어간다는 사실을 언제 어디서 *알 수 있는지*, 그리고 한 머신에 들어간다고 보장할 수 없을 때 무엇을 해야 하는지에 대해 아주 명확해질 필요성을 부각하기 위한, 느슨하고 부정확하며 의도적으로 모호한 표현이다. 나아가 데이터와 계산 부하에 거의 선형으로 확장되기를 원한다. 물론 로그가 큰 N-log-N 속도로 확장돼도 훌륭하다.

##### 확장 가능한 앱의 흔한 패턴 몇 가지를 기술하기

거의 무한한 확장이 비즈니스 로직에 미치는 영향은 무엇일까? 나는 확장이 프로그램을 작성할 때 *엔티티(entity)*라는 새로운 추상화를 사용하는 것을 함의한다고 주장한다. 엔티티는 한 시점에 한 머신 위에 살고, 애플리케이션은 한 번에 하나의 엔티티만 조작할 수 있다. 거의 무한한 확장의 귀결은 이 프로그래밍 추상화가 비즈니스 로직 개발자에게 노출되어야 한다는 것이다.

아직 이름이 없는 이 개념에 이름을 붙이고 논의함으로써, 일관된 프로그래밍 접근법과 확장 가능한 시스템 구축에 얽힌 쟁점들에 대한 일관된 이해에 합의할 수 있을 것이다.

나아가 엔티티의 사용은 엔티티들을 연결하는 메시징 패턴에도 영향을 미친다. 이는 확장 가능한 해법으로 비즈니스 문제를 풀려는 죄 없는 애플리케이션 개발자에게 들이닥치는 메시지 전달의 비일관성에 대처하는 상태 기계의 탄생으로 이어진다.

#### 몇 가지 가정

다음 세 가지 가정을 살펴보자. 이 가정들은 근거를 대지 않고 단언하는 것이다. 경험에 비추어 참이라고 가정하자.

##### 애플리케이션의 계층과 규모 불가지성

먼저 모든 확장 가능한 애플리케이션이 그림 1처럼 최소 두 계층으로 이루어진다고 전제하자. 이 계층들은 확장에 대한 인식에서 서로 다르다. 다른 차이도 있을 수 있지만 이 논의와는 무관하다.

![그림 1](https://dl.acm.org/cms/attachment/7392452e-870f-441a-8c95-72509df3ee17/helland1.png)

애플리케이션의 하위 계층은 시스템을 확장하기 위해 컴퓨터가 더 추가된다는 사실을 이해한다. 다른 일들에 더해, 이 계층은 상위 계층 코드를 물리 머신과 그 위치에 매핑하는 일을 관리한다. 하위 계층은 이 매핑을 이해한다는 점에서 *규모 인지적(scale-aware)*이다. 나는 하위 계층이 상위 계층에게 *규모 불가지적 프로그래밍 추상화(scale-agnostic programming abstraction)*를 제공한다고 전제한다. 규모 불가지적 프로그래밍 추상화의 예는 많으며, MapReduce(참고문헌 3)도 그중 하나다.

이 규모 불가지적 프로그래밍 추상화를 사용하면 애플리케이션 코드의 상위 계층은 확장 문제를 걱정하지 않고 작성된다. 규모 불가지적 프로그래밍 추상화를 고수하면, 점점 늘어나는 부하 위에 배포될 때 일어나는 변화를 걱정하지 않는 애플리케이션 코드를 작성할 수 있다.

시간이 지나면 이런 애플리케이션의 하위 계층은 규모 불가지적 API의 작성을 단순화해 주는 새로운 플랫폼이나 미들웨어로 진화할 수 있다.

##### 트랜잭션 범위

분산 시스템 위에서 강한 일관성의 트랜잭션을 제공한다는 개념에 대해 많은 학술 연구가 이루어졌다. 2PC(2단계 커밋, 참고문헌 1), Paxos(참고문헌 5), 그리고 최근의 Raft(참고문헌 6)가 여기 포함된다. 고전적 2PC는 Tandem NonStop System처럼 트랜잭션의 코디네이터와 참여자 자체가 내결함성을 갖추지 않는 한 머신이 실패하면 블록된다. Paxos와 Raft는 노드 실패에도 블록되지는 않지만 Tandem의 시스템과 매우 흡사하게 조율에 추가 작업을 들인다.

이 알고리즘들은 *분산 시스템 위에서 강한 일관성의 트랜잭션을 제공*한다고 기술할 수 있다. 이들의 목표는 여러 머신에 퍼진 데이터에 대한 임의의 원자적 갱신을 허용하는 것이다. 갱신은 여러 머신에 걸친 단일 트랜잭션 범위 안에 존재한다.

안타깝게도 많은 상황에서 이것은 애플리케이션 개발자에게 선택지가 아니다. 애플리케이션은 신뢰 경계, 서로 다른 플랫폼, 서로 다른 운영·배포 영역에 걸쳐야 할 수 있다. 분산 트랜잭션에 "그냥 아니오"라고 말하면 어떻게 될까?

이 논문이 처음 쓰인 지 10년이 지난 오늘날에도, 실제 시스템 개발자가 몇 대 이상의 컴퓨터에 걸쳐 강한 일관성 트랜잭션을 달성하려 시도하는 일은 드물다. 대신 그들은 여러 개의 분리된 트랜잭션 범위를 가정한다. 각 컴퓨터가 하나의 분리된 범위이며 그 안에 로컬 트랜잭션이 있다.

##### 대부분의 애플리케이션은 최소 1회(at-least-once) 메시징을 쓴다

짧게 살다 가는 Unix 스타일 프로세스라면 TCP/IP로 충분하다. 하지만 메시지를 처리해 데이터베이스에 표현된 영속 데이터를 수정하는 것이 일인 애플리케이션 개발자가 마주하는 딜레마를 생각해 보자. 메시지를 소비했지만 아직 확인 응답(acknowledge)은 하지 않았다. 데이터베이스를 갱신한 다음 메시지에 확인 응답을 한다. 실패가 발생하면 이 과정이 재시작되고 메시지는 다시 처리된다.

이 딜레마는 메시지 전달이 애플리케이션의 동작을 통하지 않고서는 영속 데이터의 갱신과 직접 결합되어 있지 않다는 사실에서 나온다. 메시지 소비를 영속 데이터의 갱신과 결합하는 것이 가능하긴 하지만, 흔히 제공되지는 않는다. 이 결합의 부재는 메시지가 두 번 이상 전달되는 실패 윈도를 낳는다. 메시지를 잃어버리느니, 메시지 배관은 메시지를 최소 1회 전달한다.

이 동작의 귀결로, 애플리케이션은 메시지 재시도와 순서가 뒤바뀐 전달을 견뎌야 한다.

#### 정당화할 견해들

의견 글을 쓰는 것의 좋은 점은 과감한 의견을 마음껏 펼 수 있다는 것이다. 이 글이 정당화하려는 견해 몇 가지는 다음과 같다.

##### 확장 가능한 앱은 고유하게 식별되는 엔티티를 쓴다

이 글은 각 애플리케이션의 상위 계층 코드가 *엔티티*라 불리는 단일 데이터 집합을 조작해야 한다고 주장한다. 단일 엔티티의 크기에는, 단일 트랜잭션 범위(즉, 한 머신) 안에 살아야 한다는 것 말고는 제한이 없다.

각 엔티티는 그림 2처럼 고유한 식별자, 즉 키를 가진다. 엔티티 키는 어떤 모양, 형식, 종류든 될 수 있다. 어떻게든 정확히 하나의 엔티티와 그 안의 데이터를 고유하게 식별하기만 하면 된다.

![그림 2](https://dl.acm.org/cms/attachment/6117aa72-42ee-46d9-84f1-77588fa006e6/helland2.png)

엔티티의 표현에는 제한이 없다. SQL 레코드, XML, JSON, 파일, 그 밖에 무엇으로든 표현할 수 있다. 가능한 표현 하나는, 여러 테이블에 걸쳐 있을 수도 있으며 기본 키의 접두사가 엔티티 키인 SQL 레코드들의 모음이다.

엔티티들은 서로소인(disjoint) 데이터 집합을 표현한다. 각 데이터는 정확히 하나의 엔티티 안에 존재한다.

애플리케이션은 많은 엔티티로 이루어진다. 예를 들어 주문 처리 애플리케이션은 많은 주문을 캡슐화하며, 각 주문은 고유한 Order-ID로 식별된다. 확장 가능한 주문 처리 애플리케이션이 되려면, 한 주문의 데이터는 다른 주문들의 데이터와 서로소여야 한다.

##### 원자적 트랜잭션은 엔티티를 넘을 수 없다

각 컴퓨터는 분리된 트랜잭션 범위로 가정된다. 뒤에서 이 글은 원자적 트랜잭션이 엔티티들을 가로지를 수 없다는 논증을 제시한다. 프로그래머는 각 트랜잭션에서 항상 단일 엔티티 안에 담긴 데이터만 다뤄야 한다.

프로그래머의 관점에서 *고유하게 식별되는 엔티티가 곧 트랜잭션 범위다*. 이 개념은 확장을 위해 설계된 애플리케이션의 동작에 강력한 영향을 미친다. 탐구할 함의 중 하나는, 거의 무한한 확장을 위해 설계할 때는 보조 인덱스(alternate index)를 트랜잭션적으로 일관되게 유지할 수 없다는 것이다.

##### 메시지는 엔티티를 수신인으로 삼는다

대부분의 메시징 시스템은 데이터의 파티셔닝 키를 고려하지 않고, 상태 없는(stateless) 프로세스가 소비하는 큐를 대상으로 삼는다. 표준 관행은 상태 없는 애플리케이션 코드가 필요한 데이터를 어디서 가져올지 알려 주는 데이터를 메시지에 담는 것이다. 이것이 엔티티 키다. 엔티티의 데이터는 애플리케이션이 어떤 데이터베이스나 다른 영속 저장소에서 가져온다.

흥미로운 흐름이 두 가지 일어나고 있다. 첫째, 엔티티들의 *집합*의 크기가 단일 컴퓨터에 들어갈 수 있는 것보다 커지고 있다. 개별 엔티티 하나는 보통 한 컴퓨터에 들어가지만, 그 집합은 그렇지 않다. 상태 없는 애플리케이션이 어떤 파티셔닝 방식에 따라 라우팅하여 엔티티를 가져오는 일이 점점 늘고 있다.

둘째, 가져오기와 파티셔닝 방식이 애플리케이션의 하위 계층으로 분리되고 있다. 이는 비즈니스 로직을 담당하는 상위 계층으로부터 의도적으로 격리된다.

이 패턴은 사실상 엔티티 키로 라우팅함으로써 엔티티를 겨냥한다. 상태 없는 Unix 스타일 프로세스와 애플리케이션의 하위 계층은 모두 비즈니스 로직에 제공되는 규모 불가지적 API 구현의 일부일 뿐이다. 상위 계층의 규모 불가지적 비즈니스 로직은 그저 엔티티라는 영속 상태를 식별하는 엔티티 키를 수신인으로 하여 메시지를 보낸다.

##### 엔티티는 파트너별 상태(액티비티)를 관리한다

규모 불가지적 메시징은 사실상 엔티티 대 엔티티 메시징이다. 보내는 엔티티는 자신의 영속 상태로 실체화되며 엔티티 키로 식별된다. 이 엔티티가 다른 엔티티에게 메시지를 보내며, 상대 역시 엔티티 키로 식별한다. 받는 엔티티는 규모 불가지적 상위 계층 비즈니스 로직과 자신의 상태를 표현하는 영속 데이터로 구성되며, 엔티티 키로 식별된다.

메시지가 최소 1회 전달된다는 가정을 떠올리자. 받는 엔티티는 무시해야 할 중복 메시지의 공세에 시달릴 수 있다. 실제로 메시지는 두 부류로 나뉜다. 엔티티의 상태에 영향을 주는 것과 주지 않는 것. 엔티티의 상태에 영향을 주지 않는 메시지는 쉽다. 자명하게 멱등(idempotent)하다. 상태를 바꾸는 메시지는 더 조심해야 한다.

멱등성을 보장하기 위해(즉, 재시도된 메시지의 처리가 무해함을 보장하기 위해), 받는 엔티티는 보통 그 메시지가 처리되었음을 기억하도록 설계된다. 성공적으로 처리된 후에 같은 메시지가 반복되면, 보통 첫 번째 메시지의 동작과 일치하는 응답을 다시 생성한다.

수신한 메시지에 대한 지식은 파트너 단위로 묶이는 상태를 만든다. 중요한 관찰은, 이 상태가 파트너별로 조직되며 각 파트너가 엔티티라는 것이다.

두 당사자 관계의 각 편에서 파트너별 메시징을 관리하는 상태에 *액티비티(activity)*라는 용어를 붙인다. 각 액티비티는 정확히 하나의 엔티티 안에 산다. 엔티티는 파트너 엔티티마다 하나의 액티비티를 가진다.

메시징 난장판을 관리하는 것에 더해, 액티비티는 느슨하게 결합된 합의를 관리하는 데도 쓰인다. 원자적 트랜잭션이 불가능한 세계에서는 잠정 연산(tentative operation)을 사용해 공동의 결과를 협상한다. 이 연산은 엔티티들 사이에서 수행되며 액티비티가 관리한다.

합의에 도달하기 위한 워크플로 구축에는 다른 곳에 잘 문서화된(참고문헌 7) 난제들이 가득하다. 이 글은 액티비티가 이 난제들을 해결한다고 주장하는 것이 아니라, 그것을 풀기 위해 필요한 상태를 저장할 토대를 제공한다고 주장한다. 거의 무한한 확장은 놀랍도록 세밀한 워크플로 스타일의 해법으로 이어진다. 참여자는 엔티티들이며, 각 엔티티는 관계된 다른 엔티티들에 대한 구체적 지식을 사용해 자신의 워크플로를 관리한다. 엔티티 안에 유지되는 그 두 당사자 지식을 액티비티라고 부른다.

액티비티의 예는 때로 미묘하다. 주문 애플리케이션이 배송 애플리케이션에 메시지를 보낸다. 메시지에는 배송 ID와 보내는 쪽 주문 ID가 들어 있다. 메시지 타입은 지정된 주문이 배송 준비되었음을 기록하도록 배송 애플리케이션의 상태 변화를 촉발하는 데 쓰일 수 있다. 구현자들은 버그가 나타나기 전까지는 재시도를 고려한 설계를 하지 않는 경우가 잦다. 드물지만 가끔은, 애플리케이션 설계자가 액티비티를 미리 생각하고 계획한다.

#### 엔티티

이 절에서는 엔티티의 본질을 더 깊이 살펴본다.

##### 서로소인 트랜잭션 범위

각 엔티티는 단일 트랜잭션 범위 안에 산다고 알려진, 고유 키를 가진 데이터의 모음으로 정의된다. 원자적 트랜잭션은 *단일 엔티티 안에서는* 언제나 수행할 수 있다.

##### 고유 키를 가진 엔티티

애플리케이션 상위 계층의 코드는 자연스럽게 고유 키를 가진 데이터 모음을 중심으로 설계된다. 고객 ID, 사회보장번호, 상품 SKU 등 고유 식별자는 애플리케이션 안에서 흔히 볼 수 있다. 이들은 애플리케이션의 데이터를 찾는 키로 쓰인다. 트랜잭션 원자성의 보장은 고유 키로 식별되는 엔티티 안에서만 온다.

##### 재파티셔닝과 엔티티

앞에서 말한 가정 중 하나는, 부상하고 있는 상위 계층은 규모 불가지적이고, 규모가 변할 때 배포가 어떻게 진화하는지는 하위 계층이 결정한다는 것이다. 배포가 진화하면서 특정 엔티티의 위치는 바뀔 가능성이 높다. 애플리케이션 상위 계층은 엔티티의 위치에 대해 어떤 가정도 할 수 없다. 그렇게 하면 규모 불가지적이지 않기 때문이다.

그림 3처럼 엔티티들은 해싱 또는 키 범위 파티셔닝을 사용해 트랜잭션 범위들에 걸쳐 펼쳐진다.

##### 원자적 트랜잭션과 엔티티

확장 가능한 시스템에서는 *서로 다른 엔티티들에 걸친 갱신에 트랜잭션을 가정할 수 없다.* 각 엔티티는 고유 키를 가지며, 각 엔티티는 하나의 트랜잭션 범위 안에 쉽게 배치된다. 거의 무한한 확장은 *엔티티의 수*를 가차 없이 증가시키지만 *개별 엔티티의 크기*는 트랜잭션 범위(즉, 한 컴퓨터)에 들어갈 만큼 작게 유지된다는 전제를 떠올리자.

서로 다른 두 엔티티가 같은 트랜잭션 범위 안에 있어서 원자적으로 갱신 가능하다는 것을 어떻게 보장할 수 있을까? 하나의 고유 키가 둘을 통합할 때만 알 수 있다. 그러면 이제 정말로 하나의 엔티티다!

엔티티 키로 해싱 파티셔닝을 하면, 서로 다른 키를 가진 두 엔티티가 언제 같은 상자에 놓일지 알 수 없다. 엔티티 키에 키 범위 파티셔닝을 쓰면, 대부분의 경우 인접한 키 값은 같은 머신에 있다. 하지만 가끔은 운이 나빠 이웃이 다른 머신에 있게 된다.

키 범위 파티셔닝에서 이웃과의 원자성에 의존하는 단순한 테스트 케이스는 대개 성공한다. 나중에 재배포가 엔티티들을 머신 사이로 옮기면 잠복해 있던 버그가 드러난다. 갱신이 더 이상 원자적이지 않은 것이다. 서로 다른 엔티티 키 값이 같은 곳에 있다고 절대 믿어서는 안 된다.

더 단순하게 말하면, 애플리케이션의 하위 계층은 각 엔티티 키(와 그 엔티티)가 단일 머신에 상주하도록 보장한다. 서로 다른 엔티티들은 어디에나 있을 수 있다.

*규모 불가지적 프로그래밍 추상화는 원자성의 경계로서 엔티티라는 개념을 반드시 가져야 한다.* 엔티티에 대한 이해, 엔티티 키의 사용, 그리고 엔티티를 가로지르는 원자성이 없다는 것에 대한 명확한 확약은 규모 불가지적 프로그래밍의 핵심이다.

오늘날 업계의 대규모 애플리케이션은 암묵적으로 이렇게 하고 있다. 다만 엔티티라는 개념에 이름이 없을 뿐이다. 상위 계층 앱의 관점에서는 엔티티가 트랜잭션의 범위라고 가정해야 한다. 그 이상을 가정하면 배포가 바뀔 때 부서진다.

##### 보조 인덱스에 대한 고찰

우리는 데이터를 여러 키나 인덱스로 접근하는 것에 익숙하다. 예를 들어 고객은 어떤 때는 사회보장번호로, 어떤 때는 신용카드 번호로, 어떤 때는 도로 주소로 참조된다. 극단적인 확장을 가정하면 이 인덱스들은 같은 머신이나 하나의 큰 클러스터 안에 상주할 수 없다. *한 고객에 대한 데이터가 단일 트랜잭션 범위 안에 상주한다고 알 수 없다.* 엔티티 자체는 단일 트랜잭션 범위에 상주한다. 문제는 보조 인덱스를 만드는 데 쓰이는 정보의 사본이 다른 트랜잭션 범위에 상주한다고 가정해야 한다는 것이다.

보조 인덱스가 같은 트랜잭션 범위에 상주하도록 보장하는 경우를 생각해 보자. 거의 무한한 확장이 시작되면 엔티티 집합은 어마어마한 수의 머신에 흩뿌려진다. 기본 인덱스와 보조 인덱스 정보가 같은 트랜잭션 범위 안에 있어야 한다. 이를 보장하는 유일한 방법은 기본 인덱스를 사용해 보조 인덱스를 찾는 것이다. 그러면 같은 트랜잭션 범위로 가게 된다. 기본 인덱스 없이 시작해 모든 트랜잭션 범위를 뒤져야 한다면, 보조 키의 일치 항목을 찾기 위해 각 보조 인덱스 조회가 거의 무한한 수의 범위를 검사해야 한다. 이는 결국 감당할 수 없게 된다.

논리적으로 남는 유일한 대안은 2단계 조회다. 먼저 보조 키를 조회해 엔티티 키를 얻는다. 다음으로 엔티티 키로 엔티티에 접근한다. 이는 관계형 데이터베이스 내부에서 보조 키로 레코드에 접근할 때 2단계를 거치는 것과 매우 비슷하다. 하지만 거의 무한한 확장이라는 전제는 두 인덱스(기본과 보조)가 같은 트랜잭션 범위에 상주한다고 알 수 없음을 의미한다. 그림 4를 보라.

![그림 4](https://dl.acm.org/cms/attachment/a2b63b82-85fe-4728-a23f-715eb6a6e9c0/helland4.png)

> 규모 불가지적 애플리케이션 프로그램은 엔티티와 그 보조 인덱스를 원자적으로 갱신할 수 없다. 상위 계층의 규모 불가지적 애플리케이션은 보조 인덱스가 기본 인덱스(즉, 엔티티 키)로 접근한 엔티티와 어긋나 있을 수 있음을 이해하도록 설계되어야 한다. 그림 4에서 보듯, 서로 다른 키(기본 엔티티 키 대 보조 키)는 같은 곳에 배치되거나 원자적으로 갱신될 수 없다.

과거에 보조 인덱스로서 자동으로 관리되던 것을 이제는 애플리케이션이 수동으로 관리해야 한다. 남은 것은 비동기 메시징을 이용한 워크플로 스타일의 갱신뿐이다. 보조 인덱스에서 데이터를 읽을 때는 그것이 엔티티 자체와 어긋나 있을 수 있음을 이해해야 한다. 보조 인덱스는 이제 더 어렵다. 이것이 거대 시스템이라는 크고 잔인한 세계의 현실이다.

#### 엔티티 간 메시징

이 절에서는 독립적인 엔티티들을 메시지로 연결하는 것을 살펴본다. 이름 짓기, 트랜잭션과 메시지, 메시지 전달 시맨틱, 엔티티 재파티셔닝의 영향을 검토한다.

##### 엔티티를 가로질러 통신하는 메시지

두 엔티티에 걸친 데이터를 같은 트랜잭션에서 갱신할 수 없다면, 서로 다른 트랜잭션에서 데이터를 갱신할 메커니즘이 필요하다. 엔티티 간의 연결은 메시지로 이루어진다.

##### 보내는 트랜잭션에 대해 비동기

메시지는 엔티티를 가로지르므로, 메시지를 보내기로 한 결정과 연관된 데이터는 한 엔티티에 있고 메시지의 목적지는 다른 엔티티에 있다. 엔티티의 정의상 이 엔티티들은 원자적으로 갱신될 수 없다. 메시지는 이 서로 다른 엔티티들을 가로질러 원자적으로 송수신될 수 없다.

트랜잭션 작업 중에 메시지를 보내고, 메시지는 발송되었는데, 트랜잭션은 중단(abort)된다면 애플리케이션 개발자에게 끔찍하게 복잡한 일이 될 것이다. 무언가를 일으켰다는 기억이 전혀 없는데 그 일은 실제로 일어난다는 뜻이 되기 때문이다. 이런 이유로 메시지의 트랜잭션적 인큐(enqueue)가 관례다. 그림 5를 보라.

![그림 5](https://dl.acm.org/cms/attachment/acbcd2cb-f2dd-4b0d-b660-ad1922a053fa/helland5.png)

보내는 트랜잭션이 커밋된 *후에야* 메시지가 목적지에서 보인다면, 그 메시지는 보내는 트랜잭션에 대해 비동기다. 각 엔티티는 트랜잭션과 함께 새로운 상태로 나아간다. 메시지는 한 트랜잭션에서 나와 새로운 엔티티에 도착해 트랜잭션을 일으키는 자극이다.

##### 메시지 목적지의 이름 짓기

한 엔티티가 다른 엔티티에게 메시지를 보내려 할 때, 애플리케이션의 규모 불가지적 부분의 프로그래밍을 생각해 보자. 목적지 엔티티의 위치는 규모 불가지적 코드가 알지 못한다. 아는 것은 엔티티 키다.

엔티티 키를 엔티티의 위치와 연결하는 일은 애플리케이션의 규모 인지적 부분의 몫이다.

##### 재파티셔닝과 메시지 전달

애플리케이션의 규모 불가지적 부분이 메시지를 보내면, 하위의 규모 인지적 부분이 목적지를 찾아내 메시지를 최소 1회 전달한다.

시스템이 확장되면서 엔티티는 이동한다. 이를 흔히 *재파티셔닝(repartitioning)*이라 부른다. 엔티티의 위치, 따라서 메시지의 목적지는 유동적일 수 있다. 때로는 메시지가 옛 위치로 쫓아갔다가 그 성가신 엔티티가 다른 곳으로 보내졌다는 것만 알게 된다. 이제 메시지가 뒤따라가야 한다.

엔티티가 이동하면, 보내는 쪽과 목적지 사이의 선입선출(FIFO) 큐라는 명료함이 가끔 흐트러진다. 메시지는 반복된다. 나중 메시지가 먼저 것보다 앞서 도착한다. 삶은 더 지저분해진다.

이런 이유로 규모 불가지적 애플리케이션은 애플리케이션에 보이는 모든 메시징의 멱등 처리를 지원하는 쪽으로 진화하고 있다. 이는 메시지 전달의 순서 뒤바뀜도 함의한다.

#### 액티비티: 지저분한 메시지에 대처하기

이 절에서는 메시지 재시도와 순서 뒤바뀜이라는 난제에 대처하는 방법을 논한다. 파트너 엔티티와의 관계를 관리하는 데 필요한 로컬 정보로서의 액티비티 개념을 소개한다.

##### 재시도와 멱등성

어떤 메시지든 여러 번 전달될 수 있으므로, 애플리케이션에는 반복된 메시지에 대처하는 규율이 필요하다. 중복 메시지 제거를 저수준에서 지원하도록 만드는 것이 가능하긴 하지만, 거의 무한한 확장 환경에서는 그 저수준 지원이 엔티티를 알아야 한다. 어떤 메시지가 그 엔티티에 전달되었는지에 대한 지식은 재파티셔닝으로 엔티티가 이동할 때 함께 이동해야 한다. 실제로는 이 지식의 저수준 관리는 거의 이루어지지 않는다. 메시지는 두 번 이상 전달될 수 있다.

보통은 애플리케이션의 규모 불가지적(상위) 부분이 들어오는 메시지의 멱등성을 보장하는 메커니즘을 구현해야 한다. 이것이 문제의 본질에서 필연은 아니다. 중복 제거를 애플리케이션의 규모 인지적 부분에 넣을 수도 있다. 다만 아직 제공되지 않을 뿐이다. 그러니 규모 불가지적 애플리케이션의 딱한 개발자가 무엇을 구현해야 하는지 살펴보자.

##### 실질적 동작의 멱등성 정의

메시지의 처리가 멱등하다는 것은 그 처리를 다시 실행해도 엔티티에 *실질적 변화(substantive change)*를 일으키지 않는 것이다. 이는 무엇이 실질적이고 무엇이 아닌지의 규정을 애플리케이션에 열어 두는 모호한 정의다.

메시지가 호출된 엔티티를 바꾸지 않고 정보만 읽는다면 그 처리는 멱등하다. 읽기를 기술하는 로그 레코드가 쓰이더라도 마찬가지다. 로그 레코드는 엔티티의 동작에 실질적이지 않다. 무엇이 실질적이고 무엇이 아닌지의 정의는 애플리케이션마다 다르다.

##### 자연적 멱등성

멱등성을 달성하려면 메시지가 실질적 부수 효과를 일으키지 않는 것이 핵심이다. 어떤 메시지들은 언제 처리되든 실질적 작업을 유발하지 않는다. 이런 메시지는 *자연적으로(naturally)* 멱등하다.

엔티티에서 데이터만 읽는 메시지는 자연적으로 멱등하다. 메시지 처리가 엔티티를 바꾸긴 하되 실질적이지 않은 방식으로 바꾼다면? 그것도 자연적으로 멱등하다.

이제부터가 어렵다. 어떤 메시지가 함의하는 작업은 실제로 실질적 변화를 일으킨다. 이런 메시지는 자연적으로 멱등하지 않다. 애플리케이션은 이런 메시지도 멱등해지도록 보장하는 메커니즘을 갖추어야 한다. 이는 메시지가 처리되었음을 어떤 식으로든 기억해 두어, 이후의 시도가 실질적 변화를 일으키지 않게 한다는 뜻이다.

다음 절에서는 자연적으로 멱등하지 않은 메시지의 처리를 살펴본다.

##### 메시지를 상태로 기억하기

자연적으로 멱등하지 않은 메시지의 멱등 처리를 보장하려면, 엔티티는 그것들이 처리되었음을 기억해야 한다. 이 지식이 곧 상태다. 메시지가 처리되면서 상태는 쌓여 간다.

또한 응답이 필요하다면 같은 응답을 반환해야 한다. 원래 보낸 쪽이 응답을 받았는지 알 수 없기 때문이다.

##### 파트너별 상태 관리

관계와 수신한 메시지를 추적하기 위해, 규모 불가지적 애플리케이션 안의 각 엔티티는 파트너들에 대한 상태 정보를 어떻게든 기억해야 한다. 이 상태는 파트너 단위로 포착해야 한다. 이 상태에 *액티비티*라는 이름을 붙이자. 그림 6을 보라. 엔티티가 많은 다른 엔티티와 상호작용한다면 액티비티도 많이 가질 수 있다. 액티비티는 각 파트너와의 상호작용을 추적한다.

![그림 6](https://dl.acm.org/cms/attachment/2b83d86e-c85c-46e1-9ccc-94f6f00b16a5/helland6.png)

각 엔티티는 액티비티들의 집합과, 어쩌면 액티비티들을 아우르는 다른 데이터로 구성된다.

> 여러 구매 품목으로 이루어진 주문의 처리를 생각해 보자. 각 개별 품목의 배송을 위한 재고 예약은 각각 별도의 액티비티가 된다. 주문을 위한 엔티티가 있고, 창고가 관리하는 각 품목마다 별도의 엔티티가 있다. 이 엔티티들을 가로지르는 트랜잭션은 가정할 수 없다.
>
> 주문 안에서 각 재고 품목은 개별적으로 관리된다. 메시징 프로토콜도 개별적으로 관리되어야 한다. 주문 엔티티 안에 담긴 재고 품목별 데이터가 액티비티다. 그런 이름으로 불리지는 않지만, 이 패턴은 대규모 앱에 빈번히 존재한다.

거의 무한하게 확장된 애플리케이션에서는 관계에 대해 아주 명확해야 한다. 무엇이 관련되어 있는지 그냥 쿼리로 알아낼 수는 없다. 모든 것이 두 당사자 관계의 그물망으로 형식적으로 짜여 있어야 한다. 그 짜임은 엔티티 키로 이루어진다. 파트너가 멀리 떨어져 있기 때문에, 파트너의 소식이 도착하면 그것을 새로운 지식으로 삼아 파트너의 상태에 대한 이해를 형식적으로 관리해야 한다. 멀리 있는 파트너에 대해 로컬에서 아는 정보를 액티비티라고 부른다. 그림 7을 보라.

##### 액티비티로 최대 1회(at-most-once) 수용 보장하기

자연적으로 멱등하지 않은 메시지의 처리는 각 메시지가 최대 1회 처리되도록(즉, 메시지의 실질적 영향이 최대 1회만 일어나도록) 보장해야 한다. 이를 위해 메시지의 어떤 고유한 특성을 기억해서 두 번 이상 처리되지 않도록 해야 한다.

엔티티는 메시지가 처리해도 되는 상태에서, 처리해도 실질적 영향이 없을 상태로 넘어가는 전이를 영속적으로 기억해야 한다.

보통 엔티티는 이 상태 관리를 파트너 단위로 구현하는 데 자신의 액티비티들을 사용한다. 이는 필수적이다. 엔티티는 때로 여러 다른 파트너를 상대하며, 각 파트너는 그 관계에 결부된 메시지 패턴을 밟아 나가기 때문이다. 파트너별 상태 모음이 그것을 가능하게 한다.

#### 액티비티: 원자성 없이 대처하기

이 절에서는 초대형 확장 시스템이 분산 트랜잭션 없이 어떻게 결정을 내리는지 다룬다.

분산된 합의를 관리하는 것은 힘든 일이다. 거의 무한하게 확장 가능한 환경에서는 불확실성의 표현이 파트너별 관계를 중심으로 세밀하게 이루어져야 한다. 이 데이터는 액티비티 개념을 사용해 엔티티 안에서 관리된다.

##### 멀리 있는 불확실성

분산 트랜잭션의 부재는 서로 다른 엔티티들을 가로질러 결정에 이르려 할 때 불확실성을 수용한다는 뜻이다. 분산 시스템을 가로지르는 결정에는 한동안 불확실성을 수용하는 일이 불가피하게 따른다. 분산 트랜잭션을 쓸 수 있을 때는 그 불확실성이 데이터에 걸린 락으로 나타나며 트랜잭션 매니저가 관리한다.

분산 트랜잭션에 의존할 수 없는 시스템에서는 불확실성의 관리를 비즈니스 로직 안에 구현해야 한다. 결과의 불확실성은 레코드 락이 아니라 비즈니스 시맨틱 안에 담긴다. 이것이 바로 워크플로다. 마법이 아니다. 분산 트랜잭션을 쓸 수 없으니 워크플로를 쓰는 것이다.

엔티티와 메시지로 이끈 가정들은 이제, 규모 불가지적 애플리케이션이 워크플로를 사용해 불확실성을 스스로 관리해야 한다는 결론으로 이끈다. 이는 여러 엔티티에 걸쳐 합의에 도달하는 데 필요하다.

> 기업 간에 흔한 상호작용 방식을 생각해 보라. 기업 간 계약에는 시한 약속, 해지 조항, 예약된 자원 등 많은 것이 담긴다. 불확실성은 비즈니스 기능의 동작 안에 감싸여 있다. 분산 트랜잭션을 쓰는 것보다 구현이 더 복잡하지만, 현실 세계는 그렇게 돌아간다...
>
> 다시 말하지만, 이것은 그저 워크플로를 쓰자는 논증이다.

##### 액티비티와 불확실성의 관리

엔티티는 때로 다른 엔티티와 상호작용하면서 불확실성을 수용한다. 이 불확실성은 파트너 단위로 관리되어야 하며, 그 파트너에 대한 액티비티 상태 속에 구체화(reify)되어 있다고 그려 볼 수 있다.

많은 경우 불확실성은 관계로 표현된다. 파트너별로 추적할 필요가 있다. 액티비티는 새로운 상태로 나아가는 각 파트너를 추적한다.

> 주문 시스템이 창고에서 재고를 예약하면, 창고는 그 재고가 실제로 쓰일지 모르는 채로 재고를 할당한다. 그것이 불확실성의 수용이다. 나중에 창고는 예약된 재고가 필요해질지 여부를 알게 된다. 이것이 불확실성의 해소다.
>
> 창고 재고 관리자는 자기 품목을 구속하는 각 주문에 대한 관계 데이터를 유지해야 한다. 품목과 주문을 연결할 때 이 데이터는 품목별로 조직된다. 각 품목은 그 품목에 대한 미결 주문 정보를 유지한다. 품목 안의 각 액티비티(주문당 하나)가 그 주문의 불확실성을 관리한다.

##### 잠정 비즈니스 연산 수행하기

엔티티들 사이에 합의에 도달하려면 한 엔티티가 다른 엔티티에게 불확실성을 수용해 달라고 요청한다. 한 엔티티가 나중에 취소될 수도 있는 요청을 다른 엔티티에게 보낸다. 이를 *잠정 연산(tentative operation)*이라 부른다. 이 단계가 끝나면 한 엔티티는 상대 엔티티의 뜻에 따르기로 합의한 상태가 된다.

##### 잠정 연산, 확정, 취소

잠정 연산의 핵심은 취소할 권리다. 요청한 엔티티가 진행하지 않기로 결정하면 *취소 연산(cancellation operation)*을 발행한다. 진행하기로 결정하면 *확정 연산(confirmation operation)*을 발행한다.

엔티티가 잠정 연산을 수행하기로 합의한다는 것은 다른 엔티티가 결과를 결정하도록 맡긴다는 것이다. 불확실성을 수용하는 것이고, 이는 혼란을 더한다. 확정과 취소가 도착하면서 불확실성이 줄어들고 혼란도 줄어든다. 오래된 문제가 해소되고 새로운 문제가 무릎 위에 떨어지면서, 불확실성이 늘었다 줄었다 하는 채로 삶을 살아가는 것은 정상이다.

다시 말하지만 이것은 그저 워크플로다. 다만 엔티티들이 참여자인 세밀한 워크플로다.

##### 불확실성과 거의 무한한 확장

불확실성의 관리는 보통 두 당사자 간 합의를 중심으로 돌아간다. 두 당사자 합의가 여럿 있을 수 있다. 이들은 엔티티 키를 연결 고리로, 멀리 있는 파트너의 알려진 상태를 추적하는 액티비티를 사용하여, 세밀한 두 당사자 합의의 그물망으로 짜인다.

> 주택 구매와 에스크로 회사와의 관계를 생각해 보자. 구매자는 에스크로 회사와 신뢰의 합의를 맺고, 판매자, 대출 회사, 그리고 거래에 관여하는 모든 다른 당사자도 마찬가지다.
>
> 집을 사려고 서류에 서명하러 갈 때, 당신은 거래의 결과를 알지 못한다. 에스크로가 종결될 때까지 불확실하다는 것을 받아들인다. 의사 결정을 통제하는 유일한 당사자는 에스크로 회사다.
>
> 이것은 분산 트랜잭션 없이 많은 당사자의 합의를 이끌어 내는 데 쓰이는, 허브 앤 스포크 형태의 두 당사자 관계 모음이다.

거의 무한한 확장을 고려할 때 두 당사자 관계를 생각해 보는 것은 흥미롭다. 두 당사자 간의 잠정/취소/확정(전통적 워크플로와 똑같다)을 쌓아 올림으로써 분산 합의를 달성하는 토대를 볼 수 있다. 에스크로 회사(위 사례 참고)에서처럼, 많은 엔티티가 합성(composition)을 통해 하나의 합의에 참여할 수 있다.

관계가 두 당사자 사이의 것이기 때문에, "그 파트너에 대해 내가 기억하는 것"이라는 단순한 액티비티 개념이 거대한 시스템을 관리하는 기반이 된다. 데이터가 엔티티에 저장되어 있고 그 엔티티가 어디에 사는지 모를 때조차 그렇다. 멀리 있다고 가정해야 한다. 그래도 규모 불가지적 방식으로 프로그래밍할 수 있다.

현실 세계의 거의 무한한 규모의 애플리케이션들은 전역 트랜잭션 범위라는 사치를 누리고 싶어 할 것이다. 안타깝게도 시스템 실패 시의 취약성을 끌어들이지 않고서는 대부분의 우리에게 이것이 쉽게 주어지지 않는다.

대신 잠정 작업의 불확실성 관리는 규모 불가지적 애플리케이션 개발자의 손에 넘겨진다. 예약된 재고, 신용 한도에 대한 할당 등 애플리케이션 고유의 개념으로 다루어야 한다.

#### 결론

늘 그렇듯 컴퓨터 업계는 유동적이다.

오늘날 비즈니스 문제를 풀고 싶을 뿐인 프로그래머들에게 새로운 설계 압력이 떠넘겨지고 있다. 그들의 현실은 그들을 거의 무한한 확장의 세계로 데려가, 정작 눈앞의 비즈니스와는 대체로 무관한 설계 문제로 몰아넣고 있다. 이것은 오늘날에도 사실이고, 이 글이 2007년 처음 발표되었을 때도 사실이었다.

안타깝게도 전자상거래, 공급망 관리, 금융, 의료 애플리케이션 같은 비즈니스 목표를 좇는 프로그래머들은 분산 트랜잭션 없는 확장을 점점 더 많이 고민해야 한다. 대부분의 개발자에게는 확장 가능한 분산 트랜잭션을 제공하는 견고한 시스템에 접근할 길이 없다.

우리는 이런 애플리케이션을 만드는 패턴들이 보이기 시작했지만 아직 아무도 그 패턴들을 일관되게 적용하지 않는 갈림길에 서 있다. 이 글은 이 태동기의 패턴들이 거의 무한한 확장을 위해 설계되는 애플리케이션의 수제작 개발에 더 일관되게 적용될 수 있다고 주장한다.

이 글은 대규모 애플리케이션에서 부상하고 있는 두 가지 형식을 소개하고 이름 붙였다.

*• 엔티티*는 이름(키)이 붙은 데이터의 모음으로, 엔티티 안에서는 원자적으로 갱신할 수 있지만 엔티티를 가로질러서는 절대 원자적으로 갱신할 수 없다.

*• 액티비티*는 하나의 파트너 엔티티와의 메시징 관계를 관리하는 데 쓰이는, 엔티티 안의 상태 모음이다.

결정에 도달하기 위한 워크플로는 엔티티 안의 액티비티 안에서 작동한다. 거의 무한한 확장을 들여다볼 때 놀라운 것은 워크플로의 세밀함이다.

오늘날 많은 애플리케이션이 암묵적으로 엔티티와 액티비티 둘 다를 사용해 설계되고 있다. 단지 형식화되어 있지 않고 일관되게 사용되지 않을 뿐이다. 사용이 일관되지 않은 곳에서는 버그가 발견되고 결국 땜질된다. 이 패턴들을 논의하고 일관되게 사용함으로써 더 나은 대규모 애플리케이션을 만들 수 있고, 업계 전체로는 비즈니스 로직 프로그래머가 확장의 문제가 아니라 비즈니스 문제에 집중할 수 있게 해 주는 해법에 더 가까이 갈 수 있다.

## 파티션 감내는 희생할 수 없다

> 원문: [You Can't Sacrifice Partition Tolerance](https://web.archive.org/web/20231224104704/https://codahale.com/you-cant-sacrifice-partition-tolerance/)
> 저자: Coda Hale | 번역일: 2026-07-10

최근 여러 분산 데이터베이스가 자신을 ["CA"라고](https://en.wikipedia.org/w/index.php?title=Membase&oldid=384896988) [설명하는](http://danweinreb.org/blog/voltdb-versus-nosql) 것을 봤다. 즉, 파티션 감내(partition tolerance)는 제공하지 않으면서 일관성과 가용성을 모두 제공한다는 것이다. 내가 보기에 이는 이 시스템들의 개발자가 CAP 정리와 그 함의를 이해하지 못하고 있다는 뜻이다.

### 빠른 복습

2000년 Eric Brewer 박사는 *Proceedings of the Annual ACM Symposium on Principles of Distributed Computing*[^1] 기조연설에서 그의 유명한 CAP 정리를 내놓았다. *공유 데이터 시스템은 다음 세 속성 중 최대 두 가지만 가질 수 있다: 일관성(Consistency), 가용성(Availability), 네트워크 파티션에 대한 감내(tolerance to network Partitions).* 2002년 Gilbert와 Lynch[^2]는 "Brewer의 추측"을 비형식적 증명이 딸린 더 형식적인 정의로 바꾸었다. 내가 보기에는 그 후로 줄곧 오해되어 왔다.

그러니 우리가 쓰는 용어부터 분명히 하자.

### 일관성에 관하여

Gilbert와 Lynch[^2]에서:

> 원자적(atomic), 즉 선형화 가능(linearizable) 일관성은 오늘날 대부분의 웹 서비스가 기대하는 조건이다. 이 일관성 보장 아래에서는 모든 연산에 대한 전순서(total order)가 존재해서, 각 연산이 마치 한 순간에 완료된 것처럼 보여야 한다. 이는 분산 공유 메모리에 대한 요청이 마치 단일 노드에서 실행되면서 연산을 한 번에 하나씩 응답하는 것처럼 동작하기를 요구하는 것과 동등하다.

대부분의 사람이 이를 이해하는 것 같지만, 반복할 가치가 있다. 시스템이 일관적이라는 것은 갱신이 동일한 논리적 시각에 모든 관련 노드에 적용되는 것이다. 여기서 따라 나오는 것 중 하나는, 표준적인 데이터베이스 복제(replication)는 *강한 일관성이 아니라는 것*이다. 읽기 레플리카가 마스터에서 어긋나 본 적 있는 사람이라면 누구나 알듯, 복제 지연을 다루려면 특별한 로직을 도입해야 한다.

그렇긴 해도, 즉각적이면서 전역적인 일관성은 불가능하다. 우주가 그것을 허용하지 않는다. 그러니 여기서의 목표는 일관성이 무너지는 시간 해상도를 우리가 더 이상 알아차리지 못하는 지점까지 밀어붙이는 것이다. 자신의 빛원뿔(light cone) 밖에서 행동하려 들지만 말라...

### 가용성에 관하여

다시 Gilbert와 Lynch[^2]에서:

> 분산 시스템이 지속적으로 가용하려면, 시스템의 실패하지 않은 노드가 받은 모든 요청은 응답으로 귀결되어야 한다. 즉, 서비스가 사용하는 어떤 알고리즘도 결국에는 종료되어야 한다 … 파티션 감내 요건과 결합되면, 이는 가용성의 강한 정의로 볼 수 있다. 심각한 네트워크 장애가 발생하더라도 모든 요청은 종료되어야 한다.

["가능한 한 100% 업타임"](http://blog.mongodb.org/post/381927266/what-about-durability)이라는 관념에도 불구하고 가용성에는 한계가 있다. 데이터 한 조각이 노드 다섯 대에 있는데 다섯 대가 모두 죽으면, 그 데이터는 사라진 것이고, 처리에 그 데이터가 필요한 어떤 요청도 처리될 수 없다.

(주의: `500 The Bees They're In My Eyes` 응답은 네트워크 타임아웃과 마찬가지로 실제 응답으로 치지 않는다. 응답이란 요청된 작업의 결과를 담고 있는 것이다.)

### 파티션 감내에 관하여

한 번 더 Gilbert와 Lynch[^2]에서:

> 파티션 감내를 모델링하기 위해, 네트워크가 한 노드에서 다른 노드로 보낸 메시지를 임의 개수만큼 잃어버릴 수 있다고 허용한다. 네트워크가 파티션되면, 파티션의 한 컴포넌트에 속한 노드가 다른 컴포넌트의 노드로 보내는 모든 메시지는 유실된다. (그리고 어떤 메시지 유실 패턴이든, 메시지가 유실되는 바로 그 순간에 통신 중인 노드들을 갈라놓는 일시적 파티션으로 모델링할 수 있다.)

이 부분이 대부분의 사람이 오해하는 지점 같다.

어떤 시스템은 파티션될 수 없다. 단일 노드 시스템(예: 복제가 없는 단일 Oracle 서버)은 네트워크 파티션을 겪을 수가 없다. 하지만 현실적으로 이런 시스템은 드물다. 그 단일 Oracle 서버에 원격 클라이언트를 붙이면 네트워크 파티션을 겪을 *수 있는* 분산 시스템이 된다(예: Oracle 서버가 접근 불가능해진다).

네트워크 파티션은 패킷 유실에 국한되지 않는다. 크래시된 서버도 네트워크 파티션으로 볼 수 있다. 실패한 노드는 사실상 자기 파티션 컴포넌트의 유일한 구성원이고, 따라서 그 노드로 가는 모든 메시지는 "유실"된다(즉, 노드의 실패 때문에 처리되지 않는다). 크래시된 머신을 처리하는 것도 파티션 감내에 해당한다. (**업데이트: 이 부분은 내가 틀렸다. [여기](#2010년-10월-22일-업데이트)를 보라.**) (주의: 오프라인이 된 노드는 사실 다루기 가장 쉬운 종류의 실패다. 죽은 노드가 시스템의 다른 부분에 잘못된 응답을 주지 않는다는 것이 보장되기 때문이다.)

분산(즉, 다중 노드) 시스템이 파티션 감내를 필요로 **하지 않으려면**, *메시지를 절대 잃어버리지 않는다고(늦게 전달하지도 않는다고) 보장되는* 네트워크 위에서, *절대 죽지 않는다고 보장되는* 노드들로 돌아가야 한다. 당신과 나는 이런 시스템으로 일하지 않는다. 왜냐하면 **그런 것은 존재하지 않기 때문이다.**

### 실패가 선택지인 시스템이 주어졌을 때

[Michael Stonebraker의 주장](http://voltdb.com/voltdb-webinar-sql-urban-myths)이야 어떻든, 파티션(읽어라: 실패)은 일어나며, 노드 중 하나라도 실패할 확률은 노드 수가 늘어남에 따라 지수적으로 뛰어오른다.

```
P(무언가 실패) = 1 - P(개별 노드가 실패하지 않을 확률)^(노드 수)
```

단일 노드가 특정 기간 동안 실패하지 않을 확률이 99.9%라면, 40대 클러스터가 실패하지 않을 확률은 96.1%다. 다시 말해 *무언가* 잘못될 확률이 약 4%다. (그리고 이것은 실패들이 서로 무관하다는 가정 아래서다. 실제로 실패는 연쇄되는 경향이 있다.)

따라서 스스로에게 물어야 할 질문은 이것이다.

> 실패가 일어났을 때, 이 시스템은 무엇을 희생할 것인가? 일관성인가 가용성인가?

### 가용성 대신 일관성을 선택하기

파티션(다시 한번, 읽어라: 실패) 앞에서 가용성보다 일관성을 제공하기로 선택한 시스템은, 일부 요청에 대한 응답을 거부함으로써 원자적 읽기와 쓰기의 보장을 지킨다. 아예 전부 멈추기로 할 수도 있고(단일 노드 데이터 저장소의 클라이언트들처럼), 쓰기를 거부할 수도 있고(2단계 커밋처럼), 데이터의 "마스터" 노드가 자기 파티션 컴포넌트 안에 있는 데이터에 대해서만 읽기와 쓰기에 응답할 수도 있다(Membase처럼).

*이것은 전적으로 합리적이다.* 강한 일관성 시스템 덕분에 훨씬 쉬워지는(혹은 비로소 가능해지는) 것들이 많다(원자적 카운터가 하나의 예다). 이는 특정 비즈니스 요구 사항을 충족하는 데 완벽히 유효한 종류의 도구다.

### 일관성 대신 가용성을 선택하기

파티션(다 같이 외치자: 실패) 앞에서 일관성보다 가용성을 제공하기로 선택한 시스템은 모든 요청에 응답하되, 오래된(stale) 읽기를 반환하고 충돌하는 쓰기를 받아들일 수 있다. 이런 비일관성은 흔히 벡터 클록 같은 인과 순서(causal ordering) 메커니즘과 애플리케이션별 충돌 해소 절차로 해결된다. (Dynamo 계열 시스템은 보통 둘 다 제공한다. Cassandra의 하드코딩된 Last-Writer-Wins 충돌 해소가 주요 예외다.)

다시 말하지만, *이것도 전적으로 합리적이다.* 충돌 해소에 적합하고 오래된 읽기가 허용되는 데이터 모델이 많으며(얄궂게도 이런 데이터 모델 중 다수가 금융 업계에 있다), 그런 시스템의 비가용성은 막대한 순익 손실로 이어진다. (Amazon의 쇼핑 카트 시스템이 Dynamo 모델의 정석적 사례다[^3].)

### 하지만 둘 다는 절대 안 된다

> 그러나 분산 시스템에서 일관성과 가용성을 둘 다 선택할 수는 없다.

사고 실험으로, 세 노드 A, B, C로 데이터 한 조각을 관리하면서 네트워크 파티션 앞에서 일관성과 가용성을 둘 다 제공한다고 주장하는 분산 시스템을 상상해 보자. 불운이 닥쳐 그 시스템이 {A, B}와 {C} 두 컴포넌트로 파티션된다. 이 상태에서 그 데이터를 갱신하라는 쓰기 요청이 노드 C에 도착한다.

그 노드에게는 두 가지 선택지밖에 없다.

1. 쓰기를 받아들인다. 파티션이 회복될 때까지 A도 B도 이 새 데이터를 알지 못하리라는 것을 알면서.
2. 쓰기를 거부한다. 파티션이 회복될 때까지 클라이언트가 A나 B에 접속하지 못할 수도 있다는 것을 알면서.

가용성(1번 문)을 선택하거나 일관성(2번 문)을 선택하거나 둘 중 하나다. 둘 다 선택할 수는 없다.

둘 다 한다고 주장하는 것은, 시스템이 단일 노드에서 동작한다고(따라서 분산이 아니라고) 주장하거나, 네트워크 파티션의 한 컴포넌트에 있는 노드에 적용된 갱신이 다른 파티션 컴포넌트의 노드에도 ***마법처럼*** 적용된다고 주장하는 것이다.

짐작하다시피, 이것이 사실인 경우는 드물다.

### 초점의 재조정

CAP 정리, 특히 Gilbert와 Lynch의 정식화에 대한 실무적 해석에서 문제의 일부는, 대부분의 실제 분산 시스템이 원자적 일관성이나 완벽한 가용성을 요구하지 않으며, 임의의 메시지 유실을 겪는 네트워크 위에서 동작하라고 요구받을 일도 없다는 사실이라고 생각한다. 일관성, 가용성, 파티션 감내는 분산 시스템의 플라톤적 이데아다. 비즈니스 요구 사항을 충족할 만큼은 취할 수 있지만, 현실의 본성상 언제나 타협이 있을 것이다.

그러므로 분산 시스템을 설계하거나 평가할 때는, 세 덕목 중 어느 둘이 가장 마음에 드는지보다 상황이 나빠질 때 시스템이 어떤 타협을 하는지에 더 집중해야 한다고 생각한다. (상황은 [나빠질 것이기](http://blog.foursquare.com/2010/10/05/so-that-was-a-bummer/) 때문이다.)

이 지점에서 Brewer의 앞선 지혜에 닿게 된다. **수율**(yield)과 **수확**(harvest)이다. Fox와 Brewer의 "Harvest, Yield, and Scalable Tolerant Systems"[^4]에서 나온 개념이다.

> 클라이언트가 서버에 쿼리를 보낸다고 가정하면, 올바른 동작에 대한 지표가 최소 두 가지 있다. **수율**은 요청을 완료할 확률이고, **수확**은 응답에 반영된 데이터의 비율, 즉 쿼리에 대한 답의 완전성을 측정한다.

### 수율에 관하여

이후의 글[^5]에서 Brewer는 **수율**과 그 용도를 확장한다.

> 수치상 이것은 보통 업타임에 매우 가깝지만, 실무에서는 더 유용하다. 사용자 경험에 직접 대응되고, 모든 초(second)가 같은 가치를 갖지 않는다는 사실을 올바르게 반영하기 때문이다. 쿼리가 없을 때 1초 동안 다운되는 것은 사용자나 수율에 아무 영향이 없지만 업타임은 줄인다. 마찬가지로 피크 시간대와 한산한 시간대에 각각 1초 다운되는 것은 같은 업타임을 만들지만, 피크 시간대의 초와 최저 부하 시간대의 초 사이에는 부하가 한 자릿수 차이 날 수 있으므로 수율은 크게 달라진다. 그래서 우리는 업타임이 아니라 수율에 집중한다.

### 수확에 관하여

**수확**은 훨씬 더 간과되는 지표이며, 관계형 데이터베이스의 시대에는 특히 그렇다. 하지만 검색 엔진에서 일한다고 상상하면, 단어마다 별도의 인덱스가 있다고 상상할 수 있다. "cute"라는 단어를 쓰는 웹 페이지의 인덱스는 노드 A에, "baby"를 쓰는 웹 페이지의 인덱스는 노드 B에, "animals"의 인덱스는 머신 C에 있다. 그러면 노드 {A, B, C}의 결과를 합친 "cute baby animals" 검색은 수확이 100%다. 하지만 노드 B가 사용 불가능하다면, "cute animals"만의 결과를 반환할 수 있고 그 수확은 66%가 된다. 다시 말해:

```
수확 = 사용 가능한 데이터 / 전체 데이터
```

또 다른 예는 문서의 버전들을 저장하는 시스템이다. 일부 노드가 다운된 상황에서, 시스템은 저장된 것 중 최신 버전이 아닐 확률이 있다는 것을 알면서도 자신이 찾을 수 있는 가장 최신 버전의 문서를 제시하기로 선택할 수 있다.

### 더 나은 휴리스틱

시스템이 수율과 수확 중 어느 쪽을 선호하는지(애초에 수확을 줄이는 것이 *가능한지*조차)는 그 설계의 산물인 경향이 있다.

Brewer의 표현을 빌리면[^5]:

> 핵심 통찰은 장애가 수율에 영향을 미칠지, 수확에 영향을 미칠지, 둘 다에 미칠지를 우리가 좌우할 수 있다는 것이다. 복제(replicated) 시스템은 장애를 용량 감소로(그리고 높은 사용률에서는 수율 저하로) 매핑하는 경향이 있는 반면, 파티션(partitioned) 시스템은 데이터베이스의 일부가 일시적으로 사라지면서 장애를 수확 감소로 매핑하는 경향이 있다. 다만 초당 쿼리 용량은 그대로 유지된다.

분산 시스템을 만드는 사람들(요즘 세상에 안 만드는 사람이 있나?)에게 주는 일반적 조언으로는, 다음이 훨씬 효과적이라고 생각한다.

> 최선을 다하더라도 시스템은 결국 수율을 줄일지(즉, 요청에 대한 응답을 멈출지) 수확을 줄일지(즉, 불완전한 데이터에 기반한 답을 줄지) 선택해야 할 만큼의 장애를 겪게 된다. 이 결정은 비즈니스 요구 사항에 기반해야 한다.

### 그래서 이제 어쩌라고

이 글이 사람들이 분산 시스템을 만드는 방식을 바꿀 가능성은 지극히 낮다. 우리의 동기 대부분은 비즈니스 관심사에서 나온다("우리 쇼핑 카트는 *절대* 죽으면 안 돼" 또는 "나중에 이걸 대사(reconcile)할 방법이 없어"). 다만 내가 보고 싶은 것은, 자기도 모르게 자기 시스템을 논리적 불가능으로 설명하는 사람들이 훨씬 줄어드는 것이다.

### tl;dr

CAP 정리의 일관성, 가용성, 파티션 감내 중에서 파티션 감내는 분산 시스템에서 필수다. 선택하지 **않을** 수 없다. CAP 대신, 가용성을 *수율*(성공적으로 응답한 요청의 비율)과 *수확*(응답에 실제로 포함된 필요 데이터의 비율)의 관점에서 생각하고, 실패가 일어날 때 시스템이 이 둘 중 무엇을 희생할지 생각해야 한다.

### 2010년 10월 22일 업데이트

반박문에서 Stonebraker 박사는 이렇게 말한다.

> Coda의 관점에서는 죽은 노드가 하나의 파티션에 있고 나머지 N-1개 노드가 다른 파티션에 있다. CAP 정리의 지침은 네트워크 파티션이 존재할 때 A와 C 중 하나를 선택해야 한다는 것이다. 현실 세계에서 자명하듯, 이 실패 모드에서는 C와 A를 둘 다 달성하는 것이 가능하다. 트랜잭션적으로 일관된 방식으로 레플리카로 페일오버하면 그만이다. 특히 적어도 Tandem과 Vertica는 수년간 정확히 이렇게 해 왔다. 따라서 노드 실패를 파티션으로 간주하는 것은 명백히 부적절한 CAP 정리 결론으로 이어진다.

그가 옳다. 죽은(혹은 완전히 파티션된) 노드는 요청을 전혀 받을 수 없으므로, 여기서는 다른 노드들이 일관성이나 가용성을 해치지 않고 쉽게 보완할 수 있다. 내 오류는 Gilbert와 Lynch의 가용성 정식화가 실패하지 않은 노드에게만 응답을 요구한다는 것, 그리고 파티션 안에 살아 있는 노드가 하나도 없으면 스플릿 브레인(split-brain) 증후군의 여지 자체가 없다는 것을 잊은 데 있다. 오류를 사과하며, 이를 지적해 준 그와 Brewer 박사 두 분께 감사한다.

그렇긴 해도, "[파티션을] 견뎌내는 것은 가용성의 바늘을 움직이지 못할 것이다. 더 빈번한 사건들이 전역 장애를 일으킬 것이기 때문이다"라는 Stonebraker 박사의 주장은 틀렸다. 다중 노드 실패는 단일 노드 실패보다 드물지 몰라도, 비즈니스에 심각한 영향을 줄 만큼은 충분히 흔하다. 내 제한된 경험 안에서도 단일 데이터센터(DC) 안의 장기 네트워크 파티션, PDU 고장, 스위치 고장, 랙 전체의 우발적 전원 사이클, DC 전체의 백본 장애, DC 전체의 정전, 그리고 저혈당 상태의 운전자가 포드 픽업트럭을 DC의 HVAC 시스템에 들이박은 사건까지 겪었다. 나는 심지어 운영 담당자도 아니다.

사실을 말하자면, 대부분의 실제 시스템은 가용성 보장에 비해 일관성 보장은 상당히 낮은 수준만 요구한다. 예를 들어 Amazon의 쇼핑 카트는 완전한 ACID 처리를 요구하지 않고, Twitter의 타임라인이나 Facebook의 뉴스 피드, Google의 인덱스도 마찬가지다. 격리된 트랜잭션의 정석적 사례인 은행 계좌 간 이체조차 24시간의 미확정 기간을 두고 일어난다. 사실 데이터베이스 트랜잭션을 실제로 닮은 몇 안 되는 금융 거래 중 하나는 현금과 상품의 물리적 교환이다. 완전히 아날로그적인 경험이다.

하지만 일관성의 실패는 용인되거나 심지어 예상되는 반면, 가용성의 실패는 거의 전부 돈의 손실을 의미한다. 실패한 Google 검색 하나하나가 광고 노출과 광고주 과금의 감소를 뜻하고, 사용자가 쇼핑 카트에 담지 못한 상품 하나하나가 판매 감소를 뜻하며, 처리되지 못한 신용카드 청구 하나하나가 규제 벌금의 위험이다. 일관성 대신 가용성을 선택하는 것은 기술적 선택이 아니라 비즈니스 선택이다.

이런 경제적 맥락을 놓고 보면, 의미 있는 규모의 실무자 대부분이 고가용성의 최종적 일관성(eventually consistent) 시스템으로 비즈니스 요구를 충족하는 이유가 분명해진다.

Jepsen은 분산 시스템의 안전성 속성을 분석한다. 가장 대표적으로는 일관성 모델 위반을 찾아낸다. 그런데 일관성 모델이란 무엇인가? 각 모델은 어떤 현상을 허용하는가? 주어진 프로그램에 정말로 필요한 일관성은 어떤 종류인가?

이 레퍼런스 가이드는 다양한 일관성 모델의 기본 정의, 직관적인 설명, 이론적 토대를 문헌 링크와 함께 제공한다. 업계 실무자, 학계 연구자, 애호가 모두가 일관성 속성에 쉽게 접근할 수 있게 하는 것이 목표다.

### [모델(Models)](https://jepsen.io/consistency/models)

[일관성 모델](https://jepsen.io/consistency/models)은 시스템이 무엇을 할 수 있는지 선언하는 안전성 속성이다. 형식적으로 말하면, 일관성 모델은 시스템이 합법적으로 실행할 수 있는 히스토리들의 집합을 정의한다. 예를 들어 [직렬화 가능성(Serializability)](https://jepsen.io/consistency/models/serializable)이라는 모델은 모든 합법적 히스토리가 전순서(totally ordered) 실행과 동등해야 함을 보장한다.

### [현상(Phenomena)](https://jepsen.io/consistency/phenomena)

일관성 모델은 흔히 금지되는 [현상](https://jepsen.io/consistency/phenomena), 즉 특정한 연산 패턴으로 정의된다. 예를 들어 [G1a(중단된 읽기, Aborted Read)](https://jepsen.io/consistency/phenomena/g1a)는 어떤 트랜잭션이 중단된(aborted) 다른 트랜잭션이 수행한 쓰기를 관찰할 때 발생한다.

### [의존성(Dependencies)](https://jepsen.io/consistency/dependencies)

일관성 모델과 현상은 흔히 서로 다른 연산 사이의 [의존성](https://jepsen.io/consistency/dependencies)으로 정의된다. 예를 들어 트랜잭션 T2가 T1이 쓴 값을 읽으면 T2가 T1에 쓰기-읽기(write-read) 의존한다고 말한다. 이 의존성들은 그래프를 이룬다. 그 그래프에서 특정 사이클을 금지하면 서로 다른 일관성 모델이 생겨난다.

## 일관성 모델 (Consistency Models)

Jepsen은 분산 시스템의 안전성 속성을 분석한다. 가장 대표적으로는 일관성 모델 위반을 찾아낸다. 그런데 일관성 모델이란 무엇인가? 각 모델은 어떤 현상을 허용하는가? 주어진 프로그램에 정말로 필요한 일관성은 어떤 종류인가?

이 레퍼런스 가이드는 엔지니어와 학계 모두를 위해 다양한 일관성 모델의 기본 정의, 직관적인 설명, 이론적 토대를 제공한다.

![일관성 모델 지도](https://jepsen.io/consistency/models/map.svg)

이 클릭 가능한 지도([Bailis, Davidson, Fekete 외](http://www.vldb.org/pvldb/vol7/p181-bailis.pdf)와 [Viotti와 Vukolic](https://arxiv.org/pdf/1512.00168.pdf)에서 변형)는 동시성 시스템에서 흔히 쓰이는 일관성 모델들 사이의 관계를 보여준다. 화살표는 일관성 모델 간의 관계를 나타낸다. 예를 들어 strict serializable은 serializability와 linearizability를 모두 함의하고, linearizability는 순차 일관성(sequential consistency)을 함의하는 식이다. 색깔은 비동기 네트워크 위의 분산 시스템에서 각 모델이 얼마나 가용(available)할 수 있는지를 보여준다.

이 지도는 일관성 모델들을 계층 구조로 배열한다. 지도에 표시된 가장 강한 모델은 [strict serializable](https://jepsen.io/consistency/models/strict-serializable)이다. Strict serializable은 서로 겹치지 않는 두 일관성 모델 계열, 즉 다중 객체 트랜잭션에 대한 모델들과 단일 객체 연산에 대한 모델들을 하나로 통합한다. 모델 x가 y를 함의한다(implies)고 말할 때는, x가 성립하는 모든 히스토리에서 y도 성립한다는 뜻이다. 이때 x는 y보다 "강하다".

다중 객체 쪽에서는 strict serializable이 [serializable](https://jepsen.io/consistency/models/serializable)을 함의하고, serializable은 다시 [repeatable read](https://jepsen.io/consistency/models/repeatable-read)와 [snapshot isolation](https://jepsen.io/consistency/models/snapshot-isolation)을 함의한다. (일반화된 정의를 가정하면) snapshot isolation과 repeatable read는 둘 다 [monotonic atomic view](https://jepsen.io/consistency/models/monotonic-atomic-view)를 함의한다. Repeatable read는 [cursor stability](https://jepsen.io/consistency/models/cursor-stability)를 함의한다. Cursor stability와 monotonic atomic view는 둘 다 [read committed](https://jepsen.io/consistency/models/read-committed)를 함의하고, read committed는 [read uncommitted](https://jepsen.io/consistency/models/read-uncommitted)를 함의한다.

단일 객체 모델 쪽에서는 strict serializable이 [linearizable](https://jepsen.io/consistency/models/linearizable)을 함의하고, linearizable은 [sequential](https://jepsen.io/consistency/models/sequential)을, sequential은 [causal](https://jepsen.io/consistency/models/causal)을 함의한다. Causal은 [writes follow reads](https://jepsen.io/consistency/models/writes-follow-reads)와 [PRAM](https://jepsen.io/consistency/models/pram)을 함의한다. PRAM은 [monotonic reads](https://jepsen.io/consistency/models/monotonic-reads), [monotonic writes](https://jepsen.io/consistency/models/monotonic-writes), [read your writes](https://jepsen.io/consistency/models/read-your-writes)를 함의한다.

Cursor stability, snapshot isolation, sequential과 같거나 그보다 강한 모든 모델은 비동기 네트워크에서 완전 가용(totally available)할 수 없다. Read your writes와 같거나 그보다 강한 모든 모델은 기껏해야 스티키 가용(sticky available)할 수 있다. (여기 나열된 것 중) 더 약한 모델들은 완전 가용할 수 있다.

### 기본 개념 (Fundamental Concepts)

#### 시스템 (Systems)

분산 시스템은 동시성 시스템의 한 종류이며, 동시성 제어에 관한 문헌 상당수가 분산 시스템에 그대로 적용된다. 실제로 우리가 다룰 개념 대부분은 원래 단일 노드 동시성 시스템을 위해 정식화된 것이다. 다만 가용성과 성능 면에서는 몇 가지 중요한 차이가 있다.

시스템은 시간에 따라 변하는 논리적 상태를 가진다. 예를 들어 단순한 시스템은 정수 변수 하나일 수 있고, 그 상태는 `0`, `3`, `42` 같은 것이다. 뮤텍스는 잠김과 풀림, 두 가지 상태만 가진다. 키-값 저장소의 상태는 키에서 값으로 가는 맵일 수 있다. 예: `{cat: 1, dog: 1}` 또는 `{cat: 4}`.

#### 프로세스 (Processes)

프로세스[^1]는 계산을 수행하고 연산을 실행하는, 논리적으로 싱글 스레드인 프로그램이다. 프로세스는 절대 비동기적이지 않다. 비동기 계산은 독립적인 프로세스들로 모델링한다. "논리적으로 싱글 스레드"라고 말하는 이유는, 프로세스가 한 번에 한 가지 일만 할 수 있긴 하지만 그 구현은 여러 스레드, 운영체제 프로세스, 심지어 물리 노드에 걸쳐 있을 수 있음을 강조하기 위해서다. 그 구성 요소들이 일관된 싱글 스레드 프로그램이라는 환상을 제공하기만 하면 된다.

#### 연산 (Operations)

연산은 상태에서 상태로의 전이다. 예를 들어 단일 변수 시스템에는 그 변수의 값을 읽고 쓰는 `read`와 `write` 같은 연산이 있을 수 있다. 카운터에는 증가, 감소, 읽기 같은 연산이 있을 수 있다. SQL 저장소에서 연산은 여러 개의 select, update, delete 등으로 구성된 트랜잭션일 수 있다.

##### 함수, 인자, 반환값 (Functions, Arguments & Return Values)

이론상으로는 모든 상태 전이에 고유한 이름을 붙일 수도 있다. 락은 정확히 두 가지 전이, `lock`과 `unlock`을 가진다. 정수 레지스터는 무한히 많은 읽기와 쓰기를 가진다: `read-the-value-1`, `read-the-value-2`, …, 그리고 `write-1`, `write-2`, ….

이를 다루기 쉽게 만들기 위해, 전이들을 `read`, `write`, `cas`, `increment` 같은 함수와 그 함수를 매개변수화하는 값으로 쪼갠다. 단일 레지스터 시스템에서 1을 쓰는 연산은 이렇게 쓸 수 있다.

```clojure
{:f :write, :value 1}
```

키-값 저장소가 주어졌을 때, 키 "a"의 값을 3만큼 증가시키는 것은 이렇게 표현할 수 있다.

```clojure
{:f :increment, :value ["a" 3]}
```

트랜잭션 저장소에서는 값이 복잡한 트랜잭션일 수 있다. 여기서는 하나의 상태 전이 안에서 `a`의 현재 값을 읽어 2를 얻고, `b`를 `3`으로 설정한다.

```clojure
{:f :txn, :value [[:read "a" 2] [:write "b" 3]]}
```

##### 호출 시각과 완료 시각 (Invocation & Completion Times)

연산은 일반적으로 시간이 걸린다. 멀티스레드 프로그램에서 연산은 함수 호출일 수 있다. 분산 시스템에서 연산은 서버에 요청을 보내고 응답을 받는 것을 의미할 수 있다.

이를 모델링하기 위해, 각 연산에는 호출 시각(invocation time)이 있고, 완료된다면 그보다 엄격히 큰 완료 시각(completion time)이 있다고 본다. 둘 다 상상 속의[^2], 완벽히 동기화된, 전역적으로 접근 가능한 시계가 부여한다.[^3] 이런 시계는 실시간(real-time) 순서를 제공한다고 말하는데, 인과적 순서만 추적하는 시계와 구분하기 위해서다.[^4]

##### 동시성 (Concurrency)

연산은 시간이 걸리므로, 두 연산이 시간상 겹칠 수 있다. 예를 들어 두 연산 A와 B가 있을 때, A가 시작하고, B가 시작하고, A가 완료된 다음, B가 완료될 수 있다. A와 B가 둘 다 실행 중인 시간이 존재하면 두 연산 A와 B가 동시적(concurrent)이라고 말한다.

프로세스는 싱글 스레드이므로, 같은 프로세스가 실행한 두 연산은 절대 동시적일 수 없다.

##### 크래시 (Crashes)

어떤 연산이 어떤 이유로든 완료되지 않으면(타임아웃이 났거나 핵심 구성 요소가 크래시했기 때문일 수 있다), 그 연산에는 완료 시각이 없으며, 일반적으로 그 호출 시각 이후의 모든 연산과 동시적이라고 간주해야 한다. 그 연산은 실행될 수도, 되지 않을 수도 있다.

이런 상태의 연산을 가진 프로세스는 사실상 멈춘 것이며, 다시는 다른 연산을 호출할 수 없다. 만약 다른 연산을 호출한다면 싱글 스레드 제약을 위반하게 된다. 프로세스는 한 번에 한 가지 일만 한다.

#### 히스토리 (Histories)

히스토리는 연산들의 모음이며, 그 동시적 구조까지 포함한다.

일부 논문은 이를 연산들의 집합으로 표현한다. 각 연산은 호출 시각과 완료 시각을 나타내는 두 숫자를 포함하고, 동시적 구조는 프로세스 간 시간 구간을 비교해서 추론한다.

Jepsen은 [히스토리를](https://github.com/jepsen-io/history) 호출 연산과 완료 연산의 순서 있는 리스트로 표현하며, 사실상 각 연산을 둘로 쪼갠다. 이 표현은 동시 연산과 가능한 상태의 표현을 유지하면서 히스토리를 순회하는 알고리즘에 더 편리하다.

#### 일관성 모델 (Consistency Models)

일관성 모델은 히스토리들의 집합이다. 우리는 일관성 모델을 사용해 시스템에서 어떤 히스토리가 "좋은" 또는 "합법적인" 것인지 정의한다. 어떤 히스토리가 "serializability를 위반한다"거나 "serializable하지 않다"고 말할 때는, 그 히스토리가 serializable한 히스토리들의 집합에 속하지 않는다는 뜻이다.

일관성 모델 A가 B의 부분집합이면 A가 모델 B를 함의한다고 말한다. 예를 들어 linearizability는 순차 일관성을 함의하는데, linearizable한 모든 히스토리는 순차적으로도 일관되기 때문이다. 이 덕분에 일관성 모델들을 계층 구조로 연관 지을 수 있다.

격식 없이 말할 때, 더 작고 더 제약이 강한 일관성 모델을 "더 강하다"고, 더 크고 더 관대한 일관성 모델을 "더 약하다"고 부른다.

모든 일관성 모델이 직접 비교 가능한 것은 아니다. 두 모델이 서로 다른 동작을 허용하되 어느 쪽도 다른 쪽을 포함하지 않는 경우가 흔하다. 예를 들어 [Snapshot Isolation](https://jepsen.io/consistency/models/snapshot-isolation)은 [A5B(쓰기 스큐, Write Skew)](https://jepsen.io/consistency/phenomena/a5b)라는 현상을 허용하는데, 이는 [Repeatable Read](https://jepsen.io/consistency/models/repeatable-read)에서는 금지된다. 반면 Repeatable Read는 프레디킷(predicate)에 대한 [G-single](https://jepsen.io/consistency/phenomena/g-single)을 허용하는데, 이는 Snapshot Isolation에서는 금지된다. 어느 모델도 다른 쪽보다 엄격히 강하지 않다. 이럴 때 Snapshot Isolation과 Repeatable Read는 비교 불가능(incomparable)하다고 말한다.

[^1]: 문헌에 따라 프로세스를 노드, 호스트, 액터, 에이전트, 사이트, 스레드라고 부르기도 하며, 맥락에 따라 미묘한 차이가 있는 경우가 많다.

[^2]: 이 마법 같은 동기화 시계가 실제로 존재할 필요는 없다. 다만 일부 일관성 모델은 그런 시계가 존재한다면 어떤 연산이 다른 연산보다 먼저 일어난다는 것을 함의한다.

[^3]: "상대성 이론 때문에 동시성(simultaneity)이라는 것은 존재하지 않는다"는 말을 동기화된 시계가 존재할 수 없다는 논거로 들어봤을지 모른다. 이는 오해다. 특수 상대성과 일반 상대성의 방정식은 시간 변환에 대한 정확한 식을 제공하며, 합리적이고 전역적으로 동기화된 시계를 얼마든지 정의할 수 있다. 이런 시계를 참조하는 일관성 제약은 시계의 선택에 의존한다. 예컨대 기준틀(reference frame)에 따라 어떤 시스템은 linearizability를 제공할 수도, 제공하지 않을 수도 있다. 다행인 점은 a) 사실상 모든 실용적 목적에서, 지구상의 시계들은 서로의 속도와 가속도가 워낙 가까워서 오차가 사이드 채널 지연보다 훨씬 작다는 것, b) 비동기 네트워크에서 실시간 경계를 보장하는 알고리즘 다수가 인과적 메시지를 사용해 실시간 순서를 강제하며, 그 결과 순서는 모든 기준틀에서 불변이라는 것이다.

[^4]: "실시간(real-time)"은 일정 시간 안에 실행을 보장하는 프로그램을 가리키기도 하지만, 여기서는 동기화되지 않았을 수 있는 로컬 시계나 어떤 논리적 시간 관계가 아니라, 현실 세계의 시간을 가리키는 뜻으로 쓴다.
