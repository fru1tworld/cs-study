# Kafka 비용과 효율

## Apache Kafka에서 클러스터 리밸런싱의 숨겨진 비용

> **원문:** [The Hidden Costs of Cluster Rebalancing in Apache Kafka](https://www.confluent.io/blog/cluster-rebalancing-costs/)
>
> **저자:** Confluent
>
> **게시일:** Confluent Blog

---

### 서론

Apache Kafka는 분산 이벤트 스트리밍의 사실상 표준이 되었다. 조직들은 실시간 데이터 파이프라인과 스트리밍 애플리케이션을 구축하기 위해 Kafka에 의존하고 있다. 그러나 Kafka 클러스터를 운영하는 데 있어 종종 간과되는 비용 중 하나가 바로 **클러스터 리밸런싱**이다.

리밸런싱은 Kafka의 핵심 메커니즘으로, 컨슈머 그룹 내에서 파티션 할당을 재분배하는 프로세스이다. 컨슈머가 그룹에 참여하거나 떠날 때, 또는 토픽의 파티션 수가 변경될 때 리밸런싱이 트리거된다. 이 프로세스는 정확성과 공정한 부하 분산을 보장하지만, 상당한 운영 비용을 수반할 수 있다.

---

### 리밸런싱이란 무엇인가?

Kafka 컨슈머 그룹에서 각 컨슈머 인스턴스는 토픽의 하나 이상의 파티션에서 메시지를 읽는다. **리밸런싱**은 그룹 내 컨슈머들 간에 파티션 소유권을 재분배하는 프로토콜이다.

리밸런싱은 다음과 같은 상황에서 트리거된다:

- **컨슈머가 그룹에 참여할 때** - 새로운 컨슈머 인스턴스가 시작되는 경우
- **컨슈머가 그룹을 떠날 때** - 컨슈머가 종료되거나 크래시되는 경우
- **컨슈머가 비정상으로 간주될 때** - 하트비트 타임아웃이 만료되는 경우
- **토픽 메타데이터가 변경될 때** - 파티션이 추가되는 경우
- **구독이 변경될 때** - 컨슈머가 새로운 토픽을 구독하는 경우

리밸런싱 프로세스는 그룹 코디네이터(Group Coordinator)라 불리는 특정 Kafka 브로커에 의해 조정된다. 그룹 코디네이터는 컨슈머 그룹의 멤버십을 관리하고, 리밸런싱이 필요할 때 프로토콜을 시작한다.

---

### 전통적인 "Stop-the-World" 리밸런싱의 비용

Kafka의 초기 리밸런싱 프로토콜은 **Eager Rebalancing**(즉시 리밸런싱)이라고 불리며, 이는 본질적으로 "stop-the-world" 접근 방식이다. 이 프로토콜에서는 리밸런싱이 트리거될 때 다음과 같은 일이 발생한다:

1. **모든 컨슈머가 파티션 할당을 포기한다** - 그룹의 모든 컨슈머가 현재 소유한 모든 파티션을 반납한다.
2. **모든 처리가 중단된다** - 파티션 할당이 없으므로 어떤 컨슈머도 메시지를 읽을 수 없다.
3. **그룹이 다시 참여한다** - 모든 컨슈머가 JoinGroup 요청을 보내고, 리더가 새로운 할당을 계산한다.
4. **새로운 할당이 배포된다** - SyncGroup 응답을 통해 각 컨슈머에게 새로운 파티션이 할당된다.
5. **처리가 재개된다** - 컨슈머가 할당받은 파티션에서 다시 메시지를 소비하기 시작한다.

#### 이 접근 방식의 문제점

Eager Rebalancing의 가장 큰 문제는 **리밸런싱 기간 동안 전체 컨슈머 그룹이 완전히 중단**된다는 것이다. 이로 인해 다음과 같은 비용이 발생한다:

- **처리 중단 시간:** 리밸런싱이 진행되는 동안 어떤 메시지도 소비되지 않는다. 대규모 컨슈머 그룹에서는 이 중단이 수 초에서 수 분까지 지속될 수 있다.

- **컨슈머 랙 증가:** 처리가 중단되는 동안 프로듀서는 계속 메시지를 보내므로, 컨슈머 랙이 급격히 증가한다. 리밸런싱이 완료된 후 이 랙을 따라잡는 데 추가 시간이 소요된다.

- **상태 재구축 비용:** Kafka Streams와 같은 상태 기반 애플리케이션에서는 리밸런싱 후 로컬 상태 저장소를 재구축해야 할 수 있다. 이는 changelog 토픽에서 대량의 데이터를 다시 읽어야 함을 의미하며, 복구 시간이 상당히 길어질 수 있다.

- **중복 처리 가능성:** `enable.auto.commit=true`가 설정된 경우, 리밸런싱 전에 처리되었지만 아직 커밋되지 않은 오프셋이 있을 수 있다. 리밸런싱 후 새로운 컨슈머가 해당 파티션을 인수하면 마지막으로 커밋된 오프셋부터 다시 처리하게 되어 중복이 발생할 수 있다.

- **연쇄 리밸런싱(Cascading Rebalances):** 리밸런싱이 오래 걸리면, 일부 컨슈머가 `session.timeout.ms` 내에 하트비트를 보내지 못해 그룹에서 제외될 수 있다. 이는 또 다른 리밸런싱을 트리거하여, 이른바 "리밸런싱 폭풍(rebalance storm)"이 발생할 수 있다.

### 리밸런싱의 실제 비용 측정

리밸런싱의 비용은 여러 요인에 따라 달라진다:

#### 컨슈머 그룹의 크기

컨슈머 그룹이 클수록 리밸런싱에 더 오래 걸린다. 모든 컨슈머가 JoinGroup 요청을 보내고 SyncGroup 응답을 기다려야 하기 때문이다. `max.poll.interval.ms` 타임아웃 내에 리밸런싱이 완료되지 않으면 컨슈머가 제외되어 연쇄 리밸런싱이 발생할 수 있다.

#### 파티션 수

파티션 수가 많을수록 할당 알고리즘의 계산 시간이 증가하고, 각 컨슈머가 처리해야 하는 메타데이터 양도 늘어난다.

#### 상태 기반 처리

Kafka Streams를 사용하는 경우, 파티션 재할당은 로컬 상태 저장소의 마이그레이션을 의미한다. 상태 저장소의 크기가 클수록 복구 시간이 길어진다.

#### 네트워크 지연

분산 환경에서 컨슈머들이 지리적으로 분산되어 있다면, JoinGroup과 SyncGroup 프로토콜의 왕복 시간이 증가하여 리밸런싱이 더 오래 걸린다.

### 비용을 줄이기 위한 개선: 협력적 리밸런싱

Kafka 2.4부터 도입된 **Cooperative Rebalancing**(협력적 리밸런싱, 일명 Incremental Cooperative Rebalancing)은 전통적인 Eager Rebalancing의 "stop-the-world" 문제를 해결하기 위해 설계되었다.

#### 협력적 리밸런싱의 동작 방식

Eager 프로토콜과 달리, 협력적 리밸런싱에서는:

1. **컨슈머가 기존 할당을 유지한다** - 리밸런싱이 시작되더라도 컨슈머는 현재 소유한 파티션을 즉시 반납하지 않는다.
2. **점진적 재할당이 이루어진다** - 실제로 이동이 필요한 파티션만 해제되고 재할당된다.
3. **두 단계로 진행된다** - 첫 번째 리밸런싱에서 이동할 파티션을 식별하고, 두 번째 리밸런싱에서 해당 파티션을 새 소유자에게 할당한다.

이 접근 방식의 핵심 이점은 **이동이 필요하지 않은 파티션의 처리가 계속된다**는 것이다. 즉, 리밸런싱 중에도 대부분의 파티션에서 메시지 소비가 중단되지 않는다.

#### 협력적 리밸런싱 활성화

협력적 리밸런싱을 사용하려면 컨슈머 설정에서 `partition.assignment.strategy`를 변경해야 한다:

```properties
# 컨슈머 설정
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

Kafka Streams의 경우:

```properties
# Kafka Streams 설정
upgrade.from=<이전 버전>
```

#### Eager에서 Cooperative로의 롤링 업그레이드

기존 Eager 프로토콜에서 Cooperative 프로토콜로 전환할 때는 **롤링 업그레이드**를 수행해야 한다. 모든 컨슈머를 동시에 변경하면 호환성 문제가 발생할 수 있기 때문이다.

1. **1단계:** 모든 컨슈머의 `partition.assignment.strategy`에 두 가지 전략을 모두 포함하도록 설정한다:
   ```properties
   partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor,org.apache.kafka.clients.consumer.RangeAssignor
   ```

2. **2단계:** 모든 컨슈머가 업데이트된 후, Eager 전략을 제거한다:
   ```properties
   partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
   ```

### 정적 그룹 멤버십(Static Group Membership)

Kafka 2.3에서 도입된 **정적 그룹 멤버십**은 리밸런싱의 빈도를 줄이는 또 다른 중요한 최적화이다.

#### 문제: 불필요한 리밸런싱

기본적으로 Kafka 컨슈머는 그룹에 참여할 때마다 새로운 멤버 ID를 부여받는다. 이는 컨슈머가 일시적으로 재시작되는 경우(예: 롤링 배포)에도 "새로운" 컨슈머로 인식되어 리밸런싱이 트리거됨을 의미한다.

#### 해결: group.instance.id

정적 그룹 멤버십은 각 컨슈머에 고유한 `group.instance.id`를 할당하여 이 문제를 해결한다:

```properties
# 컨슈머 설정
group.instance.id=consumer-host-1
```

정적 그룹 멤버십이 활성화되면:

- **컨슈머가 재시작될 때 리밸런싱이 즉시 트리거되지 않는다.** 그룹 코디네이터는 `session.timeout.ms` 동안 해당 멤버가 다시 돌아오기를 기다린다.
- **같은 `group.instance.id`로 다시 참여하는 컨슈머는 이전과 동일한 파티션 할당을 받는다.** 이는 파티션 이동을 최소화한다.
- **롤링 배포 시 리밸런싱이 완전히 방지될 수 있다.** 각 컨슈머가 `session.timeout.ms` 내에 재시작된다면 그룹 멤버십이 유지되므로 리밸런싱이 발생하지 않는다.

#### 권장 설정

정적 그룹 멤버십을 사용할 때는 `session.timeout.ms`를 충분히 크게 설정해야 한다. 컨슈머 재시작에 걸리는 시간보다 커야 하므로, 일반적으로 더 높은 값(예: 5분에서 10분)이 권장된다:

```properties
session.timeout.ms=300000  # 5분
group.instance.id=consumer-host-1
heartbeat.interval.ms=10000
```

### 브로커 수준 리밸런싱: 파티션 재할당

컨슈머 그룹 리밸런싱 외에도, **브로커 수준의 파티션 재할당**은 또 다른 형태의 리밸런싱이다. 이는 다음과 같은 상황에서 발생한다:

- **새로운 브로커 추가:** 기존 파티션이 새 브로커로 이동해야 한다.
- **브로커 해제:** 브로커를 제거하기 전에 해당 브로커의 파티션을 다른 브로커로 이동해야 한다.
- **부하 불균형 해소:** 특정 브로커에 파티션이 집중된 경우 재분배가 필요하다.

#### 파티션 재할당의 비용

브로커 간 파티션 재할당은 대량의 데이터 복제를 수반한다. 이는 다음과 같은 비용을 발생시킨다:

- **네트워크 대역폭 소비:** 파티션 데이터를 새 브로커로 복제하면 브로커 간 네트워크 트래픽이 급증한다.
- **디스크 I/O 증가:** 소스 브로커에서의 읽기와 대상 브로커에서의 쓰기가 동시에 발생한다.
- **프로덕션 트래픽에 대한 영향:** 재할당 트래픽이 클라이언트 요청과 네트워크 및 디스크 리소스를 경쟁한다.
- **복제 지연 시간 증가:** 기존 파티션의 팔로워 복제가 느려질 수 있다.

#### 스로틀링으로 영향 제어

Kafka는 파티션 재할당의 속도를 제한하기 위한 **스로틀링** 메커니즘을 제공한다:

```bash
# kafka-reassign-partitions.sh를 사용한 스로틀링 예시
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --reassignment-json-file reassignment.json \
  --execute \
  --throttle 50000000  # 50MB/s로 제한
```

스로틀 값은 바이트/초 단위이며, 너무 낮게 설정하면 재할당이 매우 오래 걸리고, 너무 높게 설정하면 프로덕션 트래픽에 영향을 미친다. 적절한 밸런스를 찾는 것이 중요하다.

### 셀프 밸런싱 클러스터(Self-Balancing Clusters)

Confluent Platform과 Confluent Cloud는 **셀프 밸런싱 클러스터** 기능을 제공한다. 이 기능은 수동 파티션 재할당의 운영 부담을 크게 줄여준다.

#### 셀프 밸런싱의 동작 방식

셀프 밸런싱 클러스터는 다음과 같이 동작한다:

- **자동 감지:** 클러스터의 부하 불균형, 새 브로커 추가, 브로커 제거 등의 이벤트를 자동으로 감지한다.
- **지능적 계획:** 최소한의 데이터 이동으로 최적의 균형을 달성하는 재할당 계획을 자동으로 생성한다.
- **점진적 실행:** 프로덕션 워크로드에 미치는 영향을 최소화하면서 백그라운드에서 점진적으로 파티션을 이동한다.
- **지속적 모니터링:** 클러스터 상태를 지속적으로 모니터링하고 필요에 따라 조정한다.

#### 셀프 밸런싱의 이점

- **운영 복잡성 감소:** 수동으로 재할당 계획을 작성하고 실행할 필요가 없다.
- **더 빠른 확장:** 브로커를 추가하거나 제거할 때 자동으로 부하가 재분배된다.
- **프로덕션 영향 최소화:** 지능적인 스로틀링과 스케줄링으로 클라이언트 성능에 미치는 영향을 최소화한다.

### 리밸런싱 비용을 최소화하기 위한 모범 사례

#### 1. 협력적 리밸런싱 프로토콜 사용

가능하다면 항상 `CooperativeStickyAssignor`를 사용한다. 이는 리밸런싱 중 처리 중단을 최소화하는 가장 효과적인 방법이다.

#### 2. 정적 그룹 멤버십 활성화

모든 컨슈머에 `group.instance.id`를 설정하여 불필요한 리밸런싱을 방지한다. 특히 롤링 배포가 빈번한 환경에서 큰 효과를 발휘한다.

#### 3. 세션 타임아웃 적절히 설정

`session.timeout.ms`와 `max.poll.interval.ms`를 워크로드에 맞게 적절히 설정한다. 너무 짧으면 불필요한 리밸런싱이 발생하고, 너무 길면 실제 장애 감지가 늦어진다.

```properties
session.timeout.ms=45000
heartbeat.interval.ms=15000
max.poll.interval.ms=300000
```

#### 4. 파티션 수 신중하게 결정

토픽의 파티션 수를 신중하게 결정한다. 파티션 수가 많을수록 리밸런싱에 더 많은 시간이 소요된다. 처리량 요구 사항과 리밸런싱 비용 사이의 균형을 고려해야 한다.

#### 5. 모니터링 및 알림 설정

리밸런싱 관련 메트릭을 모니터링하고 적절한 알림을 설정한다:

- **컨슈머 랙:** 리밸런싱 후 컨슈머 랙이 증가하는지 모니터링한다.
- **리밸런싱 빈도:** 비정상적으로 빈번한 리밸런싱은 문제의 징후이다.
- **리밸런싱 시간:** 각 리밸런싱에 소요되는 시간을 추적한다.
- **JoinGroup/SyncGroup 지연:** 프로토콜 단계별 지연 시간을 모니터링한다.

#### 6. 브로커 재할당 시 스로틀링 활용

브로커 수준의 파티션 재할당을 수행할 때는 항상 스로틀링을 설정하여 프로덕션 트래픽에 대한 영향을 제어한다.

---

### 결론

클러스터 리밸런싱은 Kafka 운영에서 피할 수 없는 부분이지만, 그 비용을 이해하고 관리하는 것이 중요하다. 전통적인 Eager Rebalancing의 "stop-the-world" 접근 방식은 상당한 처리 중단과 연쇄 장애를 유발할 수 있다.

다행히 Kafka 커뮤니티는 이러한 비용을 줄이기 위한 여러 개선 사항을 도입했다:

- **협력적 리밸런싱(Cooperative Rebalancing):** 점진적 파티션 재할당으로 처리 중단을 최소화한다.
- **정적 그룹 멤버십(Static Group Membership):** 불필요한 리밸런싱을 방지한다.
- **셀프 밸런싱 클러스터(Self-Balancing Clusters):** 브로커 수준의 파티션 재할당을 자동화한다.

이러한 기능들을 적절히 활용하고, 모니터링과 올바른 설정을 통해 리밸런싱의 숨겨진 비용을 최소화함으로써, Kafka 클러스터를 보다 안정적이고 효율적으로 운영할 수 있다. 리밸런싱이 불가피한 상황에서도 그 영향을 최소화하는 것이 핵심이며, 이를 위해 협력적 프로토콜 채택, 정적 멤버십 설정, 적절한 타임아웃 튜닝, 그리고 지속적인 모니터링이 필수적이다.

## Apache Kafka 마이그레이션의 진정한 비용

> **원문:** [The True Cost of Migrating from Apache Kafka](https://www.confluent.io/blog/cost-of-kafka-migration/)
>
> **저자:** Confluent Team
>
> **게시일:** 2025년

---

### 도입

Apache Kafka를 대체하거나 다른 메시징 또는 스트리밍 플랫폼으로 마이그레이션하는 것은 표면적으로 매력적으로 보일 수 있다. 비용 절감, 더 단순한 운영, 또는 최신 기술 도입 등의 이유로 마이그레이션을 고려하는 조직이 있다. 그러나 Kafka 마이그레이션의 진정한 비용은 단순한 라이선스 비용이나 인프라 비용을 훨씬 넘어선다.

이 글에서는 Kafka에서 다른 시스템으로 마이그레이션할 때 발생하는 숨겨진 비용, 기술적 리스크, 그리고 운영상의 복잡성에 대해 심층적으로 살펴본다.

---

### 마이그레이션 비용의 빙산

Kafka 마이그레이션의 비용을 생각할 때, 많은 조직이 눈에 보이는 직접적인 비용만 고려하는 실수를 범한다. 그러나 실제 비용의 대부분은 수면 아래에 숨겨져 있다. 마치 빙산처럼, 보이지 않는 부분이 훨씬 더 크고 위험하다.

#### 눈에 보이는 비용

- **새로운 플랫폼의 라이선스 및 인프라 비용:** 새로운 메시징 시스템의 구매 또는 구독 비용
- **초기 설정 및 구성:** 새 시스템의 설치, 클러스터 구성, 네트워크 설정 등
- **기본적인 데이터 마이그레이션:** 기존 토픽과 데이터를 새 시스템으로 이전하는 작업

#### 숨겨진 비용

눈에 보이지 않지만 마이그레이션 전체 비용의 대부분을 차지하는 항목들이 있다:

- **애플리케이션 재작성:** Kafka의 프로듀서, 컨슈머, Streams API, Connect API를 사용하는 모든 애플리케이션을 새 시스템에 맞게 재작성해야 한다.
- **테스트 및 검증:** 마이그레이션된 시스템의 기능적, 비기능적 요구사항을 모두 검증하기 위한 광범위한 테스트가 필요하다.
- **다운타임 및 비즈니스 영향:** 마이그레이션 과정에서 발생하는 서비스 중단이 비즈니스에 미치는 영향
- **팀 재교육:** 엔지니어링 팀이 새로운 시스템을 학습하고 전문성을 쌓는 데 소요되는 시간과 비용
- **운영 리스크:** 새로운 시스템의 안정성이 검증되기까지의 기간 동안 발생할 수 있는 장애와 성능 저하
- **기회비용:** 마이그레이션에 투입되는 엔지니어링 리소스가 새로운 기능 개발이나 비즈니스 혁신에 사용되지 못하는 것

---

### 애플리케이션 재작성의 복잡성

Kafka 마이그레이션에서 가장 큰 비용 요소 중 하나는 기존 애플리케이션의 재작성이다. Kafka는 단순한 메시지 큐가 아니라, 풍부한 에코시스템과 API를 갖춘 완전한 이벤트 스트리밍 플랫폼이다.

#### 프로듀서와 컨슈머 애플리케이션

Kafka의 프로듀서와 컨슈머 API는 강력하면서도 세밀한 제어를 제공한다. 파티션 기반 순서 보장, 컨슈머 그룹을 통한 부하 분산, 정확한 오프셋 관리 등의 기능은 많은 애플리케이션의 핵심 로직에 깊이 통합되어 있다.

새로운 시스템으로 마이그레이션할 때, 이러한 의미론(semantics)을 정확히 재현해야 한다. 그렇지 않으면:

- **메시지 순서가 보장되지 않을 수 있다:** 특히 키 기반 파티셔닝에 의존하는 애플리케이션에서 문제가 발생한다.
- **정확히 한 번(exactly-once) 처리가 불가능할 수 있다:** Kafka의 트랜잭션 기능에 의존하는 애플리케이션은 대안을 찾아야 한다.
- **재처리(reprocessing) 기능이 제한될 수 있다:** Kafka의 오프셋 리셋 기능을 통한 데이터 재처리는 많은 시스템에서 지원하지 않는다.

#### Kafka Streams 애플리케이션

Kafka Streams는 Kafka 위에 구축된 스트림 처리 라이브러리로, 상태 저장 처리(stateful processing), 윈도잉(windowing), 조인(join), 집계(aggregation) 등의 고급 기능을 제공한다. Kafka Streams 애플리케이션을 다른 스트림 처리 프레임워크로 마이그레이션하는 것은 다음과 같은 이유로 매우 복잡하다:

- **상태 저장소(state store)의 마이그레이션:** Kafka Streams의 내부 상태 저장소는 변경 로그(changelog) 토픽을 통해 내결함성이 보장된다. 이 상태를 새 시스템으로 마이그레이션하는 것은 매우 어렵다.
- **처리 토폴로지의 재구현:** 복잡한 스트림 처리 토폴로지를 다른 프레임워크에서 동일한 의미론으로 재구현해야 한다.
- **정확히 한 번 의미론:** Kafka Streams의 정확히 한 번 처리 보장은 Kafka의 트랜잭션과 긴밀하게 통합되어 있으며, 다른 시스템에서 이를 동일하게 구현하기는 어렵다.

#### Kafka Connect 파이프라인

Kafka Connect는 데이터베이스, 클라우드 스토리지, 검색 엔진, 데이터 웨어하우스 등 다양한 외부 시스템과 Kafka를 연결하는 커넥터 프레임워크다. 수백 개의 사전 구축된 커넥터가 있으며, 많은 조직이 이를 통해 데이터 파이프라인을 구축하고 있다.

Kafka Connect에서 마이그레이션할 때 고려해야 할 사항:

- **커넥터 호환성:** 새 시스템에 동일한 수준의 커넥터 에코시스템이 있는가?
- **변경 데이터 캡처(CDC):** Debezium과 같은 CDC 커넥터에 의존하는 파이프라인은 대안을 찾기 어려울 수 있다.
- **스키마 관리:** Schema Registry와 통합된 데이터 파이프라인의 스키마 진화(schema evolution)를 어떻게 처리할 것인가?
- **오프셋 관리:** 커넥터의 오프셋 추적 메커니즘이 달라지면 데이터 정합성 문제가 발생할 수 있다.

---

### 데이터 마이그레이션의 리스크

#### 데이터 손실 가능성

마이그레이션 과정에서 데이터 손실은 가장 심각한 리스크 중 하나다. Kafka에 저장된 이벤트 데이터는 종종 비즈니스 크리티컬한 정보를 포함하고 있으며, 이를 새 시스템으로 완벽하게 이전하는 것은 쉽지 않다.

- **보존 정책(retention policy)이 다른 시스템:** Kafka의 로그 기반 보존 모델과 다른 메시징 시스템의 보존 모델이 다를 수 있다.
- **컴팩션(compaction) 토픽:** Kafka의 로그 컴팩션은 키별 최신 값만 유지하는 독특한 기능이며, 이를 다른 시스템에서 정확히 재현하기 어렵다.
- **대용량 데이터 이전:** 테라바이트 또는 페타바이트 규모의 데이터를 이전하는 것은 시간과 네트워크 대역폭 측면에서 상당한 도전이다.

#### 스키마 호환성

Kafka 에코시스템에서 Schema Registry는 프로듀서와 컨슈머 간의 데이터 계약(data contract)을 관리하는 핵심 구성 요소다. Avro, Protobuf, JSON Schema를 지원하며, 스키마 진화 규칙을 통해 하위 및 상위 호환성을 보장한다.

새 시스템으로 마이그레이션할 때, 이 스키마 관리 체계를 어떻게 유지하거나 대체할 것인지가 중요한 과제다.

#### 마이그레이션 기간 동안의 이중 운영

현실적으로 대규모 Kafka 마이그레이션은 즉시 전환(big bang)이 아닌 점진적 접근이 필요하다. 이는 상당 기간 동안 기존 Kafka 시스템과 새 시스템을 병렬로 운영해야 함을 의미한다.

이중 운영의 비용은 다음을 포함한다:

- **두 시스템의 인프라 비용:** 마이그레이션 기간 동안 두 시스템 모두의 인프라를 유지해야 한다.
- **데이터 동기화:** 두 시스템 간의 데이터 일관성을 유지하기 위한 브리지 또는 미러링 메커니즘이 필요하다.
- **운영 복잡성 증가:** 운영팀이 두 가지 서로 다른 시스템을 동시에 관리해야 한다.
- **모니터링 이중화:** 두 시스템 모두에 대한 모니터링과 알림을 구성해야 한다.

---

### 운영 전문성의 손실

#### Kafka 전문성은 조직의 자산이다

수년에 걸쳐 축적한 Kafka 운영 전문성은 조직의 중요한 자산이다. 성능 튜닝 경험, 장애 대응 절차, 용량 계획 노하우, 모니터링 및 알림 설정 등은 새 시스템에서는 처음부터 다시 쌓아야 한다.

#### 새로운 시스템의 학습 곡선

새로운 메시징 또는 스트리밍 시스템으로 전환하면, 엔지니어링 팀은 다음을 학습해야 한다:

- **새 시스템의 아키텍처와 내부 동작 원리**
- **구성 옵션 및 최적화 전략**
- **장애 모드와 복구 절차**
- **모니터링 메트릭과 문제 진단 방법**
- **보안 모델과 접근 제어 메커니즘**
- **클라이언트 라이브러리와 API**

이 학습 과정은 수개월에서 수년이 걸릴 수 있으며, 그 동안 생산성 저하와 운영 리스크 증가가 불가피하다.

---

### 에코시스템과 통합의 가치

Apache Kafka는 단독으로 사용되는 것이 아니라, 광범위한 에코시스템의 중심에 있다. 이 에코시스템은 수년에 걸쳐 성숙해졌으며, 다음을 포함한다:

#### 풍부한 커넥터 에코시스템

- **200개 이상의 사전 구축된 Kafka Connect 커넥터:** 데이터베이스(MySQL, PostgreSQL, Oracle, MongoDB), 클라우드 서비스(AWS S3, Google BigQuery, Azure Blob Storage), 검색 엔진(Elasticsearch), 데이터 웨어하우스(Snowflake, Databricks) 등과의 통합
- **Debezium 기반 CDC(Change Data Capture):** 데이터베이스 변경 사항을 실시간으로 캡처하여 스트리밍하는 표준 솔루션
- **싱크 커넥터를 통한 다양한 대상 시스템으로의 데이터 전달**

#### 스트림 처리 에코시스템

- **Kafka Streams:** 경량 스트림 처리 라이브러리
- **ksqlDB:** SQL 기반 스트림 처리 엔진
- **Apache Flink, Apache Spark Streaming:** 대규모 스트림 처리 프레임워크와의 네이티브 통합

#### 모니터링 및 관리 도구

- **다양한 모니터링 솔루션:** Confluent Control Center, Burrow, Kafka Manager 등
- **메트릭 통합:** Prometheus, Grafana, Datadog 등과의 통합
- **스키마 관리:** Confluent Schema Registry를 통한 데이터 거버넌스

이러한 에코시스템의 가치를 새 시스템에서 대체하는 것은 막대한 비용과 시간이 필요하며, 많은 경우 동등한 수준의 대안이 존재하지 않는다.

---

### 성능 및 확장성 고려사항

#### Kafka의 검증된 성능

Apache Kafka는 대규모 실시간 데이터 스트리밍에 최적화된 아키텍처를 갖추고 있다:

- **높은 처리량(throughput):** 초당 수백만 건의 메시지를 처리할 수 있는 능력
- **낮은 지연 시간(latency):** 밀리초 단위의 엔드투엔드 지연 시간
- **수평 확장성:** 브로커와 파티션을 추가하여 선형적으로 확장 가능
- **내구성:** 복제를 통한 데이터 안전성 보장
- **순서 보장:** 파티션 내 메시지 순서의 엄격한 보장

새 시스템이 이러한 성능 특성을 모두 충족하는지 철저히 검증해야 하며, 특히 프로덕션 워크로드와 유사한 조건에서의 벤치마킹이 필수적이다.

#### 확장성 한계

마이그레이션 대상 시스템이 현재의 워크로드뿐만 아니라 미래의 성장까지 수용할 수 있는지 평가해야 한다. Kafka는 수천 개의 파티션, 수백 개의 컨슈머 그룹, 페타바이트 규모의 데이터를 처리하는 것으로 입증되어 있다.

---

### 마이그레이션 대신 최적화를 고려하라

많은 경우, Kafka에서 다른 시스템으로 마이그레이션하는 것보다 기존 Kafka 환경을 최적화하는 것이 더 나은 선택이다.

#### 비용 최적화 전략

- **적절한 파티션 수 설정:** 과도한 파티션은 불필요한 오버헤드를 유발한다.
- **보존 정책 최적화:** 데이터 보존 기간을 비즈니스 요구사항에 맞게 조정한다.
- **압축(compression) 활용:** 적절한 압축 알고리즘(lz4, zstd, snappy)을 사용하여 스토리지와 네트워크 비용을 절감한다.
- **계층형 스토리지(tiered storage):** 오래된 데이터를 비용 효율적인 오브젝트 스토리지로 이전한다.
- **적절한 인스턴스 크기 선정:** 워크로드에 맞는 적절한 하드웨어 또는 클라우드 인스턴스를 선택한다.

#### 운영 최적화 전략

- **완전 관리형 서비스 활용:** Confluent Cloud와 같은 관리형 Kafka 서비스를 사용하여 운영 부담을 줄인다.
- **자동화된 운영:** 클러스터 스케일링, 파티션 재분배, 롤링 업그레이드 등을 자동화한다.
- **셀프 밸런싱 클러스터:** Confluent의 Self-Balancing Clusters 기능을 활용하여 브로커 간 부하를 자동으로 균형 맞춘다.

#### Confluent를 통한 최적화

Confluent는 Apache Kafka 기반의 완전한 데이터 스트리밍 플랫폼을 제공하며, 다음과 같은 이점을 통해 마이그레이션 없이도 운영 비용과 복잡성을 대폭 줄일 수 있다:

- **Confluent Cloud:** 완전 관리형 클라우드 네이티브 Kafka 서비스로, 인프라 관리와 운영 부담을 제거한다.
- **kora 엔진:** Confluent의 클라우드 네이티브 엔진으로, 오픈소스 Kafka 대비 최대 10배의 탄력성과 비용 효율성을 제공한다.
- **클러스터 링킹(Cluster Linking):** 서로 다른 Kafka 클러스터 간의 데이터 미러링을 간소화하여 하이브리드 및 멀티 클라우드 아키텍처를 지원한다.
- **스트림 거버넌스(Stream Governance):** 스키마 관리, 데이터 카탈로그, 데이터 계보(lineage) 등을 통한 데이터 거버넌스를 제공한다.

---

### TCO(총 소유 비용) 분석 프레임워크

Kafka 마이그레이션을 고려할 때, 다음과 같은 포괄적인 TCO 분석이 필수적이다:

#### 직접 비용

| 비용 항목 | 현재 Kafka | 마이그레이션 대상 시스템 |
|---|---|---|
| 인프라 비용 | 기존 비용 | 새 시스템 인프라 + 이중 운영 기간 비용 |
| 라이선스/구독 비용 | 기존 비용 | 새 시스템 라이선스 비용 |
| 마이그레이션 프로젝트 비용 | 해당 없음 | 컨설팅, 도구, 인력 비용 |

#### 간접 비용

| 비용 항목 | 설명 |
|---|---|
| 애플리케이션 재작성 | 모든 프로듀서, 컨슈머, 스트림 처리 애플리케이션의 재개발 |
| 테스트 | 기능 테스트, 성능 테스트, 회귀 테스트, 장애 복구 테스트 |
| 다운타임 | 마이그레이션 중 서비스 중단으로 인한 비즈니스 손실 |
| 교육 | 엔지니어링 팀 재교육 비용 |
| 생산성 저하 | 학습 곡선으로 인한 개발 및 운영 속도 저하 |
| 기회비용 | 새 기능 개발에 투입하지 못한 엔지니어링 리소스 |
| 에코시스템 재구축 | 커넥터, 모니터링, 관리 도구 등의 재구축 |

#### 리스크 비용

| 리스크 항목 | 잠재적 영향 |
|---|---|
| 데이터 손실 | 마이그레이션 과정에서의 데이터 유실 |
| 장기 프로젝트 | 예상보다 오래 걸리는 마이그레이션으로 인한 추가 비용 |
| 성능 저하 | 새 시스템의 성능이 기대에 미치지 못하는 경우 |
| 기능 격차 | 새 시스템에서 지원하지 않는 기능으로 인한 워크어라운드 비용 |

### 결론

Apache Kafka에서 다른 시스템으로 마이그레이션하는 것은 단순한 기술적 전환이 아니다. 이는 조직 전반에 영향을 미치는 대규모 프로젝트로, 애플리케이션 재작성, 데이터 마이그레이션, 운영 전문성 재구축, 에코시스템 대체 등 광범위한 작업을 수반한다.

마이그레이션을 고려하기 전에, 다음 질문에 대한 답을 가지고 있어야 한다:

1. **마이그레이션의 진정한 동기는 무엇인가?** 비용, 성능, 기능 중 어떤 것이 핵심 동기인가?
2. **기존 Kafka 환경의 최적화로 해결할 수 있는 문제인가?** 완전 관리형 서비스나 아키텍처 최적화가 더 나은 대안일 수 있다.
3. **마이그레이션의 전체 TCO를 정확히 산출했는가?** 숨겨진 비용과 리스크를 포함한 포괄적인 분석이 필요하다.
4. **마이그레이션 대상 시스템이 현재와 미래의 요구사항을 모두 충족하는가?** 단기적 이점에 현혹되지 말고 장기적 관점에서 평가해야 한다.
5. **마이그레이션에 필요한 시간, 인력, 리소스가 확보되어 있는가?** 대규모 마이그레이션은 수개월에서 수년이 걸릴 수 있다.

대부분의 경우, Kafka에서 마이그레이션하는 것보다 Kafka 환경을 최적화하거나 Confluent와 같은 관리형 플랫폼을 도입하는 것이 더 비용 효율적이고 리스크가 낮은 선택이다. Kafka는 이미 전 세계 수천 개 기업에서 미션 크리티컬 워크로드를 처리하는 데 검증된 플랫폼이며, 그 에코시스템의 성숙도와 커뮤니티의 규모는 다른 어떤 스트리밍 플랫폼과도 비교하기 어렵다.

마이그레이션을 결정하기 전에, 반드시 진정한 비용을 면밀히 분석하고, 모든 이해관계자와 함께 종합적인 판단을 내려야 한다.

## Apache Kafka 모니터링은 당신이 생각하는 것보다 더 많은 비용을 초래하고 있다

> **원문:** [Apache Kafka Monitoring Is Costing You More Than You Think](https://www.confluent.io/blog/kafka-monitoring-costs/)
> **저자:** Bijoy Choudhury (기술 리드, 클라우드 지원 엔지니어링) | Confluent Staff
> **게시일:** 2024년 12월 22일 | **읽는 시간:** 8분

Apache Kafka에 의존하는 조직에게 모니터링 기능은 단순한 "있으면 좋은 것"이 아니라, 프로덕션 환경에서의 안정적인 성능과 비즈니스 연속성을 위한 기본 요구사항이다. 그러나 Kafka 모니터링의 실제 비용은 종종 오해를 받는다. 이는 청구서의 단일 항목이 아니라, 엔지니어링 예산을 조용히 잠식하고 총소유비용(TCO)을 부풀리는 숨겨진 비용들의 집합체이다.

이 글에서는 이러한 숨겨진 비용이 어디에서 발생하는지, 자체 구축(DIY) 모니터링이 규모 확장 시 왜 실패하는지, 그리고 더 효율적이고 미래에 대비한 관측 가능성 전략을 어떻게 구축할 수 있는지를 살펴본다.

### Apache Kafka 모니터링이 "무료"처럼 느껴지지만 실제로는 그렇지 않은 이유

브로커, 토픽, 컨슈머 상태를 추적하는 것은 클러스터 안정성을 보장하고 예기치 않은 다운타임과 데이터 손실을 방지하기 위해 필수적이다. Kafka 상태에 대한 전체적인 그림을 얻으려면 다음을 추적해야 한다:

- **클러스터 및 클라이언트 상태 메트릭:** 브로커, 토픽, 파티션, 컨슈머 그룹, 프로듀서 성능
- **감사 로그:** 브로커 로그, 애플리케이션 로그, Kafka Connect 로그
- **트레이스:** 마이크로서비스 전반에 걸친 엔드투엔드 요청 흐름

많은 팀에서 모니터링은 "무료"로 시작된다. Prometheus와 Grafana 같은 오픈소스 스택을 구축하고, JMX 메트릭을 수집하고, 대시보드를 만든다. 초기 비용은 단지 이를 실행하는 인프라 비용뿐인 것처럼 보인다.

문제는 이러한 DIY 분산 접근 방식이 확장되지 않는다는 것이다. 클러스터가 성장함에 따라 로깅 도구를 사용하기 시작하고, 그 다음에는 트레이싱 도구, 그리고 컨슈머 랙을 감시하기 위한 커스텀 스크립트를 추가한다. 새로운 구성 요소가 추가될 때마다 새로운 숨겨진 비용이 발생한다:

- **엔지니어링 시간:** DIY 모니터링 파이프라인을 구축, 튜닝, 유지보수하는 것은 끝없는 순환이 된다.
- **라이선스 비용:** 대부분의 기업은 결국 기능이 중복되는 여러 도구를 채택한다. 각각의 관측 가능성 플랫폼에 대한 비용이 전체 비용에 합산된다.
- **인지적 부하:** 엔지니어들은 단일 Kafka 이슈를 디버깅하기 위해 4~7개의 서로 다른 도구를 오가야 한다.

"무료"로 시작한 것이 빠르게 엔지니어링 팀의 가장 큰 시간과 비용 낭비가 된다. Kafka 아키텍처에 대한 깊은 이해는 추적해야 할 복잡한 구성 요소가 얼마나 많은지를 보여주며, 이는 분산된 도구가 처리하기에 적합하지 않은 작업이다.

### Kafka 모니터링은 어떻게 비용을 증가시키는가?

일반적인 Kafka 모니터링 스택은 다음과 같다:

- 메트릭을 위한 Datadog 또는 New Relic
- 로그를 위한 Splunk/ELK
- 트레이싱을 위한 OpenTelemetry
- Kafka 랙을 위한 커스텀 스크립트

결국 동일한 데이터를 저장하기 위해 여러 벤더에 비용을 지불하게 된다. 하지만 숨겨진 비용은 단순한 라이선스 비용을 훨씬 넘어선다. 여러 도구와 수동 프로세스에 의존할 때, Kafka 모니터링의 숨겨진 비용은 빠르게 복합적으로 증가한다:

- **도구 난립과 라이선스 중복:** 많은 조직이 메트릭 플랫폼, 별도의 로깅 플랫폼, 그리고 APM 도구에 각각 비용을 지불한다. 이러한 도구들은 종종 기능이 겹치므로, 동일한 데이터를 저장하고 분석하기 위해 여러 벤더에 비용을 지불하는 셈이다.
- **수동 대시보드 구축 및 유지보수:** 그 "완벽한" Grafana 대시보드는 특정 시점의 스냅샷에 불과하다. 새로운 서비스가 온보딩되거나, 토픽이 재구성되거나, 브로커가 추가되는 순간 이미 쓸모없어진다. 플랫폼 엔지니어들은 주당 10~20%의 시간을 대시보드 관리인 역할에 소비한다.
- **알림 튜닝을 위한 높은 엔지니어링 오버헤드:** 대규모 클러스터에서 "정상"은 계속 변하는 목표이다. 엔지니어들은 종종 몇 달간 알림을 튜닝하지만, 규모가 변경되면 이 사이클을 반복해야 한다. 이 시간은 새로운 제품을 구축하는 데 사용되지 못한다.
- **놓친 신호로 인한 다운타임:** 이것이 가장 큰 비용이다. 분산된 도구들이 브로커 레이턴시의 급증과 컨슈머 랙의 증가를 상관관계로 연결하지 못할 때, 그 결과는 서비스 다운타임, 데이터 손실, 그리고 실질적인 매출 영향이다.

### 모니터링 비용이 폭증하는 이유: 규모 확장 시 Kafka 모니터링의 도전

단일 클러스터에서 작동하는 모니터링 전략은 10개 클러스터에 적용하면 완전히 실패한다. 비용과 복잡성은 단순히 더해지는 것이 아니라 기하급수적으로 복합된다. 그 방식은 다음과 같다:

- **대시보드는 선형적으로 확장되지 않는다:** 새로운 클러스터, 팀, 애플리케이션마다 고유한 대시보드, 알림, 구성이 필요하다. 수동 유지보수 부담은 시간이 지남에 따라 불균형적으로 증가한다.
- **스토리지 비용이 급등한다:** Kafka는 매우 많은 데이터를 생성한다. 대규모 클러스터는 하루에 수십억 개의 메트릭 데이터 포인트를 생성할 수 있다. 이러한 고카디널리티 데이터를 서드파티 관측 가능성 플랫폼에 저장하는 것은 매우 비싸며, 종종 최상위 클라우드 인프라 비용이 된다.

예를 들어, 200개의 토픽(각각 6개의 파티션)을 가진 5-브로커 클러스터는 스크레이프당 100,000~250,000개의 시계열 샘플을 쉽게 생성할 수 있다.

30초 스크레이프 간격에서:

- 하루 약 2억 8,800만 개 샘플
- 여러 클러스터에 걸쳐 곱하면 하루 수십억 개의 샘플

이것은 가장 높은 관측 가능성 비용 중 하나가 된다.

- **너무 많은 알림, 너무 적은 집중:** 메트릭 볼륨이 증가함에 따라 "노이즈"도 증가한다. 엔지니어들은 끊임없는 오탐(false positive) 스트림에 무감각해져서, 임박한 장애를 알리는 중요한 알림을 놓치기 쉬워진다.

규모 확장에서 Kafka를 성공적으로 운영하려면 클러스터와 함께 확장되는, 클러스터에 역행하지 않는 관측 가능성 전략이 필요하다.

### Kafka 비용을 높이는 일반적인 모니터링 함정

우리는 팀들이 동일한 비용이 많이 드는 함정에 빠지는 것을 본다. Kafka 모니터링에서 가장 흔한 실수는 거의 항상 잘못된 것을 모니터링하거나, 올바른 것을 잘못된 도구로 모니터링하는 경우이다.

- **무관한 메트릭의 과도한 모니터링:** 많은 팀이 브로커당 수천 개의 저수준 JMX 메트릭을 수집하고 저장한다. 이는 스토리지와 대시보드를 실행 가능한 인사이트를 제공하지 않는 "허영 메트릭"으로 넘치게 하여, 가치 없이 비용만 증가시킨다.
- **핵심 메트릭의 부족한 모니터링:** 반대로, 팀들은 실제로 비즈니스에 영향을 미치는 메트릭을 추적하지 못하는 경우가 많다. 가장 흔한 문제는 컨슈머 그룹 랙(데이터 신선도)과 파티션 편향(클러스터 핫스팟)이다. 효과적인 Kafka 랙 모니터링은 타협할 수 없는 필수 사항이지만, 종종 사후 고려사항으로 취급된다.
- **중앙 집중화된 관측 가능성의 부재:** 플랫폼 팀은 Grafana에서 브로커 메트릭을 보고, 애플리케이션 팀은 Splunk에서 로그를 보고, SRE(사이트 안정성 엔지니어)는 다른 도구에서 트레이스를 본다. 아무도 전체 그림을 볼 수 없어, 5분이면 해결할 문제가 5시간짜리 장애로 변한다.
- **사후 대응적 모니터링:** 대부분의 DIY 구성은 순전히 사후 대응적이다: 시스템이 이미 고장난 후에야 알림이 발생한다. 이 접근 방식은 "이 토픽은 48시간 내에 디스크 공간이 부족해질 것으로 예상된다"와 같은 사전 예방적 인사이트를 제공하지 못하며, 이러한 인사이트가 있었다면 장애를 완전히 예방할 수 있었을 것이다.

### 비효율적인 Kafka 모니터링의 비즈니스 영향

이러한 기술적 함정은 비즈니스에 직접적이고 측정 가능한 영향을 미치며, Kafka TCO를 청구서에 표시된 것보다 훨씬 넘어서 부풀리고(ROI는 감소시킨다). 실제 비즈니스 영향은 다음의 조합이다:

- **낭비되는 클라우드 및 스토리지 비용:** 하나 이상의 관측 가능성 플랫폼에서 중복되거나 가치가 낮은 메트릭을 수집, 저장, 쿼리하기 위해 프리미엄 가격을 지불한다.
- **엔지니어링 시간 손실:** 이것이 종종 가장 높은 비용이다. 가장 재능 있고 (비용이 높은) 엔지니어들이 새로운 기능과 제품을 제공하는 대신, 모니터링 파이프라인 유지보수와 알림 디버깅의 사후 대응적 루프에 갇히게 된다.
- **느린 대응 시간과 SLA 위약금:** 모니터링이 실패하면 평균 복구 시간(MTTR)이 급등한다. 이는 서비스 수준 계약(SLA) 위반, 불만족한 고객, 잠재적 매출 손실, 고객 이탈로 직접 이어진다.

제대로 모니터링되지 않는 Kafka 클러스터는 엔지니어링 시간만 비용이 드는 것이 아니라, 비즈니스 목표를 적극적으로 훼손하고 실제 Kafka TCO를 부풀린다.

- **도구 체인 통합:** 기존 모니터링 스택을 평가하고 여러 전문 도구를 더 포괄적이고 통합된 플랫폼으로 통합할 기회를 찾는다. 이는 라이선스를 간소화하고, 벤더 종속을 줄이며, 관리 오버헤드를 단순화하고, 인프라 및 교육 측면에서 규모의 경제를 종종 가져온다.
- **대시보드 및 알림 프로비저닝 자동화:** 정적이고 수동으로 구성된 값에만 의존하는 대신, 과거 데이터, 계절성, 또는 머신러닝 알고리즘에 기반하여 자동으로 조정되는 동적 또는 자동화된 알림 임계값을 구현한다. 이는 오탐(false positive)과 노이즈를 크게 줄여 엔지니어링 시간을 절약한다. 또한 알림의 정확성을 향상시켜 팀이 실제 이슈에 대해 더 효과적으로 알림을 받을 수 있게 한다.
- **모니터링을 거버넌스와 통합:** 모니터링 데이터와 알림을 기존 IT 거버넌스, 보안 사고 대응, 컴플라이언스 워크플로에 직접 내장한다. 이는 모니터링을 더 넓은 조직 프로세스의 원활한 일부로 만들어 운영 효율성을 향상시킨다. 보안 위협을 더 일찍 식별하고, 컴플라이언스를 보장하며, 감사 및 의사결정을 위한 더 풍부한 컨텍스트를 제공하여 궁극적으로 서로 다른 시스템을 관리하는 전체 비용을 줄일 수 있다.

### Kafka 모니터링 비용 - 자주 묻는 질문 (FAQ)

**Kafka 모니터링이란 무엇인가?**

Kafka 모니터링은 고가용성, 낮은 레이턴시, 전반적인 클러스터 안정성을 보장하기 위해 Kafka 브로커, 토픽, 프로듀서, 컨슈머의 상태와 성능을 추적하는 실천이다.

**Kafka 모니터링이 왜 그렇게 비용이 많이 드는가?**

Kafka 모니터링 비용은 도구 난립(중복되는 여러 라이선스), 높은 메트릭 스토리지 비용, 그리고 대시보드와 알림을 수동으로 구축, 유지보수, 튜닝하는 데 필요한 상당한 엔지니어링 오버헤드로 인해 특히 규모 확장 시 증가한다.

**Kafka에서 어떤 메트릭을 모니터링해야 하는가?**

많은 메트릭이 있지만, 가장 중요한 메트릭은 컨슈머 그룹 랙(데이터 신선도), 브로커 상태(디스크, CPU, 네트워크), 토픽/파티션 처리량(메시지 속도), 요청 레이턴시(프로듀서/컨슈머 성능)이다.

**Kafka 모니터링에서 흔한 실수는 무엇인가?**

흔한 실수로는 낮은 가치의 메트릭을 과도하게 모니터링하는 것(비용 증가), 랙 같은 중요한 메트릭을 부족하게 모니터링하는 것, 중앙 집중화된 뷰 없이 분산된 도구를 사용하는 것, 사전 예방적 인사이트 대신 사후 대응적 알림에 의존하는 것이 있다.

**Confluent는 어떻게 Kafka 모니터링 비용을 줄이는가?**

Confluent는 Confluent Cloud 내에서 완전 관리형 통합 관측 가능성 솔루션을 제공한다. 이는 사전 구축된 대시보드, 지능적인 알림, 기본 제공 엔드투엔드 가시성을 통해 도구 난립, 메트릭 스토리지 비용, 수동 유지보수를 제거하여 총소유비용(TCO)을 극적으로 낮춘다.

**Kafka 모니터링과 Kafka 관측 가능성의 차이점은 무엇인가?**

모니터링은 Kafka 클러스터의 상태를 추적하기 위해 사전 정의된 메트릭을 수집하고 분석하는 프로세스이다. 이는 사후 대응적이며, 디스크 공간 부족이나 컨슈머 지연 같은 발생할 수 있을 것으로 예상되는 이슈인 "알려진 것들(known-knowns)"에 초점을 맞춘다. 관측 가능성은 "세 가지 기둥"(메트릭, 로그, 트레이스)을 사용하여 시스템의 외부 출력을 통해 내부 상태를 이해하도록 돕는 더 전체론적인 접근 방식이다. 이는 사전 예방적이며, 분산 환경에서의 복잡하고 예측 불가능한 이슈인 "알려지지 않은 것들(unknown-unknowns)"을 디버깅하는 데 도움을 주도록 설계되었다.

이 차이를 Kafka에 적용하면, 모니터링은 Kafka 환경 내에서 Kafka 클러스터, 클라이언트 애플리케이션, IT 인프라에 영향을 미치는 무언가가 잘못되었다는 것을 아는 것이다. 반면에 Kafka 관측 가능성은 문제가 왜 발생하는지, 그리고 레이턴시를 줄이고, 확장성을 높이고, 데이터 손실을 방지하기 위한 올바른 아키텍처 및 구성 변경을 어떻게 할 수 있는지를 아는 것이다.

---

Apache, Apache Kafka, Kafka는 미국 및/또는 기타 국가에서 Apache Software Foundation의 등록 상표이다. 이러한 마크의 사용이 Apache Software Foundation의 승인을 의미하지는 않는다. 기타 모든 상표는 해당 소유자의 자산이다.

## Apache Kafka 스키마 관리가 생각보다 더 많은 비용을 초래하는 이유

> **원문:** [Why Managing Your Apache Kafka Schemas Is Costing You More Than You Think](https://www.confluent.io/blog/schema-management-costs/)

> **저자:** Mohtasham Sayeed Mohiuddin, Associate Solutions Architect, Confluent Staff | **게시일:** 2024년 12월 23일 | **읽는 시간:** 10분

---

이벤트 기반 시스템을 구축하는 개발자에게 스키마는 Apache Kafka에서 프로듀서와 컨슈머 간의 데이터 계약을 정의하는 데 필수적이며, 모든 메시지가 올바르게 해석될 수 있도록 보장합니다. 그러나 스키마 관리를 수동으로 또는 DIY(직접 구축) 솔루션을 통해 처리하면, 조직은 배포 규모가 커질수록 복합적으로 증가하는 비용에 직면하게 됩니다.

이 게시물에서는 수동 스키마 관리가 왜 비용 증가, 호환성 위험, 엔지니어링 오버헤드로 이어지는지 살펴보겠습니다. 이러한 문제는 초기 인프라 예산에는 나타나지 않는 방식으로 발생하는 경우가 많습니다.

### 스키마 관리는 어떻게 숨겨진 비용을 초래하는가?

Kafka 여정 초기에는 스키마를 수동으로 관리하는 실제 비용을 과소평가하기 쉽습니다. Kafka에서의 스키마 관리는 프로듀서와 컨슈머 간의 데이터 호환성을 보장합니다. 이는 스트리밍 데이터가 원활하게 흐르도록 유지하는 가드레일입니다. 그러나 조직이 확장됨에 따라, 스키마를 수동으로 처리하거나 임시 레지스트리를 유지하는 "단순한" 접근 방식은 빠르게 숨겨진 비용 센터가 됩니다.

처음에는 스키마를 수동으로 정의하고 진화시키는 것이 무해해 보일 수 있습니다. 여기에 JSON 하나, 저기에 Avro 하나. 그러나 더 많은 팀이 토픽 전반에 걸쳐 데이터를 발행하고 소비하게 되면, 모든 스키마 변경은 운영 위험을 초래합니다. 이제 각 수정 사항은 다운스트림 시스템을 깨뜨리지 않기 위해 조정, 검증, 버전 관리가 필요합니다. 이를 수십 개의 팀, 파이프라인, 환경에 걸쳐 곱하면, 총 엔지니어링 시간(과 위험)은 복합적으로 증가합니다.

Kafka용 중앙 집중식 스키마 레지스트리가 없으면 팀은 종종 다음과 같은 문제에 직면합니다:

- 프로듀서와 컨슈머가 서로 다른 속도로 진화할 때 발생하는 **호환성 장애**
- 통제되지 않는 스키마 진화로 인한 **데이터 불일치**
- 수동 스키마 검증 및 디버깅에서 오는 **운영 오버헤드**
- 데이터 구조가 중앙에서 관리되지 않을 때 증가하는 **컴플라이언스 노출**

대부분의 팀이 컴퓨팅이나 스토리지 비용 최적화에 집중하는 반면, Kafka에서의 스키마 진화가 숨겨진 재작업, 예상치 못한 다운타임, 개발자 생산성 저하를 통해 총 소유 비용(TCO)을 조용히 부풀릴 수 있다는 사실을 깨닫는 팀은 거의 없습니다.

반면, Confluent Schema Registry와 같은 도구를 통해 이 프로세스를 중앙 집중화하고 자동화하면 즉각적인 투자 수익(ROI)을 얻을 수 있습니다: 더 적은 프로덕션 이슈, 더 빠른 개발 주기, 더 강력한 데이터 거버넌스.

### DIY 스키마 관리의 숨겨진 비용은 무엇인가?

자체 Kafka 스키마 관리 프로세스를 구축하는 것은 처음에는 쉬운 승리처럼 느껴질 수 있지만, DIY 접근 방식은 데이터 생태계가 성숙해짐에 따라 확장되는 비효율성의 거미줄을 숨기고 있는 경우가 많습니다. 비용이 항상 즉각적으로 나타나지는 않지만, 엔지니어링, 운영, 컴플라이언스 전반에 걸쳐 축적되며 Kafka TCO를 직접적으로 부풀립니다.

아래는 스키마 관리를 수동으로 또는 일관되지 않게 처리할 때 발생하는 네 가지 주요 숨겨진 비용입니다:

- **수동 검증은 엔지니어링 시간 낭비로 이어집니다:** 개발자가 스키마 변경을 수동으로 검증할 때, 호환성 확인, 프로듀서와 컨슈머 통합 테스트, 다운스트림 애플리케이션 업데이트 등 반복적인 작업에 귀중한 시간을 소비합니다. 이러한 수동 단계는 확장되지 않으며 혁신에서 초점을 빼앗습니다. 시간이 지나면 이는 생산성 손실과 더 높은 인건비로 이어집니다.

- **호환성 문제는 장애와 소방 대응으로 이어집니다:** 내장된 스키마 호환성 검사가 없으면, 필드 이름 변경이나 데이터 타입 변경과 같은 작은 변경도 프로덕션에서 컨슈머를 깨뜨릴 수 있습니다. 이러한 인시던트는 파이프라인 다운타임, 디버깅 마라톤, SLA 지연으로 이어집니다. 소방 대응에 투입되는 매 시간은 비즈니스 가치 손실의 또 다른 시간입니다.

- **스키마 드리프트는 데이터 손상과 재처리로 이어집니다:** "스키마 드리프트"는 중앙 집중식 감독 없이 데이터가 진화할 때 발생합니다. 동일한 스키마의 일관되지 않은 버전은 손상된 데이터, 깨진 분석, 비용이 많이 드는 재처리 작업으로 이어질 수 있습니다. 팀은 일관성을 복원하기 위해 테라바이트의 데이터를 다시 수집하거나 정리해야 할 수도 있으며, 이는 운영 효율성과 클라우드 스토리지 예산에 직접적인 타격을 줍니다.

- **분절된 거버넌스는 컴플라이언스 및 감사 위험을 증가시킵니다:** 스키마가 Git 리포지토리, 스프레드시트 또는 개별 서비스에 존재할 때, 거버넌스를 적용하거나 추적성을 보장하는 것은 거의 불가능해집니다. 누락된 문서화와 버전 격차는 감사를 고통스럽게 만들어, 컴플라이언스 위험과 법적 노출을 증가시킵니다. 특히 계보와 구조가 중요한 금융 서비스와 같은 규제 산업에서 더욱 그렇습니다.

이러한 비효율성은 엔지니어링 속도와 재무 성과를 조용히 갉아먹습니다. Confluent Schema Registry와 같은 중앙 집중식 레지스트리를 통해 거버넌스를 중앙 집중화하면, 조직은 데이터 스트림 전반에 걸쳐 호환성을 보장하고, 드리프트를 최소화하며, 스키마 검증을 자동화하여 이러한 비용 함정이 확장되기 전에 방지할 수 있습니다.

#### 스키마 드리프트는 어떻게 Kafka TCO를 부풀리는가?

스키마 드리프트는 Kafka 스키마 관리에서 가장 과소평가된 비용 동인 중 하나입니다. Kafka 환경에서 이것이 발생하면, 동일한 토픽에 대해 서로 다른 프로듀서나 환경이 일치하지 않는 스키마 버전을 사용하고 있다는 것을 의미합니다.

스키마는 종종 분산된 소유권, 수동 프로세스 또는 불량한 버전 관리로 인해 일관되지 않게 진화합니다. 이것은 누락된 필드나 변경된 데이터 타입과 같은 작은 불일치로 시작될 수 있지만, 다운스트림 결과는 전체 데이터 흐름을 통해 파급됩니다. 시간이 지남에 따라, 예상치 못한 데이터 구조 변경의 축적은 데이터에 대한 신뢰를 침식하고, 팀 간의 마찰을 만들며, 비용을 크게 부풀립니다.

스키마 드리프트가 데이터 파이프라인 전반에 걸쳐 숨겨진 비용을 유발하는 네 가지 방법을 분석해 보겠습니다:

##### 비용이 많이 드는 데이터 재처리

호환되지 않는 스키마가 컨슈머에 도달하면, 파이프라인은 종종 조용히 실패하거나 잘못된 형식의 레코드를 생성합니다. 그러면 팀은 일관성을 복원하기 위해 며칠 동안 과거 데이터를 재처리하는 데 시간을 소비합니다. 이는 내장된 스키마 진화 제어로 피할 수 있었을 컴퓨팅, 스토리지, 엔지니어링 시간을 소모합니다.

##### 깨진 파이프라인 디버깅

단일 스키마 불일치는 여러 다운스트림 시스템을 깨뜨릴 수 있습니다. 근본 원인을 감지하는 것은 거의 간단하지 않습니다. 엔지니어는 로그, 스키마 버전, 컨슈머 코드를 추적해야 합니다. 이러한 반응적 디버깅은 장기간의 다운타임, SLA 위반, 개발자 생산성 손실로 이어집니다.

##### 비즈니스 다운타임과 데이터 접근 불가

스키마 드리프트는 단지 기술 부채만 유발하는 것이 아닙니다. 비즈니스 운영을 방해합니다. 분석 대시보드나 머신러닝 모델이 손상된 스트림에 의존할 때, 의사결정자는 실시간 인사이트에 대한 접근을 잃게 됩니다. 데이터 사용 불가의 매 시간은 실질적인 비즈니스 손실로 이어집니다.

##### 인프라 비용 증가

잦은 재처리, 중복 데이터를 위한 추가 스토리지, 반복적인 수집 주기 모두 클라우드 비용에 추가됩니다. 사소해 보이는 스키마 실수가 컴퓨팅 비용을 배로 늘리고 연간 수천 달러씩 TCO를 부풀릴 수 있습니다.

스키마 드리프트는 특히 변경 데이터 캡처(CDC) 파이프라인에 영향을 미칩니다. 여기서 데이터베이스 스키마 변경은 Kafka를 통해 다운스트림 시스템으로 올바르게 전파되어야 합니다. 단일 호환되지 않는 CDC 이벤트가 전체 데이터 동기화 프로세스를 중단시킬 수 있습니다.

### Kafka 스키마 관리에서 피해야 할 일반적인 실수는 무엇인가?

조직들은 동일한 스키마 관리 오류를 반복적으로 범하며, 각 오류는 운영 비용 증가에 기여합니다:

**호환성 모드를 적용하지 않는 것**이 가장 빈번한 실수입니다. 호환성 모드(예: 역방향, 순방향, 전체, 없음)는 어떤 스키마 변경이 허용되는지를 정의합니다. 테스트와 적용 규칙 없이, 개발자는 부주의하게 파괴적인 변경을 배포합니다. 해결책은 간단해 보입니다. 적용을 추가하면 됩니다. 그러나 조직이 필요성을 인식할 때쯤이면, 수백 개의 호환되지 않는 스키마가 이미 프로덕션에 존재합니다.

**각 팀이 독립적으로 스키마를 정의하도록 두면** 조직적 사일로가 생깁니다. 결제 팀은 타임스탬프를 문자열로 사용하고, 재고 팀은 에포크 밀리초를 사용합니다. 둘 다 같은 개념을 다르게 표현하여, 다운스트림 컨슈머가 여러 형식을 처리하도록 강제합니다. 이 분절화는 교차 기능 데이터 제품을 구축하는 것을 기하급수적으로 어렵게 만듭니다.

**레지스트리 대신 임시로 스키마를 저장하면** 중앙 집중식 거버넌스의 가능성이 완전히 사라집니다. 스키마는 애플리케이션 코드, 구성 파일, 위키, 개발자 노트북에 흩어져 있습니다. 버전 관리가 불가능해집니다. 프로덕션에서 실제로 실행 중인 스키마 버전을 발견하려면 여러 시스템에 걸친 탐정 작업이 필요합니다.

**스키마 변경에 대한 모니터링 부재**는 컨슈머가 실패할 때까지 팀이 호환성 문제가 발생했는지 알지 못한다는 것을 의미합니다. 스키마 진화 패턴에 대한 가시성이 없으면, 조직은 위험한 관행을 식별하거나 팀에 적절한 절차를 교육할 수 없습니다.

Kafka 개발자 모범 사례를 따르면 이러한 함정이 개발 문화에 내재되어 비즈니스에 영향을 미치기 전에 피할 수 있습니다.

#### 부실한 스키마 관리의 비즈니스 영향

부적절한 스키마 관리의 기술적 비용은 결국 경영진이 주목하는 비즈니스 수준의 재무적 영향으로 이어집니다:

##### 개발자 생산성 손실이 더 높은 인재 비용을 유발

개발자가 수동으로 스키마를 검증하거나, 컨슈머 장애를 디버깅하거나, 데이터 불일치를 조정할 때마다 팀의 효율성이 떨어집니다. 새로운 기능을 구축하는 대신 소방 대응에 나서고 있는 것입니다. 1년에 걸쳐 이러한 비효율성은 팀당 수백 시간의 엔지니어링 시간 낭비로 누적될 수 있으며, 이는 혁신을 가속화할 수 있었을 시간입니다.

##### 장애로 인한 SLA 위약금과 수익 손실

단일 호환되지 않는 스키마가 중요한 프로덕션 파이프라인을 깨뜨릴 수 있습니다. 데이터 기반 비즈니스의 경우, 단 한 시간의 다운타임도 분석을 지연시키고, 고객 경험에 영향을 미치거나, 수익을 창출하는 서비스를 중단시킬 수 있습니다. 이러한 숨겨진 장애는 가동 시간 손실과 계약상 SLA 위약금을 통해 조용히 Kafka TCO를 부풀립니다.

##### 컴플라이언스 및 감사 위험 비용 증가

중앙 집중식 스키마 거버넌스가 없으면, 데이터 계보와 구조적 변경을 추적하는 것이 거의 불가능해집니다. 이러한 가시성 부족은 특히 데이터 추적성과 구조적 무결성이 요구되는 GDPR이나 HIPAA와 같은 규정하에서 주요 컴플라이언스 과제를 제기합니다. 시정 조치나 벌금의 비용은 적절한 거버넌스 비용을 훨씬 초과합니다.

### Confluent Schema Registry는 어떻게 Kafka TCO를 줄이는가?

잘못 관리하면, 스키마 관리는 조용히 데이터 인프라에서 가장 비용이 많이 들고 오류가 발생하기 쉬운 부분 중 하나가 될 수 있습니다. Confluent Schema Registry를 사용하면 검증을 확장 가능하게 자동화하고, 호환성을 적용하며, 엔드투엔드 스키마 거버넌스를 제공할 수 있습니다. 이 모든 것이 총 소유 비용(TCO)을 극적으로 줄여줍니다.

DIY 스키마 관리 접근 방식과 비교했을 때 Confluent Schema Registry를 사용하면 어떻게 측정 가능한 비즈니스 및 운영 효율성을 제공하는지 정확히 분석해 보겠습니다.

- **중앙 집중식 레지스트리 사용으로 DIY 난립을 제거합니다:** 팀, 리포지토리 또는 서비스 전반에 걸쳐 스키마를 저장하는 대신, Confluent Schema Registry는 모든 데이터 정의에 대한 단일 진실 원천 역할을 합니다. 중앙 집중화는 중복을 제거하고, 일관성을 보장하며, 프로듀서와 컨슈머 전반에 걸쳐 즉각적인 스키마 발견을 가능하게 합니다. 이는 여러 분절된 도구나 맞춤형 스키마 저장소를 유지하는 비용을 제거합니다.

- **내장된 호환성 검사로 비용이 많이 드는 파손을 방지합니다:** Confluent는 배포 전에 기존 버전에 대해 스키마 변경을 자동으로 검증합니다. 이러한 사전 호환성 적용은 데이터 손상과 다운스트림 장애를 방지하여 재처리, 디버깅, 프로덕션 복구에 드는 시간을 절약합니다.

- **거버넌스 및 감사 제어로 컴플라이언스 비용을 줄입니다:** Confluent의 스키마 거버넌스를 통해 조직은 스키마 진화를 추적하고, 소유권을 관리하며, 네이밍이나 구조 규약을 대규모로 적용할 수 있습니다. 감사 추적과 버전 이력은 컴플라이언스 감사를 더 빠르게 만들고 위약금 위험을 줄여줍니다. 거버넌스는 더 이상 수동이 아닙니다. 스트리밍 플랫폼에 내장되어 있습니다.

- **완전 관리형 거버넌스로 운영 오버헤드를 줄입니다:** 클라우드에서 Kafka를 실행하는 팀에게 Confluent Cloud는 Schema Registry를 완전 관리형 서비스로 제공합니다. 설정, 유지보수, 스케일링 고민이 필요 없습니다. 이는 DevOps 부담을 줄이고, 다운타임 위험을 제거하며, 예측 가능한 성능을 보장하여 운영 비용과 관리 복잡성을 모두 낮춥니다.

#### DIY 스키마 관리 vs Confluent로 스키마 관리

| 측면 | DIY 스키마 관리 | Confluent Schema Registry |
|------|----------------|--------------------------|
| 검증 | 수동 코드 리뷰 | 자동화된 호환성 검사 |
| 저장소 | 리포지토리 전반에 흩어짐 | 중앙 집중식 레지스트리 |
| 거버넌스 | 맞춤형 도구 필요 | 내장된 감사 로그 및 접근 제어 |
| 운영 | 자체 관리 인프라 | 완전 관리형 서비스 |
| 비용 모델 | 엔지니어링 시간에 숨겨져 있음 | 예측 가능한 구독 |
| 장애 모드 | 프로덕션 장애 | 프로덕션 전 검증 오류 |

수동 스키마 관리를 제거함으로써, Confluent는 팀이 비용을 확장하지 않고도 자신감 있게 확장할 수 있도록 지원합니다.

### 스키마 관리 비용을 줄이기 위한 모범 사례

이러한 사례를 구현하면 레지스트리 솔루션에 관계없이 스키마 관련 운영 비용을 줄일 수 있습니다:

- **중앙 집중식 레지스트리 사용:** 항상 단일 레지스트리에서 스키마를 저장하고 관리하십시오. 여러 리포지토리나 서비스에 분산시키지 마십시오. Kafka용 스키마 레지스트리는 권위 있는 진실 원천 역할을 하여 모든 프로듀서와 컨슈머가 정렬된 상태를 유지합니다. 중앙 집중화는 중복을 제거하고 팀 간 스키마 발견을 단순화합니다.

- **기본적으로 호환성 모드 적용:** 명확한 호환성 정책(예: 역방향, 순방향 또는 전체)을 정의하고 자동으로 적용하십시오. 이는 호환되지 않는 스키마 변경이 기존 컨슈머를 깨뜨리는 것을 방지하여 비용이 많이 드는 장애와 재처리 주기를 줄여줍니다.

- **스키마 변경을 지속적으로 모니터링:** 스키마 모니터링을 CI/CD 파이프라인에 통합하십시오. 알림과 감사 로그를 통해 무단 또는 위험한 스키마 변경을 조기에 감지하여 프로덕션 서프라이즈를 피할 수 있습니다. 사전 모니터링은 반응적 디버깅에 드는 수많은 시간을 절약합니다.

- **스키마 거버넌스를 컴플라이언스 정책과 정렬:** 스키마 레지스트리는 개발자만을 위한 것이 아닙니다. 거버넌스 도구입니다. 네이밍 규약을 적용하고, 데이터 계보를 추적하며, 감사 준비가 된 스키마 이력을 제공하는 데 사용하십시오. Confluent의 중앙 집중식 스키마 거버넌스는 추가 오버헤드 없이 조직의 컴플라이언스를 보장합니다.

- **검증 및 버전 관리 자동화:** 수동 스키마 검증은 인적 오류에 취약합니다. Confluent Schema Registry와 같은 도구를 사용하여 검증 단계를 자동화하십시오. 이 도구는 내장된 버전 관리, 검증 API, 호환성 적용을 제공합니다. 자동화는 반복적인 수동 작업을 제거하고 진화를 예측 가능하게 유지합니다.

- **팀에 스키마 진화 사례 교육:** 엔지니어링 팀 전반에 걸쳐 일관된 스키마 진화 원칙을 촉진하십시오. 개발자가 호환성 모드, 폐기 전략, 레지스트리 워크플로우를 이해하도록 교육하면 장기적인 효율성이 보장되고 스키마 관련 이슈가 줄어듭니다.

#### 지금 바로 스키마 관리를 단순화하세요

스키마 관리는 데이터 전략에서 숨겨진 비용이 되어서는 안 됩니다. Confluent Cloud의 Schema Registry와 전체 Stream Governance 제품군을 통해, 수동 검증을 제거하고, 데이터 드리프트를 방지하며, 모든 Kafka 데이터 스트림에 걸쳐 호환성을 보장할 수 있습니다. 이 모든 것이 Kafka TCO를 낮추면서 가능합니다.

Confluent Cloud 무료로 시작하여 빌드를 시작하세요. 플랫폼에는 $400의 크레딧, 관리형 Kafka 클러스터, 스트림 처리 기능, 사전 구축된 커넥터가 포함되어 있습니다. 인프라 복잡성 없이 첫 번째 실시간 앱을 만드는 데 필요한 모든 것이 갖춰져 있습니다.

### 스키마 관리 FAQ

#### Kafka에서 스키마 관리란 무엇인가?

Kafka에서의 스키마 관리는 토픽을 통해 흐르는 메시지의 구조를 정의하고, 저장하고, 버전 관리하고, 검증하는 것을 포함합니다. 프로듀서와 컨슈머가 데이터 형식에 합의하도록 보장하여 역직렬화 실패와 데이터 손상을 방지합니다. 효과적인 스키마 관리에는 호환성 규칙 적용, 버전 이력 유지, 스키마 정의에 대한 중앙 집중식 접근 제공이 포함됩니다.

#### 수동 스키마 관리는 왜 비용이 많이 드는가?

수동 스키마 관리는 호환성 검증, 배포 조정, 파괴적 변경으로 인한 프로덕션 인시던트 소방 대응에 엔지니어링 시간을 소비합니다. 손상된 데이터 재처리, 장애 대응, 맞춤형 거버넌스 도구 구축에 숨겨진 비용을 만들어냅니다. 조직은 일반적으로 이러한 비용을 과소평가하는데, 이는 단일 항목으로 나타나기보다 많은 팀과 인시던트에 분산되어 있기 때문입니다.

#### 스키마 드리프트의 위험은 무엇인가?

스키마 드리프트는 서로 다른 서비스가 충돌하는 스키마 버전을 사용함에 따라 시스템 전반에 걸쳐 호환되지 않는 데이터 형식을 만들어냅니다. 위험에는 컨슈머가 메시지를 역직렬화할 수 없을 때 발생하는 프로덕션 장애, 비용이 많이 드는 재처리를 필요로 하는 데이터 손상, 잘못된 비즈니스 인사이트를 생성하는 실패한 분석 쿼리, PII 추적이 불가능해질 때의 컴플라이언스 위반이 포함됩니다. 스키마 드리프트는 팀이 조율되지 않은 변경을 함에 따라 시간이 지날수록 복합적으로 악화됩니다.

#### Confluent Schema Registry는 어떻게 TCO를 낮추는가?

Confluent Schema Registry는 수동 엔지니어링 작업이 필요했을 검증을 자동화하고, 사전 배포 호환성 검사를 통해 프로덕션 장애를 방지하고, 자체 관리 인프라의 운영 오버헤드를 제거하며, 컴플라이언스 비용을 줄이는 내장 거버넌스 기능을 제공함으로써 총 소유 비용을 낮춥니다. 반응적 소방 대응에서 사전 예방으로의 전환은 엔지니어링 시간의 직접 비용과 기회 비용을 모두 줄여줍니다.

#### Confluent Schema Registry를 사용하면 스키마 관리를 위한 다른 Kafka 도구가 여전히 필요한가?

Confluent Schema Registry가 Kafka에서 스키마 관리의 산업 표준이지만, 전문적인 프로덕션 환경에서 유일하게 사용하는 도구인 경우는 드뭅니다. CI/CD 통합, 가시성, 고급 거버넌스를 위한 도구로 보완할 필요가 있을 것입니다.

예를 들어, Schema Registry를 Maven/Gradle 플러그인, Confluent CLI 또는 코드 생성 도구와 결합하면 Schema Registry의 REST API를 수동으로 사용하는 복잡성을 피할 수 있습니다. 또한 데이터 계약에 대한 사람이 읽을 수 있는 뷰를 얻기 위해 모니터링 및 데이터 포털 도구를 사용하는 것이 좋습니다.

Confluent를 선택하면, Confluent Cloud의 완전 관리형 거버넌스 제품군인 Stream Governance의 일부인 데이터 카탈로그와 데이터 계보 추적기인 Data Portal과 Stream Lineage를 활용할 수 있습니다. 바닐라 Kafka를 실행하는 경우, 스키마를 시각화하고 프로듀서가 등록된 ID와 일치하는 데이터를 전송하는지 확인하는 데 사용할 수 있는 서드파티 Kafka 콘솔 UI가 있습니다.

#### Schema Registry와 스키마 스토리지의 차이점은 무엇인가?

스키마 스토리지는 단순히 스키마 정의를 영속합니다. 이는 종종 코드 리포지토리나 구성 관리 시스템에 저장됩니다. Schema Registry는 능동적인 검증, 호환성 검사, 버전 관리, 런타임 스키마 해석을 제공합니다. 스토리지가 수동적인 반면, 레지스트리는 규칙을 능동적으로 적용하고 프로듀서 및 컨슈머와 통합하여 호환성 문제가 프로덕션에 도달하기 전에 방지합니다.

---

Apache, Apache Kafka 및 Kafka는 미국 및/또는 기타 국가에서 Apache Software Foundation의 등록 상표입니다. Apache Software Foundation이 이러한 마크의 사용을 보증하는 것은 아닙니다. 기타 모든 상표는 해당 소유자의 자산입니다.

## 실시간 데이터 스트리밍의 진정한 비용

>
> **저자:** Quincy Perera, Confluent
>
> **게시일:** 2025년

---

### 소개

실시간 데이터 스트리밍은 현대 기업이 비즈니스를 운영하는 방식을 근본적으로 변화시키고 있다. 고객 경험 개인화부터 실시간 사기 탐지, 운영 인텔리전스에 이르기까지, 데이터가 발생하는 즉시 이를 처리하고 활용하는 능력은 더 이상 선택이 아닌 필수가 되었다. 그러나 많은 조직이 실시간 데이터 스트리밍 인프라를 구축하고 운영하는 데 드는 **진정한 비용**(true cost)을 제대로 이해하지 못한 채 프로젝트를 시작하고 있다.

이 블로그 포스트에서는 실시간 데이터 스트리밍의 총 소유 비용(Total Cost of Ownership, TCO)을 구성하는 다양한 요소를 심층적으로 살펴본다. 라이선스 비용이나 인프라 비용 같은 직접적인 비용뿐만 아니라, 운영 오버헤드, 기회비용, 숨겨진 비용까지 포괄적으로 분석하여, 조직이 더 나은 의사결정을 내릴 수 있도록 돕고자 한다.

---

### 빙산의 일각: 눈에 보이는 비용

많은 조직이 데이터 스트리밍의 비용을 평가할 때 가장 먼저 보는 것은 인프라 비용과 소프트웨어 라이선스 비용이다. 그러나 이것은 빙산의 일각에 불과하다.

#### 인프라 비용

인프라 비용에는 다음이 포함된다:

- **컴퓨팅(Compute):** Kafka 브로커, ZooKeeper(또는 KRaft 컨트롤러), Connect 워커, 스트림 처리 애플리케이션 등을 실행하기 위한 서버 또는 클라우드 인스턴스
- **스토리지(Storage):** 메시지 로그를 저장하기 위한 고성능 디스크. 데이터 보존 기간과 복제 계수에 따라 필요한 스토리지 용량이 크게 달라진다.
- **네트워크(Network):** 데이터 센터 간 데이터 복제, 클라이언트와 브로커 간의 데이터 전송, 크로스 리전(cross-region) 트래픽 등에 따른 네트워크 비용

클라우드 환경에서는 이러한 비용이 사용량에 따라 청구되지만, 실제 운영 시 예상보다 훨씬 빠르게 증가하는 경우가 많다. 특히 데이터 볼륨이 성장함에 따라 스토리지와 네트워크 비용이 기하급수적으로 늘어날 수 있다.

#### 소프트웨어 라이선스 비용

오픈 소스 Apache Kafka 자체는 무료이지만, 프로덕션 환경에서 필요한 엔터프라이즈 기능들은 추가 비용이 발생할 수 있다:

- 상용 Kafka 배포판 라이선스
- 모니터링 및 관리 도구
- 보안 기능(RBAC, 감사 로깅 등)
- 커넥터 라이선스

---

### 수면 아래: 숨겨진 비용

실시간 데이터 스트리밍의 진정한 비용 대부분은 수면 아래에 숨어 있다. 이러한 비용은 종종 초기 예산 책정 시 과소평가되거나 완전히 간과되지만, 장기적으로 총 소유 비용의 가장 큰 부분을 차지하는 경우가 많다.

#### 인력 비용

Kafka 클러스터를 프로덕션 수준으로 운영하려면 전문 인력이 필요하다. 이는 가장 큰 숨겨진 비용 중 하나다.

- **Kafka 전문 엔지니어:** Kafka의 내부 동작 원리를 깊이 이해하고, 성능 튜닝, 문제 해결, 용량 계획 등을 수행할 수 있는 전문가가 필요하다. 이러한 인재는 시장에서 높은 보수를 요구하며, 채용 자체가 어려울 수 있다.
- **인프라/DevOps 엔지니어:** 클러스터 프로비저닝, 자동화, CI/CD 파이프라인 구축, 인프라 관리를 담당할 엔지니어가 필요하다.
- **보안 전문가:** 데이터 스트리밍 환경의 보안을 관리할 인력이 필요하다.
- **온콜(On-call) 지원:** 24/7 운영 환경에서는 야간 및 주말 온콜 로테이션이 필요하며, 이는 추가적인 인력 비용과 직원 피로도를 유발한다.

일반적으로 셀프 매니지드 Kafka 클러스터를 프로덕션에서 운영하려면 최소 2-3명의 전담 엔지니어가 필요하며, 규모가 커지면 그 이상이 요구된다. 이러한 인력의 연간 보수만으로도 수억 원에 달할 수 있다.

#### 운영 오버헤드

Kafka 클러스터의 일상적인 운영에는 수많은 작업이 수반된다:

##### 클러스터 관리

- **브로커 추가 및 제거:** 용량 변화에 따라 브로커를 추가하거나 제거해야 하며, 이때 파티션 재분배(partition reassignment)가 필요하다.
- **롤링 업그레이드:** Kafka 버전 업그레이드는 데이터 손실 없이 수행되어야 하며, 각 브로커를 순차적으로 업그레이드하는 롤링 방식이 일반적이다. 이 과정은 클러스터 규모에 따라 수 시간에서 수일이 걸릴 수 있다.
- **파티션 리밸런싱:** 브로커 간 부하를 균등하게 분배하기 위한 파티션 리밸런싱은 복잡하고 시간이 많이 소요되는 작업이다.
- **설정 변경:** 성능 최적화를 위한 다양한 파라미터 조정이 지속적으로 필요하다.

##### 모니터링 및 문제 해결

- **모니터링 인프라 구축:** Prometheus, Grafana, 또는 상용 모니터링 도구를 설정하고 유지 관리해야 한다.
- **대시보드 구성:** 핵심 메트릭에 대한 대시보드와 알림을 구성하고 지속적으로 업데이트해야 한다.
- **문제 진단:** 성능 저하, Consumer 지연(lag) 증가, 디스크 용량 부족 등의 문제를 신속하게 진단하고 해결해야 한다. 이를 위해서는 깊은 Kafka 지식이 필요하다.

##### 보안 관리

- **인증 및 인가(Authentication & Authorization):** SASL, TLS, ACL 등을 설정하고 관리해야 한다.
- **인증서 관리:** TLS 인증서의 생성, 배포, 갱신을 자동화해야 한다.
- **감사 로깅:** 규제 준수를 위한 감사 로그를 수집하고 관리해야 한다.
- **취약점 패치:** 보안 취약점이 발견될 때 신속하게 패치를 적용해야 한다.

#### 다운타임 비용

계획되지 않은 다운타임은 실시간 데이터 스트리밍 시스템에서 막대한 비용을 초래할 수 있다:

- **직접적인 매출 손실:** 실시간 시스템이 다운되면 트랜잭션 처리가 중단되어 직접적인 매출 손실이 발생한다.
- **고객 신뢰 하락:** 서비스 중단은 고객 경험을 저해하고, 장기적으로 고객 이탈을 초래할 수 있다.
- **SLA(Service Level Agreement) 위반 패널티:** 내부 또는 외부 SLA를 위반하면 금전적 패널티가 발생할 수 있다.
- **복구 비용:** 다운타임 발생 후 시스템을 정상 상태로 복구하는 데 드는 엔지니어링 시간과 비용

#### 기회비용

셀프 매니지드 Kafka 인프라를 운영하는 데 소요되는 시간과 리소스는 본질적으로 기회비용이다:

- **혁신 지연:** 인프라 운영에 투입되는 엔지니어링 리소스는 새로운 비즈니스 기능 개발에 사용할 수 없다.
- **시장 진입 시간(Time-to-Market) 증가:** 인프라 구축과 관리에 시간이 소요되면서 새로운 데이터 제품과 서비스의 출시가 지연된다.
- **기술 부채 누적:** 바쁜 운영 일정 속에서 장기적인 개선 작업이 후순위로 밀리면서 기술 부채가 누적된다.

### 규모에 따른 비용 변화

데이터 스트리밍 환경이 성장함에 따라 비용 구조도 변화한다. 초기에는 소규모 클러스터로 시작하지만, 사용 사례가 늘어나고 데이터 볼륨이 증가하면 비용이 비선형적으로 증가하는 경우가 많다.

#### 데이터 볼륨 증가

- 데이터 볼륨이 증가하면 더 많은 브로커, 더 큰 스토리지, 더 높은 네트워크 대역폭이 필요하다.
- 복제 계수(replication factor)를 고려하면, 실제 필요한 스토리지는 데이터 볼륨의 3배(일반적인 복제 계수 3 기준)에 달한다.
- 보존 기간이 길어질수록 스토리지 비용은 더욱 증가한다.

#### 사용 사례 확산

- 하나의 Kafka 클러스터가 성공적으로 운영되면, 조직 내 다른 팀들도 Kafka를 활용하고 싶어한다.
- 이에 따라 토픽 수, Consumer 그룹 수, 커넥터 수가 증가하며, 멀티 테넌시(multi-tenancy) 관리의 복잡성이 급격히 높아진다.
- 각 팀의 서로 다른 SLA 요구사항, 보안 정책, 성능 요구사항을 동시에 만족시켜야 한다.

#### 멀티 클러스터 / 멀티 리전

- 비즈니스가 성장하면 단일 클러스터에서 멀티 클러스터, 나아가 멀티 리전 배포로 확장해야 할 수 있다.
- 클러스터 간 데이터 복제, 글로벌 토픽 관리, 재해 복구(DR) 설정 등은 복잡성과 비용을 크게 증가시킨다.

### 자체 구축(DIY) vs. 완전 관리형 서비스

실시간 데이터 스트리밍의 비용을 평가할 때, 자체 구축(DIY)과 완전 관리형 서비스 간의 비교는 필수적이다.

#### 자체 구축(DIY) 접근법

자체 구축 접근법을 선택하면 다음과 같은 작업을 조직이 직접 수행해야 한다:

- **인프라 프로비저닝 및 관리:** 서버 또는 클라우드 인스턴스 프로비저닝, 운영 체제 구성, 네트워크 설정
- **Kafka 설치 및 설정:** Kafka 클러스터 설치, 초기 설정, 보안 구성
- **모니터링 스택 구축:** 모니터링, 알림, 대시보드를 위한 별도의 인프라와 도구 구축
- **운영 자동화:** 배포, 확장, 백업, 복구 등을 위한 자동화 스크립트 및 도구 개발
- **지속적인 유지 관리:** 버전 업그레이드, 패치 적용, 성능 튜닝, 용량 계획
- **전문 인력 확보:** 위의 모든 작업을 수행할 Kafka 전문 엔지니어 채용 및 유지

이러한 모든 작업을 합산하면, 셀프 매니지드 Kafka의 TCO는 인프라 비용의 3배에서 5배에 달할 수 있다.

#### 완전 관리형 서비스 접근법

Confluent Cloud와 같은 완전 관리형 서비스를 사용하면:

- **인프라 관리 제거:** 클러스터 프로비저닝, 확장, 패치, 업그레이드 등의 인프라 관리 부담이 사라진다.
- **운영 부담 최소화:** 자동 스케일링, 셀프 밸런싱, 자동 업그레이드 등으로 운영 부담이 크게 줄어든다.
- **보안 내장:** 암호화, 인증, 인가, 감사 로깅 등이 기본으로 제공된다.
- **모니터링 내장:** 별도의 모니터링 인프라를 구축할 필요 없이 내장된 모니터링과 알림 기능을 사용할 수 있다.
- **사용량 기반 과금:** 실제 사용량에 따라 과금되어, 초기 대규모 투자 없이 시작할 수 있다.
- **인력 재배치:** 인프라 운영에 투입되던 엔지니어를 비즈니스 가치를 창출하는 애플리케이션 개발에 재배치할 수 있다.

### TCO 비교 프레임워크

조직이 실시간 데이터 스트리밍의 TCO를 정확하게 평가하기 위해 다음과 같은 프레임워크를 사용할 수 있다.

#### 직접 비용(Direct Costs)

| 항목 | 자체 구축(DIY) | 완전 관리형 |
|------|---------------|------------|
| 컴퓨팅 | 서버/인스턴스 비용 | 서비스 요금에 포함 |
| 스토리지 | 디스크/EBS 비용 | 서비스 요금에 포함 |
| 네트워크 | 데이터 전송 비용 | 데이터 전송 비용 |
| 소프트웨어 라이선스 | 오픈 소스(무료) 또는 상용 | 서비스 요금에 포함 |

#### 간접 비용(Indirect Costs)

| 항목 | 자체 구축(DIY) | 완전 관리형 |
|------|---------------|------------|
| 전문 인력 | 2-3명 이상 전담 필요 | 최소화 |
| 운영 오버헤드 | 높음 | 매우 낮음 |
| 모니터링 인프라 | 별도 구축 필요 | 내장 |
| 보안 관리 | 직접 구현/관리 | 내장 |
| 교육/학습 비용 | 높음 | 낮음 |

#### 위험 비용(Risk Costs)

| 항목 | 자체 구축(DIY) | 완전 관리형 |
|------|---------------|------------|
| 다운타임 위험 | 높음 | 낮음 (SLA 보장) |
| 데이터 손실 위험 | 구성에 따라 다름 | 내장 보호 |
| 보안 사고 위험 | 관리 능력에 따라 다름 | 전문팀 관리 |
| 인력 이탈 위험 | 높음 (핵심 인재 의존) | 낮음 |

### 비용 최적화 전략

어떤 접근법을 선택하든, 다음과 같은 전략으로 데이터 스트리밍 비용을 최적화할 수 있다.

#### 데이터 거버넌스

- **데이터 보존 정책 최적화:** 비즈니스 및 규제 요구사항에 맞게 보존 기간을 설정하여 불필요한 스토리지 비용을 줄인다.
- **Tiered Storage 활용:** 자주 접근하지 않는 오래된 데이터는 저비용 스토리지 티어로 이동시킨다. Confluent의 Tiered Storage는 이를 자동으로 처리한다.
- **스키마 관리:** Schema Registry를 활용하여 데이터 스키마를 관리하고, 효율적인 직렬화/역직렬화를 통해 네트워크와 스토리지 비용을 절감한다.

#### 효율적인 리소스 사용

- **올바른 인스턴스 유형 선택:** 워크로드 특성에 맞는 인스턴스 유형을 선택한다. I/O 집약적 워크로드에는 스토리지 최적화 인스턴스가, CPU 집약적 스트림 처리에는 컴퓨팅 최적화 인스턴스가 적합하다.
- **압축(Compression) 활용:** 네트워크 대역폭과 스토리지를 절약하기 위해 적절한 압축 알고리즘(LZ4, zstd 등)을 사용한다.
- **파티션 전략 최적화:** 필요 이상으로 많은 파티션을 생성하지 않는다. 파티션이 너무 많으면 메타데이터 오버헤드와 리밸런싱 비용이 증가한다.

#### 아키텍처 최적화

- **이벤트 기반 아키텍처(Event-Driven Architecture):** 불필요한 폴링과 배치 처리를 줄이고, 이벤트가 발생할 때만 처리하도록 아키텍처를 설계한다.
- **스트림 처리 활용:** 데이터가 흐르는 도중에 실시간으로 필터링, 변환, 집계를 수행하여 다운스트림 시스템의 부하와 스토리지 비용을 줄인다.
- **토픽 설계 최적화:** 너무 세분화하거나 너무 통합된 토픽 구조를 피하고, 사용 사례에 맞는 적절한 토픽 구조를 설계한다.

### 숨겨진 가치: ROI 관점

비용만을 고려해서는 안 된다. 실시간 데이터 스트리밍이 가져다주는 비즈니스 가치도 함께 평가해야 한다.

#### 실시간 인사이트

- 고객 행동을 실시간으로 분석하여 개인화된 경험을 제공할 수 있다.
- 운영 데이터를 실시간으로 모니터링하여 문제를 조기에 감지하고 대응할 수 있다.
- 실시간 대시보드를 통해 비즈니스 의사결정을 가속화할 수 있다.

#### 운영 효율성

- 배치 처리에서 실시간 처리로 전환하면 데이터 파이프라인의 복잡성을 줄이고 운영 효율성을 높일 수 있다.
- 이벤트 기반 아키텍처를 통해 시스템 간 결합도를 낮추고, 더 유연하고 확장 가능한 시스템을 구축할 수 있다.

#### 새로운 비즈니스 기회

- 실시간 데이터 스트리밍은 이전에는 불가능했던 새로운 비즈니스 모델과 서비스를 가능하게 한다.
- 실시간 사기 탐지, 동적 가격 책정, 실시간 추천 엔진 등은 실시간 데이터 스트리밍 없이는 구현하기 어려운 기능들이다.

### Confluent의 접근법

Confluent는 실시간 데이터 스트리밍의 TCO를 최소화하면서 비즈니스 가치를 극대화할 수 있도록 설계되었다.

#### Confluent Cloud

Confluent Cloud는 완전 관리형 Apache Kafka 서비스로, 인프라 관리의 부담을 제거하고 개발자가 비즈니스 로직에 집중할 수 있게 한다.

- **서버리스(Serverless) 클러스터:** 인프라 관리 없이 사용량에 따라 자동으로 확장되고, 사용한 만큼만 과금된다.
- **전용(Dedicated) 클러스터:** 고성능과 격리가 필요한 워크로드를 위한 전용 인프라를 제공한다.
- **글로벌 배포:** 전 세계 주요 클라우드 리전에서 사용할 수 있으며, Cluster Linking을 통한 크로스 리전 복제를 지원한다.

#### 통합 플랫폼

Confluent는 Kafka 브로커 이상의 통합 플랫폼을 제공한다:

- **Confluent Schema Registry:** 스키마 관리와 데이터 거버넌스
- **Kafka Connect:** 200개 이상의 사전 구축된 커넥터로 다양한 시스템과 연동
- **ksqlDB / Flink:** 실시간 스트림 처리 및 분석
- **Stream Governance:** 데이터 계보(lineage), 품질, 카탈로그 기능
- **Cluster Linking:** 클러스터 간 실시간 데이터 복제

이러한 통합 플랫폼 접근법은 각 구성 요소를 별도로 구축하고 관리하는 것에 비해 총 소유 비용을 크게 절감한다.

### 비용을 넘어선 고려사항

TCO 분석 시 금전적 비용 외에도 다음과 같은 요소를 고려해야 한다:

#### 개발자 생산성

- 개발자가 인프라 관리 대신 비즈니스 로직 개발에 집중할 수 있는 환경이 중요하다.
- 잘 설계된 API, SDK, 문서, 개발 도구는 개발자 생산성을 크게 향상시킨다.

#### 민첩성(Agility)

- 새로운 데이터 스트리밍 사용 사례를 얼마나 빠르게 구축하고 배포할 수 있는가?
- 인프라 프로비저닝에 수주가 걸리는 환경과 몇 분 만에 새 클러스터를 생성할 수 있는 환경의 차이는 크다.

#### 확장성(Scalability)

- 비즈니스 성장에 따라 데이터 스트리밍 인프라를 얼마나 쉽게 확장할 수 있는가?
- 수동 확장은 시간이 걸리고 오류가 발생하기 쉬우며, 자동 확장은 비용 효율성과 성능을 동시에 보장한다.

#### 신뢰성(Reliability)

- 99.95% 이상의 가용성을 달성하기 위해 필요한 투자와 노력은 상당하다.
- SLA가 보장되는 완전 관리형 서비스는 이러한 부담을 서비스 제공자에게 전가한다.

### 결론

실시간 데이터 스트리밍의 진정한 비용은 인프라 비용과 소프트웨어 라이선스만으로는 측정할 수 없다. 인력 비용, 운영 오버헤드, 다운타임 위험, 기회비용까지 포함하면, 셀프 매니지드 데이터 스트리밍의 TCO는 많은 조직이 예상하는 것보다 훨씬 높다.

핵심 요약:

- **빙산의 일각만 보지 말라.** 인프라 비용은 TCO의 일부분에 불과하다. 인력, 운영, 위험, 기회비용을 모두 고려해야 한다.
- **규모 성장에 따른 비용 변화를 예측하라.** 데이터 볼륨과 사용 사례가 증가함에 따라 비용이 비선형적으로 증가할 수 있다.
- **DIY와 완전 관리형을 공정하게 비교하라.** 직접 비용뿐 아니라 간접 비용과 위험 비용까지 포함한 TCO 기준으로 비교해야 한다.
- **비용만이 아닌 가치를 평가하라.** 실시간 데이터 스트리밍이 가져다주는 비즈니스 가치와 ROI도 함께 고려해야 한다.
- **비용 최적화 전략을 수립하라.** 데이터 거버넌스, 효율적인 리소스 사용, 아키텍처 최적화를 통해 TCO를 지속적으로 관리하라.

조직의 특성, 규모, 기술 역량에 맞는 접근법을 선택하되, 숨겨진 비용까지 포괄적으로 고려한 의사결정이 필요하다. Confluent는 이러한 복잡성을 줄이고, 조직이 실시간 데이터 스트리밍의 가치에 집중할 수 있도록 돕는 것을 목표로 한다.
