### 동기(Motivation)

Kafka는 대규모 실시간 데이터 피드를 처리하기 위한 통합 플랫폼으로 설계됨. 시스템은 로그 집계와 같은 높은 처리량의 이벤트 스트림을 지원하고, 오프라인 시스템에서 발생하는 대규모 데이터 백로그를 관리하며, 저지연 메시징을 처리하고, 내결함성을 보장하는 파티션된 분산 처리를 가능하게 해야 했음.

### 영속성(Persistence)

#### 파일시스템을 두려워하지 마세요

Kafka는 파일시스템 스토리지와 캐싱에 크게 의존함. "디스크는 느리다"는 것이 일반적인 인식이지만, 순차적 디스크 성능은 랜덤 액세스보다 훨씬 뛰어남. 최신 하드 드라이브는 순차 쓰기(linear writes)에서 약 600MB/sec를 달성하는 반면, 랜덤 쓰기(random writes)는 약 100k/sec에 불과함. 이는 6000배의 차이임.

운영체제는 대용량 블록으로 데이터를 미리 읽고(read-ahead) 작은 쓰기를 더 큰 물리적 쓰기로 그룹화하는(write-behind) 최적화를 제공함. 최신 운영체제는 여유 메모리를 디스크 캐싱에 적극적으로 사용하며, "순차적 디스크 액세스는 경우에 따라 랜덤 메모리 액세스보다 빠를 수 있음."

Java 애플리케이션은 메모리 오버헤드 문제에 직면함. 객체 오버헤드가 데이터 크기를 두 배로 늘리는 경우가 많고, 가비지 컬렉션은 대용량 힙에서 문제가 됨. 파일시스템과 OS 페이지캐시를 활용함으로써 Kafka는 다음을 달성함:

- 사용 가능한 캐시 용량이 자동으로 두 배로 증가
- 서비스 재시작 후에도 캐시가 유지됨
- 캐시 일관성을 위한 코드 단순화
- 32GB 머신에서 GC 패널티 없이 캐시 크기가 28-30GB에 도달

모든 데이터 쓰기는 디스크로 플러시하지 않아도 즉시 영구 로그에 기록됨. 커널의 페이지캐시가 이 전송을 처리함.

#### 상수 시간으로 충분합니다

전통적인 메시징 시스템은 메타데이터 관리를 위해 BTree 또는 유사한 구조의 컨슈머별 큐를 사용 → O(log N) 연산 필요. 디스크 탐색(seek)은 각각 약 10밀리초가 소요되며, 고정 캐시에서 데이터가 증가할수록 성능 저하가 초선형적으로 발생함.

Kafka는 영구 큐에 단순한 파일 추가(file appends)를 사용하여 O(1) 연산을 제공하며, 읽기가 쓰기를 차단하지 않음. 이 접근 방식은 데이터 크기와 성능을 분리 → 단일 서버가 탐색 성능이 좋지 않음에도 불구하고 저렴하고 대용량인 SATA 드라이브를 활용할 수 있게 함.

이 설계는 성능 저하 없이 관대한 메시지 보존(분 단위가 아닌 주 단위)을 가능하게 하여, 컨슈머에게 재생(replay) 및 재처리(reprocessing)의 유연성을 제공함.

### 효율성(Efficiency)

효율성은 멀티테넌트 운영에 직접적인 영향을 미침. 인프라는 애플리케이션이 용량 한계에 도달하기 전에 병목 현상이 되어서는 안 됨.

#### 배칭(Batching)

프로토콜은 메시지를 함께 그룹화하는 "메시지 세트" 추상화를 사용함. 배칭은 다음을 달성함:

- 네트워크 라운드트립 오버헤드 분산
- 더 큰 순차적 디스크 연산
- 연속적인 메모리 블록
- 수 배에서 수십 배의 속도 향상

버스트성 랜덤 메시지 쓰기가 컨슈머 방향의 선형 흐름으로 변환됨.

#### 제로카피 최적화(Zero-Copy Optimization)

Kafka는 프로듀서·브로커·컨슈머 전체에서 표준화된 바이너리 메시지 포맷을 사용 → 중간 변환을 제거함. 브로커의 메시지 로그는 프로듀서/컨슈머 포맷의 메시지 세트로 채워진 파일들로 구성됨.

최신 Unix 시스템은 페이지캐시에서 소켓으로 데이터를 전송하기 위한 최적화된 코드 경로를 제공함. Linux의 `sendfile` 시스템 콜은 기존의 4회 복사·2회 시스템 콜 경로를 피함:

전통적인 경로: OS가 디스크 데이터 읽기 → 애플리케이션이 커널 데이터 읽기 → 애플리케이션이 소켓 버퍼에 쓰기 → OS가 NIC 버퍼로 복사

`sendfile`을 사용하면 OS가 페이지캐시에서 네트워크로 직접 데이터를 전송 → NIC 버퍼로의 마지막 복사만 필요함.

컨슈머가 최신 상태를 유지하는 클러스터에서는 디스크가 전적으로 캐시에서 데이터를 제공하며 읽기 활동이 전혀 없음.

참고: TLS/SSL 라이브러리는 사용자 공간에서 작동하며, 커널 수준의 SSL_sendfile은 현재 Kafka에서 지원되지 않으므로 SSL이 활성화된 경우 `sendfile`이 사용되지 않음.

#### 엔드투엔드 배치 압축(End-to-End Batch Compression)

네트워크 대역폭은 데이터 파이프라인, 특히 광역 네트워크에서 병목 현상이 될 수 있음. 메시지 수준 압축은 메시지 간에 중복성이 존재하기 때문에(필드 이름, 사용자 에이전트, 공통 문자열) 압축 비율이 좋지 않음.

Kafka는 메시지를 배치로 묶고, 그룹을 압축한 다음, 압축된 배치를 서버로 전송함. 브로커는 검증을 위해 배치를 압축 해제한 후 압축된 데이터를 디스크에 기록함. 배치는 로그와 컨슈머에게 전송되는 동안 압축된 상태로 유지되며, 컨슈머가 수신된 데이터를 압축 해제함.

지원되는 압축 프로토콜: GZIP, Snappy, LZ4, ZStandard

### 프로듀서(The Producer)

#### 로드 밸런싱(Load Balancing)

프로듀서는 중간 라우팅 없이 파티션을 리드하는 브로커에 직접 데이터를 전송함. 모든 Kafka 노드는 살아있는 서버와 파티션 리더십에 대한 메타데이터 요청에 응답 → 적절한 요청 방향을 설정할 수 있게 함.

클라이언트는 랜덤 로드 밸런싱 또는 시맨틱 파티셔닝 함수를 통해 파티션 발행을 제어함. 파티션 키를 지정하면 해당 키의 모든 데이터가 동일한 파티션으로 전달 → 컨슈머의 지역성 민감(locality-sensitive) 처리가 가능함.

#### 비동기 전송(Asynchronous Send)

배칭이 효율성을 높임. 프로듀서는 메모리에 데이터를 축적하고 단일 요청으로 더 큰 배치를 전송함. 설정은 고정된 메시지 수 또는 지연 시간 한계(예: 64k 또는 10밀리초)를 제한함. 이는 처리량 향상을 위해 약간의 지연 시간 증가를 교환함.

### 컨슈머(The Consumer)

Kafka 컨슈머는 파티션 리더 브로커에 fetch 요청을 보내면서 로그 오프셋을 지정함. 브로커는 해당 위치부터 로그 청크를 반환 → 컨슈머가 소비 위치를 직접 제어할 수 있고 재처리를 위한 데이터 되감기도 가능함.

#### Push vs. Pull

Kafka는 프로듀서가 브로커에 푸시하고 컨슈머가 브로커에서 풀하는 전통적인 풀 모델을 따름. 푸시 기반 시스템은 브로커가 전송 속도를 제어하기 때문에 다양한 컨슈머를 지원하기 어려움. 소비 속도가 생산 속도보다 느려지면 컨슈머가 감당할 수 없게 되어 사실상 서비스 거부 상태가 됨.

풀 기반 시스템은 컨슈머가 뒤처지더라도 가능할 때 따라잡을 수 있게 함. 또한 컨슈머가 항상 현재 위치 이후의 모든 사용 가능한 메시지를 가져오므로(설정 가능한 제한까지) 적극적인 데이터 배칭을 가능하게 함.

순진한 풀 시스템은 브로커에 데이터가 없을 때 타이트 루프 폴링의 위험이 있음. Kafka는 데이터가 도착하거나 설정 가능한 바이트 임계값이 충족될 때까지 컨슈머 요청이 "롱 폴(long poll)"에서 차단되도록 허용하는 풀 파라미터를 통해 이를 방지함.

#### 컨슈머 위치(Consumer Position)

소비 추적은 핵심 성능 요소임. 대부분의 시스템은 소비 메타데이터를 브로커에 즉시 또는 컨슈머 확인 시점에 저장함. 그러나 소비 상태에 대한 브로커-컨슈머 간 합의는 간단하지 않음.

소비 즉시 기록 방식은 컨슈머가 전달 후 실패할 경우 처리되지 않은 메시지가 건너뛰어질 위험이 있음. 확인 기반 방식은 손실을 방지하지만 복잡성이 증가함. 컨슈머가 메시지를 처리한 후 확인 전에 충돌하면 복구 시 중복 소비가 발생함.

Kafka의 접근 방식은 근본적으로 다름: 각 파티션은 구독하는 컨슈머 그룹당 정확히 하나의 컨슈머에게 할당됨. 컨슈머 위치는 파티션당 단일 정수(다음 메시지 오프셋)가 됨. 이는 소비 상태 크기를 최소화하고 주기적인 체크포인팅만 필요로 함.

컨슈머는 재생을 위해 의도적으로 이전 오프셋으로 되감을 수 있으며, 이는 전통적인 큐 계약을 위반하지만 버그 수정 후 필수적인 재처리를 가능하게 함.

#### 오프라인 데이터 로드(Offline Data Load)

확장 가능한 영속성은 Hadoop이나 데이터 웨어하우스로의 배치 데이터 로드와 같은 주기적 컨슈머를 가능하게 함. Hadoop 병렬화는 노드/토픽/파티션 조합당 맵 태스크로 로드를 분할 → 완전한 병렬성을 제공함. 실패한 태스크는 중복 위험 없이 원래 위치에서 재시작됨.

#### 정적 멤버십(Static Membership)

리밸런스 프로토콜은 그룹 코디네이터가 멤버에게 임시 엔티티 ID를 할당하는 방식에 의존함. 멤버가 재시작하여 다시 참여하면 ID가 바뀌어 리밸런싱이 트리거됨. 상태 저장 애플리케이션에서는 이로 인해 태스크 할당이 뒤섞여 긴 상태 복구 기간과 부분적 비가용성이 발생함.

정적 멤버십은 멤버가 영구적인 엔티티 ID를 제공할 수 있게 함. 이러한 ID를 기반으로 한 멤버십 안정성은 불필요한 리밸런싱을 방지함. 구현에는 다음이 필요함:

- 브로커 및 클라이언트를 버전 2.3 이상으로 업그레이드
- 브로커 `inter.broker.protocol.version`을 2.3 이상으로 설정
- 컨슈머 인스턴스당 고유한 `ConsumerConfig#GROUP_INSTANCE_ID_CONFIG` 설정
- Kafka Streams의 경우: KafkaStreams 인스턴스당 하나의 고유 ID

이전 버전의 브로커는 클라이언트가 `GROUP_INSTANCE_ID_CONFIG`를 설정하면 `UnsupportedException`을 발생시킴. 중복 ID는 `FencedInstanceIdException`을 트리거 → 즉각적인 종료를 강제함.

### 메시지 전달 시맨틱스(Message Delivery Semantics)

Kafka는 간단한 시맨틱스를 제공함:

- 최대 한 번(At most once): 메시지가 손실될 수 있지만 재전달되지 않음
- 최소 한 번(At least once): 메시지가 손실되지 않지만 재전달될 수 있음
- 정확히 한 번(Exactly once): 각 메시지가 정확히 한 번만 처리됨

이는 발행 및 소비 보장 문제로 나뉨. "정확히 한 번"을 주장하는 시스템은 실제 동작이 실패 시나리오·다중 컨슈머 프로세스·디스크 손실 가능성에 따라 달라지므로 주의 깊게 살펴봐야 함.

#### Kafka의 보장

메시지는 모든 동기화 복제본(ISR) 멤버가 로그에 적용할 때 "커밋"됨. 커밋된 메시지는 하나의 복제 브로커가 살아있는 한 손실되지 않음.

0.11.0.0 이전에는 실패한 프로듀서가 네트워크 오류가 커밋 전에 발생했는지 후에 발생했는지 확인할 수 없었음. 이는 자동 생성 키 데이터베이스 삽입과 유사함. 프로듀서는 재전송만 할 수 있었고, 이는 중복 가능성이 있는 최소 한 번 시맨틱스를 제공했음.

0.11.0.0 이후, 멱등성(idempotent) 프로듀서 전달은 재전송이 중복을 만들지 않음을 보장함. 브로커는 프로듀서 ID를 할당하고 시퀀스 번호를 사용 → 중복을 제거함. 프로듀서는 원자적 다중 파티션 트랜잭션도 지원 → 모든 메시지가 성공하거나 모두 실패하도록 보장함.

#### 프로듀서 옵션

모든 사용 사례가 강력한 보장을 필요로 하지는 않음. 지연 시간에 민감한 프로듀서는 내구성 수준을 지정할 수 있음: 커밋 대기(10밀리초), 완전 비동기 전송, 또는 리더 수신만 대기(팔로워는 불필요).

#### 컨슈머 시맨틱스

동일한 로그가 동일한 오프셋과 메시지 순서로 모든 복제본에 존재함. 컨슈머는 로그 위치를 제어함. 메모리 내 위치 저장은 충돌 방지 시나리오에서 작동하지만, 실패 복구에는 대체 접근 방식이 필요함.

컨슈머는 처리 시 다음 옵션을 직면함:

1. 읽기 → 위치 저장 → 처리: 위치 저장 후 처리 전에 충돌하면 처리되지 않은 메시지가 건너뛰어짐 (최대 한 번)
2. 읽기 → 처리 → 위치 저장: 처리 후 저장 전에 충돌하면 복구 시 재처리됨 (최소 한 번)

멱등성 업데이트(기본 키)는 최소 한 번을 실용적으로 만듦. 중복 메시지가 동일한 데이터로 덮어씀.

#### 정확히 한 번 처리(Exactly-Once Processing)

Kafka 토픽을 소비하고 다른 토픽으로 생성할 때(Kafka Streams 애플리케이션), 0.11.0.0 이후의 트랜잭션 프로듀서는 정확히 한 번 시맨틱스를 가능하게 함. 컨슈머 위치는 내부 토픽에 저장 → 단일 트랜잭션에서 오프셋 쓰기와 처리된 데이터 생성을 허용함.

중단된 트랜잭션은 컨슈머 위치를 되돌림(컨슈머는 자동으로 되감기보다 커밋된 오프셋을 다시 가져와야 함). 처리된 데이터는 "read_committed" 격리 수준을 사용하는 다른 컨슈머에게 보이지 않음(기본값인 "read_uncommitted"는 중단된 트랜잭션 데이터를 포함한 모든 메시지를 표시함).

외부 시스템 쓰기는 대부분의 시스템이 2단계 커밋을 지원하지 않으므로 다른 접근 방식이 필요함. 솔루션에는 대상 시스템에 출력과 함께 오프셋을 저장하여 원자적 출력-오프셋 업데이트를 보장하는 것이 포함됨. Kafka Connect 커넥터가 이 패턴을 예시함.

Kafka는 Kafka Streams에서 정확히 한 번을 지원하고 일반 사용을 위해 트랜잭션 프로듀서와 read-committed 컨슈머 격리를 통해 이를 가능하게 함. 외부 시스템의 정확히 한 번은 일반적으로 시스템 협력이 필요함. 그렇지 않으면 Kafka는 기본적으로 최소 한 번을 보장하며, 비활성화된 프로듀서 재시도와 처리 전 오프셋 커밋을 통해 최대 한 번을 허용함.

### 트랜잭션 사용하기(Using Transactions)

Kafka 트랜잭션은 다른 메시징 시스템과 다름. 컨슈머와 프로듀서가 분리되어 있으며 프로듀서만 트랜잭션을 수행함. 다만 프로듀서는 전체적인 정확히 한 번 동작을 위해 트랜잭션으로 컨슈머 위치를 업데이트할 수 있음.

#### 세 가지 핵심 측면

1. 컨슈머는 그룹당 각 파티션의 단독 처리를 보장하는 파티션 할당을 사용함
2. 프로듀서는 모든 레코드 생성과 오프셋 업데이트를 원자적으로 만드는 트랜잭션을 사용함
3. 컨슈머 인스턴스당 하나의 프로듀서 인스턴스가 리밸런싱과 함께 트랜잭션을 처리함

read-committed 격리 수준 사용이 권장됨(엄격하게 필수는 아니지만).

#### 설정

컨슈머: `isolation.level=read_committed` 및 `enable.auto.commit=false`

프로듀서: `transactional.id`를 트랜잭션 ID 이름으로 설정

#### 예외 처리

예외 카테고리는 이제 다음을 포함함:

- RetriableException: 자동 클라이언트 재시도가 있는 임시 예외, 애플리케이션에 도달하지 않음
- RefreshRetriableException: 재시도 전 메타데이터 새로 고침 필요, 내부적으로 처리됨
- AbortableException: 트랜잭션 중단 필요, 처리를 위해 애플리케이션에 버블업
- ApplicationRecoverableException: 사용자 정의 복구가 필요한 애플리케이션 처리 예외
- InvalidConfigurationException: 애플리케이션 처리가 필요한 설정 문제
- KafkaException: 애플리케이션 처리를 위한 일반 Kafka 예외

간단한 예외 처리: Kafka 객체를 폐기하고 다시 생성하여 새로 시작함. 컨슈머 그룹 리밸런싱은 마지막으로 커밋된 오프셋을 가져와 중단 전 상태로 효과적으로 되감음.

정교한 애플리케이션은 자동 되감기에 의존하는 대신 `KafkaConsumer.seek`를 사용하여 수동으로 되감을 수 있음.

### 공유 그룹(Share Groups)

공유 그룹은 Apache Kafka 4.1의 협력적 레코드 소비를 위한 프리뷰 기능임. 전통적인 컨슈머 그룹과 달리 공유 그룹은 다음을 가능하게 함:

- 여러 컨슈머가 레코드를 협력적으로 소비
- 파티션을 여러 컨슈머에게 할당
- 컨슈머 수가 파티션 수를 초과할 수 있음
- 개별 레코드 확인
- 처리할 수 없는 레코드에 대한 전달 시도 횟수 계산

#### 메커니즘

동일한 토픽을 구독한 모든 공유 그룹 컨슈머는 해당 레코드를 협력적으로 소비함. 토픽에 액세스하는 여러 공유 그룹은 독립적으로 소비함.

컨슈머는 구독할 토픽을 동적으로 설정함. 페칭 시 컨슈머는 일치하는 토픽-파티션에서 레코드를 수신하며, 레코드에는 시간 제한된 획득 잠금(기본 30초, 그룹 설정 `share.record.lock.duration.ms`로 제어)이 걸림. 잠긴 레코드는 다른 컨슈머에서 사용할 수 없음.

잠금을 보유한 컨슈머는 다음을 할 수 있음:
- 성공적인 처리 확인
- 다른 전달 시도를 위해 레코드 해제
- 처리할 수 없는 레코드 거부
- 잠금 기간 만료 시 자동 해제 허용

브로커는 `group.share.partition.max.record.locks`를 통해 공유 그룹의 토픽-파티션별 획득 레코드 수를 제한함. 이 제한에 도달하면 획득된 레코드가 타임아웃으로 줄어들 때까지 페칭이 일시적으로 중단됨.

### 복제(Replication)

Kafka는 설정 가능한 서버 수에 걸쳐 토픽 파티션 로그를 복제하며, 토픽마다 복제 팩터를 지정할 수 있음. 이를 통해 서버 장애 시 복제본으로 자동 페일오버가 이루어지면서 메시지 가용성을 유지함.

복제를 선택 사항으로 취급하는 일부 시스템과 달리 Kafka는 복제를 기본값으로 구현함. 단일 복제본 토픽도 복제 팩터가 1인 복제된 토픽임.

복제 단위는 토픽 파티션임. 정상 조건에서 각 파티션은 하나의 리더와 0개 이상의 팔로워를 가짐. 리더를 포함한 모든 복제본이 복제 팩터를 구성함. 모든 쓰기는 파티션 리더로 전달되고, 읽기는 리더 또는 팔로워에서 처리됨. 파티션 수는 일반적으로 브로커 수보다 많으며 리더는 고르게 분산됨. 팔로워 로그는 리더 로그와 동일한 오프셋·메시지·순서를 가짐(리더가 일시적으로 아직 복제되지 않은 메시지를 가질 수 있음).

팔로워는 일반 Kafka 컨슈머처럼 리더로부터 소비하며 자연스럽게 적용된 로그 항목을 배치로 처리함.

#### 노드 활성 상태(Node Liveness)

분산 시스템 장애 처리에는 정확한 "활성" 정의가 필요함. 특별한 "컨트롤러" 노드가 브로커 등록 및 장애 감지를 관리함. 브로커 활성 상태에는 다음이 필요함:

1. 정기적인 메타데이터 업데이트를 수신하는 컨트롤러와의 활성 세션 유지
2. 팔로워가 "너무 뒤처지지" 않고 리더 쓰기를 복제

활성 세션은 클러스터 설정에 따라 달라짐. KRaft 클러스터는 주기적인 컨트롤러 하트비트를 통해 세션을 유지함. 세션 타임아웃은 `broker.session.timeout.ms`로 설정됨. 타임아웃 전에 하트비트가 누락되면 노드가 오프라인으로 표시됨.

두 조건을 모두 충족하는 노드는 "동기화 중(in sync)"으로 간주되며 리더가 동기화 복제본(ISR) 세트로 추적함. ISR 세트는 클러스터 메타데이터에 유지되며 변경 시 업데이트됨. 조건을 충족하지 못하면 해당 브로커가 ISR에서 제거됨. 죽은 팔로워는 세션 만료로 제거되고, 뒤처진 팔로워는 `replica.lag.time.max.ms`로 결정되는 복제 지연 초과 시 제거됨.

Kafka는 노드가 작동을 멈췄다가 나중에 복구되는 "fail/recover" 장애 모델을 처리하며, 임의적이거나 악의적인 응답을 생성하는 "비잔틴(Byzantine)" 장애는 처리하지 않음.

커밋된 메시지만 컨슈머에게 전달 → 리더 장애 시 손실 우려를 방지함. 프로듀서는 `acks` 설정을 통해 커밋 대기 여부를 선택하여 지연과 내구성을 교환함. 토픽은 프로듀서가 전체 ISR 확인을 요청할 때 확인되는 최소 동기화 복제본(`min.insync.replicas`)을 설정함. 덜 엄격한 확인(acks=0)은 ISR 간에 비동기적으로 커밋하고, acks=1은 리더에서만 동기화함.

`acks` 설정에 관계없이 컨슈머 가시성에는 다음이 필요함:

1. 모든 동기화 복제본에 복제
2. 동기화 복제본 수가 `min.insync.replicas` 설정을 초과

Kafka의 보장: 커밋된 메시지는 최소 하나의 살아있는 동기화 복제본이 있는 한 손실되지 않음.

노드 장애 시 짧은 페일오버 후 가용성이 계속되지만 네트워크 파티션에서는 그렇지 않을 수 있음.

#### 복제된 로그: 쿼럼, ISR, 상태 머신

Kafka 파티션은 근본적으로 복제된 로그임. 이는 분산 데이터 시스템의 가장 기본적인 프리미티브 중 하나임. 복제된 로그는 순서화된 값 시퀀스에 대한 합의를 모델링함.

가장 간단한 구현은 리더가 선택한 순서를 사용함. 리더가 살아있는 한 팔로워는 값과 순서만 복사하면 됨.

리더 실패 시 팔로워 중에서 새 리더를 선출해야 함. 그러나 팔로워는 지연되거나 충돌할 수 있으므로 최신 팔로워를 선택해야 함. 로그 복제 알고리즘은 다음을 보장해야 함: 클라이언트가 메시지가 커밋되었음을 알게 되고 리더가 실패하면 새로 선출된 리더는 해당 메시지를 가지고 있어야 함. 이는 트레이드오프를 만듦: 리더가 커밋 전에 더 많은 팔로워 확인을 기다릴수록 잠재적으로 선출 가능한 리더가 더 많아짐.

쿼럼 접근 방식은 커밋에 필요한 확인 수와 리더 선출 로그 비교 수 사이에 보장된 중복을 만듦.

일반적인 접근 방식은 커밋과 선출 모두에 과반수 투표를 사용함: 2f+1 복제본에서 커밋 전에 f+1 복제본이 메시지를 수신하도록 요구하고 가장 완전한 로그를 가진 f+1 복제본에서 새 리더를 선출하면 f개 이하의 장애 시 리더가 커밋된 메시지를 손실하지 않음을 보장함. f+1 복제본 중 적어도 하나는 모든 커밋된 메시지를 포함하고, 해당 복제본의 가장 완전한 로그가 새 리더가 됨. 많은 알고리즘이 존재함(ZooKeeper의 Zab, Raft, Viewstamped Replication, Microsoft의 PacificA). 이 개요는 세부 사항을 단순화함.

과반수 투표의 장점: 지연 시간은 가장 빠른 서버에만 의존함. 3개의 복제본에서 지연 시간은 느린 팔로워가 아닌 빠른 팔로워를 따름.

과반수 투표의 단점: 장애가 빠르게 선출 가능한 리더를 제거함. 하나의 장애 허용에는 3개의 데이터 복사본이 필요하고, 두 개의 장애 허용에는 5개의 복사본이 필요함. 단일 장애 중복은 실용적인 시스템에 충분하지 않고, 5개 복사본 오버헤드는 대용량 데이터에 실용적이지 않음.

#### Kafka의 ISR 접근 방식

Kafka는 과반수 투표 대신 동적 동기화 복제본(ISR) 세트를 사용함. ISR 멤버만 리더십에 적합함. 파티션 쓰기는 모든 ISR 멤버가 쓰기를 수신할 때만 커밋됨. ISR 세트는 변경 사항과 함께 클러스터 메타데이터에 유지됨.

f+1 복제본과 ISR 모델에서 Kafka는 커밋된 메시지 손실 없이 f개의 장애를 허용함.

대부분의 사용 사례에서 이 트레이드오프는 합리적임. 실제로 두 접근 방식 모두 장애 허용을 위해 동일한 복제본 확인 수를 기다림(과반수 쿼럼은 3개의 복제본과 1개의 확인이 필요하고, ISR은 2개와 1개가 필요). 과반수 투표의 장점(가장 느린 서버 없이 커밋)은 클라이언트가 커밋 차단 여부를 선택할 수 있게 하여 완화됨. 낮은 복제 팩터 요구 사항은 처리량과 디스크 공간 이점을 제공함.

중요한 구분: Kafka는 충돌한 노드가 데이터가 온전한 상태로 복구될 것을 요구하지 않음. 복제 알고리즘은 일반적으로 장애-복구 시나리오에서도 데이터가 손실되지 않는 "안정적인 저장소"가 있다고 가정함. 두 가지 문제가 존재함: 디스크 오류(가장 흔한 운영 문제)는 종종 데이터를 온전하게 두지 않으며, 모든 쓰기에 fsync(일관성 보장을 가능하게 함)는 성능을 2-3배 감소시킴. Kafka의 복제본 재참여 프로토콜은 플러시되지 않은 데이터가 손실된 충돌 후에도 완전한 재동기화를 요구함.

#### 비정상 리더 선출(Unclean Leader Election)

Kafka의 데이터 손실 보장은 최소 하나의 동기화 복제본이 남아있음을 가정함. 모든 복제 노드가 죽으면 이 보장이 제거됨.

실용적인 시스템은 모든 복제본 죽음을 처리해야 함. 두 가지 가능한 구현:

1. ISR 복제본이 살아나기를 기다리고 부활을 리더로 선택(데이터가 살아있기를 희망)
2. 첫 번째 부활하는 복제본(반드시 ISR이 아닌)을 리더로 선택

이는 가용성과 일관성을 교환함. ISR 복제본을 기다리면 해당 복제본이 돌아올 때까지 비가용성을 의미함. 파괴되거나 데이터가 손실된 복제본은 영구적인 다운타임을 의미함. 비ISR 복제본 리더십은 커밋된 메시지 보장이 없음에도 불구하고 해당 로그가 진실이 됨을 의미함.

0.11.0.0 이후 Kafka는 일관성을 선호하여 일관된 복제본을 기다림. `unclean.leader.election.enable` 설정 속성은 가용성을 선호하는 사용 사례를 지원함.

이 딜레마는 Kafka에만 국한되지 않음. 모든 쿼럼 방식이 이에 직면함. 과반수 서버 영구 장애 시 과반수 투표는 100% 데이터 손실 또는 일관성 위반 중 선택을 강제함.

#### 가용성과 내구성 보장

프로듀서는 확인을 선택함: 0, 1 또는 모든(-1) 복제본. "모든 복제본" 확인은 할당된 전체 복제본 수신을 보장하지 않음. acks=all에서 확인은 현재 동기화 복제본이 메시지를 수신할 때 발생함. 하나의 실패한 복제본이 있는 2개 복제본 토픽에서 acks=all이 성공함. 나머지 복제본도 실패하면 이러한 쓰기가 손실될 수 있음.

이는 최대 가용성을 보장하지만 내구성 선호를 희생할 수 있음. 두 가지 토픽 설정이 내구성을 선호함:

1. 비정상 리더 선출 비활성화: 비가용 파티션은 최근 리더가 돌아올 때까지 비가용 상태로 유지되어 손실보다 비가용성을 선호
2. 최소 ISR 크기 지정: 파티션은 ISR이 최소값을 초과할 때만 쓰기를 수락하여 단일 복제본 손실을 방지. acks=all에서만 작동하며 최소 동기화 복제본 확인을 보장. 높은 최소값은 일관성을 향상시키고(더 많은 복제본이 더 낮은 손실 확률을 보장) 가용성을 감소시킴(더 적은 동기화 복제본이 쓰기 비가용성을 유발)

#### 복제본 관리

복제된 로그 논의는 단일 로그/파티션을 다룸. Kafka 클러스터는 수백 또는 수천 개를 관리함. 파티션은 클러스터 전체에 라운드 로빈으로 균형을 맞추어 적은 노드에 대용량 토픽이 클러스터링되는 것을 방지함. 리더십도 균형을 맞추어 노드당 비례적인 리더 분배를 보장함.

리더 선출 효율성은 비가용성 시간을 결정하므로 매우 중요함. 단순한 구현이라면 장애 노드가 보유한 파티션마다 개별 선출을 실행함. 하지만 "컨트롤러" 노드가 브로커 등록과 장애 감지를 관리하며 남은 ISR 멤버를 리더로 선출함. 리더십 알림을 배치 처리하여 파티션이 많아도 선출이 빠르고 효율적으로 이루어짐. 컨트롤러 장애 시에는 새 컨트롤러 선출이 트리거됨.

### 로그 압축(Log Compaction)

로그 압축은 Kafka가 단일 토픽 파티션 로그 내에서 각 메시지 키에 대해 마지막으로 알려진 값을 보존하도록 보장함. 이는 애플리케이션 충돌·시스템 장애·유지보수 중 캐시 리로드 후 상태 복원을 처리함.

#### 사용 사례

전통적인 보존은 고정된 기간 후 또는 미리 결정된 크기에 도달하면 오래된 로그 데이터를 삭제함. 이는 레코드가 독립적인 시간적 이벤트 데이터에 적합함. 그러나 중요한 데이터 스트림은 가변적인 키 데이터 변경(예: 데이터베이스 테이블 변경)을 추적함.

예시: 사용자 이메일 토픽은 사용자 ID를 기본 키로 사용하여 이메일 주소 변경 시 메시지를 수신함:

```
123 => bill@microsoft.com
...
123 => bill@gatesfoundation.org
...
123 => bill@gmail.com
```

로그 압축은 각 기본 키에 대한 마지막 업데이트가 유지되도록 보장하는 세분화된 보존을 제공함. 이를 통해 로그가 최근 변경된 키뿐만 아니라 모든 키의 최종 상태를 포함하도록 보장함. 다운스트림 컨슈머는 전체 변경 이력 없이 토픽에서 상태를 복원할 수 있음.

유용한 시나리오:

1. 데이터베이스 변경 구독: 여러 시스템(RDBMS, 캐시, 검색 클러스터, Hadoop)에 필요한 데이터셋. 실시간 변경에는 최근 로그가 필요하고, 캐시/검색 리로드 또는 장애 복구에는 완전한 데이터셋이 필요함
2. 이벤트 소싱: 변경 로그를 기본 저장소로 하는 쿼리 처리를 공존시키는 애플리케이션 설계
3. 고가용성 저널링: 변경 로깅을 통한 내결함성 로컬 연산으로 장애 시 로그 재생을 통해 다른 프로세스가 복구할 수 있음. 스트림 시스템의 카운트, 집계, group-by 처리에 유용. Samza가 이를 상태 관리에 사용

이러한 사례는 실시간 변경 피드가 필요하지만, 머신 충돌이나 데이터 리로드·재처리 시 전체 데이터 로드가 필요하기도 함.

#### 로그 압축 기본 사항

압축된 테일을 가진 Kafka 로그는 메시지당 오프셋이 있는 논리적 구조를 보여줌. 로그 헤드는 모든 메시지를 보존하는 조밀하고 순차적인 오프셋을 가진 전통적인 Kafka 로그와 유사함. 로그 압축은 테일 처리 옵션을 추가함.

압축된 테일 메시지는 원래 오프셋을 유지함. 오프셋은 절대 변경되지 않음. 모든 위치는 유효한 로그 위치로 유지되며, 압축된 메시지는 다음으로 높은 나타나는 오프셋과 구별할 수 없게 됨. 오프셋 36, 37, 38은 모두 동일한 위치를 나타내며, 어느 것에서든 읽으면 38부터 시작하는 메시지 세트를 반환함.

압축은 삭제를 허용함: 키가 있는 null 페이로드 메시지는 삭제 레코드(톰스톤)가 됨. 삭제 마커는 이전의 일치하는 키 메시지를 제거하고 공간을 확보하기 위해 시간이 지나면 자체적으로 사라짐. "삭제 보존 지점"은 이 타임라인을 표시함.

백그라운드 압축은 읽기를 차단하지 않고 주기적으로 로그 세그먼트를 다시 복사함. 스로틀링은 프로듀서/컨슈머에게 영향을 미치는 과도한 I/O를 방지함. 세그먼트 압축은 다음과 유사함:

1. 헤드 대 테일 비율이 가장 높은 로그 선택
2. 키당 로그 헤드 오프셋 요약을 공간 압축으로 생성
3. 시작부터 끝까지 로그를 다시 복사하고 나중에 발생하는 키 제거
4. 새로운 깨끗한 세그먼트를 로그로 교체

#### 로그 압축 보장

로그 압축은 다음을 제공함:

1. 따라잡은 컨슈머: 로그 헤드 내에 있는 컨슈머는 순차적 오프셋으로 모든 기록된 메시지를 봄. 토픽 `min.compaction.lag.ms`는 메시지에 대한 최소 압축 전 시간을 보장함. 토픽 `max.compaction.lag.ms`는 최대 압축 적격 지연을 보장함
2. 메시지 순서: 압축은 순서를 유지함. 메시지만 제거함
3. 영구적 오프셋: 메시지 오프셋은 절대 변경되지 않음
4. 완전한 최종 상태: 로그 시작부터 진행하는 컨슈머는 쓰기 순서로 모든 레코드의 최종 상태를 봄. 삭제 마커는 컨슈머가 `delete.retention.ms` 설정(기본 24시간) 내에 헤드에 도달하면 나타남. 삭제 마커 동시 제거는 `delete.retention.ms`를 초과하여 지연될 때 컨슈머가 마커를 놓칠 수 있음을 의미함

#### 로그 압축 세부 사항

로그 클리너(백그라운드 스레드 풀)는 헤드 중복 키를 제거하면서 세그먼트를 다시 복사함. 각 스레드:

1. 헤드 대 테일 비율이 가장 높은 로그 선택
2. 헤드에 대한 마지막 키 오프셋 요약 생성
3. 시작부터 끝까지 로그를 다시 복사하고 나중에 발생하는 키 제거
4. 깨끗한 세그먼트를 로그로 교체

헤드 요약은 항목당 24바이트를 사용하는 공간 압축 해시 테이블임. 8GB 클리너 버퍼로 반복은 약 366GB 헤드 로그(1k 메시지 평균)를 정리함.

#### 로그 클리너 설정

로그 클리너는 기본적으로 활성화되어 클리너 스레드 풀을 시작함. 특정 토픽에서 압축을 활성화:

```
log.cleanup.policy=compact
```

이 브로커 설정은 `server.properties`에서 재정의하지 않으면 클러스터의 모든 토픽에 적용됨. 클리너는 압축 시간 지연을 통해 최소한의 압축되지 않은 "헤드" 양을 유지할 수 있음:

```
log.cleaner.min.compaction.lag.ms
```

이는 최소값보다 새로운 메시지가 압축되지 않도록 방지함. 설정 없이 현재 쓰기 중인 세그먼트를 제외한 모든 세그먼트가 적격이 됨. 활성 세그먼트는 나이에 관계없이 압축되지 않음.

최대 압축 지연은 낮은 생산 속도 로그가 무한히 부적격 상태로 남는 것을 방지함:

```
log.cleaner.max.compaction.lag.ms
```

이는 무한한 부적격성을 방지함. 설정 없이 `min.cleanable.dirty.ratio`를 초과하지 않는 로그는 압축되지 않음. 압축 마감일에는 하드 보장이 없으며 가용성과 실제 시간이 적용됨.

`uncleanable-partitions-count`, `max-clean-time-secs`, `max-compaction-delay-secs` 메트릭 모니터링 필요.

### 쿼터(Quotas)

Kafka 클러스터는 클라이언트 그룹에 의한 브로커 리소스 사용을 제어하는 요청 쿼터를 적용함. 두 가지 쿼터 유형이 그룹별로 적용됨:

1. 네트워크 대역폭 쿼터: 바이트 속도 임계값 (0.9 이후)
2. 요청 속도 쿼터: 네트워크 및 I/O 스레드의 CPU 사용률 백분율 (0.11 이후)

#### 쿼터가 중요한 이유

대용량을 생산·소비하거나 높은 속도로 요청을 보내는 프로듀서·컨슈머는 브로커 리소스를 독점하고 네트워크를 포화시켜 다른 클라이언트와 브로커에 DoS 공격 수준의 영향을 줄 수 있음. 쿼터는 이러한 문제로부터 보호함. 이는 멀티테넌트 클러스터에서 잘못 동작하는 클라이언트 세트가 잘 동작하는 사용자 경험을 저하시키는 것을 방지하는 데 중요함. 서비스 운영 Kafka는 계약에 따른 API 제한을 적용함.

#### 클라이언트 그룹

Kafka 클라이언트의 사용자는 보안 클러스터에서 인증된 사용자 주체(principal)임. 인증되지 않은 클러스터는 설정 가능한 `PrincipalBuilder`를 통해 사용자를 그룹화함. client-id는 의미 있는 애플리케이션 이름을 사용하는 논리적 클라이언트 그룹화임. (user, client-id) 튜플은 주체와 ID를 모두 공유하는 보안 클라이언트 그룹을 정의함.

쿼터 적용 대상은 (user, client-id), user 또는 client-id 그룹임. 연결당 가장 구체적인 일치 쿼터가 적용됨. 그룹은 설정된 쿼터를 공유함. 예를 들어 (user="test-user", client-id="test-client")에 10MB/sec 생산 쿼터가 있으면 "test-client" client-id를 가진 모든 "test-user" 프로듀서 인스턴스에서 공유됨.

#### 쿼터 설정

설정은 (user, client-id), user, client-id 그룹에 대한 쿼터를 정의함. 재정의를 통해 필요한 수준에서 더 높은(또는 더 낮은) 쿼터를 허용함. 토픽별 로그 설정 재정의와 유사하게 작동함. 사용자 및 (user, client-id) 쿼터 재정의는 메타데이터 로그에 기록됨. 모든 브로커는 이를 읽고 롤링 재시작 없이 즉시 적용함.

우선순위 순서:

1. 일치하는 user 및 client-id 쿼터
2. 일치하는 user 및 기본 client-id 쿼터
3. 일치하는 user 쿼터
4. 기본 user 및 일치하는 client-id 쿼터
5. 기본 user 및 기본 client-id 쿼터
6. 기본 user 쿼터
7. 일치하는 client-id 쿼터
8. 기본 client-id 쿼터

#### 네트워크 대역폭 쿼터

네트워크 대역폭 쿼터는 클라이언트 그룹당 바이트 속도 임계값을 정의함. 기본적으로 고유 그룹은 브로커별로 클러스터 전체에 설정된 고정 바이트/초 쿼터를 받음. 각 그룹은 스로틀링 전에 브로커당 최대 X 바이트/초를 발행/페치함.

#### 요청 속도 쿼터

요청 속도 쿼터는 클라이언트가 쿼터 윈도우에서 브로커당 요청 핸들러 I/O 스레드와 네트워크 스레드를 활용할 수 있는 시간의 백분율을 정의함. n% 쿼터는 하나의 스레드의 n%를 나타내며 총 ((num.io.threads + num.network.threads) * 100)%임. 그룹은 스로틀링 전에 모든 I/O 및 네트워크 스레드에서 최대 n%를 사용함.

I/O 및 네트워크 스레드 할당은 코어 수에 기반하므로 요청 속도 쿼터는 클라이언트가 사용할 수 있는 총 CPU 백분율을 나타냄.

#### 적용

기본적으로 고유 클라이언트 그룹은 클러스터 전체에 설정된 고정 쿼터를 받으며 브로커별로 정의됨. 브로커별 정의는 브로커 간 클라이언트 쿼터 사용 공유가 필요한 고정 클러스터 전체 접근 방식보다 우수함. 다만 올바르게 구현하기는 더 어려움.

쿼터 위반 시 브로커는 클라이언트가 쿼터 이하로 돌아오는 데 필요한 지연 시간을 계산 → 즉시 응답을 반환함. 이때 페치 응답에는 데이터가 포함되지 않음. 브로커는 클라이언트 채널을 음소거하여 지연이 경과할 때까지 추가 요청 처리를 막음. 응답을 수신한 Kafka 클라이언트도 지연 동안 추가 요청을 보내지 않음. 즉, 스로틀된 클라이언트 요청은 양측 모두에서 차단됨.

브로커 지연 응답을 존중하지 않는 이전 클라이언트 구현은 브로커 소켓 채널 음소거를 통해 여전히 스로틀됨. 추가 스로틀된 채널 요청은 지연 후에만 응답을 받음.

바이트 속도 및 스레드 사용률은 빠른 쿼터 위반 감지를 위해 여러 작은 윈도우(예: 30개의 1초 윈도우)에서 측정됨. 큰 윈도우(예: 10개의 30초 윈도우)는 큰 트래픽 버스트와 긴 지연을 유발함. 이는 좋지 않은 사용자 경험임.

### 5.1 네트워크 레이어 (Network Layer)

네트워크 레이어는 비교적 단순한 NIO 서버로 구현되어 있으며, 여기서는 자세히 다루지 않음. `sendfile` 구현은 `TransferableRecords` 인터페이스의 `writeTo` 메서드를 통해 수행됨. 덕분에 파일 기반 메시지 집합은 프로세스 내 버퍼링 대신 더 효율적인 `transferTo` 구현을 사용할 수 있음. 스레딩 모델은 단일 acceptor 스레드와 각각 고정된 수의 연결을 처리하는 N개의 프로세서 스레드로 구성됨. 이 설계는 다른 곳에서도 검증되었으며 간단하고 빠른 것으로 입증됨. 프로토콜은 향후 다른 언어로 클라이언트를 구현할 수 있도록 의도적으로 단순하게 유지됨.

### 5.2 메시지 (Messages)

메시지는 가변 길이 헤더, 가변 길이 불투명(opaque) 키 바이트 배열, 그리고 가변 길이 불투명 값 바이트 배열로 구성됨. 헤더 형식은 다음 섹션에서 설명함. 키와 값을 불투명하게 유지하는 것은 합당한 설계 결정임. 현재 직렬화 라이브러리 분야에서 활발한 발전이 이루어지고 있으며, 특정 선택이 모든 용도에 적합할 가능성은 낮음. Kafka를 사용하는 특정 애플리케이션은 구현의 일부로 특정 직렬화 유형을 요구할 수 있음.

`RecordBatch` 인터페이스는 메시지에 대한 반복자(iterator)로서 NIO `Channel`에서 대량으로 읽고 쓰기 위한 특수 메서드를 제공함.

### 5.3 메시지 형식 (Message Format)

메시지(레코드)는 항상 배치 단위로 기록됨. 메시지 배치의 공식 명칭은 레코드 배치(record batch)이며, 레코드 배치는 하나 이상의 레코드를 포함함. 비정상적인 경우에는 레코드 배치가 단일 레코드만 포함할 수 있음.

#### 5.3.1 레코드 배치 (Record Batch)

다음은 디스크 상의 RecordBatch 형식임:

```
baseOffset: int64
batchLength: int32
partitionLeaderEpoch: int32
magic: int8 (현재 magic 값은 2)
crc: uint32
attributes: int16
    bit 0~2:
        0: 압축 없음
        1: gzip
        2: snappy
        3: lz4
        4: zstd
    bit 3: timestampType
    bit 4: isTransactional (0은 트랜잭션이 아님을 의미)
    bit 5: isControlBatch (0은 제어 배치가 아님을 의미)
    bit 6: hasDeleteHorizonMs (0은 배치에 삭제 지평선이 있는 레코드가 없음을 의미)
    bit 7~15: 미사용
lastOffsetDelta: int32
baseTimestamp: int64
maxTimestamp: int64
producerId: int64
producerEpoch: int16
baseSequence: int32
records: [Record]
```

참고: CRC 계산 시 magic 바이트 앞의 데이터(파티션 리더 에포크 필드 포함)는 건너뜀. 클라이언트가 이 필드에 값을 할당하지 않기 때문에 의도된 동작임. magic 바이트부터 배치 끝까지의 모든 데이터는 CRC에 포함됨. 따라서 CRC는 압축 후 모든 배치 수준 필드를 대상으로 계산됨(CRC 필드 자체는 제외).

CRC-32C(Castagnoli) 다항식이 계산에 사용됨.

압축에 대해: 레코드 배치에서 압축이 활성화되면 압축된 레코드 데이터가 레코드 수 바로 뒤에 직렬화됨. 압축 데이터 해석 방식은 사용하는 압축 코덱에 따라 다름. snappy, gzip, lz4, zstd 코덱은 여러 레코드의 연결(concatenation)을 지원하며, 브로커에서 연속 배치를 함께 압축할 때 일반적으로 활용됨. 각 코덱의 압축 해제 후 레코드 수는 레코드 수 필드로 지정됨. gzip 압축 시에는 기본 gzip 압축 수준이 적용됨. zstd의 경우 클라이언트에서 `zstd.compression.level` 구성으로 압축 수준을 조정할 수 있음.

압축에 대한 추가 참고: 타임스탬프 델타 범위가 `Long.MAX_VALUE - baseTimestamp`를 초과하면 타임스탬프 델타가 `INT_MAX` 또는 `INT_MIN` 경계를 넘을 수 있음. 이 경우 타임스탬프 델타의 오버플로를 방지하기 위해 압축 중에 배치가 분할됨.

`baseTimestamp`는 CRC 계산에 포함되는 반면, `MaxTimestamp`는 압축 후 리더에 의해 업데이트됨. 따라서 CRC를 검증하지 않는 소비자는 `MaxTimestamp`를 사용해야 함.

##### 제어 배치 (Control Batches)

제어 배치는 제어 레코드라고 불리는 단일 레코드를 포함함. 제어 레코드는 애플리케이션에 전달되어서는 안 됨. 대신, 중단된 트랜잭션 메시지를 필터링하기 위해 소비자가 사용함.

제어 레코드의 키는 다음 스키마를 따름:

```
version: int16 (현재 항상 0)
type: int16 (0은 중단을 나타내고, 1은 커밋을 나타냄)
```

제어 레코드의 값 스키마는 다음과 같음:

- 0: 값이 무시됨

키와 값의 버전 태그는 향후 더 복잡한 제어 레코드 스키마가 필요할 경우 독립적인 발전을 허용하기 위한 것임.

#### 5.3.2 레코드 (Record)

레코드 수준 헤더는 Kafka 0.11.0에서 도입됨. 헤더가 있는 레코드의 디스크 형식은 아래에 설명됨.

```
length: varint
attributes: int8
    bit 0~7: 미사용
timestampDelta: varlong
offsetDelta: varint
keyLength: varint
key: byte[]
valueLen: varint
value: byte[]
Headers => [Header]
```

##### 레코드 헤더 (Record Header)

```
headerKeyLength: varint
headerKey: String
headerValueLength: varint
headerValue: byte[]
```

헤더 배열에는 별도의 개수 필드가 없음. 대신 레코드 항목 수는 레코드 배치의 레코드 개수 필드를 사용함.

#### 5.3.3 레거시 메시지 형식

0.11 이전의 Kafka에서는 메시지가 메시지 집합(message sets) 내에서 전송되고 저장되었음. 메시지 집합에서 각 메시지는 고유한 메타데이터를 가짐. 메시지 집합은 단순히 파일과 네트워크에서 동일한 형식을 갖는 메시지 배열임.

```
MessageSet (Version: 0) => [offset message_size message]
    offset => INT64
    message_size => INT32
    message => crc magic_byte attributes key value
        crc => INT32
        magic_byte => INT8
        attributes => INT8
            bit 0~2:
                0: 압축 없음
                1: gzip
                2: snappy
            bit 3~7: 미사용
        key => BYTES
        value => BYTES
```

```
MessageSet (Version: 1) => [offset message_size message]
    offset => INT64
    message_size => INT32
    message => crc magic_byte attributes timestamp key value
        crc => INT32
        magic_byte => INT8
        attributes => INT8
            bit 0~2:
                0: 압축 없음
                1: gzip
                2: snappy
                3: lz4
            bit 3: timestampType
                0: 생성 시간 (CreateTime)
                1: 로그 추가 시간 (LogAppendTime)
            bit 4~7: 미사용
        timestamp => INT64
        key => BYTES
        value => BYTES
```

레거시 메시지 형식에서 압축은 다르게 처리됨. 각 압축된 메시지의 값 필드에는 메시지 집합이 포함되어 있으며, 이 메시지 집합 내에 실제 메시지(적절한 오프셋·키·값 포함)와 재귀적으로 중첩된 메시지 집합(추가 압축된 메시지 포함)이 있음.

참고: CRC-32 IEEE 다항식은 레거시 메시지에 대해 계산됨.

### 5.4 로그 (Log)

"my_topic"이라는 이름과 두 개의 파티션을 가진 토픽의 로그는 두 개의 디렉토리(my_topic_0과 my_topic_1)로 구성되며, 해당 토픽의 메시지를 담은 데이터 파일로 채워짐. 로그 파일의 형식은 "로그 항목(log entries)"의 시퀀스임. 각 로그 항목은 메시지의 바이트 수를 나타내는 4바이트 정수 N과 그 뒤에 오는 N개의 메시지 바이트로 구성됨. 각 메시지는 64비트 정수 오프셋으로 고유하게 식별되며, 이 오프셋은 해당 파티션으로 전송된 전체 메시지 스트림에서 해당 메시지가 시작하는 바이트 위치를 나타냄. 각 메시지의 디스크 형식은 아래에서 설명함. 각 로그 파일의 이름은 파일에 포함된 첫 번째 메시지의 오프셋임. 따라서 생성된 첫 번째 파일은 00000000000000000000.log가 되고, 이후 파일들은 대략 S바이트(S는 구성에 지정된 최대 로그 파일 크기) 간격의 오프셋 이름을 갖게 됨.

메시지 고유 식별자로 GUID 대신 오프셋을 사용하는 것은 의도적인 설계 결정임. 랜덤 ID와 오프셋 위치 간의 매핑을 유지하는 무거운 데이터 구조 대신 단순한 단조 증가 정수를 사용할 수 있음. 이 정수는 파티션 범위를 벗어나면 고유하지 않으므로 외부 시스템에서 직접 사용할 수는 없지만, 소비자 API가 이 세부 사항을 감춰줌.

레코드는 항상 배치 단위로 기록됨. 레코드 배치에는 하나 이상의 레코드가 포함되며, 비정상적인 경우에는 단일 레코드만 포함될 수 있음. 레코드 배치와 레코드는 각각 고유한 헤더를 가지며, 형식은 위에서 설명한 바와 같음.

#### 5.4.1 쓰기 (Writes)

로그는 마지막 파일에 순차적으로 추가됨. 이 파일이 구성 가능한 크기(예: 1GB)에 도달하면 새 파일로 롤오버됨. 로그는 두 가지 구성 매개변수를 사용함. M은 OS가 파일을 디스크로 강제 플러시하기 전에 기록할 메시지 수이고, S는 강제 플러시가 발생하는 시간(초)임. 이를 통해 시스템 충돌 시 최대 M개의 메시지 또는 S초 분량의 데이터까지만 손실될 수 있다는 내구성을 보장함.

#### 5.4.2 읽기 (Reads)

읽기는 64비트 논리 오프셋과 최대 청크 크기 S바이트를 지정하여 수행됨. 이 호출은 S바이트 버퍼에 포함된 메시지의 반복자를 반환함. S는 단일 메시지보다 크게 설정해야 하지만, 비정상적으로 큰 메시지의 경우 읽기를 여러 번 재시도하면서 버퍼 크기를 매번 두 배로 늘릴 수 있음(단일 메시지만 반환되더라도). 최대 메시지 및 버퍼 크기를 지정하면 서버가 해당 크기까지 버퍼를 확대하도록 할 수 있으며, 클라이언트 측에서도 최대 크기까지 반복 시도하도록 설정할 수 있음. 읽기 버퍼가 전체 메시지가 아닌 부분 메시지로 끝나는 경우, 크기 구분자로 쉽게 감지되며 버퍼를 추가로 읽거나 확장하여 해결됨.

지정된 오프셋에서 읽는 실제 과정은 다음과 같음. 먼저 데이터가 저장된 로그 세그먼트 파일을 찾고, 전역 오프셋 값에서 해당 파일의 파일 내 오프셋을 계산한 뒤, 그 오프셋에서 읽음. 검색은 각 파일에 대해 메모리에 유지되는 간단한 범위를 대상으로 이진 탐색으로 수행됨.

로그는 아직 존재하지 않는 오프셋 검색도 허용하므로 로그 끝을 넘어서는 데이터 요청이 가능함. 해당 메시지가 아직 없지만 고가용성 보장이 활성화된 경우 나중에 나타날 수 있을 때 유용함. 자세한 내용은 복제 섹션 참조.

#### 5.4.3 삭제 (Deletes)

데이터는 한 번에 하나의 로그 세그먼트씩 삭제됨. 로그 관리자는 구성 가능한 방식으로 로그 tail의 세그먼트를 삭제할 수 있음. 현재 두 가지 정책이 있음: 오래된 로그를 삭제하는 시간 기반 보존 정책과 로그 크기에 따른 크기 기반 정책. 활성화하려면 구성 섹션의 보존 정책 설정 참조. 사용 가능한 옵션은 시간 기반·크기 기반·압축임.

보존 시간 기반 정책: 세그먼트 파일의 가장 큰 타임스탬프보다 보존 기간이 더 오래된 경우 해당 세그먼트가 삭제됨.

크기 기반 보존 정책: 파티션의 전체 크기가 구성된 크기 이하가 될 때까지 가장 오래된 세그먼트부터 순서대로 삭제됨.

참고: 세그먼트 내 모든 레코드가 만료된 경우에도 시간 기반 보존에 의해 즉시 삭제되지 않을 수 있음. 세그먼트에 만료되지 않은 레코드가 하나라도 있으면 해당 레코드가 모두 만료될 때까지 세그먼트가 삭제되지 않음.

참고: 세그먼트는 읽기를 차단하지 않는 copy-on-write 스타일로 삭제됨.

#### 5.4.4 보장 (Guarantees)

로그는 디스크에 플러시된 모든 레코드 배치에 대해 CRC32 체크섬을 유지함. 로그 복구 시 각 레코드 배치의 유효성이 검사됨. 기록된 각 레코드 배치에 대해 길이와 오프셋이 단조 증가하는지 확인함. 손상이 감지되면(레코드 길이가 음수이거나, 오프셋이 단조롭게 증가하지 않거나, CRC가 일치하지 않는 경우) 로그는 마지막으로 유효한 오프셋으로 잘림.

또한 오프셋이 불연속적으로 건너뛰는 두 가지 위험 시나리오도 방지해야 함:

1. 커밋되지 않은 데이터를 잃는 장애 — 오프셋 5의 메시지가 커밋되고 오프셋 6의 메시지가 프로듀서에게 승인되었지만, 복제본이 이를 기록하기 전에 장애가 발생하는 시나리오
2. 데이터가 "재출현"하는 장애 — 메시지 6을 수락한 복제본이 장애 후 클러스터에서 제거되고, 오프셋 6에 다른 메시지가 기록된 뒤 해당 복제본이 다시 합류하면 원래 오프셋 6이 다시 나타나 복제본 간 오프셋/데이터 불일치가 발생하는 시나리오

복제된 로그의 오프셋/데이터 일관성은 Kafka의 복제 프로토콜이 보장하며, 아래에서 다룸.

### 5.5 분산 (Distribution)

#### 소비자 오프셋 추적 (Consumer Offset Tracking)

Kafka 소비자는 소비한 파티션의 최대 오프셋을 추적하고, 서버 장애 시 해당 오프셋에서 재개할 수 있도록 오프셋을 커밋할 수 있음.

Kafka는 지정된 소비자 그룹의 모든 오프셋을 그룹 코디네이터(group coordinator)라고 불리는 브로커에 저장하는 옵션을 제공함. 즉, 해당 소비자 그룹의 모든 소비자 인스턴스는 오프셋 커밋과 페치 요청을 코디네이터 브로커에 전송해야 함. 소비자 그룹에는 그룹 이름을 기반으로 코디네이터가 할당됨. 소비자는 임의의 Kafka 브로커에 `FindCoordinatorRequest`를 보내고 코디네이터 세부 정보가 담긴 `FindCoordinatorResponse`를 받아 코디네이터를 찾을 수 있음. 이후 소비자는 코디네이터 브로커에서 오프셋을 커밋하거나 페치함. 코디네이터가 변경되면 소비자는 코디네이터를 다시 찾아야 함. 오프셋 커밋은 소비자가 자동 또는 수동으로 수행할 수 있음.

그룹 코디네이터가 `OffsetCommitRequest`를 받으면 해당 요청을 `__consumer_offsets`라는 특수 압축 Kafka 토픽에 추가함. 브로커는 오프셋 토픽의 모든 복제본이 오프셋을 수신한 후에만 소비자에게 성공 응답을 보냄. 오프셋이 구성된 시간 내에 복제되지 않으면 오프셋 커밋이 실패하며, 소비자는 백오프 후 커밋을 재시도할 수 있음. (엔드 투 엔드 시나리오에서는 고가용성 보장에 의해 자동으로 처리됨.)

브로커는 주기적으로 `__consumer_offsets` 토픽을 압축함. 압축 과정에서 오래된 오프셋 커밋은 삭제됨.

코디네이터는 빠른 오프셋 페치를 위해 오프셋을 메모리 테이블에 캐시함. 브로커가 특정 소비자 그룹의 코디네이터가 되면(또는 시작 시 로드하면), 소비자에게 응답하기 전에 오프셋 토픽 파티션을 캐시로 읽어 들임. 오프셋 페치 요청이 들어오면 코디네이터는 오프셋 캐시에서 마지막으로 커밋된 오프셋 벡터를 조회하여 반환함.

코디네이터가 오프셋 토픽 파티션을 로딩하는 중에 요청이 도착하면 `CoordinatorLoadInProgressException`이 발생하며, 소비자는 백오프 후 `OffsetFetchRequest`를 재시도할 수 있음.

### 요약

Apache Kafka 구현의 핵심 설계 원칙은 다음과 같음:

1. 네트워크 레이어: NIO 기반의 효율적인 서버로, `sendfile` 시스템 콜을 활용한 제로 카피 전송을 지원함.

2. 메시지 형식: 유연한 직렬화를 위해 불투명한 키-값 구조를 사용하며, 레코드 배치 단위로 효율적으로 처리함.

3. 로그 저장: 순차 추가 방식의 로그 구조, 오프셋 기반 메시지 식별, CRC32 체크섬을 통한 데이터 무결성을 보장함.

4. 분산 처리: 그룹 코디네이터를 통해 소비자 오프셋을 관리하고, `__consumer_offsets` 토픽으로 오프셋을 저장·복제함.
