# ChaCha20-Poly1305

> 원문: https://en.wikipedia.org/wiki/ChaCha20-Poly1305

## 개요

- ChaCha20-Poly1305: ChaCha20 스트림 암호와 Poly1305 메시지 인증 코드를 결합한 AEAD(Authenticated Encryption with Associated Data) 알고리즘
- 하드웨어 가속이 없는 시스템에서 소프트웨어만으로 구현 시 → 일반적으로 AES-GCM보다 빠른 성능
- 타이밍 공격에 대한 내성도 더 강함

## 역사

### 구성 요소의 탄생

- ChaCha20-Poly1305를 구성하는 두 요소는 Daniel J. Bernstein이 각각 독립적으로 설계
  - Poly1305 (2005): 일회용 키 기반의 메시지 인증 코드 · 원래 AES와 함께 Poly1305-AES로 제안됨
  - ChaCha20 (2008): Salsa20 스트림 암호의 변형 · 라운드당 확산(diffusion) 향상 · Salsa20 eSTREAM 프로젝트의 수상작을 기반으로 함

### IETF 표준화 과정

- 2013년 3월: IETF TLS 워킹 그룹에 RC4 기반 암호 스위트를 대체하기 위해 Salsa20을 사용하는 제안서 제출
- 이후 논의를 거쳐 Adam Langley가 제안한 변형이 채택됨
  - 32비트 블록 카운터와 96비트 논스를 사용하는 ChaCha20 변형
  - Poly1305의 수정 버전
- 이 조합은 TLS 및 DTLS용 IETF 인터넷 초안으로 작성됨

### OpenSSH의 채택

- OpenSSH는 `chacha20-poly1305@openssh.com` 암호를 통해 AEAD 모드 통합
- 이 구현은 원래의 64비트 카운터와 논스를 유지 (IETF 변형의 32비트 카운터/96비트 논스와는 다름)

### 표준화 연혁

- 2015년: RFC 7539 → ChaCha20-Poly1305 AEAD 알고리즘 표준화
- 2015년: RFC 7634 → IPsec에서의 ChaCha20-Poly1305 사용
- 2015년: Cloudflare 채택 → 대체 암호 스위트로 통합
- 2016년: RFC 7905 → TLS 1.2 및 DTLS 1.2에서의 구현 기술
- 2018년: RFC 8439 → RFC 7539를 대체하는 최신 규격

## 상세 설명

### 알고리즘 구조

- ChaCha20-Poly1305는 256비트 키와 96비트 논스를 입력으로 받음
- 암호문에 128비트(16바이트)의 인증 태그가 추가됨

#### 암호화 과정

- Poly1305 키 생성: ChaCha20의 첫 번째 블록(카운터 = 0)을 사용하여 Poly1305용 일회용 키(256비트) 생성
- 키스트림 생성: ChaCha20의 카운터를 1부터 시작하여 키스트림 블록 생성
- 암호화: 키스트림과 평문을 XOR하여 암호문 생성
- 인증: 연관 데이터(AAD)와 암호문을 Poly1305로 인증하여 128비트 태그 생성

#### ChaCha20 내부 상태

- ChaCha20의 내부 상태는 4x4 행렬의 32비트 워드(총 512비트 = 64바이트)로 구성

```
상태 = [상수, 상수, 상수, 상수,
        키,   키,   키,   키,
        키,   키,   키,   키,
        카운터, 논스, 논스, 논스]
```

- 상수: "expand 32-byte k"의 ASCII 인코딩 (4워드)
- 키: 256비트 키 (8워드)
- 카운터: 32비트 블록 카운터 (1워드)
- 논스: 96비트 논스 (3워드)

#### 쿼터 라운드 연산

- ChaCha20은 쿼터 라운드(quarter round) 연산을 핵심 구성 요소로 사용
- 각 쿼터 라운드는 4개의 32비트 워드(a, b, c, d)에 다음 연산 적용

```
a += b; d ^= a; d <<<= 16;
c += d; b ^= c; b <<<= 12;
a += b; d ^= a; d <<<= 8;
c += d; b ^= c; b <<<= 7;
```

- 20라운드(10 더블 라운드) 수행 → 각 더블 라운드는:
  - 컬럼 라운드: 4개의 열에 쿼터 라운드 적용
  - 대각선 라운드: 4개의 대각선에 쿼터 라운드 적용

#### Poly1305 인증

- Poly1305 동작 순서
  - 입력 메시지를 16바이트 블록으로 분할
  - 각 블록을 소수 p = 2^130 - 5에 대한 모듈러 산술로 처리
  - 인증 키 r과 일회용 키 s를 사용하여 다음 식으로 태그 계산
    - tag = ((c₁·r^n + c₂·r^(n-1) + ... + cₙ·r) mod p) + s mod 2^128
    - c_i는 메시지 블록을 인코딩한 정수

#### ChaCha20의 블록 크기 이점

- ChaCha20의 블록 크기는 64바이트(512비트)로, AES의 16바이트(128비트)보다 4배 큼
- 이점
  - 최신 CPU에서 더 나은 성능 (더 적은 블록 암호 호출)
  - 32비트 카운터로도 256 GiB까지 암호화 가능 (AES-CTR의 64 GiB 대비)

#### Poly1305 인증 대상 구성

- 인증 태그 계산에 사용되는 데이터의 구성

```
연관 데이터(AAD) || 패딩 || 암호문 || 패딩 || AAD 길이(8바이트) || 암호문 길이(8바이트)
```

- 패딩은 각 섹션을 16바이트 경계에 맞추기 위해 영(zero) 바이트를 추가

## 변형

### XChaCha20-Poly1305 - 확장 논스 변형

- XChaCha20-Poly1305: ChaCha20 대신 XChaCha20을 사용하여 논스를 192비트(24바이트)로 확장

#### 동작 원리

- XChaCha20은 두 단계로 동작
  - HChaCha20: 256비트 키와 192비트 논스의 처음 128비트를 사용하여 256비트 서브키 생성
  - ChaCha20: 서브키와 192비트 논스의 마지막 64비트(+ 32비트 0 패딩)를 사용하여 키스트림 생성

#### 이점

- 랜덤 논스 안전성: 192비트 논스 공간이 충분히 커서 → 논스를 랜덤으로 생성해도 충돌 확률이 무시할 수 있을 정도로 낮음 (생일 역설 기준 약 2^96개의 메시지까지 안전)
- 상태 비유지: 카운터 관리 없이 랜덤 논스 사용 가능

#### 표준화 상태

- XChaCha20-Poly1305에 대한 인터넷 초안 작성됨 → 2020년 7월 만료
- 표준화는 이루어지지 않았으나, libsodium 등 주요 라이브러리에서 지원

### Salsa20-Poly1305 및 XSalsa20-Poly1305

- 이 변형들은 ChaCha 변형 대신 Salsa20과 XSalsa20을 사용
- NaCl(Networking and Cryptography library)과 libsodium에 구현됨
- 표준화되지 않음
- ChaCha 변형이 Salsa20 변형보다 라운드당 확산(diffusion)이 더 우수 → 실질적으로 ChaCha 변형이 선호됨

### 축소 라운드 변형

- ChaCha20(20라운드) 대신 라운드 수를 줄인 변형
  - ChaCha20-Poly1305
    - 라운드 수: 20
    - 보안성: 전체 보안 마진
    - 성능: 기준
  - ChaCha12-Poly1305
    - 라운드 수: 12
    - 보안성: 충분한 보안 마진
    - 성능: 약 1.7배 빠름
  - ChaCha8-Poly1305
    - 라운드 수: 8
    - 보안성: 최소 보안 마진
    - 성능: 약 2.5배 빠름
- XChaCha20-Poly1305에도 동일한 축소 라운드 변형(XChaCha12, XChaCha8) 적용 가능
- RustCrypto 팀이 이러한 비표준 변형들을 구현 중

## 사용

- ChaCha20-Poly1305는 다음 프로토콜과 시스템에서 사용됨

### 네트워크 프로토콜

- IPsec: RFC 7634 → ESP(Encapsulating Security Payload)
- SSH: OpenSSH → chacha20-poly1305@openssh.com 암호
- TLS 1.2: RFC 7905 → 암호 스위트
- DTLS 1.2: RFC 7905 → 데이터그램 TLS
- TLS 1.3: RFC 8446 → 필수 암호 스위트 중 하나

### VPN 및 터널링

- WireGuard: 유일한 데이터 채널 암호화 알고리즘

### 메시징 및 이메일

- S/MIME 4.0: 보안 이메일
- OTRv4: Off-the-Record 메시징 프로토콜 v4

### 스토리지 및 파일시스템

- Borg: 백업 소프트웨어의 기본 데이터 암호화
- Bcachefs: 선택적 전체 파일시스템 암호화

### 네트워크 도구

- V2Ray: 다중 암호화 트래픽 방법 중 하나

### 암호화 라이브러리

- OpenSSL: 범용 암호화 라이브러리
- libsodium: 고수준 암호화 라이브러리 · XChaCha20-Poly1305도 지원

## 성능

### 소프트웨어 성능 특성

- ChaCha20-Poly1305는 AES-NI 하드웨어 가속이 없는 시스템에서 일반적으로 AES-GCM보다 성능 우수
- 이유
  - 상수 시간 구현 용이: ChaCha20은 ARX(Addition-Rotation-XOR) 연산만 사용 → 테이블 조회 불필요 → 캐시 타이밍 부채널에 본질적으로 안전
  - SIMD 친화적: 쿼터 라운드 연산은 SIMD(단일 명령 다중 데이터) 명령어에 직접 매핑됨
  - 큰 블록 크기: 64바이트 블록은 AES의 16바이트 블록보다 호출 오버헤드가 적음

### ARM 기기에서의 이점

- 하드웨어 AES 가속이 없는 ARM 기반 CPU를 사용하는 모바일 기기에서 ChaCha20-Poly1305는 특히 중요
  - AES-GCM의 소프트웨어 구현보다 상당히 빠름
  - 전력 소비가 적음: 더 적은 연산 오버헤드로 배터리 소모 감소
  - 구형 Android 기기에서 HTTPS 성능을 크게 개선 (Google Chrome이 이 이유로 ChaCha20-Poly1305를 우선 선택)

### AES-NI 지원 시스템에서의 비교

- AES-NI가 있는 시스템에서는 AES-GCM이 일반적으로 더 빠름
- 다만 ChaCha20의 AVX2/AVX-512 최적화 구현은 AES-GCM과 경쟁력 있는 성능 달성 가능

## 보안

### 보안 증명

- ChaCha20-Poly1305 구성은 표준 모델(standard model)과 이상적 순열 모델(ideal permutation model)에서 단일 사용자 및 다중 사용자 환경 모두에 대해 일반적 보안 증명됨

### 논스 고유성 요구

- GCM과 마찬가지로, ChaCha20-Poly1305의 보안은 각 암호화 메시지에 고유한 논스를 사용하는 것에 의존
- 동일한 키-논스 쌍을 재사용하면:
  - 동일한 키스트림이 생성되어 두 평문의 XOR 노출
  - Poly1305 키가 동일해져 인증 태그 위조 가능해질 수 있음

### 타이밍 공격 내성

- ChaCha20-Poly1305 구현은 AES-GCM 구현에 비해 타이밍 공격에 덜 취약
  - ChaCha20은 테이블 조회를 사용하지 않음 → 캐시 타이밍 부채널 부재
  - Poly1305도 데이터 종속적인 분기나 메모리 접근 패턴 없음
  - AES의 소프트웨어 구현은 S-box 테이블 조회로 인해 캐시 타이밍 공격에 취약할 수 있음 (하드웨어 AES-NI 사용 시 이 문제 해결)

### Terrapin 공격

- SSH에서 ChaCha20-Poly1305를 사용할 때 Terrapin 공격에 취약해짐
- 이 공격은 2023년에 공개됨
  - SSH 핸드셰이크 중 메시지 시퀀스 번호를 조작하여 초기 메시지 삭제 가능
  - SSH의 메시지 순서 번호가 논스로 사용되는 특성을 악용
  - 이 취약점은 ChaCha20-Poly1305 자체의 결함이 아니라, SSH 프로토콜이 이를 사용하는 방식의 문제
  - 대응책으로 "strict key exchange" 확장 도입됨

### 데이터 크기 제한

- 32비트 카운터(IETF 변형): 단일 키-논스 쌍으로 최대 256 GiB 암호화 가능
- 이 한계 초과 시 키 재생성(rekeying) 필요
