  - 데이터 집약적 애플리케이션을 별도 범주로 다뤄야 하는 Chapter 1의 출발점과 연결됨
- 핵심 내용
  - 과학 및 산업 현장에서 생성되는 데이터가 기하급수적으로 증가함
  - 데이터를 확보하는 능력에 비해 저장, 이동, 분석하여 의미 있는 결과를 내는 능력이 부족해짐
  - 기존 계산 집약적 접근만으로는 데이터 이동과 I/O 병목을 해결하기 어려움
  - 새로운 소프트웨어, 알고리즘, 하드웨어를 함께 설계해야 적시에 분석 결과를 얻을 수 있음
  - 데이터 관리, 분석, 시각화, 워크플로를 결합한 종합적 접근이 필요함
- 요지
  - 현대 시스템의 핵심 제약이 CPU 연산에서 데이터 관리로 이동함
  - 데이터 시스템 설계는 저장 용량뿐 아니라 이동 비용, 분석 지연, 도구 간 통합을 함께 고려해야 함

## Reference 002

- [x] 번역 및 요약 완료
- 원문: [Local-first software: you own your data, in spite of the cloud](https://www.inkandswitch.com/essay/local-first/)
- 한국어 제목: 로컬 우선 소프트웨어 — 클라우드를 사용해도 데이터는 사용자가 소유함
- 확인 범위: 공개 전문에서 문제 제기, 일곱 가지 이상, CRDT 논의, 결론 확인
- DDIA 연결 맥락
  - 데이터 저장 위치와 권위 있는 사본의 선택이 사용자 경험, 통제권, 가용성에 미치는 영향 설명
  - 클라우드 중심 구조 외에도 요구사항에 따라 다른 데이터 시스템 구조를 선택할 수 있음을 보여줌
- 핵심 내용
  - 클라우드 앱은 여러 기기 접근과 실시간 협업을 제공하지만 서버 운영자에게 데이터와 서비스의 통제권을 집중함
  - 서비스가 종료되거나 계정 접근이 차단되면 데이터 내보내기만으로 애플리케이션의 지속 사용을 보장하기 어려움
  - 로컬 우선 구조에서는 사용자 기기의 사본을 기본 사본으로 취급하고 서버 사본은 동기화를 돕는 보조 역할을 맡음
  - 지향점은 즉각적인 반응, 다중 기기, 오프라인 작업, 협업, 장기 보존, 기본 보안과 프라이버시, 사용자 통제권임
  - 로컬 읽기 및 쓰기로 네트워크 왕복 지연을 사용자 경로에서 제거하고 동기화는 백그라운드에서 수행함
  - 기존 파일, 이메일, Git, 클라우드 앱은 일부 요구사항만 만족하며 모든 이상을 동시에 충족하지는 못함
  - CRDT는 여러 사용자가 각자 로컬에서 변경한 상태를 중앙 조정 없이 병합할 수 있는 기반 기술 후보임
- 요지
  - 데이터 시스템의 권위 있는 사본을 어디에 둘지는 단순한 구현 세부사항이 아님
  - 성능, 협업, 가용성, 프라이버시, 데이터 소유권 사이의 제품 수준 트레이드오프를 결정함

  - OLAP이라는 용어와 다차원 분석 모델의 역사적 배경 제공

  - 사용자 분석가는 매출을 시간, 지역, 제품, 시나리오처럼 여러 차원으로 바라봄

  - OLAP 도구는 기존 스프레드시트 및 그래픽 도구에 자연스럽게 결합되고 데이터 출처의 이질성을 감춰야 함
  - 여러 데이터 원천에 접근하되 사용자가 변환 및 추출의 복잡성을 직접 다루지 않도록 해야 함
  - 보고 성능, 클라이언트 서버 구조, 희소 행렬 처리, 다중 사용자 지원, 차원 간 연산을 평가 기준으로 제시함
  - 유연한 보고와 차원 및 집계 수준의 확장성도 핵심 조건으로 봄
- 요지
  - OLAP는 단순히 큰 질의를 실행하는 기능이 아니라 분석가의 다차원 사고방식을 시스템 모델로 제공하는 방식임
  - 분석 시스템은 표현력, 사용성, 일관된 성능을 함께 충족해야 함

- DDIA 연결 맥락
  - 같은 실시간 분석 범주 안에서도 시스템별 데이터 모델과 운영 특성이 달라짐을 구체적으로 보여줌
  - 하나의 데이터 시스템이 모든 사용 사례에 최적일 수 없다는 Chapter 1의 문제의식과 연결됨
- 핵심 내용
  - 배치 보고에서 데이터 생성 직후 밀리초 단위로 분석하는 실시간 OLAP 수요로 이동함
  - 세 제품을 데이터 원천, 수집 방식, 스키마, 인덱스, 질의 기능, 보안, 클라우드 운영 관점에서 비교함
  - Pinot은 실시간 스트림과 변경 데이터 캡처, 다양한 인덱스, 운영 자동화에 강점을 둠
  - Druid는 배치와 스트림 수집 및 수집 단계 전처리에 강점이 있으나 실시간 upsert 제약이 있음
  - ClickHouse는 단일 노드 시작과 데이터 형식 및 질의 기능이 편리하지만 분산 운영과 스트림 pull 방식에는 추가 고려가 필요함
  - 인덱스는 스캔 범위를 줄여 지연시간과 서버당 자원 사용량을 크게 낮출 수 있음
  - 데이터 원천, 갱신 방식, 질의 복잡도, 운영 인력에 따라 적합한 선택이 달라짐
- 해석 시 주의
  - Pinot 관련 기업이 작성하고 이후 제품 버전에 맞게 갱신한 비교 자료임
  - 제품 우열보다 비교 축과 설계 차이를 이해하는 자료로 사용하는 편이 적절함

- 핵심 내용
  - 실시간 가격, 재고, 추천, 사기 탐지, 위험 분석, IoT는 빠른 트랜잭션과 최신 데이터 분석을 함께 요구함
  - 일부 애플리케이션은 트랜잭션 안에서 분석 질의까지 수행해야 함
  - OLTP와 OLAP는 각각 효율적인 최적화 방향과 아키텍처가 달라 한 시스템에서 함께 처리하기 어려움
  - HTAP 해법은 단일 통합 시스템부터 OLTP 저장소와 Spark 같은 분석 플랫폼의 느슨한 결합까지 다양함
  - 비교 축은 수집 및 질의 엔진, 저장 방식, 데이터 배치, 트랜잭션 의미론, 분석 데이터 최신성, 인덱스 지원 등임
  - 핵심 과제는 한 워크로드가 다른 워크로드의 지연시간과 처리량을 훼손하지 않도록 격리하는 것임
- 요지
  - HTAP는 단순한 기능 합치기가 아니라 상충하는 워크로드를 어떤 구조로 공존시킬지의 문제임
  - 데이터 최신성, 격리, 저장 중복, 운영 복잡성 사이에서 선택이 필요함

- 확인 범위: 공개 전문의 초록, 서론, 저장 구조 분류, 핵심 기술, 과제
- DDIA 연결 맥락
  - HTAP 시스템의 다양한 저장 구조를 공통 분류로 정리하여 제품별 차이를 비교할 기준 제공
  - 최신 데이터 분석과 트랜잭션 성능을 동시에 달성할 때 발생하는 구조적 선택을 보여줌
- 핵심 내용
  - HTAP는 별도 ETL 파이프라인의 지연 없이 트랜잭션 데이터에 대한 실시간 분석을 제공하려 함
  - 시스템을 주 row store와 메모리 column store, 분산 row store와 column replica, 주 row store와 분산 메모리 column store, 주 column store와 delta row store의 네 구조로 분류함
  - row store는 지점 조회, 갱신에 유리하고 column store는 압축, 벡터화, 대규모 스캔에 유리함
  - 두 표현을 함께 유지하면 워크로드별 성능을 높일 수 있지만 복제 비용과 데이터 최신성 문제가 발생함
  - 주요 기술 과제는 혼합 워크로드 처리, 데이터 조직, 동기화, 질의 최적화, 자원 스케줄링임
  - 평가 시 트랜잭션 처리량과 분석 지연시간뿐 아니라 데이터 신선도와 워크로드 간 간섭도 측정해야 함
- 요지
  - HTAP의 핵심은 row와 column 가운데 하나를 고르는 문제가 아니라 두 장점을 어떤 비용으로 결합할지 결정하는 것임
  - 저장 중복, 동기화 지연, 자원 격리, 질의 최적화가 실제 성능과 운영 복잡성을 좌우함
