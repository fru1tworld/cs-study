# NAT

## RFC 3022 - 전통적인 IP 네트워크 주소 변환기 (Traditional NAT)

```
Network Working Group                                       P. Srisuresh
Request for Comments: 3022                              Jasmine Networks
Obsoletes: 1631                                               K. Egevang
Category: Informational                                Intel Corporation
                                                            January 2001
```

### 개요

- 이 문서는 정보 제공(Informational) 성격 → 인터넷 표준을 규정하지 않음
- RFC 1631에서 소개된 주소 변환을 확장 → 새로운 유형의 네트워크 주소·TCP/UDP 포트 변환 포함
- RFC 1631의 체크섬 조정 알고리즘 수정 + NAT 동작·제한사항 상세 논의

### 요약

- 기본 NAT(Basic NAT): IP 주소를 한 그룹에서 다른 그룹으로 매핑 → 최종 사용자에게 투명
- NAPT(네트워크 주소 포트 변환): 여러 네트워크 주소와 TCP/UDP 포트를 단일 네트워크 주소·포트로 변환
- 기본 NAT + NAPT = 전통적인 NAT
  - 사설 주소를 가진 영역과 전역적으로 고유한 등록 주소를 가진 외부 영역을 연결하는 메커니즘 제공

### 1. 소개

- IP 주소 변환 필요성: 내부 IP 주소가 프라이버시 이유 또는 외부에서 유효하지 않아 사용 불가할 때 발생
- 로컬 도메인 외부 토폴로지 변경 사유: 제공업체 변경 · 백본 재구성 · 제공업체 합병/분할
  - 외부 토폴로지 변경 시 로컬 도메인 내 주소 할당도 반영되어야 함
  - 이런 변경을 단일 주소 변환 라우터에 집중 → 도메인 내 사용자에게는 숨김 가능
- 기본 주소 변환의 역할
  - 사설 네트워크 호스트가 외부 네트워크에 투명하게 접근
  - 외부에서 선택적인 로컬 호스트로의 접근도 가능
  - 주로 내부용이면서 가끔 외부 접근이 필요한 조직에 적합
- SOHO(소규모 사무실·홈 오피스)·재택근무 사용 사례
  - 사무실 내 다수 노드가 TCP/UDP 애플리케이션 실행
  - 원격 접근 라우터에는 서비스 제공업체가 할당한 단일 IP 주소만 존재
  - NAPT 적용 시 다수 노드가 단일 IP 주소로 원격 네트워크에 동시 접근 가능
- 변환 방법 사용상의 제한
  - 세션 관련 요청·응답 모두 동일한 NAT 라우터를 통해야 함(필수)
  - 확인 방법: 스텁 도메인에 고유한 경계 라우터 기반으로 NAT 적용 → 모든 IP 패킷이 그 경로로만 통과
  - 여러 NAT 장치로 보장하는 방법도 존재
    - 사설 도메인이 서로 다른 제공업체로 두 개의 출구 지점을 가질 수 있음
    - 세션 흐름은 목적지에 대해 가장 좋은 메트릭을 가진 NAT 장치를 통과
    - 한 NAT 라우터 실패 시 다른 라우터가 트래픽 라우팅 가능
    - 주의점: 재라우팅된 흐름이 전환 시점에 실패할 가능성 있음
    - 극복 방법: 라우터들이 동일한 NAT 구성을 공유하고 상태 정보를 교환 → 서로 안전한 백업 보장
- 주소 변환과 ALG(애플리케이션별 게이트웨이)
  - 주소 변환은 애플리케이션에 독립적 → 종종 페이로드 모니터링/변경을 수행하는 ALG를 동반
  - FTP: NAT 장치에 상주하는 가장 인기 있는 ALG
  - ALG 개입이 필요한 애플리케이션은 페이로드가 인코딩되면 안 됨 → 인코딩 시 ALG가 복호화 키 없이는 무력화됨
- 이 솔루션의 트레이드오프
  - 단점: IP 주소의 종단 간 의미 상실 + 네트워크 상태 증가
    - NAT 장치가 경로 중에 있으면 IPSec이 보장하는 종단 간 보안이 종단 호스트에 적용된다고 가정 불가
  - 장점: 호스트·라우터 변경 없이 설치 가능
- 용어("주소 영역"·"투명 라우팅"·"TU 포트"·"ALG" 등)의 정의는 [NAT-TERM] 참조

### 2. 전통적인 NAT 개요

- 이 문서에서 다루는 주소 변환 동작 = "전통적인 NAT" (다른 변형은 다루지 않음)
- 특징
  - 사설 네트워크 호스트가 외부 네트워크 호스트에 투명하게 접근
  - 세션은 단방향: 사설 네트워크 → 외부
  - 반대 방향 세션은 미리 선택된 호스트에 대한 정적 주소 매핑으로 예외적 허용
  - 기본 NAT: 변환이 IP 주소로 제한
  - NAPT: 변환이 IP 주소 + 전송 식별자(TCP/UDP 포트, ICMP 쿼리 ID 등)까지 확장
- 이후 이 문서에서 "주소 변환"·"NAT"는 별도 언급 없으면 기본 NAT + NAPT를 모두 의미
- 그림 1: 스텁 경계 라우터만 주소 변환 수행 가능

```
        \ | /                 .                                /
   +---------------+  WAN     .           +-----------------+/
   |Regional Router|----------------------|Stub Router w/NAT|---
   +---------------+          .           +-----------------+\
                              .                      |         \
                              .                      |  LAN
                              .               ---------------
                        Stub border

            그림 1: 전통적인 NAT 구성
```

#### 2.1 기본 NAT 개요

- 동작
  - 사설 스텁 도메인의 사설 주소 집합을 전역적으로 유효한 주소 집합에 동적으로 매핑 → 외부 네트워크와 통신
  - 로컬 노드 수 ≤ 전역 주소 수 → 각 로컬 주소에 매핑할 전역 주소 보장
  - 로컬 노드 수 > 전역 주소 수 → 동시 외부 접근 가능한 노드 수는 전역 주소 수로 제한
  - 특정 로컬 주소를 특정 전역 주소에 정적으로 매핑 가능
    - 용도: 외부 접근 보장, 고정 공용 주소를 통한 외부→로컬 접근 허용
  - 동일 주소 매핑으로 로컬 노드에서 여러 동시 세션 시작 가능
- 스텁 도메인 주소 특성
  - 도메인에 로컬 → 도메인 외부에서는 무효 → 다른 스텁 도메인에서 재사용 가능
  - 예: 단일 클래스 A 주소를 다수 스텁 도메인에서 사용 가능
  - NAT는 스텁 도메인-백본 사이 각 출구 지점에 설치
  - 출구 지점이 둘 이상이면 각 NAT가 동일한 변환 테이블을 가져야 함(매우 중요)
- 예시(그림 2)
  - 스텁 A·B 모두 내부적으로 클래스 A 사설 주소 블록 10.0.0.0/8 [RFC 1918] 사용
  - 스텁 A의 NAT: 클래스 C 블록 198.76.29.0/24 할당
  - 스텁 B의 NAT: 클래스 C 블록 198.76.28.0/24 할당
  - 클래스 C 주소는 전역적으로 고유 → 다른 NAT 박스에서 사용 불가

```
                                    \ | /
                                  +---------------+
                                  |Regional Router|
                                  +---------------+
                                WAN |           | WAN
                                    |           |
                Stub A .............|....   ....|............ Stub B
                                    |           |
                  {s=198.76.29.7,^  |           |  v{s=198.76.29.7,
                   d=198.76.28.4}^  |           |  v d=198.76.28.4}
                    +-----------------+       +-----------------+
                    |Stub Router w/NAT|       |Stub Router w/NAT|
                    +-----------------+       +-----------------+
                          |                         |
                          |  LAN               LAN  |
                    -------------             -------------
                              |                 |
            {s=10.33.96.5, ^  |                 |  v{s=198.76.29.7,
             d=198.76.28.4}^ +--+             +--+ v d=10.81.13.22}
                             |--|             |--|
                            /____\           /____\
                          10.33.96.5       10.81.13.22

                      그림 2: 기본 NAT 동작
```

- 동작 흐름
  - 스텁 A 호스트 10.33.96.5 → 스텁 B 호스트 10.81.13.22로 전송 시
    - 목적지는 전역 주소 198.76.28.4 사용, 패킷을 기본 라우터로 전송
    - 스텁 라우터는 198.76.0.0에 대한 정적 경로 존재 → 패킷이 WAN 링크로 전달
    - NAT가 패킷 전달 전 출발지 주소 10.33.96.5 → 전역 주소 198.76.29.7로 변환
    - 반환 경로 패킷도 동일하게 변환
  - 호스트·라우터 변경 불필요
    - 스텁 A 호스트 관점에서 198.76.28.4는 스텁 B 호스트가 쓰는 주소
    - 주소 변환은 대부분 종단 호스트에 투명
  - 단순한 예시이며 탐구할 문제가 다수 존재

#### 2.2 NAPT 개요

- 전제: 조직이 사설 IP 네트워크 + 서비스 제공업체 WAN 링크를 보유
  - 스텁 라우터의 WAN 링크에 전역 유효 주소 할당
  - 조직 내 나머지 노드는 로컬 의미만 있는 IP 주소 보유
- NAPT 동작: (로컬 IP 주소, 로컬 TU 포트 번호) 튜플 → (등록 IP 주소, 할당된 TU 포트 번호) 튜플로 매핑
  - 다수 사설 노드가 단일 등록 IP 주소로 외부 네트워크에 동시 접근 가능
- 적용 사례
  - SOHO 그룹이 단일 IP 주소로 외부 네트워크에 접근하는 요구에 적합
  - 확장: 등록 IP 주소의 서비스 TU 포트별로 로컬 노드를 정적 매핑 → 인바운드 접근 허용 가능
- 예시(그림 3)
  - 스텁 A는 내부적으로 클래스 A 블록 10.0.0.0/8 사용
  - 스텁 라우터 WAN 인터페이스에 서비스 제공업체가 IP 주소 138.76.28.4 할당

```
                                     \ | /
                                   +-----------------------+
                                   |Service Provider Router|
                                   +-----------------------+
                                 WAN |
                                     |
                 Stub A .............|....
                                     |
         ^{s=138.76.28.4,sport=1024, |  v{s=138.76.29.7, sport = 23,
         ^ d=138.76.29.7,dport=23}   |  v d=138.76.28.4, dport = 1024}
                         +------------------+
                         |Stub Router w/NAPT|
                         +------------------+
                           |
                           |  LAN
     --------------------------------------------
        |        ^{s=10.0.0.10,sport=3017, |  v{s=138.76.29.7, sport=23,
        |        ^ d=138.76.29.7,dport=23} |  v d=10.0.0.10, dport=3017}
        |                                  |
       +--+      +--+                    +--+
       |--|      |--|                    |--|
      /____\    /____\                  /____\
     10.0.0.1  10.0.0.2   .....        10.0.0.10

      그림 3: 네트워크 주소 포트 변환(NAPT) 동작
```

- 동작 흐름
  - 스텁 A 호스트 10.0.0.10 → 호스트 138.76.29.7로 텔넷 패킷 전송 시
    - 목적지는 전역 주소 138.76.29.7 사용, 패킷을 기본 라우터로 전송
    - 스텁 라우터는 138.76.0.0/16에 대한 정적 경로 존재 → WAN 링크로 전달
    - NAPT가 전달 전 (출발지 주소 10.0.0.10, 출발지 TCP 포트 3017) → (전역 주소 138.76.28.4, 할당된 TCP 포트 예: 1024)로 변환
    - 반환 경로 패킷은 목적지 IP·포트에 대해 유사하게 변환
  - 호스트·라우터 변경 불필요, 변환은 완전히 투명
- 세션 제약
  - 이 설정에서는 TCP/UDP 세션만 허용, 로컬 네트워크에서 시작되어야 함
  - 단 DNS 등 인바운드 접근이 필요한 서비스 존재
  - 스텁 라우터에서 잘 알려진 TU 포트 서비스 [RFC 1700]를 특정 노드로 정적 구성 가능
- ICMP 처리
  - TCP/UDP 외 REDIRECT를 제외한 ICMP 메시지도 NAPT 라우터가 모니터링 가능
  - ICMP 쿼리 유형 패킷: ICMP 헤더의 식별자 필드를 등록 IP 주소의 쿼리 식별자에 매핑
    - 식별자 필드는 쿼리 송신자가 설정, 응답 메시지에서 변경 없이 반환
    - (로컬 IP 주소, 로컬 ICMP 쿼리 식별자) → (등록 IP 주소, 할당된 ICMP 쿼리 식별자)로 매핑
  - ICMP 오류 메시지 수정은 페이로드 + IP/ICMP 헤더 수정 포함 → 이후 섹션에서 논의(4.3 참고)
- 라우터 자체 세션과 로컬 세션의 구별
  - 등록 IP 주소 = 스텁 라우터 WAN 인터페이스 IP 주소인 경우, 라우터는 자체 시작 세션과 로컬 노드 시작 세션을 구별해야 함
  - 모든 인바운드 세션(TCP·UDP·ICMP 쿼리 포함)은 대상 서비스 포트가 다른 노드에 정적 매핑되지 않는 한 NAT 라우터를 종단 노드로 가정
- TCP·UDP·ICMP 쿼리 유형 외 세션은 NAPT 라우터가 서비스하는 로컬 노드에서 허용 안 됨

### 3.0. 세션의 변환 단계

- 전통적인 NAT의 변환 단계 자체는 [NAT-TERM]과 동일
- 이하 하위 섹션은 전통적인 NAT에 특정한 항목만 식별

#### 3.1. 주소 바인딩

- 기본 NAT
  - 첫 아웃바운드 세션이 사설 호스트에서 시작될 때 사설 주소가 외부 주소에 바인딩
  - 이후 동일 사설 주소에서 시작되는 다른 아웃바운드 세션은 동일 바인딩 사용
- NAPT
  - 다수 사설 주소가 단일 전역 주소에 매핑
  - 바인딩: (사설 주소, 사설 TU 포트) 튜플 → (할당된 주소, 할당된 TU 포트) 튜플
  - 첫 아웃바운드 세션이 시작될 때 바인딩 결정(기본 NAT와 동일 원리)
  - 예외적으로 동일 (사설 주소, 사설 TU 포트) 튜플에서 다수 동시 세션이 시작 가능
    - 이 경우 단일 바인딩이 해당 튜플에서 시작되는 모든 세션의 패킷 변환에 사용 가능

#### 3.2. 주소 조회 및 변환

- 주소 바인딩(또는 NAPT의 (주소, TU 포트) 튜플 바인딩) 설정 후, 연결별 소프트 상태 유지 가능
- 동일 세션 소속 패킷은 변환을 위해 세션 조회 대상
- 변환의 정확한 특성은 4.0 참고

#### 3.3. 주소 언바인딩

- 바인딩 기반 마지막 세션이 종료되면 바인딩 자체도 종료 가능

### 4.0. 패킷 변환

- NAT 관리 세션에 관련된 패킷은 양방향으로 변환됨
- 개별 변환 문제는 이하 하위 섹션에서 다룸

#### 4.1. IP, TCP, UDP 및 ICMP 헤더 조작

- 기본 NAT
  - 모든 패킷의 IP 헤더 수정 필요
  - 수정 대상: IP 주소(아웃바운드=출발지, 인바운드=목적지) + IP 체크섬
  - TCP/UDP 세션: TCP/UDP 헤더 체크섬도 업데이트 필요 → TCP/UDP 체크섬이 출발지·목적지 IP를 포함하는 의사 헤더도 커버하기 때문
    - 예외: 체크섬이 0인 UDP 헤더는 수정하면 안 됨
  - ICMP 쿼리 패킷: ICMP 헤더 체크섬이 IP 주소를 커버하지 않음 → 추가 변경 불필요
- NAPT
  - IP 헤더 수정은 기본 NAT와 유사
  - TCP/UDP 세션: TU 포트 변환(아웃바운드=출발지 포트, 인바운드=목적지 포트)까지 확장 수정
  - ICMP 쿼리 패킷: 쿼리 ID + ICMP 헤더 체크섬 교체 수정 필요
    - 사설 호스트 쿼리 ID: 아웃바운드에서 할당된 ID로 변환, 인바운드에서 역변환
    - ICMP 헤더 체크섬은 쿼리 ID 변환을 반영해 수정

#### 4.2. 체크섬 조정

- NAT 수정은 패킷 단위 + 체크섬 수정 포함 → 계산 집약적일 수 있음
- 아래 알고리즘으로 IP·TCP·UDP·ICMP 헤더 체크섬 조정을 간단하고 효율적으로 처리 가능
  - 모든 헤더가 1의 보수 합 사용 → 변환 전후 주소의 산술 차이를 체크섬에 더하면 됨
  - 적용 조건: 짝수 오프셋(optr이 헤더 시작에서 짝수 오프셋) + 짝수 길이(olen·nlen이 짝수)

```c
void checksumadjust(unsigned char *chksum, unsigned char *optr,
int olen, unsigned char *nptr, int nlen)
/* 가정: unsigned char는 8비트, long은 32비트.
  - chksum은 패킷의 체크섬을 가리킴
  - optr은 패킷의 이전 데이터를 가리킴
  - nptr은 패킷의 새 데이터를 가리킴
*/
{
  long x, old, new;
  x=chksum[0]*256+chksum[1];
  x=~x & 0xFFFF;
  while (olen)
  {
      old=optr[0]*256+optr[1]; optr+=2;
      x-=old & 0xffff;
      if (x<=0) { x--; x&=0xffff; }
      olen-=2;
  }
  while (nlen)
  {
      new=nptr[0]*256+nptr[1]; nptr+=2;
      x+=new & 0xffff;
      if (x & 0x10000) { x++; x&=0xffff; }
      nlen-=2;
  }
  x=~x & 0xFFFF;
  chksum[0]=x/256; chksum[1]=x & 0xff;
}
```

#### 4.3. ICMP 오류 패킷 수정

- ICMP 오류 메시지([ICMP]) 변경 범위
  - 외부 계층 IP·ICMP 헤더 변경
  - ICMP 오류 메시지 페이로드에 포함된 패킷의 헤더 변경
- NAT가 종단 호스트에 투명하려면
  - 페이로드 내 포함된 IP 헤더의 IP 주소 수정
  - 포함된 IP 헤더의 체크섬 필드 수정
  - 페이로드 변경을 반영해 ICMP 헤더 체크섬도 수정
- NAPT 설정에서 ICMP 내 포함된 메시지가 TCP·UDP·ICMP 쿼리 패킷인 경우
  - TCP/UDP 헤더의 TU 포트 번호 또는 ICMP 쿼리 헤더의 쿼리 식별자 필드도 수정 필요
- ICMP 패킷 자체의 IP 헤더도 수정 필요

#### 4.4. FTP 지원

- FTP([FTP])는 제어 세션 페이로드를 모니터링해 데이터 세션 매개변수를 결정 → ALG 필요
  - FTP ALG는 대부분의 NAT 구현에서 필수 요소
- FTP ALG 필요 사항
  - 출발지·목적지 포트가 FTP인 TCP 시퀀스·확인 응답 번호 수정용 특별 테이블 필요
  - 테이블 항목: 출발지 주소 · 목적지 주소 · 출발지 포트 · 목적지 포트 · 시퀀스 번호 델타 · 타임스탬프
  - 새 항목은 FTP PORT 명령 또는 PASV 응답 감지 시에만 생성
  - 시퀀스 번호 델타는 PORT 명령·PASV 응답마다 증가/감소 가능
  - 시퀀스 번호는 아웃바운드에서 델타만큼 증가, 확인 응답 번호는 인바운드에서 델타만큼 감소
- FTP 페이로드 변환 범위
  - 기본 NAT: 사설 주소·할당된 외부 주소(ASCII 개별 옥텟 인코딩)로 제한
  - NAPT: 주소 옥텟 다음의 TCP 포트 옥텟(ASCII)까지 확장

#### 4.5 DNS 지원

- 전통적인 NAT의 세션은 주로 사설 도메인에서 아웃바운드 → DNS ALG가 불필요할 수 있음
- 구조
  - 사설 도메인 내부 DNS 서버: 내부 호스트 + 일부 외부 호스트에 대한 이름-IP 매핑 유지
  - 외부 DNS 서버: 외부 호스트 이름 매핑만 유지(내부 호스트는 유지 안 함)
  - 내부 DNS 서버가 없으면 모든 DNS 요청을 외부 DNS 서버로 전송해 외부 주소 매핑 조회

#### 4.6. IP 옵션 처리

- Record Route · Strict Source Route · Loose Source Route IP 옵션이 있는 데이터그램은 중간 라우터 IP 주소를 기록/사용
- NAT 중간 라우터의 대응
  - 이런 옵션을 지원하지 않거나
  - 옵션 처리 중 주소를 변환하지 않고 남겨둘 수 있음
    - 이 경우 소스 경로를 따라 사설 주소가 종단 간에 노출됨
    - 단 각 라우터는 다음 홉만 보므로 패킷 통과 경로 자체는 위태롭지 않음

### 5. 기타 문제

#### 5.1. 로컬 및 전역 주소의 분할

- NAT가 작동하려면 IP 주소 공간을 두 부분으로 분할 필요: 스텁 도메인 내부 사설 주소 · 전역적으로 고유한 주소
  - 주어진 주소는 사설 또는 전역 중 하나여야 함, 중복 불가
- 중복 문제 예시
  - 스텁 A 호스트 → 스텁 B 호스트로 전송 시, 스텁 B의 전역 주소가 스텁 A의 사설 주소와 겹치는 경우
  - 스텁 A 라우터가 스텁 B의 전역 주소를 자신의 사설 주소와 구별 불가

#### 5.2. 사설 주소 공간 권장사항

- [RFC 1918]: 사설 네트워크 주소 공간 할당 권장사항 제공
- IANA가 사설 인터넷용으로 보유한 3개 블록
  - 10.0.0.0/8: 클래스 A 네트워크 1개
  - 172.16.0.0/12: 연속된 클래스 B 네트워크 16개 집합
  - 192.168.0.0/16: 연속된 클래스 C 네트워크 256개 집합
- 조직은 IANA·인터넷 레지스트리와 조정 없이 이 주소 공간 사용 가능
  - 경계 라우터에서 NAT 동작이 활성화된 채로 다수 독립 조직이 동시에 비공개 사용 가능

#### 5.3. NAT를 통한 라우팅

- NAT 라우터는 사설 네트워크를 백본에 광고하면 안 됨
  - 전역 주소를 가진 네트워크만 스텁 외부에 알려질 수 있음
  - 단 스텁 경계 라우터가 수신하는 전역 정보는 일반적인 방식으로 스텁에서 광고 가능
- 일반적인 구성
  - NAT 스텁 라우터: 모든 외부 트래픽을 WAN 링크로 서비스 제공업체 라우터에 전달하는 정적 경로
  - 서비스 제공업체 라우터: NAT 관리 전역 주소 목록에 속하는 목적지 패킷을 WAN 링크로 NAT 라우터에 전달하는 정적 경로

#### 5.4. 기본 NAT에서 NAPT로의 전환

- 문제 상황: 기본 NAT에서 사설 노드 수가 매핑 가능한 전역 주소 수를 초과(예: 클래스 B 사설 네트워크가 클래스 C 전역 블록에 매핑)
  - 마지막 전역 주소 사용 후 일부 로컬 노드의 외부 접근이 갑자기 차단 → 불편·제약적
- 해결책: 기본 NAT 라우터가 마지막 전역 주소에 대해 선택적으로 NAPT 설정으로 전환
  - 효과: 사설 네트워크 호스트가 대부분 애플리케이션에서 지속적·중단 없는 외부 접근 확보
  - 부작용: 기본 NAT에서 동작하던 일부 애플리케이션이 NAPT 전환으로 갑자기 중단될 수 있음 → 혼란 유발 가능

### 6.0. NAT 제한사항

- [NAT-TERM]이 모든 NAT 유형의 제한사항을 광범위하게 다룸
- 이하는 전통적인 NAT에 특정한 제한사항만 식별

#### 6.1. 프라이버시와 보안

- 전통적인 NAT의 프라이버시 측면
  - 세션이 사설 호스트에서 단방향 + 실제 주소가 외부 호스트에 비노출 → 프라이버시 메커니즘 역할
- 트레이드오프
  - 프라이버시 강화 특성이 곧 디버깅(보안 위반 포함)을 어렵게 만듦
  - 사설 네트워크 호스트가 인터넷을 남용해도(공격 시도·스팸 발송 등) IP 주소가 NAT 라우터에 숨겨져 실제 원인 추적이 어려움

#### 6.2. LAN 인터페이스에서 NAT 매핑된 전역 주소에 대한 ARP 응답

- NAT는 스텁 도메인의 경계 라우터에서만 활성화되어야 함
- 문서 내 예시는 NAT 라우터-외부 라우터 간 WAN 링크를 전제
- WAN 링크가 LAN 연결로 대체되고 NAT 매핑용 전역 주소 일부/전체가 LAN 세그먼트와 동일 서브넷인 경우
  - NAT 라우터가 해당 서브넷 주소 범위에 대한 ARP 지원 제공 필요
  - 기본 NAT 설정: NAT 매핑된 전역 주소에 대한 ARP 요청에 자체 MAC 주소로 응답 필수
    - 응답하지 않으면 그 주소의 소유권을 가진 다른 노드가 없어 요청이 응답되지 않음
- NAPT 설정에서는 이 시나리오 가능성이 낮음
  - 예외: NAPT 매핑에 사용된 단일 주소가 NAT 라우터의 인터페이스 주소가 아닌 경우(5.4의 전환 상황 등)
- 직접 연결된 서브넷 주소 범위를 NAT 매핑에 사용 → 서비스 제공업체 라우터의 정적 경로 구성이 불필요해짐
- 저자 의견: 서비스 제공업체 라우터에 대한 LAN 링크는 흔하지 않음, 다만 벤더가 만약을 위해 프록시 ARP를 선택적으로 지원할 수는 있음

#### 6.3. NAPT 설정에서 아웃바운드 TCP/UDP 단편화 패킷 변환

- NAPT 설정에서 사설 호스트가 발생시킨 아웃바운드 TCP/UDP 단편 변환은 실패할 운명
- 원인
  - 첫 단편만 TCP/UDP 헤더 포함(패킷을 세션에 연결하는 데 필요) → 변환 가능
  - 후속 단편은 TCP/UDP 포트 정보 없이 첫 단편과 동일한 단편화 식별자만 전달
  - 두 사설 호스트가 동일 목적지로 동일 단편화 식별자를 사용해 단편화 패킷을 발생시킨 경우
    - 대상 호스트는 동일 단편화 ID + 동일 할당 호스트 주소를 가진 두 데이터그램을 구별 불가
    - 결과: 두 세션 모두 손상

### 7.0. 현재 구현

- 이 문서의 NAT 설명을 준수하는 다수 상업적 구현이 업계에 존재
- Linux 공개 도메인 소프트웨어: "IP masquerade"라는 이름의 NAT 포함(GNU 라이선스)
- FreeBSD 공개 도메인 소프트웨어: 데몬으로 실행되는 NAPT 구현(UC Berkeley 라이선스)
- 두 소프트웨어 모두 무료 → 배포 비용 수준의 CD-ROM 구매 가능, 최신 패치와 함께 다수 FTP 사이트에서 온라인 이용 가능

### 8.0. 보안 고려사항

- [NAT-TERM]에서 설명하는 NAT의 모든 변형에 대한 보안 고려사항이 전통적인 NAT에도 그대로 적용
