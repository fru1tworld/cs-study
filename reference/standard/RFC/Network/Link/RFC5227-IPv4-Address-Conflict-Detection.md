                    IPv4 주소 충돌 감지


### Abstract

같은 링크에 있는 두 호스트가 동시에 같은 IPv4 주소를 사용하려 하면
(사전에 조율된 드문 특수 사례를 제외하고), 한쪽 또는 양쪽 호스트에
문제가 발생한다. 이 문서는 (i) 이러한 잘못된 설정이 발생하지 않도록
호스트가 사전에 취할 수 있는 간단한 예방 조치와, (ii) 만약 잘못된
설정이 발생했을 경우 호스트가 사후에 이를 수동적으로 감지할 수 있는
간단한 메커니즘을 기술한다.

※ 이 RFC는 RFC 826(ARP)을 갱신(Updates)한다.


1. 서론
-------

역사적으로, 실수로 두 인터넷 호스트에 같은 IP 주소를 설정하는 것은
성가시고 진단하기 어려운 문제였다.

기존 주소 해석 프로토콜(ARP)은 호스트가 이러한 잘못된 설정을 감지하고
사용자에게 보고할 수 있는 쉬운 방법을 제공한다. DHCP 명세 [RFC2131]는
잘못된 설정 감지에서 ARP의 역할을 간략히 언급하며, RFC 2131에서
다음 세 가지 발췌를 예시로 들 수 있다:

- 클라이언트는 새로 받은 주소를 탐침(probe)해야 한다(SHOULD), 예를 들어
  ARP로
- 클라이언트는 매개변수에 대한 최종 확인을 수행해야 한다(SHOULD)
  (예: 할당된 네트워크 주소에 대한 ARP)
- 클라이언트가 주소가 이미 사용 중임을 감지하면(예: ARP를 통해),
  클라이언트는 서버에 DHCPDECLINE 메시지를 보내야 한다(MUST)

안타깝게도, DHCP 명세는 구현자에게 다음을 안내하지 않는다:
보내야 할 ARP 패킷의 수, 패킷 간 간격, 주소를 안전하게 사용할 수 있다고
결론짓기까지의 총 대기 시간, 또는 이 결정을 위해 호스트가 어떤 종류의
패킷을 수신 대기해야 하는지. 주소를 안전하게 사용할 수 있다고 결론지은
후에 그것이 틀렸음을 발견한 경우 호스트가 취해야 할 조치도 명시하지
않는다. 또한 DHCP 서버가 여러 번 DECLINE된 같은 주소를 반복적으로
OFFER하는 등의 비정상적 실패 사례에 대해 DHCP 클라이언트가 취해야 할
주의 사항도 명시하지 않는다.

이 문서는 빠진 부분을 보완하여 다음에 필요한 동작을 명확히 규정한다:

1. 주소 사용이 충돌로 이어질 가능성이 있는지 판단. 여기에는 (a) 주소가
   이미 같은 링크의 다른 호스트에 의해 활발히 사용되고 있는 경우와,
   (b) 두 호스트가 실수로 같은 주소를 사용하려 하면서 동시에 탐침
   과정에 있는 경우가 포함된다 (2.1절).

2. 네트워크의 다른 호스트가 실수로 같은 주소를 사용하고 있다는 사후
   수동 감지. 모든 호스트가 이미 사용 중인 주소를 피하는 예방 조치를
   취하더라도, 초기 인터페이스 설정 시 두 호스트가 통신 불가 상태였다면
   여전히 충돌이 발생할 수 있다 (2.4절).

3. 반복적 충돌이 지나치게 많을 경우 주소 획득 시도의 속도 제한
   (2.1절).

IPv4 주소 충돌 감지(ACD)의 유용성은 DHCP 클라이언트에 국한되지 않는다.
주소가 어떻게 설정되었든 — 사용자의 수동 입력, DHCP 서버로부터 받은
정보, 기타 설정 정보 소스 — 충돌 감지는 유용하다.

IPv4 링크-로컬 주소 할당 [RFC3927]은 이 메커니즘의 특수한 경우로 볼 수
있다. 설정 에이전트가 의사 난수 생성기이고, 충돌을 알렸을 때 하는 일이
다른 난수를 선택하여 다시 시도하는 것이다.


### 1.1. 이 문서에서 사용하는 용어

이 문서에서 '송신자 IP 주소' 또는 '대상 IP 주소'라는 용어를 ARP 패킷
맥락에서 사용할 때, ARP 명세 [RFC826]에서 `ar$spa` (Sender Protocol
Address)와 `ar$tpa` (Target Protocol Address)로 식별되는 필드를 가리킨다.

**ARP Probe** (ARP 탐침): 로컬 링크에 브로드캐스트되는 ARP Request
패킷으로, '송신자 IP 주소'가 모두 0이다. '송신자 하드웨어 주소'는
패킷을 보내는 인터페이스의 하드웨어 주소여야 한다(MUST). '송신자 IP
주소' 필드는 모두 0으로 설정해야 한다(MUST). 이는 해당 주소가 이미
다른 호스트에 의해 사용 중인 경우 같은 링크의 다른 호스트의 ARP
캐시를 오염시키지 않기 위해서다. '대상 하드웨어 주소' 필드는 무시되며
모두 0으로 설정해야 한다(SHOULD). '대상 IP 주소' 필드는 탐침 중인
주소로 설정해야 한다(MUST). ARP Probe는 질문("이 주소를 사용하는
호스트가 있는가?")과 함축적 진술("이것이 내가 사용하고자 하는
주소다.")을 모두 전달한다.

**ARP Announcement** (ARP 공고): 위에서 설명한 ARP Probe와 동일한 ARP
Request 패킷이지만, 송신자와 대상 IP 주소 필드 모두에 공고하려는 IP
주소가 들어간다. "이것이 내가 지금 사용하고 있는 주소다."라는 더 강한
진술을 전달한다.

다음 타이밍 상수가 이 프로토콜에서 사용된다 (고정 상수이며 구현자,
운영자, 최종 사용자가 수정하도록 만든 것이 아니다):

```
PROBE_WAIT            1초     (초기 랜덤 지연)
PROBE_NUM             3       (탐침 패킷 수)
PROBE_MIN             1초     (반복 탐침까지의 최소 지연)
PROBE_MAX             2초     (반복 탐침까지의 최대 지연)
ANNOUNCE_WAIT         2초     (공고 전 지연)
ANNOUNCE_NUM          2       (공고 패킷 수)
ANNOUNCE_INTERVAL     2초     (공고 패킷 간 시간)
MAX_CONFLICTS        10       (속도 제한 전 최대 충돌 수)
RATE_LIMIT_INTERVAL  60초     (연속 시도 간 지연)
DEFEND_INTERVAL      10초     (방어적 ARP 간 최소 간격)
```


### 1.2. RFC 826과의 관계

이 문서는 RFC 826의 어떤 프로토콜 규칙도 수정하지 않는다. 패킷 형식이나
필드의 의미를 변경하지 않는다. '패킷 생성'과 '패킷 수신'에 대한 기존
규칙은 RFC 826에 명시된 대로 정확히 적용된다.

이 문서는 RFC 826을 확장하여 다음을 규정한다:

(1) 인터페이스가 설정될 때 주소가 이미 사용 중인지 확인하기 위해 특정
    ARP Request를 생성해야 한다.

(2) 수신된 각 ARP 패킷에 대해 수행해야 할 간단한 검사를 추가로
    규정하여, 수동적이고 지속적인 충돌 감지를 용이하게 한다. 이 추가
    검사는 네트워크에 추가 패킷 부하를 일으키지 않으며
    호스트에 대한 CPU 부담도 무시해도 될 수준이다.

RFC 826에 이미 명시되어 있듯이, ARP Request 패킷은 두 가지 기능을
수행한다:

* 단언(Assertion): `ar$sha` (송신자 하드웨어 주소)와 `ar$spa` (송신자
  프로토콜 주소) 필드가 함께 하나의 사실을 단언한다: 명시된 프로토콜
  주소가 명시된 하드웨어 주소에 매핑된다.

* 질문(Question): `ar$tha` (대상 하드웨어 주소, 0)와 `ar$tpa` (대상
  프로토콜 주소) 필드가 질문으로 기능한다: 명시된 프로토콜 주소가 어떤
  하드웨어 주소에 매핑되는지.


#### 1.2.1. 브로드캐스트 ARP Reply

IPv4 주소 충돌 감지(ACD)의 일부 응용에서는 유니캐스트 대신 브로드캐스트로
ARP Reply를 전달하는 것이 유리할 수 있다. 이렇게 하면 주소 충돌을 더 빨리
감지할 수 있기 때문이다. 예를 들어, "IPv4 링크-로컬 주소의 동적 설정"
[RFC3927]은 여기에 명시된 대로 ACD를 사용하되, ARP Reply를 브로드캐스트로
보내도록 추가 규정한다.


### 1.3. 적용 범위

이 명세는 이더넷 [802.3], 토큰 링 [802.5], IEEE 802.11 무선 LAN [802.11]을
포함한 모든 IEEE 802 근거리 통신망(LAN)과, 최소 1 Mb/s의 데이터 전송률에
최대 1초의 왕복 지연을 가지며 IP 주소를 링크 계층 하드웨어 주소로
매핑하는 데 ARP [RFC826]를 사용하는 기타 링크 계층 기술에 적용된다.

ARP를 지원하지만 1 Mb/s 미만의 전송률이나 1초 이상의 지연을 가진
링크 계층 기술에서도 이 프로토콜은 올바르게 동작하지만, 탐침 단계가
완료된 후 뒤늦게 감지되는 충돌을 더 자주 처리해야 할 수 있다.

이 문서에서 규정하는 프로토콜이 효과적이기 위해, 링크의 모든 호스트가
이를 구현할 필요는 없다. 이 명세를 구현하는 호스트가 우발적 주소 충돌로부터
보호받기 위해 필요한 것은, 같은 링크의 상대 호스트가 RFC 826에 명시된
ARP 프로토콜을 올바르게 구현하는 것뿐이다.

이 문서에서 '호스트'라는 용어를 사용할 때, 호스트/라우터가 현재 패킷을
포워딩하고 있는지 여부와 관계없이 라우터나 기타 멀티홈 호스트의
인터페이스에도 동일하게 적용된다.


2. 주소 탐침, 공고, 충돌 감지 및 방어
--------------------------------------

이 절에서는 주소가 이미 사용 중인지 안전하게 확인하기 위한 초기 탐침,
선택한 주소의 공고, 지속적인 충돌 확인, 그리고 더 빠른 충돌 감지를 위한
브로드캐스트 ARP Reply의 선택적 사용을 기술한다.


### 2.1. 주소 탐침

IPv4 주소를 사용하기 전에 (수동 설정, DHCP 또는 다른 수단으로 받았든),
이 명세를 구현하는 호스트는 ARP Probe 패킷을 브로드캐스트하여 주소가
이미 사용 중인지 검사해야 한다(MUST). 이는 네트워크 인터페이스가
비활성에서 활성 상태로 전환될 때, 컴퓨터가 절전 모드에서 깨어날 때,
이더넷 케이블이 연결되었음을 링크 상태 변경이 알릴 때, 802.11 무선
인터페이스가 새 기지국에 연결될 때, 또는 호스트가 논리적 링크에
활발히 연결되는 기타 연결 변경이 발생할 때에도 적용된다.

호스트는 일상적으로 이 확인을 주기적으로 수행해서는 안 된다(MUST NOT).
이는 네트워크 대역폭의 낭비이며, 2.4절에 설명된 수동적 충돌 발견
능력 때문에 불필요하다.


#### 2.1.1. 탐침 세부사항

호스트는 원하는 주소에 대한 ARP Request를 브로드캐스트하여 주소가
이미 사용 중인지 탐침한다. 클라이언트는 ARP Request의 '송신자 하드웨어
주소' 필드에 패킷을 보내는 인터페이스의 하드웨어 주소를 채워야
한다(MUST). '송신자 IP 주소' 필드는 모두 0으로 설정해야 한다(MUST).
'대상 하드웨어 주소' 필드는 무시되며 모두 0으로 설정해야 한다(SHOULD).
'대상 IP 주소' 필드는 탐침 중인 주소로 설정해야 한다(MUST). 이렇게
구성된, '송신자 IP 주소'가 모두 0인 ARP Request를 'ARP Probe'라 한다.

탐침을 시작할 준비가 되면, 호스트는 먼저 0에서 PROBE_WAIT초 사이에서
균일하게 선택된 랜덤 시간 간격만큼 대기한 다음, PROBE_NUM개의 탐침
패킷을 보내야 하며, 각 탐침 패킷은 PROBE_MIN에서 PROBE_MAX초 사이에서
랜덤하고 균일하게 간격을 둔다. 이 초기 랜덤 지연은 동시에 전원이
켜진 다수의 호스트가 모두 초기 탐침 패킷을 동시에 보내지 않도록 한다.

탐침 과정의 시작부터 마지막 탐침 패킷 전송 후 ANNOUNCE_WAIT초까지의
기간 동안, 호스트가 탐침 중인 인터페이스에서 패킷의 '송신자 IP 주소'가
탐침 중인 주소인 ARP 패킷(Request 또는 Reply)을 수신하면, 호스트는
이 주소를 다른 호스트에 의해 사용 중인 것으로 취급해야 하며(MUST),
설정 에이전트(운영자, DHCP 서버 등)에게 제안된 주소가 수용할 수 없음을
알려야 한다.

또한, 이 기간 동안 호스트가 '대상 IP 주소'가 탐침 중인 주소이고 패킷의
'송신자 하드웨어 주소'가 호스트의 어떤 인터페이스의 하드웨어 주소도
아닌 ARP Probe를 수신하면, 호스트는 이를 주소 충돌로 취급하고 위와
같이 설정 에이전트에 오류를 알려야 한다(SHOULD). 이는 두 개(이상)의
호스트가 같은 주소로 설정되어 동시에 해당 주소를 탐침 중일 때 발생할
수 있다.

이 명세를 구현하는 호스트는 새 후보 주소를 탐침하는 속도를 제한하는
조치를 취해야 한다(MUST): 주어진 인터페이스에서 MAX_CONFLICTS 이상의
주소 충돌을 경험하면, 호스트는 해당 인터페이스에서 새 주소 시도
속도를 RATE_LIMIT_INTERVAL당 최대 1회로 제한해야 한다(MUST). 이는
같은 주소를 요청하는 모든 호스트에게 반복적으로 할당하는 결함 있는
DHCP 서버 같은 비정상적 실패 사례에서 치명적인 ARP 폭풍을 방지하기
위함이다.

마지막 ARP Probe 전송 후 ANNOUNCE_WAIT초까지 충돌하는 ARP Reply나
ARP Probe가 수신되지 않으면, 호스트는 원하는 주소를 안전하게 사용할
수 있다고 성공적으로 판단한 것이다.


### 2.2. 적절한 네트워크 기술에서의 짧은 타임아웃

이 문서에서 요구하는 것보다 짧은 지연이 적절한 네트워크 기술이 등장할
수 있다. 후속 IETF 발행물이 해당 기술에서 PROBE_WAIT, PROBE_NUM,
PROBE_MIN, PROBE_MAX의 다른 값에 대한 지침을 제공할 수 있다.

링크의 서로 다른 호스트가 다른 타이밍 매개변수를 사용하는 상황이
발생하더라도 문제가 되지 않는다. 이 프로토콜은 링크의 모든 호스트가
같은 버전의 프로토콜을 구현하는 것에 의존하지 않으며, 모든 호스트가
이 프로토콜을 구현하는 것에도 의존하지 않는다.


### 2.3. 주소 공고

원하는 주소를 안전하게 사용할 수 있다고 탐침으로 판단한 후, 이 명세를
구현하는 호스트는 ANNOUNCE_NUM개의 ARP Announcement를 ANNOUNCE_INTERVAL초
간격으로 브로드캐스트하여 이 주소의 사용 시작을 공고해야 한다(MUST).
ARP Announcement는 위에서 설명한 ARP Probe와 동일하지만, 송신자와 대상
IP 주소 필드 모두 호스트가 새로 선택한 IPv4 주소를 포함한다. 이 ARP
Announcement의 목적은 같은 링크의 다른 호스트가 이전에 같은 주소를
사용했던 다른 호스트로부터 남아 있는 오래된 ARP 캐시 항목을 가지고
있지 않도록 하기 위함이다. 호스트는 첫 번째 ARP Announcement를
보낸 직후부터 IP 주소를 합법적으로 사용하기 시작할 수 있다.


### 2.4. 지속적인 주소 충돌 감지 및 주소 방어

주소 충돌 감지는 초기 인터페이스 설정 시 ARP Probe를 보내는 때에만
국한되지 않는다. 주소 충돌 감지는 호스트가 주소를 사용하는 동안 계속
유효한 지속적 과정이다. 호스트가 '송신자 IP 주소'가 해당 인터페이스에
설정된 호스트 자신의 IP 주소(중 하나)이지만 '송신자 하드웨어 주소'가
호스트 자신의 인터페이스 주소 중 어느 것과도 일치하지 않는 ARP 패킷
(Request 또는 Reply)을 수신하면, 이는 충돌하는 ARP 패킷이며, 다른
호스트도 이 주소를 유효하게 사용하고 있다고 판단함을 나타낸다.

주소 충돌을 해결하기 위해, 호스트는 아래의 (a), (b), (c) 중 하나에
따라 충돌하는 ARP 패킷에 응답해야 한다(MUST):

(a) 충돌하는 ARP 패킷을 수신하면, 호스트는 즉시 해당 주소 사용을
    중단하고 위에 설명된 대로 설정 에이전트에 오류를 알릴 수
    있다(MAY).

(b) 호스트가 현재 활성 TCP 연결이나 같은 IPv4 주소를 유지해야 할
    다른 이유가 있고, 최근 DEFEND_INTERVAL초 이내에 다른 충돌하는
    ARP 패킷을 보지 않았다면, 주소를 방어하려 시도할 수 있다(MAY).
    충돌하는 ARP 패킷이 수신된 시각을 기록한 후, 자신의 IP 및
    하드웨어 주소를 송신자 주소로 하는 단일 ARP Announcement를
    브로드캐스트한다. 이후 호스트는 추가적인 특별한 조치 없이
    정상적으로 주소를 계속 사용할 수 있다. 그러나 이것이 첫 번째
    충돌하는 ARP 패킷이 아니고, 이전 충돌하는 ARP 패킷의 기록 시각이
    DEFEND_INTERVAL초 이내이면, 호스트는 즉시 이 주소 사용을
    중단해야 한다(MUST). 이는 두 호스트가 같은 주소를 방어하려는
    무한 루프에 빠지지 않도록 하기 위해 필요하다.

(c) 호스트가 어떤 상황에서도 주소를 포기해서는 안 되도록 설정된
    경우 (예를 들어 링크의 기본 라우터나 DNS 서버처럼 잘 알려진
    안정적 IP 주소가 필요한 장치), 주소를 무기한 방어할 수
    있다(MAY). 이러한 호스트가 충돌하는 ARP 패킷을 수신하면,
    ARP 패킷의 출처 이더넷 주소 등 유용한 정보를 기록하고 관리자에게
    알리는 적절한 조치를 취해야 한다. 최근 DEFEND_INTERVAL초 이내에
    다른 충돌하는 ARP 패킷을 보지 않았다면, 시각을 기록하고 단일
    ARP Announcement를 브로드캐스트해야 한다(MUST). 그러나 이전
    충돌하는 ARP 패킷의 기록 시각이 DEFEND_INTERVAL초 이내이면,
    다른 방어적 ARP Announcement를 보내서는 안 된다(MUST NOT).
    이는 잘못 설정된 두 호스트가 같은 주소를 방어하려다 브로드캐스트
    트래픽으로 네트워크를 범람시키는 무한 루프에 빠지지 않도록 하기
    위해 필요하다.

신뢰할 수 있는 네트워크 운영을 제공하려는 호스트는 위의 (a), (b),
(c)에 설명된 대로 충돌하는 ARP 패킷에 응답해야 한다(MUST). 충돌하는
ARP 패킷을 무시하면 진단하기 어렵고 사용자가 겪기 힘든 간헐적
네트워크 장애가 생긴다.

충돌로 인해 주소를 포기하기 전에, 호스트는 해당 주소를 사용하는 기존
연결을 적극적으로 리셋하려 시도해야 한다(SHOULD). 이는 5절에서 논의하는
주소 재설정으로 인한 일부 보안 위협을 완화한다.


### 2.5. 계속 운영

호스트가 첫 번째 ARP Announcement를 보낸 시점부터 해당 IP 주소 사용을
중단하는 시점까지, 호스트는 ARP 명세 [RFC826]에서 요구하는 일반적인
방식으로 ARP Request에 응답해야 한다(MUST). 구체적으로, 호스트가
2.4절에서 설명한 충돌하는 ARP 패킷이 아닌 ARP Request를 수신하고
ARP Request의 '대상 IP 주소'가 해당 인터페이스에 설정된 호스트 자신의
IP 주소(중 하나)이면, 호스트는 RFC 826에 설명된 대로 ARP Reply로
응답해야 한다(MUST).


### 2.6. 브로드캐스트 ARP Reply

수동으로 할당된 주소의 주의 깊게 운영되는 네트워크나, 신뢰할 수 있는
DHCP 서버와 DHCP 클라이언트가 있는 네트워크에서는 주소 충돌이 드문
장애 시나리오에서만 발생해야 하므로, 위의 2.4절에 설명된 수동적
모니터링으로 충분하다.

그러나 충돌 설정이 감지되기 전에 짧은 시간 동안 지속될 수 있다.
호스트 A와 B가 실수로 같은 IP 주소 X를 할당받았다고 가정하자.
이들이 주소를 안전하게 사용할 수 있는지 탐침할 때 통신 링크가 작동하지
않아서 인터페이스 설정 시 충돌을 감지하지 못했다고 하자. 이제 통신
링크가 복원되고, 세 번째 호스트 C가 주소 X에 대한 ARP Request를
브로드캐스트한다. 충돌을 모르는 호스트 A와 B 모두 호스트 C에게
유니캐스트 ARP Reply를 보낸다. 호스트 C는 양쪽 Reply를 보겠지만,
호스트 A와 B 어느 쪽도 상대방의 Reply를 보지 못하고, 어느 쪽도
즉시 해결해야 할 충돌이 있음을 감지하지 못한다.

더 빠른 충돌 감지가 필요하다면, 유니캐스트가 아닌 링크 수준
브로드캐스트를 사용하여 ARP Reply를 보내면 된다. 이는 일반 사용에
권장되지 않지만(NOT RECOMMENDED), IPv4 ACD 기반의 다른 명세에서
적절하다고 판단하면 브로드캐스트 ARP Reply를 규정할 수 있다.


3. ARP Announcement는 왜 ARP Reply가 아닌 ARP Request 패킷으로 수행하는가?
--------------------------------------------------------------------------

2000년부터 2008년까지 IETF의 IPv4 주소 충돌 감지 논의 과정에서 거듭
나온 질문은 "ARP Announcement는 무상(gratuitous) ARP Reply 패킷으로
수행해야 하지 않는가?"였다.

원칙적으로는 합리적으로 보이지만, 실제로는 ARP Request 패킷 사용을
지지하는 두 가지 이유가 있다. 하나는 역사적 선례이고, 다른 하나는
실용주의다.

역사적 선례로, 무상 ARP는 Stevens Networking [Ste94]에서 ARP Request
패킷을 사용하는 것으로 문서화되어 있다. BSD Unix, Microsoft Windows,
Mac OS 9, Mac OS X 등 모두 Stevens에서 설명한 대로 ARP Request 패킷을
사용한다. 이 시점에서 모두 ARP Reply 패킷 사용으로 전환하도록 강제하는
것은 무의미하다.

실용적 이유로, ARP Request 패킷이 기존 ARP 구현과 더 올바르게 동작할
가능성이 높다. RFC 826의 패킷 수신 규칙은 opcode가 패킷 처리에서
마지막으로 확인하는 것이라고 명시하므로 차이가 없어야 하지만,
`ar$op` 필드에 따라 다른 패킷 처리를 하는 "독창적인" 구현이 있을 수
있으며, 이러한 구현이 무상 ARP Reply보다 무상 ARP Request를 수용할
가능성이 더 높은 여러 이유가 있다:

- 잘못된 ARP 구현이 ARP Reply가 유니캐스트로만 전송된다고 기대할 수 있다.
- 잘못된 ARP 구현이 최근에 발행한 ARP Request에 대한 응답으로만 ARP
  Reply를 수신할 것으로 기대할 수 있다.
- 잘못된 ARP 구현이 `ar$tha`가 자신의 하드웨어 주소와 일치하지 않는
  ARP Reply를 무시할 수 있다.
- 잘못된 ARP 구현이 `ar$tpa`가 자신의 IP 주소와 일치하지 않는 ARP
  Reply를 무시할 수 있다.


4. 역사적 참고
--------------

일부에서는 Stevens [Ste94]에 기술된 "무상 ARP"가 중복 주소 감지를
제공하므로 ACD가 불필요하다고 주장했다. 이는 올바르지 않다. Stevens가
무상 ARP로 설명하는 것은 이 문서에서 더 구체적인 용어인 'ARP
Announcement'로 지칭하는 것과 정확히 같은 패킷이다. 전통적인 무상 ARP
구현은 인터페이스가 처음 설정될 때 단일 ARP Announcement만 보낸다.
그 결과 기존 주소 보유자가 오류를 기록하고, 충돌을 일으킨 쪽은 대개
문제를 알아차리지도 못한 채 운영을 계속한다. 양쪽 기계 모두 같은 IP
주소를 사용하려 하면서 서로의 TCP 연결을 끊임없이 리셋하여 정상적으로
동작하지 못한다.

무상 ARP는 사실상 효과적인 중복 주소 감지를 제공하지 않는다.


5. 보안 고려사항
----------------

IPv4 주소 충돌 감지(ACD)는 ARP [RFC826]에 기반하며, 그 프로토콜의 보안
취약점을 상속한다. 악의적인 호스트가 네트워크에 위조된 ARP 패킷을 보내
다른 호스트의 올바른 동작을 방해할 수 있다. 예를 들어, 호스트가 모든
ARP Request에 자신의 하드웨어 주소를 담은 Reply로 응답하여 네트워크의
모든 주소에 대한 소유권을 주장하는 것은 쉽다.

이 명세는 이 기존 ARP 취약점을 악화시키지 않으며, 일부 측면에서 개선한다:
이유 없이 조용히 실패하는 대신, 이 명세를 구현하는 호스트는 자동
재설정을 시도하거나, 최소한 무슨 일이 일어나고 있는지 사용자에게 알린다.

2.4절 (a)항에 설명된 대로 호스트가 ARP 충돌에 응하여 자발적으로 새
주소를 선택하면, 같은 링크의 악의적인 공격자가 TCP 연결을 탈취하기
더 쉬워질 수 있다. 주소를 포기하기 전에 기존 연결을 적극적으로
리셋하면 이 위험을 완화할 수 있다.
