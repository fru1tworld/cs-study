# IPv4 주소 충돌 감지

```
Network Working Group                                        S. Cheshire
Request for Comments: 5227                                    Apple Inc.
Updates: 826                                                   July 2008
Category: Standards Track
```

## Abstract

- 같은 링크의 두 호스트가 동시에 같은 IPv4 주소를 사용하려 하면 → (사전 조율된 특수 사례 제외) 한쪽 또는 양쪽 호스트에 문제 발생
- 이 문서 기술 범위
  - (i) 잘못된 설정 발생을 막기 위해 호스트가 사전에 취할 수 있는 예방 조치
  - (ii) 잘못된 설정이 발생했을 경우 호스트가 사후에 수동적으로 감지하는 메커니즘
- RFC 826(ARP)을 갱신(Updates)

## 1. 서론

- 역사적으로, 실수로 두 인터넷 호스트에 같은 IP 주소를 설정하는 것 → 성가시고 진단하기 어려운 문제
- 기존 ARP: 호스트가 잘못된 설정을 감지·사용자 보고할 수 있는 쉬운 방법 제공
- DHCP 명세 [RFC2131]가 언급하는 ARP의 역할 (발췌 3건)
  - 클라이언트는 새로 받은 주소를 탐침(probe)해야 함(SHOULD) — 예: ARP로
  - 클라이언트는 매개변수에 대한 최종 확인을 수행해야 함(SHOULD) — 예: 할당된 네트워크 주소에 대한 ARP
  - 클라이언트가 주소가 이미 사용 중임을 감지하면(예: ARP를 통해) → 서버에 DHCPDECLINE 메시지를 보내야 함(MUST)
- DHCP 명세가 안내하지 않는 것
  - 보내야 할 ARP 패킷 수
  - 패킷 간 간격
  - 주소를 안전하게 사용할 수 있다고 결론짓기까지의 총 대기 시간
  - 이 결정을 위해 어떤 종류의 패킷을 수신 대기해야 하는지
  - 주소 사용 가능 결론 이후 그것이 틀렸음을 발견한 경우 취해야 할 조치
  - 같은 주소를 반복적으로 OFFER하는 결함 있는 DHCP 서버 등 비정상적 실패 사례에서 클라이언트가 취해야 할 주의 사항
- 이 문서가 명확히 규정하는 필요 동작
  1. 주소 사용이 충돌로 이어질 가능성이 있는지 판단 (2.1절)
     - (a) 주소가 이미 같은 링크의 다른 호스트에 의해 활발히 사용 중인 경우
     - (b) 두 호스트가 실수로 같은 주소를 사용하려 하며 동시에 탐침 중인 경우
  2. 네트워크의 다른 호스트가 실수로 같은 주소를 사용 중이라는 사후 수동 감지 (2.4절)
     - 모든 호스트가 예방 조치를 취해도, 초기 인터페이스 설정 시 두 호스트가 통신 불가 상태였다면 여전히 충돌 발생 가능
  3. 반복적 충돌이 지나치게 많을 경우 주소 획득 시도의 속도 제한 (2.1절)
- IPv4 주소 충돌 감지(ACD)의 유용성 → DHCP 클라이언트에 국한되지 않음
  - 주소가 어떻게 설정되었든(수동 입력·DHCP·기타 설정 정보 소스) 충돌 감지는 유용
- IPv4 링크-로컬 주소 할당 [RFC3927] → 이 메커니즘의 특수한 경우
  - 설정 에이전트가 의사 난수 생성기이고, 충돌을 알렸을 때 다른 난수를 선택하여 재시도

### 1.1. 이 문서에서 사용하는 용어

- '송신자 IP 주소' / '대상 IP 주소' (ARP 패킷 맥락) → ARP 명세 [RFC826]의 `ar$spa`(Sender Protocol Address), `ar$tpa`(Target Protocol Address) 필드를 가리킴

- ARP Probe (ARP 탐침): 로컬 링크에 브로드캐스트되는 ARP Request 패킷
  - '송신자 IP 주소': 모두 0
  - '송신자 하드웨어 주소': 패킷을 보내는 인터페이스의 하드웨어 주소여야 함(MUST)
  - '송신자 IP 주소' 필드: 모두 0으로 설정해야 함(MUST) → 해당 주소가 이미 다른 호스트에 의해 사용 중인 경우 같은 링크의 다른 호스트의 ARP 캐시를 오염시키지 않기 위함
  - '대상 하드웨어 주소' 필드: 무시되며 모두 0으로 설정해야 함(SHOULD)
  - '대상 IP 주소' 필드: 탐침 중인 주소로 설정해야 함(MUST)
  - 전달하는 의미: 질문("이 주소를 사용하는 호스트가 있는가?") + 함축적 진술("이것이 내가 사용하고자 하는 주소다.")

- ARP Announcement (ARP 공고): ARP Probe와 동일한 ARP Request 패킷이나 송신자·대상 IP 주소 필드 모두에 공고하려는 IP 주소가 들어감
  - 전달하는 의미: "이것이 내가 지금 사용하고 있는 주소다." (더 강한 진술)

- 타이밍 상수 (고정 상수 — 구현자·운영자·최종 사용자가 수정하도록 만든 것이 아님)

```
PROBE_WAIT            1초     (초기 랜덤 지연)
PROBE_NUM             3       (탐침 패킷 수)
PROBE_MIN             1초     (반복 탐침까지의 최소 지연)
PROBE_MAX             2초     (반복 탐침까지의 최대 지연)
ANNOUNCE_WAIT         2초     (공고 전 지연)
ANNOUNCE_NUM          2       (공고 패킷 수)
ANNOUNCE_INTERVAL     2초     (공고 패킷 간 시간)
MAX_CONFLICTS        10       (속도 제한 전 최대 충돌 수)
RATE_LIMIT_INTERVAL  60초     (연속 시도 간 지연)
DEFEND_INTERVAL      10초     (방어적 ARP 간 최소 간격)
```

### 1.2. RFC 826과의 관계

- 이 문서는 RFC 826의 어떤 프로토콜 규칙도 수정하지 않음
  - 패킷 형식·필드 의미 변경 없음
  - '패킷 생성'·'패킷 수신' 규칙은 RFC 826 그대로 적용
- 이 문서가 RFC 826을 확장하여 규정하는 것
  1. 인터페이스가 설정될 때 주소가 이미 사용 중인지 확인하기 위한 특정 ARP Request 생성
  2. 수신된 각 ARP 패킷에 대해 수행해야 할 간단한 검사 추가 → 수동적·지속적 충돌 감지 용이
     - 이 추가 검사: 네트워크에 추가 패킷 부하를 일으키지 않으며 CPU 부담도 무시해도 될 수준
- RFC 826에 이미 명시된 ARP Request 패킷의 두 기능
  - 단언(Assertion): `ar$sha`(송신자 하드웨어 주소) + `ar$spa`(송신자 프로토콜 주소) → 명시된 프로토콜 주소가 명시된 하드웨어 주소에 매핑된다는 사실 단언
  - 질문(Question): `ar$tha`(대상 하드웨어 주소, 0) + `ar$tpa`(대상 프로토콜 주소) → 명시된 프로토콜 주소가 어떤 하드웨어 주소에 매핑되는지 질문

#### 1.2.1. 브로드캐스트 ARP Reply

- ACD의 일부 응용에서 유니캐스트 대신 브로드캐스트로 ARP Reply를 전달 → 주소 충돌을 더 빨리 감지 가능
- 예: "IPv4 링크-로컬 주소의 동적 설정" [RFC3927] → 여기 명시된 ACD를 사용하되, ARP Reply를 브로드캐스트로 보내도록 추가 규정

### 1.3. 적용 범위

- 적용 대상
  - 이더넷 [802.3]·토큰 링 [802.5]·IEEE 802.11 무선 LAN [802.11]을 포함한 모든 IEEE 802 LAN
  - 최소 1 Mb/s 전송률 + 최대 1초 왕복 지연을 가지며 ARP [RFC826]로 IP 주소를 링크 계층 하드웨어 주소로 매핑하는 기타 링크 계층 기술
- ARP를 지원하지만 1 Mb/s 미만 전송률이나 1초 이상 지연을 가진 링크 계층 기술 → 프로토콜은 올바르게 동작하나, 탐침 단계 완료 후 뒤늦게 감지되는 충돌을 더 자주 처리해야 할 수 있음
- 이 프로토콜의 효과를 위해 링크의 모든 호스트가 구현할 필요는 없음
  - 필요 조건: 같은 링크의 상대 호스트가 RFC 826에 명시된 ARP 프로토콜을 올바르게 구현하는 것뿐
- '호스트' 용어 사용 범위: 라우터나 기타 멀티홈 호스트의 인터페이스에도 동일 적용 (현재 패킷 포워딩 여부와 무관)

## 2. 주소 탐침, 공고, 충돌 감지 및 방어

- 이 절에서 기술하는 내용
  - 주소가 이미 사용 중인지 안전하게 확인하기 위한 초기 탐침
  - 선택한 주소의 공고
  - 지속적인 충돌 확인
  - 더 빠른 충돌 감지를 위한 브로드캐스트 ARP Reply의 선택적 사용

### 2.1. 주소 탐침

- IPv4 주소를 사용하기 전(수동 설정·DHCP·기타 수단 무관) → ARP Probe 패킷을 브로드캐스트하여 주소가 이미 사용 중인지 검사해야 함(MUST)
- 적용 시점
  - 네트워크 인터페이스가 비활성 → 활성 상태로 전환될 때
  - 컴퓨터가 절전 모드에서 깨어날 때
  - 이더넷 케이블 연결을 링크 상태 변경이 알릴 때
  - 802.11 무선 인터페이스가 새 기지국에 연결될 때
  - 호스트가 논리적 링크에 활발히 연결되는 기타 연결 변경 발생 시
- 호스트는 이 확인을 일상적으로 주기적 수행해서는 안 됨(MUST NOT)
  - 네트워크 대역폭 낭비 + 2.4절의 수동적 충돌 발견 능력으로 불필요

#### 2.1.1. 탐침 세부사항

- 원하는 주소에 대한 ARP Request를 브로드캐스트하여 탐침
  - '송신자 하드웨어 주소' 필드: 패킷을 보내는 인터페이스의 하드웨어 주소를 채워야 함(MUST)
  - '송신자 IP 주소' 필드: 모두 0으로 설정해야 함(MUST)
  - '대상 하드웨어 주소' 필드: 무시되며 모두 0으로 설정해야 함(SHOULD)
  - '대상 IP 주소' 필드: 탐침 중인 주소로 설정해야 함(MUST)
  - 이렇게 구성된, '송신자 IP 주소'가 모두 0인 ARP Request를 'ARP Probe'라 함
- 탐침 절차
  - 0 ~ PROBE_WAIT초 사이 균일 랜덤 지연 대기
    - 목적: 동시에 전원이 켜진 다수의 호스트가 모두 초기 탐침 패킷을 동시에 보내지 않도록
  - PROBE_NUM개의 탐침 패킷 전송, 각 패킷은 PROBE_MIN ~ PROBE_MAX초 사이 랜덤·균일 간격
- 탐침 과정 시작부터 마지막 탐침 패킷 전송 후 ANNOUNCE_WAIT초까지의 기간
  - 탐침 중인 인터페이스에서 '송신자 IP 주소'가 탐침 중인 주소인 ARP 패킷(Request/Reply) 수신 시 → 다른 호스트가 사용 중인 것으로 취급해야 함(MUST) + 설정 에이전트(운영자·DHCP 서버 등)에게 제안 주소가 수용 불가함을 알려야 함(MUST)
  - '대상 IP 주소'가 탐침 중인 주소이고 '송신자 하드웨어 주소'가 호스트의 어떤 인터페이스 주소도 아닌 ARP Probe 수신 시 → 주소 충돌로 취급하고 설정 에이전트에 오류를 알려야 함(SHOULD)
    - 발생 가능 상황: 둘 이상의 호스트가 같은 주소로 설정되어 동시에 탐침 중일 때
- 새 후보 주소 탐침 속도 제한 조치를 취해야 함(MUST)
  - 어떤 인터페이스에서 MAX_CONFLICTS 이상의 주소 충돌 경험 시 → 해당 인터페이스에서 새 주소 시도 속도를 RATE_LIMIT_INTERVAL당 최대 1회로 제한해야 함(MUST)
  - 목적: 같은 주소를 반복적으로 할당하는 결함 있는 DHCP 서버 같은 비정상적 실패 사례에서 치명적인 ARP 폭풍 방지
- 마지막 ARP Probe 전송 후 ANNOUNCE_WAIT초까지 충돌하는 ARP Reply·Probe 미수신 시 → 원하는 주소를 안전하게 사용할 수 있다고 성공적으로 판단

### 2.2. 적절한 네트워크 기술에서의 짧은 타임아웃

- 이 문서 요구치보다 짧은 지연이 적절한 네트워크 기술 등장 가능
  - 후속 IETF 발행물이 해당 기술에서 PROBE_WAIT·PROBE_NUM·PROBE_MIN·PROBE_MAX의 다른 값 지침 제공 가능
- 링크의 서로 다른 호스트가 다른 타이밍 매개변수를 사용해도 문제 없음
  - 이 프로토콜: 링크의 모든 호스트가 같은 버전을 구현하는 것에 의존하지 않음
  - 모든 호스트가 이 프로토콜을 구현하는 것에도 의존하지 않음

### 2.3. 주소 공고

- 원하는 주소를 안전하게 사용할 수 있다고 탐침으로 판단한 후 → ANNOUNCE_NUM개의 ARP Announcement를 ANNOUNCE_INTERVAL초 간격으로 브로드캐스트하여 주소 사용 시작을 공고해야 함(MUST)
- ARP Announcement: ARP Probe와 동일하나 송신자·대상 IP 주소 필드 모두 호스트가 새로 선택한 IPv4 주소를 포함
  - 목적: 같은 링크의 다른 호스트가 이전 주소 사용자로부터 남은 오래된 ARP 캐시 항목을 갖지 않도록 함
- 호스트는 첫 번째 ARP Announcement 전송 직후부터 IP 주소를 합법적으로 사용 시작 가능

### 2.4. 지속적인 주소 충돌 감지 및 주소 방어

- 주소 충돌 감지 → 초기 인터페이스 설정 시 ARP Probe 전송 시점에만 국한되지 않음
  - 호스트가 주소를 사용하는 동안 계속 유효한 지속적 과정
- 충돌하는 ARP 패킷의 정의: '송신자 IP 주소'가 해당 인터페이스에 설정된 호스트 자신의 IP 주소(중 하나)이지만 '송신자 하드웨어 주소'가 호스트 자신의 인터페이스 주소 중 어느 것과도 일치하지 않는 ARP 패킷(Request/Reply)
  - 의미: 다른 호스트도 이 주소를 유효하게 사용하고 있음을 나타냄
- 주소 충돌 해결을 위해 아래 (a)·(b)·(c) 중 하나에 따라 응답해야 함(MUST)
  - (a) 충돌하는 ARP 패킷 수신 시 → 즉시 해당 주소 사용을 중단하고 설정 에이전트에 오류를 알릴 수 있음(MAY)
  - (b) 현재 활성 TCP 연결이나 같은 IPv4 주소를 유지해야 할 다른 이유가 있고, 최근 DEFEND_INTERVAL초 이내에 다른 충돌하는 ARP 패킷을 보지 않았다면 → 주소를 방어하려 시도할 수 있음(MAY)
    - 충돌하는 ARP 패킷 수신 시각을 기록한 후, 자신의 IP·하드웨어 주소를 송신자 주소로 하는 단일 ARP Announcement를 브로드캐스트
    - 이후 추가 조치 없이 정상적으로 주소를 계속 사용 가능
    - 단, 첫 번째 충돌 패킷이 아니고 이전 충돌 패킷 기록 시각이 DEFEND_INTERVAL초 이내면 → 즉시 주소 사용을 중단해야 함(MUST)
      - 목적: 두 호스트가 같은 주소를 방어하려는 무한 루프에 빠지지 않도록
  - (c) 어떤 상황에서도 주소를 포기해서는 안 되도록 설정된 경우 (예: 링크의 기본 라우터·DNS 서버처럼 잘 알려진 안정적 IP 주소가 필요한 장치) → 주소를 무기한 방어할 수 있음(MAY)
    - 충돌하는 ARP 패킷 수신 시 → 출처 이더넷 주소 등 유용한 정보를 기록하고 관리자에게 알리는 적절한 조치를 취해야 함
    - 최근 DEFEND_INTERVAL초 이내에 다른 충돌 패킷을 보지 않았다면 → 시각을 기록하고 단일 ARP Announcement를 브로드캐스트해야 함(MUST)
    - 이전 충돌 패킷 기록 시각이 DEFEND_INTERVAL초 이내면 → 다른 방어적 ARP Announcement를 보내서는 안 됨(MUST NOT)
      - 목적: 잘못 설정된 두 호스트가 같은 주소를 방어하려다 브로드캐스트 트래픽으로 네트워크를 범람시키는 무한 루프 방지
- 신뢰할 수 있는 네트워크 운영을 제공하려는 호스트 → 위 (a)·(b)·(c)대로 충돌하는 ARP 패킷에 응답해야 함(MUST)
  - 충돌 패킷을 무시하면 진단하기 어렵고 사용자가 겪기 힘든 간헐적 네트워크 장애 발생
- 충돌로 인해 주소를 포기하기 전 → 해당 주소를 사용하는 기존 연결을 적극적으로 리셋하려 시도해야 함(SHOULD)
  - 5절에서 논의하는 주소 재설정으로 인한 일부 보안 위협을 완화

### 2.5. 계속 운영

- 첫 번째 ARP Announcement 전송 시점부터 IP 주소 사용 중단 시점까지, ARP 명세 [RFC826]가 요구하는 일반적 방식으로 ARP Request에 응답해야 함(MUST)
- 구체적으로: 2.4절의 충돌하는 ARP 패킷이 아닌 ARP Request를 수신하고, '대상 IP 주소'가 해당 인터페이스에 설정된 호스트 자신의 IP 주소(중 하나)이면 → RFC 826에 설명된 대로 ARP Reply로 응답해야 함(MUST)

### 2.6. 브로드캐스트 ARP Reply

- 수동으로 할당된 주소의 주의 깊게 운영되는 네트워크, 신뢰할 수 있는 DHCP 서버·클라이언트가 있는 네트워크 → 주소 충돌이 드문 장애 시나리오에서만 발생 → 2.4절의 수동적 모니터링으로 충분
- 그러나 충돌 설정이 감지되기 전에 짧은 시간 동안 지속될 수 있는 사례
  - 호스트 A·B가 실수로 같은 IP 주소 X를 할당받음
  - 탐침 시점에 통신 링크가 작동하지 않아서 인터페이스 설정 시 충돌을 감지하지 못함
  - 통신 링크가 복원되고 세 번째 호스트 C가 주소 X에 대한 ARP Request를 브로드캐스트
  - 충돌을 모르는 A·B 모두 C에게 유니캐스트 ARP Reply를 보냄
  - C는 양쪽 Reply를 보지만, A·B 어느 쪽도 상대방의 Reply를 보지 못하고 즉시 해결해야 할 충돌을 감지하지 못함
- 더 빠른 충돌 감지가 필요하면 → 유니캐스트가 아닌 링크 수준 브로드캐스트로 ARP Reply 전송
  - 일반 사용에는 권장되지 않음(NOT RECOMMENDED)
  - ACD 기반의 다른 명세에서 적절하다고 판단하면 브로드캐스트 ARP Reply를 규정할 수 있음

## 3. ARP Announcement는 왜 ARP Reply가 아닌 ARP Request 패킷으로 수행하는가?

- 2000년부터 2008년까지 IETF의 ACD 논의 과정에서 거듭 나온 질문: "ARP Announcement는 무상(gratuitous) ARP Reply 패킷으로 수행해야 하지 않는가?"
- ARP Request 패킷 사용을 지지하는 두 가지 이유
  - 역사적 선례
    - 무상 ARP는 Stevens Networking [Ste94]에서 ARP Request 패킷을 사용하는 것으로 문서화
    - BSD Unix·Microsoft Windows·Mac OS 9·Mac OS X 모두 Stevens 방식대로 ARP Request 패킷 사용 → 이 시점에서 모두 ARP Reply 패킷 사용으로 전환하도록 강제하는 것은 무의미
  - 실용주의
    - ARP Request 패킷이 기존 ARP 구현과 더 올바르게 동작할 가능성이 높음
    - RFC 826의 패킷 수신 규칙: opcode가 패킷 처리에서 마지막으로 확인하는 항목이라 명시 → 원칙상 차이가 없어야 함
    - 그러나 `ar$op` 필드에 따라 다른 패킷 처리를 하는 "독창적인" 구현 존재 가능 → 무상 ARP Reply보다 무상 ARP Request를 수용할 가능성이 더 높은 이유
      - 잘못된 ARP 구현이 ARP Reply가 유니캐스트로만 전송된다고 기대할 수 있음
      - 잘못된 ARP 구현이 최근 발행한 ARP Request에 대한 응답으로만 ARP Reply를 수신할 것으로 기대할 수 있음
      - 잘못된 ARP 구현이 `ar$tha`가 자신의 하드웨어 주소와 일치하지 않는 ARP Reply를 무시할 수 있음
      - 잘못된 ARP 구현이 `ar$tpa`가 자신의 IP 주소와 일치하지 않는 ARP Reply를 무시할 수 있음

## 4. 역사적 참고

- 일부 주장: Stevens [Ste94]의 "무상 ARP"가 중복 주소 감지를 제공하므로 ACD가 불필요 → 올바르지 않음
- Stevens가 무상 ARP로 설명하는 것 = 이 문서에서 'ARP Announcement'로 지칭하는 것과 정확히 같은 패킷
- 전통적인 무상 ARP 구현: 인터페이스가 처음 설정될 때 단일 ARP Announcement만 전송
  - 결과: 기존 주소 보유자가 오류를 기록하고, 충돌을 일으킨 쪽은 대개 문제를 알아차리지도 못한 채 운영을 계속
  - 양쪽 기계 모두 같은 IP 주소를 사용하려 하며 서로의 TCP 연결을 끊임없이 리셋 → 정상 동작 불가
- 무상 ARP는 사실상 효과적인 중복 주소 감지를 제공하지 않음

## 5. 보안 고려사항

- ACD는 ARP [RFC826]에 기반 → 그 프로토콜의 보안 취약점을 상속
  - 악의적인 호스트가 위조된 ARP 패킷을 보내 다른 호스트의 올바른 동작을 방해할 수 있음
  - 예: 호스트가 모든 ARP Request에 자신의 하드웨어 주소를 담은 Reply로 응답 → 네트워크의 모든 주소에 대한 소유권 주장 (쉽게 가능)
- 이 명세는 기존 ARP 취약점을 악화시키지 않으며 일부 측면에서 개선
  - 이유 없이 조용히 실패하는 대신, 자동 재설정을 시도하거나 최소한 무슨 일이 일어나고 있는지 사용자에게 알림
- 2.4절 (a)항대로 호스트가 ARP 충돌에 응하여 자발적으로 새 주소를 선택하면 → 같은 링크의 악의적인 공격자가 TCP 연결을 탈취하기 더 쉬워질 수 있음
  - 완화 방법: 주소를 포기하기 전에 기존 연결을 적극적으로 리셋
