# RFC 826 - Address Resolution Protocol (ARP)

```
Network Working Group                                   David C. Plummer
Request For Comments:  826                                  (DCP@MIT-MC)
                                                           November 1982
```

> 1982년 11월 발행 → 프로토콜 주소(예: IP 주소)를 48비트 이더넷 하드웨어 주소로 동적으로 변환하는 방법을 정의한 프로토콜 명세.
> RFC 5227(ARP probe를 통한 주소 충돌 감지)·RFC 5494(오탈자 정정)에 의해 갱신(Updated)됨.
> 발행 당시 인터넷 표준의 명세가 아니라 검토·의견 수렴을 위한 제안이었음.

## 1. 개요

- 배경: 프로토콜 P의 구현이 송신 호스트 S에서 라우팅 메커니즘을 통해 같은 10Mbit 이더넷 케이블 상의 대상 호스트 T로 패킷을 전송하려 함 → 실제 전송에는 48비트 이더넷 주소 필요
- 문제: 프로토콜 P의 호스트 주소는 길이·값이 달라 이더넷 주소와 항상 호환되지 않음
- 해결: 프로토콜 P 주소 공간의 주소 A를 48비트 이더넷 주소로 변환하는 테이블을 동적으로 구축·배포하는 프로토콜 제시
- 일반화: 10Mbit 이더넷뿐 아니라 다른 하드웨어(예: 패킷 라디오 네트워크)에서도 사용 가능하도록 설계

## 2. 참고사항

- 원 설계 대상: DEC/Intel/Xerox 10Mbit 이더넷 → 이후 다른 네트워크 유형에도 일반화(논의는 주로 10Mbit 이더넷 중심, 해당 시 일반화 내용이 뒤따름)
- DOD Internet Protocol → 이하 "Internet"으로 지칭
- 바이트 순서: 이더넷 표준을 따름 → 상위 바이트가 먼저 전송됨(PDP-11·VAX의 바이트 주소 지정과는 반대) → opcode 필드(`ar$op`) 처리 시 특별한 주의 필요
- 하드웨어 이름공간 값 관리 권한: 아직 합의된 권한 없음 → 공식 권한이 수립되기 전까지 요청 제출처:

## 3. 문제

- 네트워크 아키텍처의 거의 모든 계층에 여러 프로토콜이 사용될 수 있음
  - 상위 수준: 원격 로그인용 TELNET·SUPDUP
  - 중간 수준: 신뢰성 있는 바이트 스트림 프로토콜 — CHAOS·DOD TCP·Xerox BSP·DECnet
  - 하드웨어에 가까운 수준: 논리적 전송 계층 — CHAOS·DOD Internet·Xerox PUP·DECnet
- 10Mbit 이더넷: 패킷 헤더의 타입 필드로 이 모든 프로토콜(및 그 이상)이 단일 케이블에 공존 가능
- 제약: 이더넷은 물리 케이블에서 48비트 주소를 요구 → 대부분의 프로토콜 주소는 48비트가 아니며 이더넷 주소와 무관
  - 예: CHAOS 주소 16비트 · DOD Internet 주소 32비트 · Xerox PUP 주소 8비트
- 필요: <프로토콜, 주소> 쌍과 48비트 이더넷 주소 간 대응 관계를 동적으로 배포하는 프로토콜

## 4. 동기

- 10Mbit 이더넷 사용 증가 → DEC/Intel/Xerox 사양에 맞는 인터페이스를 공급하는 제조사 증가 → 관련 소프트웨어 작성도 증가
- 두 가지 대안
  - 구현자마다 독자적인 주소 해석 방법을 각각 발명
  - 표준을 사용해 코드가 수정 없이 다른 시스템에 배포되도록 함
- 이 제안: 후자의 표준을 수립하려는 목적

## 5. 정의

이더넷 패킷 헤더 TYPE 필드 값:

```
ether_type$XEROX_PUP
ether_type$DOD_INTERNET
ether_type$CHAOS
ether_type$ADDRESS_RESOLUTION   (신규)
```

opcode 값:

```
ares_op$REQUEST (= 1, 상위 바이트가 먼저 전송됨)
ares_op$REPLY   (= 2)
```

하드웨어 타입 값:

```
ares_hrd$Ethernet (= 1)
```

## 6. 패킷 형식

<프로토콜, 주소> 쌍 → 48비트 이더넷 주소 매핑을 전달하는 패킷 형식.

```
이더넷 전송 계층 (사용자가 반드시 접근할 수 있는 것은 아님):
    48.bit: 목적지의 이더넷 주소
    48.bit: 송신자의 이더넷 주소
    16.bit: 프로토콜 타입 = ether_type$ADDRESS_RESOLUTION

이더넷 패킷 데이터:
    16.bit: (ar$hrd) 하드웨어 주소 공간 (예: Ethernet, Packet Radio Net.)
    16.bit: (ar$pro) 프로토콜 주소 공간
                     이더넷 하드웨어의 경우 ether_type$<프로토콜> 집합에서 가져옴
     8.bit: (ar$hln) 각 하드웨어 주소의 바이트 길이
     8.bit: (ar$pln) 각 프로토콜 주소의 바이트 길이
    16.bit: (ar$op)  opcode (ares_op$REQUEST | ares_op$REPLY)
    nbytes: (ar$sha) 이 패킷 송신자의 하드웨어 주소, n = ar$hln
    mbytes: (ar$spa) 이 패킷 송신자의 프로토콜 주소, m = ar$pln
    nbytes: (ar$tha) 이 패킷 대상의 하드웨어 주소 (알려진 경우)
    mbytes: (ar$tpa) 대상의 프로토콜 주소
```

## 7. 패킷 생성

- 패킷이 네트워크 계층을 통해 내려감 → 라우팅이 다음 홉의 프로토콜 주소를 가진 대상 스테이션을 찾을 것으로 예상되는 하드웨어를 결정
- 10Mbit 이더넷의 경우 주소 해석 필요 → 하위 계층(하드웨어 드라이버)이 Address Resolution 모듈에 <프로토콜 타입, 대상 프로토콜 주소> → 48비트 이더넷 주소 변환을 요청
- 처리 절차
  - 테이블에서 쌍을 찾으면: 대응하는 이더넷 주소를 호출자(하드웨어 드라이버)에게 반환 → 호출자가 패킷 전송
  - 찾지 못하면
    - 호출자에게 패킷 폐기 통지(상위 네트워크 계층에서 재전송될 것이라는 가정)
    - 타입 필드가 `ether_type$ADDRESS_RESOLUTION`인 이더넷 패킷 생성, 필드 설정
      - `ar$hrd` = `ares_hrd$Ethernet`
      - `ar$pro` = 해석 중인 프로토콜 타입
      - `ar$hln` = 6 (48비트 이더넷 주소의 바이트 수)
      - `ar$pln` = 해당 프로토콜에서 주소의 길이
      - `ar$op` = `ares_op$REQUEST`
      - `ar$sha` = 자신의 48비트 이더넷 주소
      - `ar$spa` = 자신의 프로토콜 주소
      - `ar$tpa` = 접근하려는 기계의 프로토콜 주소
      - `ar$tha`: 특별히 설정하지 않음(이것이 바로 결정하려는 값) — 구현 편의상 하드웨어의 브로드캐스트 주소(10Mbit 이더넷은 모두 1)로 설정 가능
    - 이 패킷을 라우팅 메커니즘이 원래 결정한 이더넷 케이블의 모든 스테이션에 브로드캐스트

## 8. 패킷 수신

주소 해석 패킷 수신 → 이더넷 모듈이 Address Resolution 모듈에 전달 → 다음 알고리즘 수행(부정 조건문은 처리 종료·패킷 폐기를 의미):

```
나는 ar$hrd에 있는 하드웨어 타입을 가지고 있는가?
예: (거의 확실하게)
  [선택: 하드웨어 길이 ar$hln 확인]
  나는 ar$pro에 있는 프로토콜을 사용하는가?
  예:
    [선택: 프로토콜 길이 ar$pln 확인]
    Merge_flag := false
    <프로토콜 타입, 송신자 프로토콜 주소> 쌍이 이미 변환 테이블에 있으면
        → 해당 항목의 송신자 하드웨어 주소 필드를 패킷의 새 정보로 갱신, Merge_flag := true
    나는 대상 프로토콜 주소인가?
    예:
      Merge_flag가 false이면
          → <프로토콜 타입, 송신자 프로토콜 주소, 송신자 하드웨어 주소> 삼중항을 변환 테이블에 추가
      opcode가 ares_op$REQUEST인가?  (opcode는 이 시점에야 확인)
      예:
        하드웨어·프로토콜 필드를 교환 → 로컬 하드웨어·프로토콜 주소를 송신자 필드에 배치
        ar$op 필드를 ares_op$REPLY로 설정
        요청이 수신된 것과 동일한 하드웨어로 (새로운) 대상 하드웨어 주소에 패킷 전송
```

핵심 설계 포인트:

- <프로토콜 타입, 송신자 프로토콜 주소, 송신자 하드웨어 주소> 삼중항은 opcode를 확인하기 전에 테이블에 병합됨
  - 이유: 호스트 A→B 매핑이 이미 있고 B가 A로의 매핑 없이(또는 오래된 매핑으로) 주소 해석을 시도 중일 때 → A가 B의 패킷 opcode를 확인하는 시점에는 이미 B의 새 하드웨어 주소가 테이블에 입력되어 있음
- <프로토콜 타입, 대상 프로토콜 주소>가 일치할 경우에만 삼중항이 변환 테이블에 추가됨
  - 목적: 모든 기계의 변환 테이블이 네트워크의 모든 기계 항목으로 채워지는 것 방지 · 관련 없는 정보의 테이블 유입 방지
- 대상 프로토콜 주소가 자신과 일치하고 이미 알려진 <프로토콜 타입, 송신자 프로토콜 주소>인 경우 → 테이블(기존 항목의 하드웨어 주소) 갱신이 중요
  - 이유: 호스트 이동·프로토콜 주소 재할당·NIC 교체 등으로 주소 교환이 일어나면 원래 주소의 매핑이 무효화됨 → 알고리즘은 새 정보 수용을 우선해 이 상황을 감지해야 하는 어려운 문제를 회피

## 9. 설계 근거

- 주기적 브로드캐스팅은 바람직하지 않음
  - 예: 단일 이더넷에 워크스테이션 100대, 각각 10분에 한 번 브로드캐스트 → 6초당 1패킷(거의 합리적이나 대부분 무의미)
  - 워크스테이션은 서로 통신 거의 안 함(테이블에 쓸모없는 항목 100개 발생) · 주로 메인프레임·파일 서버·브리지와, 소수의 다른 워크스테이션과만(대화형 대화 등) 통신
  - 이 프로토콜: 필요할 때 정보를 배포, 기계 부팅당 한 번(대략) 배포
- 같은 패킷에서 하나 이상의 해석을 허용하지 않음(다중화 없음) → 단순성 확보
  - 다중화 허용 시 패킷 형식이 상당히 복잡해지고 정보 대부분이 불필요해질 수 있음
  - 예: 네 가지 프로토콜을 쓰는 브리지가 워크스테이션에 네 프로토콜 주소를 모두 통지 → 그중 셋은 워크스테이션이 거의 쓰지 않을 수 있음
- 요청·응답 패킷 길이가 같고 여러 필드가 동일 → 응답 생성 시 패킷 버퍼 재사용 가능
- 하드웨어 필드(`ar$hrd`): 목적별 값 목록에서 가져옴 → 현재 정의된 값은 10Mbit 이더넷용(`ares_hrd$Ethernet` = 1)뿐 → Packet Radio Network 등 향후 매체용 추가 값 필요
- 10Mbit 이더넷의 프로토콜 필드(`ar$pro`): `ether_type$` 집합에서 가져옴(할당된 프로토콜 타입의 자연스러운 재사용)
  - opcode(`ar$op`)와 결합 시 이 프로토콜로 해석 가능한 프로토콜 수가 사실상 절반으로 감소 → 모니터/디버거 복잡도 증가
- 길이 필드(`ar$hln`·`ar$pln`): 이론상 중복(프로토콜 주소 길이는 하드웨어 타입 `ar$hrd`·프로토콜 타입 `ar$pro`로 결정 가능) → 선택적 일관성 검사·네트워크 모니터링 및 디버깅 목적으로 포함
- opcode: 요청(응답을 유발할 수 있음)인지 이전 요청에 대한 응답인지 구분 → 16비트는 과도하나 플래그 필드가 필요
- 송신자 하드웨어·프로토콜 주소: 변환 테이블에 입력되는 필드 → 반드시 필요
- 대상 프로토콜 주소: 요청 형식에서 필요(송신자 정보를 테이블에 입력할지 응답을 보낼지 결정) → 응답이 요청에 의해서만 유발된다고 가정하면 응답 형식에서는 필수 아님(완전성·네트워크 모니터링·처리 알고리즘 단순화를 위해 포함 — 이 알고리즘은 송신자 정보를 테이블에 넣은 후에야 opcode를 확인)
- 대상 하드웨어 주소: 완전성·네트워크 모니터링을 위해 포함
  - 요청 형식에서는 의미 없음(기계가 요청하는 것이 바로 이 값)
  - 응답 형식에서는 요청한 기계의 주소를 의미 → 일부 구현(예: 14바이트 이더넷 헤더에 접근 불가한 경우)에서 이 필드를 그대로 하드웨어 목적지 주소로 드라이버에 전달해 레지스터 셔플링·스택 공간 절약 가능
- 주소 사이에 패딩 바이트 없음 → 패킷 데이터 중 워드로 정의된 바이트 스트림은 3개 바이트 쌍(`ar$hrd`·`ar$pro`·`ar$op`)뿐이며 최상위 바이트가 먼저 전송됨(Ethernet/PDP-10 바이트 스타일)

## 10. 네트워크 모니터링 및 디버깅

- ARP: 기계가 이더넷 케이블에서의 상위 수준 프로토콜 활동(예: CHAOS·Internet·PUP·DECnet)에 대한 지식을 얻게 함 → 어떤 이더넷 프로토콜 타입이 사용되는지, 각 타입 내 프로토콜 주소가 무엇인지 파악 가능(모니터가 해당 프로토콜을 직접 사용할 필요조차 없음)
- 동작 개요
  - 모니터가 ARP 패킷 수신 → <프로토콜 타입, 송신자 프로토콜 주소, 송신자 하드웨어 주소>를 항상 테이블에 입력
  - `ar$hln`·`ar$pln`으로 하드웨어·프로토콜 주소 길이 결정
  - opcode = REPLY → 패킷 폐기 가능
  - opcode = REQUEST · 대상 프로토콜 주소가 모니터 자신과 일치 → 정상적으로 REPLY 전송
    - 이 방법으로는 매핑 하나만 획득(REQUEST에 대한 REPLY는 요청 호스트에게 직접 전송되기 때문)
  - 모니터가 자체 REQUEST를 보내볼 수도 있으나 두 모니터가 REQUEST 전송 루프에 빠질 위험 → 주의 필요
- 프로토콜과 opcode가 한 필드로 결합되지 않음 → 모니터가 동일 상위 프로토콜의 요청 opcode·응답 opcode 대응 관계를 알 필요 없음
- 길이 필드로 주소를 "파싱"하기에는 충분하나 주소의 의미에 대한 지식은 없음
- 동작하는 ARP 구현은 동작하지 않는 구현의 디버깅에도 활용 가능
  - 하드웨어 드라이버가 `ether_type$ADDRESS_RESOLUTION` 패킷은 성공적으로 브로드캐스트할 수 있음(초기 구현 버그·테이블 관리 문제로 패킷 형식은 완전히 올바르지 않을 수 있음)
  - 요청은 브로드캐스트되므로 모니터가 패킷을 수신해 원하는 경우 디버깅용으로 표시 가능

## 11. 예시

- 설정: 동일 10Mbit 이더넷 케이블의 기계 X·Y, 이더넷 주소 EA(X)·EA(Y), DOD Internet 주소 IPA(X)·IPA(Y), Internet의 이더넷 타입 ET(IP)
- 시나리오: X가 방금 시작됨 → 같은 케이블의 Y에게 Internet 패킷을 보내려 함
  1. X가 IPA(Y)로 보내려 함을 알고 하드웨어 드라이버(이더넷 드라이버)에게 IPA(Y) 전달 → 드라이버가 Address Resolution 모듈에 <ET(IP), IPA(Y)> → 48비트 이더넷 주소 변환 문의 → X가 방금 시작되어 이 정보 없음
  2. Internet 패킷 폐기 → 다음과 같이 ADDRESS RESOLUTION 패킷 생성:

```
(ar$hrd) = ares_hrd$Ethernet
(ar$pro) = ET(IP)
(ar$hln) = length(EA(X))
(ar$pln) = length(IPA(X))
(ar$op)  = ares_op$REQUEST
(ar$sha) = EA(X)
(ar$spa) = IPA(X)
(ar$tha) = 상관없음
(ar$tpa) = IPA(Y)
```

  3. 이 패킷을 케이블의 모든 사람에게 브로드캐스트
  4. Y가 패킷 수신 → 하드웨어 타입(Ethernet) 이해 · 표시된 프로토콜(Internet) 사용 · 자신을 위한 패킷임을 확인(`ar$tpa` = IPA(Y))
     → <ET(IP), IPA(X)>가 EA(X)에 매핑된다는 정보를 입력(기존 항목 대체 가능)
     → 이것이 요청임을 알아차림 → 필드를 교환해 EA(Y)를 새 송신자 이더넷 주소 필드(`ar$sha`)에 넣음, opcode를 응답으로 설정 → 패킷을 EA(X)에 직접 전송(브로드캐스트 아님)
     → 이 시점: Y는 X에게 보내는 방법을 알지만 X는 아직 Y에게 보내는 방법을 모름
  5. X가 Y로부터 응답 패킷 수신 → <ET(IP), IPA(Y)> → EA(Y) 매핑 형성 → 응답임을 알아차리고 폐기
  6. 다음에 X의 Internet 모듈이 이더넷으로 Y에게 패킷을 보내려 하면 변환 성공 → 패킷이 (바라건대) 도착
  7. Y의 Internet 모듈이 그 후 X와 통신하려 하면 Y가 X의 ARP 요청에서 얻은 정보를 기억하고 있으므로 이것도 성공

## 12. 관련 문제

- 테이블 에이징·타임아웃: 두는 것이 바람직할 수 있으나 구현은 이 프로토콜의 범위 밖(MOON@SCRC@MIT-MC에게 감사)
- 호스트 이동 시
  - 그 호스트가 시작한 모든 연결은 정상 동작(이동 시 자체 주소 해석 테이블이 지워진다고 가정)
  - 다른 호스트가 그 호스트에게 시작한 연결은 이전 주소를 폐기할 특별한 이유를 알지 못함
  - 단, 48비트 이더넷 주소는 고유하고 영구적으로 고정되어야 하며 변경되어서는 안 됨
  - "이동"의 실제 의미: 호스트 이름(및 다른 프로토콜 주소)이 다른 물리적 하드웨어에 재할당되는 것
  - 하드웨어·소프트웨어 오류로 잘못된 라우팅 정보가 실수로 전송될 위험 항상 존재 → 영원히 지속되도록 허용해서는 안 됨
  - 대응 방안
    - 연결 시작 실패 시 Address Resolution 모듈에 해당 정보 삭제를 알림(호스트가 도달할 수 없기 때문 — 다운되었거나 이전 변환이 더 이상 유효하지 않다는 추정)
    - 또는 호스트로부터 패킷 수신 시 그 호스트로의 주소 해석 항목 타임아웃을 재설정 → 적절한 시간 동안 패킷이 없으면 항목을 잊음(들어오는 각 패킷에 대해 테이블을 스캔하는 오버헤드 발생 → 해시나 인덱스로 완화 가능)
  - 수신 알고리즘의 설계 의도: 호스트 이동 시 복구 시간 단축
    - <프로토콜 타입, 송신자 프로토콜 주소>가 이미 테이블에 있으면 송신자 하드웨어 주소가 기존 항목을 대체함을 상기
    - 완벽한 이더넷에서 브로드캐스트 REQUEST가 케이블의 모든 스테이션에 도달 → 각 스테이션이 새 하드웨어 주소를 얻게 됨
  - 대안: 데몬에 의한 타임아웃
    - 적절한 시간 후 항목 제거를 고려 → 먼저 테이블의 이더넷 주소로 직접 opcode REQUEST 패킷 전송(필요 시 소수의 재전송)
    - 짧은 시간 내 REPLY가 없으면 항목 삭제(이더넷 전체 스테이션 방해 방지를 위해 요청은 직접 전송)
    - 단순히 항목을 잊으면 유용한 정보가 잊혀질 가능성이 높아 다시 얻어야 함
  - 호스트는 자기 자신에 대한 정보만 전송 → 호스트 재부팅 시 주소 매핑 테이블이 최신 상태가 됨
    - 잘못된 정보가 기계에서 기계로 전달되어 영원히 지속될 수는 없음(존재할 수 있는 유일한 잘못된 정보: 다른 기계가 48비트 이더넷 주소를 변경했음을 모르는 기계의 항목)
    - 주소 매핑 테이블을 수동으로 재설정(또는 지움)하면 충분할 수 있음
- 이 문제가 중요하다고 여겨지면 더 많은 검토 필요 → 주소 해석과 유사한 모든 프로토콜에 공통되는 문제
