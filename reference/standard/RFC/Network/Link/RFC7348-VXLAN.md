      가상 확장 근거리 통신망(VXLAN): 가상화된 L2 네트워크를
              L3 네트워크 위에 오버레이하기 위한 프레임워크


### Abstract

이 문서는 가상 확장 근거리 통신망(VXLAN)을 기술한다. VXLAN은 다수의
테넌트를 수용하는 가상화된 데이터센터 내에서 오버레이 네트워크의
필요성에 대응하기 위해 사용된다. 이 방식과 관련 프로토콜은 클라우드
서비스 제공자와 기업 데이터센터의 네트워크에서 사용할 수 있다.


1. 서론
-------

서버 가상화는 물리적 네트워크 인프라에 더 큰 부담을 주었다. 하나의
물리 서버가 이제 각각 고유한 MAC(Media Access Control) 주소를 가진
다수의 가상 머신(VM)을 보유한다. 이로 인해 수십만 대의 VM이 연결되고
통신해야 할 수 있으므로 스위치 이더넷 네트워크에서 더 큰 MAC 주소 테이블이
필요하다.

데이터센터의 VM이 가상 LAN(VLAN)에 따라 그룹화되는 경우, VM이 속할 수
있는 특정 그룹에 따라 트래픽을 분할하기 위해 수천 개의 VLAN이 필요할
수 있다. 현재 VLAN 한계인 4094는 이러한 상황에서 부족하다.

데이터센터는 종종 각각 자체 격리된 네트워크 도메인을 가진 다수의
테넌트를 호스팅해야 한다. 전용 인프라로 이를 실현하는 것은 경제적이지
않으므로, 네트워크 관리자는 공유 네트워크 위에서 격리를 구현한다.
이러한 시나리오에서 흔한 문제는 각 테넌트가 독립적으로 MAC 주소와
VLAN ID를 할당하여 물리 네트워크에서 중복이 발생할 수 있다는 것이다.

L2 물리 인프라를 사용하는 가상화 환경의 중요한 요구사항은 컴퓨팅,
네트워크, 스토리지 자원의 효율적 할당을 위해 L2 네트워크가 전체
데이터센터 또는 데이터센터 간에 걸쳐 확장되는 것이다. 이러한
네트워크에서 루프 없는 토폴로지를 위해 스패닝 트리 프로토콜(STP)
같은 전통적 접근법을 사용하면 많은 링크가 사용되지 못할 수 있다.

네트워크 운영자가 물리 인프라의 상호연결에 IP를 사용하는 경우(예:
등비용 다경로(ECMP)를 통한 다경로를 통한 확장성 확보)에도, VM 간 통신을 위한
L2 모델을 유지할 필요가 있다.

위에 설명된 시나리오들은 오버레이 네트워크가 필요해진다.
이 오버레이는 개별 VM의 MAC 트래픽을 캡슐화된 형식으로 논리적
"터널"을 통해 전달하는 데 사용된다.

3. VXLAN 문제 정의
------------------

### 3.1. 스패닝 트리와 VLAN 범위에 의한 제약

현재 L2 네트워크는 중복 경로로 인한 루프를 피하기 위해 IEEE 802.1D
스패닝 트리 프로토콜(STP) [802.1D]을 사용한다. STP는 프레임의 복제와
루핑을 방지하기 위해 링크 사용을 차단한다. 일부 데이터센터 운영자는
STP 때문에 실제 사용할 수 있는 것보다 더 많은 포트와 링크에 비용을
지불한다고 본다. 또한 다경로를 통한 복원력은 STP 모델에서 사용할 수
없다. TRILL [RFC6325]이나 SPB [802.1aq] 같은 새로운 이니셔티브가
다경로 지원과 STP의 일부 문제를 극복하기 위해 제안되었다.

L2 데이터센터 네트워크의 핵심 특성은 브로드캐스트 격리를 제공하기
위한 가상 LAN(VLAN)의 사용이다. 12비트 VLAN ID가 이더넷 데이터
프레임에서 더 큰 L2 네트워크를 다수의 브로드캐스트 도메인으로
나누는 데 사용된다. 이것은 4094개 미만의 VLAN을 필요로 하는 많은
데이터센터에 충분하였다. 가상화 도입이 늘면서 이 상한이 한계에 부딪히고 있다.


### 3.2. 멀티 테넌트 환경

클라우드 컴퓨팅은 멀티 테넌트 환경을 위한 온디맨드 탄력적 자원
프로비저닝을 수반한다. 가장 흔한 예는 퍼블릭 클라우드로, 클라우드
서비스 제공자가 같은 물리 인프라를 통해 여러 고객/테넌트에게 탄력적
서비스를 제공한다.

테넌트별 네트워크 트래픽 격리는 L2 또는 L3 네트워크를 통해 수행할
수 있다. L2 네트워크의 경우, VLAN이 트래픽 분리에 흔히 사용된다.
클라우드 제공자가 서비스하는 테넌트 수가 많으므로, 4094 VLAN 한계는
종종 부족하다. 또한 테넌트당 여러 VLAN이 필요한 경우가 많아 문제가
악화된다.

관련 사용 사례로 크로스-팟(cross-pod) 확장이 있다. 팟은 일반적으로
관련 네트워크 및 스토리지 연결을 가진 하나 이상의 서버 랙으로
구성된다. 테넌트가 팟에서 시작하여 확장으로 인해 다른 팟의
서버/VM이 필요할 수 있다. 이 사용 사례는 개별 서버/VM을 연결하는
"확장된" L2 환경을 필요로 한다.


### 3.3. ToR 스위치의 부족한 테이블 크기

오늘날의 가상화 환경은 서버에 연결되는 탑 오브 랙(ToR) 스위치의
MAC 주소 테이블에 추가 부담을 준다. 서버 링크당 하나의 MAC
주소 대신, ToR은 이제 개별 VM의 MAC 주소를 학습해야 한다(서버당
수백 개에 달할 수 있다). 일반적인 ToR 스위치는 서버 대면 포트의
수에 따라 24 또는 48개의 서버에 연결될 수 있다. 데이터센터는 여러
랙으로 구성될 수 있으므로, 각 ToR 스위치는 다양한 물리 서버에
걸친 통신하는 VM의 주소 테이블을 유지해야 한다.

테이블이 넘치면, 스위치는 유휴 항목이 만료될 때까지 새 주소
학습을 중단할 수 있으며, 이후의 알 수 없는 목적지 프레임의 심각한
플러딩을 초래한다.


4. VXLAN
--------

VXLAN(Virtual eXtensible Local Area Network)은 멀티 테넌트 환경에서
VM이 존재하는 L2 및 L3 데이터센터 네트워크 인프라의 위 요구사항을
해결한다. 기존 네트워킹 인프라 위에서 실행되며 L2 네트워크를
"확장"하는 수단을 제공한다. 요약하면, VXLAN은 L3 네트워크 위의 L2
오버레이 방식이다.

각 오버레이를 VXLAN 세그먼트라 한다. 같은 VXLAN 세그먼트 내의 VM만
서로 통신할 수 있다. 각 VXLAN 세그먼트는 24비트 세그먼트 ID인
"VXLAN Network Identifier(VNI)"로 식별된다. 이를 통해 같은 관리
도메인 내에 최대 1600만 VXLAN 세그먼트가 공존할 수 있다.

VNI는 개별 VM에서 보낸 내부 MAC 프레임의 범위를 식별한다. 따라서
세그먼트 간에 중복 MAC 주소를 가질 수 있지만, 트래픽이 VNI를
사용하여 격리되므로 트래픽이 "교차"하는 일은 없다.


### 4.1. 유니캐스트 VM 간 통신

VXLAN 오버레이 네트워크 내의 VM을 생각하자. 이 VM은 VXLAN을 인식하지
못한다. 다른 호스트의 VM과 통신하기 위해 대상으로의 MAC 프레임을
정상적으로 전송한다. 물리 호스트의 VTEP은 이 VM이 연결된 VNI를
조회한다. 그런 다음 목적지 MAC이 같은 세그먼트에 있는지, 그리고
목적지 MAC 주소에서 원격 VTEP으로의 매핑이 있는지 확인한다. 있다면,
원래 MAC 프레임에 외부 MAC, 외부 IP 헤더, VXLAN 헤더로 구성된 외부
헤더가 앞에 붙는다. 캡슐화된 패킷은 원격 VTEP으로 전달된다. 수신
시, 원격 VTEP은 VNI의 유효성과 해당 VNI에 내부 목적지 MAC 주소와
일치하는 MAC 주소를 사용하는 VM이 있는지 검증한다. 있다면, 패킷의
캡슐화 헤더를 벗기고 목적지 VM에 전달한다.

또한 원격 VTEP은 내부 출발지 MAC에서 외부 출발지 IP 주소로의 매핑을
학습한다. 이 매핑을 테이블에 저장하여, 목적지 VM이 응답 패킷을
보낼 때 "알 수 없는 목적지" 플러딩이 필요 없게 한다.


### 4.2. 브로드캐스트 통신과 멀티캐스트 매핑

출발지 호스트의 VM이 IP를 사용하여 목적지 VM과 통신하려 한다고
하자. 양쪽이 같은 서브넷에 있다고 가정하면, VM은 ARP(Address
Resolution Protocol) 브로드캐스트 프레임을 전송한다. 비-VXLAN
환경에서는 이 프레임이 해당 VLAN을 전달하는 모든 스위치에 걸쳐
MAC 브로드캐스트로 전송될 것이다.

VXLAN에서는 VXLAN VNI를 포함하는 헤더가 IP 헤더 및 UDP 헤더와 함께
패킷의 시작 부분에 삽입된다. 그러나 이 브로드캐스트 패킷은 해당
VXLAN 오버레이 네트워크가 실현되는 IP 멀티캐스트 그룹으로 전송된다.

이를 위해 VXLAN VNI와 그것이 사용할 IP 멀티캐스트 그룹 간의 매핑이
필요하다. 이 매핑은 관리 계층에서 수행되어 관리 채널을 통해 개별
VTEP에 제공된다. 이 매핑을 사용하여, VTEP은 필요에 따라 VXLAN 관련
IP 멀티캐스트 그룹에 참여/탈퇴하기 위해 상위 스위치/라우터에 IGMP
멤버십 보고를 제공할 수 있다.

VTEP은 `(*,G)` 조인을 사용한다. 이는 VXLAN 터널 출발지 집합이
알려지지 않고 VM이 서로 다른 호스트에서 올라오거나 내려감에 따라
자주 변경될 수 있기 때문에 필요하다.

목적지 VM은 IP 유니캐스트를 사용하여 표준 ARP 응답을 보낸다. 이
프레임은 IP 유니캐스트 VXLAN 캡슐화를 사용하여 출발지 VM이 연결된
VTEP으로 다시 캡슐화된다. 이는 ARP 응답의 목적지 MAC에서 VXLAN 터널
종단점 IP로의 매핑이 이전 ARP 요청을 통해 학습되었기 때문에 가능하다.

멀티캐스트 프레임과 "알 수 없는 MAC 목적지" 프레임도 브로드캐스트
프레임과 유사하게 멀티캐스트 트리를 사용하여 전송된다.


### 4.3. 물리 인프라 요구사항

네트워크 인프라 내에서 IP 멀티캐스트를 사용하는 경우, PIM-SM 같은
멀티캐스트 라우팅 프로토콜을 네트워크 내의 개별 L3 IP 라우터/스위치가
사용할 수 있다. 이는 멀티캐스트 프레임이 수신을 요청한 호스트에만
전송되도록 효율적인 멀티캐스트 전달 트리를 구축하는 데 사용된다.

VTEP은 VXLAN 패킷을 단편화해서는 안 된다(MUST NOT). 중간 라우터가
더 큰 프레임 크기로 인해 캡슐화된 VXLAN 패킷을 단편화할 수 있다.
목적지 VTEP은 이러한 VXLAN 단편을 조용히 폐기할 수 있다(MAY).
단편화 없는 종단 간 트래픽 전달을 보장하려면, 물리 네트워크 인프라
전반의 MTU를 캡슐화로 인한 더 큰 프레임 크기를 수용하는 값으로
설정할 것을 권장한다(RECOMMENDED). 경로 MTU 발견([RFC1191] 및
[RFC1981]) 같은 다른 기법도 이 요구사항에 대응하는 데 사용할 수
있다(MAY).


5. VXLAN 프레임 형식
--------------------

VXLAN 프레임 형식은 아래에 보인다. 외부 프레임 검사 시퀀스(FCS) 위에
출발지, 목적지 MAC 주소와 이더넷 타입, 그리고 선택적 VLAN을 가진
자체 이더넷 헤더를 가진 내부 MAC 프레임이 있다.

내부 MAC 프레임은 다음 네 개의 헤더로 캡슐화된다 (가장 안쪽 헤더부터):

**VXLAN 헤더**: 8바이트 필드

- Flags (8비트): I 플래그는 유효한 VNI를 위해 1로 설정해야
  한다(MUST). 나머지 7비트("R"로 지정)는 예약 필드이며 전송 시 0으로
  설정하고(MUST) 수신 시 무시해야 한다(MUST).

- VXLAN Segment ID / VXLAN Network Identifier (VNI): 24비트 값으로,
  통신하는 VM이 위치한 개별 VXLAN 오버레이 네트워크를 지정한다.
  서로 다른 VXLAN 오버레이 네트워크의 VM은 서로 통신할 수 없다.

- 예약 필드 (24비트 및 8비트): 전송 시 0으로 설정하고(MUST) 수신 시
  무시해야 한다(MUST).

**외부 UDP 헤더**: VTEP이 제공하는 출발지 포트와 잘 알려진 UDP 포트인
목적지 포트를 가진 외부 UDP 헤더.

- 목적지 포트: IANA가 VXLAN UDP 포트로 값 4789를 할당하였으며, 이
  값을 기본 목적지 UDP 포트로 사용해야 한다(SHOULD). 일부 초기 VXLAN
  구현은 목적지 포트에 다른 값을 사용하였다. 이러한 구현과의
  상호운용을 위해 목적지 포트는 설정 가능해야 한다(SHOULD).

- 출발지 포트: UDP 출발지 포트 번호를 내부 패킷의 필드로부터의 해시를
  사용하여 계산하는 것을 권장한다 — 한 가지 예로 내부 이더넷 프레임
  헤더의 해시가 있다. 이는 VXLAN 오버레이를 통한 VM 간 트래픽의
  ECMP/부하 분산을 위한 엔트로피를 확보하기 위함이다.
  이 방식으로 UDP 출발지 포트 번호를 계산할 때, 값이 동적/사설 포트
  범위 49152-65535 [RFC6335] 내에 있을 것을 권장한다(RECOMMENDED).

- UDP 체크섬: 0으로 전송해야 한다(SHOULD). UDP 체크섬이 0인 패킷을
  수신하면, 역캡슐화를 위해 수용해야 한다(MUST). 선택적으로,
  캡슐화 종단점이 0이 아닌 UDP 체크섬을 포함하는 경우, IP 헤더,
  UDP 헤더, VXLAN 헤더, 캡슐화된 MAC 프레임을 포함한 전체 패킷에
  걸쳐 올바르게 계산되어야 한다(MUST).

**외부 IP 헤더**: 출발지 IP 주소는 통신하는 VM(내부 출발지 MAC 주소로
표현)이 실행되고 있는 VTEP의 IP 주소를 나타낸다. 목적지 IP 주소는
유니캐스트 또는 멀티캐스트 IP 주소일 수 있다 (4.1절 및 4.2절 참조).

**외부 이더넷 헤더 (예시)**: 외부 목적지 MAC 주소는 대상 VTEP의
주소이거나 중간 L3 라우터의 주소일 수 있다. 외부 VLAN 태그는
선택적이다.

IPv4 외부 헤더를 사용한 VXLAN 프레임 형식:

6. VXLAN 배포 시나리오
----------------------

VXLAN은 일반적으로 여러 랙에 걸쳐 분산될 수 있는 가상화된 호스트의
데이터센터에 배포된다. 개별 랙은 서로 다른 L3 네트워크의 일부이거나
단일 L2 네트워크에 있을 수 있다. VXLAN 세그먼트/오버레이 네트워크는
이러한 L2 또는 L3 네트워크 위에 오버레이된다.

```
+------------+-------------+
|        Server 1          |
| +----+----+  +----+----+ |
| |VM1-1    |  |VM1-2    | |
| |VNI 22   |  |VNI 34   | |
| +---------+  +---------+ |
|                          |
| +----+----+  +----+----+ |
| |VM1-3    |  |VM1-4    | |
| |VNI 74   |  |VNI 98   | |
| +---------+  +---------+ |
| Hypervisor VTEP (IP1)    |
+--------------------------+
                       |
                       |
                       |   +-------------+
                       |   |   Layer 3   |
                       |---|   Network   |
                           |             |
                           +-------------+
                               |
                               +-----------+
                                           |
                                    +------------+-------------+
                                    |        Server 2          |
                                    | +----+----+  +----+----+ |
                                    | |VM2-1    |  |VM2-2    | |
                                    | |VNI 34   |  |VNI 74   | |
                                    | +---------+  +---------+ |
                                    |                          |
                                    | +----+----+  +----+----+ |
                                    | |VM2-3    |  |VM2-4    | |
                                    | |VNI 98   |  |VNI 22   | |
                                    | +---------+  +---------+ |
                                    | Hypervisor VTEP (IP2)    |
                                    +--------------------------+
```

한 가지 배포 시나리오는 터널 종단점이 VXLAN을 이해하는 물리 서버인
경우다. 대안 시나리오는 VXLAN 오버레이 네트워크의 노드가 VLAN 기반일
수 있는 레거시 네트워크의 노드와 통신해야 하는 경우다. VXLAN과
비-VXLAN 환경 간의 트래픽 전달을 위해 네트워크에 VXLAN 게이트웨이를
포함할 수 있다.

```
+---+-----+---+                                    +---+-----+---+
|    Server 1 |                                    |  Non-VXLAN  |
(VXLAN enabled)<-----+                       +---->|  server     |
+-------------+      |                       |     +-------------+
                     |                       |
+---+-----+---+      |                       |     +---+-----+---+
|Server 2     |      |                       |     |  Non-VXLAN  |
(VXLAN enabled)<-----+   +---+-----+---+     +---->|    server   |
+-------------+      |   |Switch acting|     |     +-------------+
                     |---|  as VXLAN   |-----|
+---+-----+---+      |   |   Gateway   |
| Server 3    |      |   +-------------+
(VXLAN enabled)<-----+
+-------------+      |
                     |
+---+-----+---+      |
| Server 4    |      |
(VXLAN enabled)<-----+
+-------------+
```


### 6.1. 내부 VLAN 태그 처리

VTEP과 VXLAN 게이트웨이의 내부 VLAN 태그 처리는 다음을 따라야 한다:

역캡슐화된 VXLAN 프레임에 내부 VLAN 태그가 있으면, 달리 설정되지
않는 한 폐기해야 한다(SHOULD). 캡슐화 측에서, VTEP은 달리 설정되지
않는 한 터널 패킷에 내부 VLAN 태그를 포함해서는 안 된다(SHOULD NOT).
VLAN 태그가 있는 패킷이 VXLAN 터널링 후보인 경우, 캡슐화하는 VTEP은
달리 설정되지 않는 한 VLAN 태그를 제거해야 한다(SHOULD).


7. 보안 고려사항
----------------

전통적으로 L2 네트워크는 '내부에서'만 불량 종단점에 의해 공격받을
수 있었다 — LAN에 부적절한 접근을 얻어 트래픽을 도청하거나, 위조된
패킷을 주입하여 다른 MAC 주소를 '탈취'하거나, 플러딩을 유발하여
서비스 거부를 일으키는 방식이다. L2 트래픽을 전달하기 위한 MAC-
over-IP 메커니즘은 이 공격 표면을 크게 넓힌다. 불량 행위자가
적절히 캡슐화된 패킷을 주입하거나, 의도된 목적지 대신 자체
터널 종단점을 만들거나, 전송 네트워크에 접근하여 터널
트래픽을 모니터링·가로채는 것으로 발생할 수 있다.

이러한 공격의 일부는 VNI가 활성화된 포트에만 VM 프레임 수용을
제한하고, 미지의 출발지로부터의 트래픽을 제한하는 등 VTEP에서의
접근 제어 기능으로 대처할 수 있다. 또한 IP 네트워크 인프라 자체에
기존 보안 장치를 배포하여 전송 네트워크를 보호할 수 있다.

VXLAN에서 캡슐화되는 VM 트래픽에 대한 기밀성, 무결성, 인증의
필요성에 대응하기 위해, 기존의 IP 보안 프로토콜(예: IPsec
[RFC4301])이 사용될 수 있다. 보안 메커니즘에 의한 오버헤드는 VXLAN의
확장성에 영향을 미칠 수 있으므로 주의 깊게 평가되어야 한다.
