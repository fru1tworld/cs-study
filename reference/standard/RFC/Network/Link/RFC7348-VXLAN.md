### Abstract

- VXLAN(가상 확장 근거리 통신망) 정의 → 다수의 테넌트를 수용하는 가상화된 데이터센터 내 오버레이 네트워크 요구에 대응
- 클라우드 서비스 제공자와 기업의 데이터센터 네트워크에서 사용 가능

### 1. 서론

서버를 가상화하면 한 물리 서버에 고유 MAC 주소를 가진 VM이 여러 개 생긴다. 수십만 대의 VM이 통신하려면 스위치가 더 큰 MAC 주소 테이블을 유지해야 한다. VM 그룹마다 VLAN으로 트래픽을 나누는 경우에는 4094개의 VLAN 한계도 문제가 될 수 있다.

여러 테넌트를 수용하는 데이터센터는 비용 때문에 공유 네트워크 위에서 각 테넌트를 격리한다. 하지만 테넌트가 MAC 주소와 VLAN ID를 독립적으로 할당하면 물리 네트워크에서 값이 겹칠 수 있다.

컴퓨팅, 네트워크, 스토리지 자원을 효율적으로 배치하려면 L2 네트워크를 데이터센터 전체나 다른 데이터센터까지 확장해야 한다. 기존 STP 방식은 루프를 막는 대신 많은 링크를 사용하지 못하게 한다. ECMP 등의 IP 네트워크로 물리 인프라를 연결하더라도 VM 사이에서는 L2 통신 모델을 유지할 필요가 있다.

오버레이 네트워크는 이 요구를 충족하기 위해 개별 VM의 MAC 트래픽을 캡슐화하고 논리적 터널로 전달한다.

### 3. VXLAN 문제 정의

#### 3.1. 스패닝 트리와 VLAN 범위에 의한 제약

- 현재 L2 네트워크: 중복 경로로 인한 루프를 피하기 위해 IEEE 802.1D 스패닝 트리 프로토콜(STP) [802.1D] 사용
  - STP는 프레임 복제와 루프를 막기 위해 일부 링크를 차단
  - 일부 데이터센터 운영자는 실제 사용하는 것보다 많은 포트와 링크의 비용을 지불
  - 다경로를 통한 복원력은 STP 모델에서 사용 불가
  - TRILL [RFC6325]과 SPB [802.1aq]는 다중 경로를 지원하고 STP의 일부 문제를 해결하기 위해 제안됨
- L2 데이터센터 네트워크의 핵심 특성: 브로드캐스트 격리를 위한 VLAN 사용
  - 12비트 VLAN ID → 이더넷 데이터 프레임에서 더 큰 L2 네트워크를 다수의 브로드캐스트 도메인으로 분할
  - 4094개 미만 VLAN이 필요한 다수 데이터센터에는 충분했음
  - 가상화 도입 증가 → 이 상한이 한계에 부딪히는 상황

#### 3.2. 멀티 테넌트 환경

- 클라우드 컴퓨팅: 멀티 테넌트 환경을 위한 온디맨드 탄력적 자원 프로비저닝 수반
  - 대표 예: 퍼블릭 클라우드 → 클라우드 서비스 제공자가 같은 물리 인프라를 통해 여러 고객/테넌트에게 탄력적 서비스 제공
- 테넌트별 네트워크 트래픽 격리: L2 또는 L3 네트워크를 통해 수행 가능
  - L2 네트워크의 경우 VLAN이 트래픽 분리에 흔히 사용
  - 클라우드 제공자가 서비스하는 테넌트 수 많음 → 4094 VLAN 한계가 종종 부족
  - 테넌트당 여러 VLAN이 필요한 경우가 많아 문제 악화
- 관련 사용 사례: 크로스-팟(cross-pod) 확장
  - 팟: 네트워크와 스토리지 연결을 갖춘 하나 이상의 서버 랙으로 구성
  - 테넌트가 팟에서 시작 → 확장으로 인해 다른 팟의 서버/VM이 필요할 수 있음
  - 이 사용 사례 → 개별 서버/VM을 연결하는 "확장된" L2 환경 필요

#### 3.3. ToR 스위치의 부족한 테이블 크기

가상화 환경의 ToR(Top of Rack) 스위치는 서버 링크당 하나가 아니라 개별 VM의 MAC 주소를 학습해야 한다. 서버 한 대에 수백 개의 주소가 생길 수 있고, 일반적인 ToR 스위치는 24대 또는 48대의 서버와 연결된다. 여러 랙의 VM이 통신하면 스위치가 유지할 주소 테이블도 커진다.

테이블이 가득 차면 스위치는 사용하지 않는 항목이 만료될 때까지 새 주소를 학습하지 못할 수 있다. 그러면 목적지를 모르는 프레임이 많아져 플러딩이 심해진다.

### 4. VXLAN

VXLAN은 L3 네트워크 위에 L2 오버레이를 만들어 기존 인프라에서 L2 네트워크를 확장한다. 각 오버레이를 VXLAN 세그먼트라고 하며, 같은 세그먼트의 VM끼리 통신한다.

세그먼트는 24비트 VXLAN Network Identifier(VNI)로 구분하므로 같은 관리 도메인에 최대 1600만 개가 공존할 수 있다. 내부 MAC 프레임의 범위도 VNI로 구분한다. 따라서 다른 세그먼트에서 같은 MAC 주소를 쓰더라도 트래픽은 격리된다.

#### 4.1. 유니캐스트 VM 간 통신

- VXLAN 오버레이 네트워크 내 VM은 VXLAN을 인식하지 못함 → 다른 호스트의 VM과 통신하기 위해 목적지로의 MAC 프레임을 정상적으로 전송
- 물리 호스트의 VTEP 동작
  - VM이 연결된 VNI 조회
  - 목적지 MAC이 같은 세그먼트에 있는지, 목적지 MAC 주소에서 원격 VTEP으로의 매핑이 있는지 확인
  - 매핑이 있으면 원래 MAC 프레임 앞에 외부 MAC 헤더, 외부 IP 헤더, VXLAN 헤더로 구성된 외부 헤더를 붙임
  - 캡슐화된 패킷을 원격 VTEP으로 전달
- 원격 VTEP의 수신 처리
  - VNI 유효성 검증, 해당 VNI에서 내부 목적지 MAC 주소와 일치하는 MAC 주소를 사용하는 VM이 있는지 검증
  - 있으면 캡슐화 헤더를 벗기고 목적지 VM에 전달
- 원격 VTEP은 내부 출발지 MAC에서 외부 출발지 IP 주소로의 매핑도 학습
  - 이 매핑을 테이블에 저장 → 목적지 VM이 응답 패킷을 보낼 때 "알 수 없는 목적지" 플러딩 불필요

#### 4.2. 브로드캐스트 통신과 멀티캐스트 매핑

- 출발지 호스트의 VM이 IP로 목적지 VM과 통신 시도, 양쪽이 같은 서브넷에 있다고 가정
  - VM이 ARP(Address Resolution Protocol) 브로드캐스트 프레임 전송
  - 비-VXLAN 환경 → 해당 VLAN을 전달하는 모든 스위치에 걸쳐 MAC 브로드캐스트로 전송
- VXLAN에서는 VNI를 포함하는 헤더를 IP 헤더 및 UDP 헤더와 함께 패킷 시작 부분에 삽입
  - 브로드캐스트 패킷은 해당 VXLAN 오버레이 네트워크가 실현되는 IP 멀티캐스트 그룹으로 전송
- 이를 위해 VXLAN VNI와 사용할 IP 멀티캐스트 그룹 간의 매핑 필요
  - 매핑은 관리 계층에서 수행 → 관리 채널을 통해 개별 VTEP에 제공
  - VTEP은 이 매핑을 사용 → 필요에 따라 VXLAN 관련 IP 멀티캐스트 그룹에 참여/탈퇴하기 위해 상위 스위치/라우터에 IGMP 멤버십 보고 제공 가능
- VTEP은 `(*,G)` 조인 사용
  - VXLAN 터널 출발지 집합이 알려지지 않고, VM이 서로 다른 호스트에서 올라오거나 내려감에 따라 자주 변경될 수 있음 → 필요
- 목적지 VM: IP 유니캐스트로 표준 ARP 응답 전송
  - 이 프레임은 IP 유니캐스트 VXLAN 캡슐화를 사용해 출발지 VM이 연결된 VTEP으로 다시 캡슐화
  - ARP 응답의 목적지 MAC에서 VXLAN 터널 종단점 IP로의 매핑이 이전 ARP 요청을 통해 학습되었기 때문에 가능
- 멀티캐스트 프레임과 MAC 목적지를 알 수 없는 프레임도 브로드캐스트 프레임처럼 멀티캐스트 트리로 전송

#### 4.3. 물리 인프라 요구사항

- 네트워크 인프라 내에서 IP 멀티캐스트를 사용하는 경우
  - PIM-SM 같은 멀티캐스트 라우팅 프로토콜을 네트워크 내 개별 L3 IP 라우터/스위치가 사용 가능
  - 목적: 멀티캐스트 프레임이 수신을 요청한 호스트에만 전송되도록 효율적인 멀티캐스트 전달 트리 구축
- VTEP은 VXLAN 패킷을 단편화해서는 안 됨(MUST NOT)
  - 중간 라우터가 더 큰 프레임 크기로 인해 캡슐화된 VXLAN 패킷을 단편화할 수 있음
  - 목적지 VTEP은 이러한 VXLAN 단편을 조용히 폐기할 수 있음(MAY)
- 단편화 없는 종단 간 트래픽 전달을 보장하려면
  - 물리 네트워크 인프라 전반의 MTU를 캡슐화로 인한 더 큰 프레임 크기를 수용하는 값으로 설정 권장(RECOMMENDED)
  - 경로 MTU 발견([RFC1191], [RFC1981]) 같은 다른 기법도 이 요구사항 대응에 사용 가능(MAY)

### 5. VXLAN 프레임 형식

- VXLAN 프레임에는 출발지와 목적지 MAC 주소, 이더넷 타입, 선택적 VLAN을 담은 자체 이더넷 헤더가 있는 내부 MAC 프레임이 포함되며 외부 프레임 검사 시퀀스(FCS)가 뒤따름
- 내부 MAC 프레임은 다음 네 개의 헤더로 캡슐화(가장 안쪽 헤더부터)
  - VXLAN 헤더: 8바이트 필드
    - Flags(8비트): I 플래그는 유효한 VNI를 위해 1로 설정해야 함(MUST). 나머지 7비트("R")는 예약 필드 → 전송 시 0으로 설정(MUST), 수신 시 무시(MUST)
    - VXLAN Segment ID / VXLAN Network Identifier(VNI): 24비트 값 → 통신하는 VM이 위치한 개별 VXLAN 오버레이 네트워크 지정. 서로 다른 VXLAN 오버레이 네트워크의 VM은 서로 통신 불가
    - 예약 필드(24비트, 8비트): 전송 시 0으로 설정(MUST), 수신 시 무시(MUST)
  - 외부 UDP 헤더: VTEP이 제공하는 출발지 포트와 잘 알려진 UDP 포트인 목적지 포트로 구성
    - 목적지 포트: IANA가 VXLAN UDP 포트로 값 4789 할당 → 기본 목적지 UDP 포트로 사용해야 함(SHOULD). 일부 초기 VXLAN 구현은 다른 값 사용 → 상호운용을 위해 목적지 포트는 설정 가능해야 함(SHOULD)
    - 출발지 포트: UDP 출발지 포트 번호를 내부 패킷 필드로부터의 해시로 계산하는 것을 권장(예: 내부 이더넷 프레임 헤더의 해시) → VXLAN 오버레이를 통한 VM 간 트래픽의 ECMP/부하 분산을 위한 엔트로피 확보 목적. 이 방식으로 계산할 때 값이 동적/사설 포트 범위 49152-65535 [RFC6335] 내에 있을 것을 권장(RECOMMENDED)
    - UDP 체크섬: 0으로 전송해야 함(SHOULD). UDP 체크섬이 0인 패킷을 수신하면 역캡슐화를 위해 수용해야 함(MUST). 선택적으로, 캡슐화 종단점이 0이 아닌 UDP 체크섬을 포함하는 경우 IP 헤더, UDP 헤더, VXLAN 헤더, 캡슐화된 MAC 프레임을 포함한 전체 패킷에 걸쳐 올바르게 계산되어야 함(MUST)
  - 외부 IP 헤더: 출발지 IP 주소는 통신하는 VM(내부 출발지 MAC 주소로 표현)이 실행되는 VTEP의 IP 주소. 목적지 IP 주소는 유니캐스트 또는 멀티캐스트 IP 주소 가능(4.1절과 4.2절 참조)
  - 외부 이더넷 헤더(예시): 외부 목적지 MAC 주소는 대상 VTEP 또는 중간 L3 라우터의 주소 가능. 외부 VLAN 태그는 선택적

```
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

VXLAN 헤더:
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

내부 이더넷 헤더:

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|OptnlEthtype = C-Tag 802.1Q    | Inner.VLAN Tag Information    |

페이로드:
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

```

### 6. VXLAN 배포 시나리오

- VXLAN은 일반적으로 여러 랙에 걸쳐 분산될 수 있는 가상화된 호스트의 데이터센터에 배포
  - 개별 랙은 서로 다른 L3 네트워크의 일부이거나 단일 L2 네트워크에 있을 수 있음
  - VXLAN 세그먼트/오버레이 네트워크는 이러한 L2 또는 L3 네트워크 위에 오버레이

```
+------------+-------------+
|        Server 1          |
| +----+----+  +----+----+ |
| |VM1-1    |  |VM1-2    | |
| |VNI 22   |  |VNI 34   | |
| +---------+  +---------+ |
|                          |
| +----+----+  +----+----+ |
| |VM1-3    |  |VM1-4    | |
| |VNI 74   |  |VNI 98   | |
| +---------+  +---------+ |
| Hypervisor VTEP (IP1)    |
+--------------------------+
                       |
                       |
                       |   +-------------+
                       |   |   Layer 3   |
                       |---|   Network   |
                           |             |
                           +-------------+
                               |
                               +-----------+
                                           |
                                    +------------+-------------+
                                    |        Server 2          |
                                    | +----+----+  +----+----+ |
                                    | |VM2-1    |  |VM2-2    | |
                                    | |VNI 34   |  |VNI 74   | |
                                    | +---------+  +---------+ |
                                    |                          |
                                    | +----+----+  +----+----+ |
                                    | |VM2-3    |  |VM2-4    | |
                                    | |VNI 98   |  |VNI 22   | |
                                    | +---------+  +---------+ |
                                    | Hypervisor VTEP (IP2)    |
                                    +--------------------------+
```

- 배포 시나리오 1: 터널 종단점이 VXLAN을 이해하는 물리 서버인 경우
- 배포 시나리오 2(대안): VXLAN 오버레이 네트워크의 노드가 VLAN 기반일 수 있는 레거시 네트워크의 노드와 통신해야 하는 경우
  - VXLAN과 비-VXLAN 환경 간 트래픽 전달을 위해 네트워크에 VXLAN 게이트웨이 포함 가능

```
+---+-----+---+                                    +---+-----+---+
|    Server 1 |                                    |  Non-VXLAN  |
(VXLAN enabled)<-----+                       +---->|  server     |
+-------------+      |                       |     +-------------+
                     |                       |
+---+-----+---+      |                       |     +---+-----+---+
|Server 2     |      |                       |     |  Non-VXLAN  |
(VXLAN enabled)<-----+   +---+-----+---+     +---->|    server   |
+-------------+      |   |Switch acting|     |     +-------------+
                     |---|  as VXLAN   |-----|
+---+-----+---+      |   |   Gateway   |
| Server 3    |      |   +-------------+
(VXLAN enabled)<-----+
+-------------+      |
                     |
+---+-----+---+      |
| Server 4    |      |
(VXLAN enabled)<-----+
+-------------+
```

#### 6.1. 내부 VLAN 태그 처리

- VTEP과 VXLAN 게이트웨이의 내부 VLAN 태그 처리 규칙
  - 역캡슐화된 VXLAN 프레임에 내부 VLAN 태그가 있으면 → 달리 설정되지 않는 한 폐기해야 함(SHOULD)
  - 캡슐화 측: VTEP은 달리 설정되지 않는 한 터널 패킷에 내부 VLAN 태그를 포함해서는 안 됨(SHOULD NOT)
  - VLAN 태그가 있는 패킷이 VXLAN 터널링 후보인 경우 → 캡슐화하는 VTEP은 달리 설정되지 않는 한 VLAN 태그를 제거해야 함(SHOULD)

### 7. 보안 고려사항

- 전통적으로 L2 네트워크는 '내부에서'만 불량 종단점에 의해 공격 가능
  - LAN에 부적절한 접근을 얻어 트래픽 도청
  - 위조된 패킷을 주입해 다른 MAC 주소를 '탈취'
  - 플러딩을 유발해 서비스 거부 발생
- L2 트래픽을 전달하기 위한 MAC-over-IP 메커니즘 → 이 공격 표면을 크게 넓힘
  - 불량 행위자가 적절히 캡슐화된 패킷을 주입
  - 의도된 목적지 대신 자체 터널 종단점 생성
  - 전송 네트워크에 접근해 터널 트래픽을 관찰하거나 가로챔
- 대응 방안
  - VTEP에서의 접근 제어: VNI가 활성화된 포트에만 VM 프레임 수용을 제한, 미지의 출발지로부터의 트래픽 제한
  - IP 네트워크 인프라 자체에 기존 보안 장치 배포 → 전송 네트워크 보호
- VXLAN으로 캡슐화한 VM 트래픽의 기밀성, 무결성, 인증에 대한 대응
  - 기존 IP 보안 프로토콜(예: IPsec [RFC4301]) 사용 가능
  - 보안 메커니즘에 의한 오버헤드는 VXLAN 확장성에 영향 가능 → 주의 깊게 평가 필요
