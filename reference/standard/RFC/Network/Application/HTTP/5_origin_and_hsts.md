# Web Origin과 HSTS

## RFC 6454 - The Web Origin Concept

> 발행일: 2011년 12월
> 상태: Standards Track

### Abstract

- 사용자 에이전트가 권한·특권 범위로 자주 사용하는 "출처(origin)" 개념 정의
- 목적: 악의적 웹 사이트 운영자가 정상 웹 사이트 동작을 방해하지 못하도록 서로 다른 출처의 콘텐츠 격리
- 다루는 내용
  - 출처 개념의 기반 원칙
  - URI의 출처 결정 방법
  - 출처의 문자열 직렬화 방법
  - HTTP 요청과 연관된 출처를 나타내는 "Origin" 헤더 필드 정의

### 1. 소개

- 사용자 에이전트는 다수 저자의 콘텐츠와 상호작용 → 일부 저자는 악의적일 수 있음
- 사용자 에이전트 구현자의 목표: 악의적 저자가 다른 콘텐츠·서버의 기밀성/무결성을 훼손하는 능력 제한
- 예: 다양한 서버의 HTML을 렌더링하는 사용자 에이전트가 문서 내 스크립트를 실행할 때, 악의적 서버의 스크립트가 방화벽 뒤 정직한 서버의 문서를 읽지 못하도록 방지 필요
- 전통적 분류 방식: 콘텐츠를 "출처"별로 분류
  - 동일 출처 콘텐츠 간 자유로운 상호작용은 허용
  - 다른 출처 콘텐츠와의 상호작용은 제한
- 이 문서의 범위
  - 동일 출처 정책의 배경 원칙 + 출처 비교·직렬화의 핵심 메커니즘 기술
  - 동일 출처 정책의 모든 세부사항은 다루지 않음 → HTML [HTML], WebSocket [RFC6455] 등 개별 명세에 위임(세부사항이 애플리케이션별로 다르기 때문)

### 2. 규약

#### 2.1. 적합성 기준

- MUST/MUST NOT/REQUIRED/SHALL/SHALL NOT/SHOULD/SHOULD NOT/RECOMMENDED/MAY/OPTIONAL → [RFC2119]에 기술된 대로 해석
- 알고리즘 내 명령형으로 표현된 요구사항(예: "선행 공백 문자를 제거하라") → 해당 알고리즘 도입부 핵심어의 의미로 해석
- 적합성 요구사항 구현 방식: 최종 결과가 동등하면 어떤 방식으로든 구현 가능 → 이 명세의 알고리즘은 이해 용이성을 위한 것, 성능을 위한 것이 아님

#### 2.2. 구문 표기법

- [RFC5234]의 ABNF(Augmented BNF) 표기법 사용
- 핵심 규칙([RFC5234] 부록 B.1 참조에 의해 포함): ALPHA·CR·CRLF·CTL·DIGIT·DQUOTE·HEXDIG·LF·OCTET·SP·HTAB·CHAR·VCHAR·WSP
- OWS 규칙
  - 0개 이상의 선형 공백 옥텟이 나타날 수 있는 곳에서 사용
  - 생성 시: 없음 또는 단일 SP로 생성(SHOULD)
  - 해석·다운스트림 전달 시: 여러 OWS 옥텟은 단일 SP로 대체하거나 모든 옥텟을 SP로 변환(SHOULD)

```
OWS            = *( SP / HTAB / obs-fold )
               ; "선택적" 공백
obs-fold       = CRLF ( SP / HTAB )
               ; 사용되지 않는 줄 접기
```

#### 2.3. 용어

- "사용자 에이전트"·"클라이언트"·"서버"·"프록시"·"출처 서버" → HTTP/1.1([RFC2616] 섹션 1.3)에서와 동일한 의미
- 전역적으로 고유한 식별자
  - 이전에 존재하는 모든 다른 값과 다른 값
  - 예: 충분히 긴 임의 문자열
  - 출처 값이 사용자 에이전트를 벗어나지 않는 경우 → 로컬 단조 증가 카운터도 전역적으로 고유한 식별자로 사용 가능

### 3. 동일 출처 정책의 원칙

- 많은 사용자 에이전트가 원격 당사자를 대신해 작업 수행
  - 예: HTTP 사용자 에이전트는 원격 서버의 리다이렉트 지시를 따름
  - 예: HTML 사용자 에이전트는 원격 서버에서 가져온 스크립트에 풍부한 DOM 인터페이스 노출
- 보안 모델이 없으면 사용자·다른 당사자에게 해로운 작업 수행 가능 → 시간이 지나며 다수 웹 기술이 통칭 "동일 출처 정책"으로 수렴(대부분 유기적으로 발전했으나 몇 가지 핵심 개념으로 이해 가능)

#### 3.1. 신뢰

- 동일 출처 정책은 URI로 신뢰를 지정
- 예: 실행할 스크립트를 URI로 지정

```
<script src="https://example.com/library.js"></script>
```

  - 사용자 에이전트가 지정 URI의 스크립트를 가져와 해당 문서의 권한으로 실행
  - → 문서는 자신이 가진 모든 권한을 URI로 지정된 리소스에 부여 = 해당 URI에서 가져온 정보의 무결성을 신뢰한다는 선언
- 예: 비밀 데이터를 URI로 지정된 원격 당사자에게 전송

```
<form method="POST" action="https://example.com/login">
 ... <input type="password"> ...
</form>
```

  - 사용자가 비밀번호를 입력하고 양식을 제출하면 URI로 지정된 네트워크 엔드포인트로 전송
  - → 문서는 자신의 비밀 데이터를 해당 URI로 내보냄 = 해당 URI로 보낸 정보의 기밀성을 신뢰한다는 선언

##### 3.1.1. 함정

- 동일 출처 정책을 사용하는 신규 프로토콜 설계 시 중요한 신뢰 구분이 URI에 드러나야 함
- 예: TLS로 보호되는 리소스와 보호되지 않는 리소스가 모두 "http" URI 스킴을 사용하는 경우([RFC2817] 방식) → 문서가 TLS 경유 스크립트만 가져오고 싶다고 지정 불가
  - "https" URI 스킴 사용 시 → 능동적 네트워크 공격자로부터 보호되는 리소스와 상호작용하기를 원한다고 나타낼 수 있음

#### 3.2. 출처

- 원칙적으로 모든 URI를 별도 보호 도메인으로 취급하고 다른 URI와의 상호작용마다 명시적 동의를 요구할 수 있으나 → 웹 애플리케이션이 협력해 동작하는 여러 리소스로 구성되는 경우가 많아 개발자에게 번거로움
- 대신 URI를 "출처"라는 보호 도메인으로 그룹화
  - 두 URI가 동일한 스킴·호스트·포트를 가지면 동일한 출처(동일한 주체를 나타냄). 전체 세부사항은 섹션 4 참조
- Q: 왜 호스트만 사용하지 않는가
  - A: 출처 튜플에 스킴을 포함하는 것은 보안에 필수
    - 스킴 미포함 시 http://example.com 과 https://example.com 사이에 격리가 없음(동일 호스트이기 때문)
    - 격리 부재 시 능동적 네트워크 공격자가 http 콘텐츠를 변조해 https 콘텐츠의 기밀성·무결성을 침해하도록 지시 가능 → TLS[RFC5246]가 제공하는 보호를 우회
- Q: 왜 "최상위" 도메인 대신 정규화된 호스트 이름을 사용하는가
  - A: DNS는 계층적 위임을 가지나 호스트 이름 간 신뢰 관계는 배포에 따라 다름
    - 예: 많은 교육 기관에서 학생이 https://example.edu/~student/ 에 콘텐츠 호스팅 가능하지만, 학생 문서가 https://grades.example.edu/ 성적 관리 애플리케이션과 동일 출처(동일 보호 도메인)여야 하는 것은 아님
  - example.edu 배포 사례: 출처별 그룹화가 모든 배포 시나리오와 완벽히 일치하지는 않음을 보여줌(모든 학생 사이트가 동일 출처가 되는 것은 바람직하지 않을 수 있음) → 출처 세분화는 보안 모델이 발전한 역사적 산물

##### 3.2.1. 예제

- 동일한 출처를 갖는 리소스
  - http://example.com/
  - http://example.com:80/
  - http://example.com/path/file
  - → 각 리소스가 동일한 스킴·호스트·포트 구성요소를 가짐
- 서로 다른 출처를 갖는 리소스
  - http://example.com/
  - http://example.com:8080/
  - http://www.example.com/
  - https://example.com:80/
  - https://example.com/
  - http://example.org/
  - http://ietf.org/
  - → 각 경우 스킴·호스트·포트 구성요소 중 적어도 하나가 나머지와 다름

#### 3.3. 권한

- 출처로 그룹화되어도 출처 내 모든 리소스가 동일한 권한을 갖는 것은 아님(보안적 의미의 "권한", [RFC3986]의 의미가 아님)
  - 이미지: 수동적 콘텐츠 → 권한 없음(자신 출처에서 사용 가능한 객체·리소스에 접근 권한 없음)
  - HTML 문서: 자신 출처의 전체 권한 보유 → 문서 내(또는 문서로 가져온) 스크립트가 출처의 모든 리소스에 접근 가능
- 권한 부여 판단 기준: 리소스의 미디어 타입
  - image/png → 이미지로 취급
  - text/html → HTML 문서로 취급
- 신뢰할 수 없는 콘텐츠(사용자 생성 콘텐츠 등) 호스팅 시 미디어 타입 제한으로 권한 제한 가능
  - 예: 사용자 생성 콘텐츠를 image/png로 제공 → text/html로 제공하는 것보다 덜 위험
  - 다수 웹 애플리케이션이 신뢰할 수 없는 콘텐츠를 HTML 문서에 통합 → 주의 깊게 수행하지 않으면 출처의 권한이 신뢰할 수 없는 콘텐츠로 누출(크로스 사이트 스크립팅 취약점)

##### 3.3.1. 함정

- 웹 플랫폼의 새 요소 설계 시 미디어 타입에 관계없이 리소스에 권한을 부여하지 않도록 주의 필요
  - 다수 웹 애플리케이션이 제한된 미디어 타입으로 신뢰할 수 없는 콘텐츠를 제공 중 → 이런 콘텐츠 조각에 권한을 부여하는 신규 기능은 기존 애플리케이션에 취약점 도입 위험
  - 바람직한 방식: 이미 출처의 전체 권한을 소유한 미디어 타입, 또는 새 권한 전달용으로 설계된 신규 미디어 타입에만 권한 부여
- 콘텐츠 스니핑(잘못된 미디어 타입을 제공하는 서버와의 호환성 유지 목적)
  - 주의 깊게 수행하지 않으면 낮은 권한 미디어 타입(이미지 등)에 높은 권한 미디어 타입(HTML 등)의 특권을 부여할 수 있어 보안 취약점으로 이어짐 [SNIFF]

#### 3.4. 정책

- 일반적으로 사용자 에이전트는 서로 다른 출처를 격리하고 출처 간 통제된 통신을 허용
- 격리·통신 제공 방식의 세부사항은 여러 요인에 따라 다름

##### 3.4.1. 객체 접근

- 사용자 에이전트가 노출하는 대부분의 객체(API)는 동일한 출처에서만 사용 가능
  - 하나의 URI에서 가져온 콘텐츠가 다른 URI에서 가져온 콘텐츠의 객체에 접근 가능한 경우는, 두 URI가 동일한 출처(동일한 스킴·호스트·포트)에 속하는 경우로 한정
- 예외
  - HTML Location 인터페이스 일부는 출처 간 사용 가능(다른 브라우징 컨텍스트의 탐색을 허용하기 위해)
  - HTML postMessage 인터페이스는 크로스 출처 통신 촉진을 위해 명시적으로 출처 간 노출
- 외부 출처에 객체를 노출하는 것은 위험 → 잠재적 공격자에게도 노출되므로 매우 주의 깊게 수행 필요

##### 3.4.2. 네트워크 접근

- 네트워크 리소스 접근은 해당 리소스가 접근을 시도하는 콘텐츠와 동일한 출처인지에 따라 달라짐
- 읽기: 일반적으로 다른 출처의 정보를 읽는 것은 금지
  - 예외: 모든 출처의 스크립트 실행·이미지 렌더링·스타일 시트 적용은 허용
  - 예외: HTML 프레임 내 다른 출처의 문서 표시 가능
  - 네트워크 리소스가 다른 출처의 읽기를 명시적으로 허용 가능(예: CORS[CORS]) → 이 경우 접근은 출처별로 부여
- 쓰기: 다른 출처로 정보를 보내는 것은 허용되나 임의 형식의 전송은 위험
  - → 사용자 에이전트는 문서가 특정 프로토콜(예: 사용자 정의 헤더 없는 HTTP 요청)만 사용하도록 제한
  - 허용 프로토콜 집합 확장(예: WebSocket 지원 추가)은 취약점 도입을 피하기 위해 신중하게 수행 필요 [RFC6455]

##### 3.4.3. 함정

- 사용자 에이전트가 한 출처가 다른 출처의 리소스와 상호작용하도록 허용할 때마다 보안 문제 발생
  - 예: 다른 출처의 이미지 표시 기능 → 이미지의 높이·너비 누출
  - 예: 다른 출처로 네트워크 요청을 보내는 기능 → 크로스 사이트 요청 위조(CSRF) 취약점 발생 [CSRF]
  - → 구현자는 이러한 위험과 크로스 출처 상호작용 허용의 이점 사이에서 균형(예: 크로스 출처 요청을 전면 차단하면 하이퍼링크 탐색 자체를 방해)
- 출처 내 특정 리소스에만 특권을 부여하고 나머지는 보류하려는 시도는 효과적이지 않음
  - → 사용자 에이전트가 출처 내 리소스를 격리하지 않으므로 특권 없는 리소스도 결국 특권을 얻을 수 있음
  - 대신 특권은 출처 전체에 부여하거나 보류해야 함(출처 내 개별 리소스를 차별하지 않음) [BOFGO]

#### 3.5. 결론

- 동일 출처 정책은 URI로 신뢰 관계를 지정 → URI는 보호 도메인을 나타내는 출처로 그룹화
- 출처 내 리소스는 권한이 차등 부여
  - 능동적 콘텐츠 → 출처의 전체 권한
  - 수동적 콘텐츠 → 출처의 권한 없음
- 출처의 권한을 전달하는 콘텐츠 → 자신 출처 내 객체·네트워크 리소스에 접근 가능 + 다른 출처의 객체·네트워크 리소스에 제한적 접근 가능(크로스 출처 특권은 보안 취약점을 피하기 위해 신중하게 설계 필요)

### 4. URI의 출처

- URI의 출처는 다음 알고리즘으로 계산되는 값
  1. URI가 이름 지정 권한으로 계층적 요소를 사용하지 않거나([RFC3986] 섹션 3.2) 절대 URI가 아닌 경우 → 새로운 전역적으로 고유한 식별자를 생성해 반환
     - 참고: 동일한 URI에 이 알고리즘을 여러 번 실행하면 매번 다른 값을 생성할 수 있음 → 사용자 에이전트는 통상 출처를 한 번 계산해 이후 보안 검사에 재사용(매번 재계산하지 않음)
  2. uri-scheme = URI의 스킴 구성요소(소문자로 변환)
  3. 구현이 uri-scheme으로 주어진 프로토콜을 지원하지 않는 경우 → 새로운 전역적으로 고유한 식별자를 생성해 반환
  4. uri-scheme이 "file"인 경우 → 구현이 구현 정의 값을 반환 가능(MAY)
     - 참고: 역사적으로 file 스킴 콘텐츠에 과도한 특권이 부여됨 → 모든 로컬 파일에 넓은 특권을 부여하면 권한 상승 공격으로 이어질 수 있음. 로컬 파일에 디렉터리 기반 특권을 부여하는 접근 방식은 널리 채택되지 않음. 각 file URI에 전역적으로 고유한 식별자를 사용하는 방식이 가장 안전
  5. uri-host = URI의 호스트 구성요소(소문자로 변환, [RFC4790]의 i;ascii-casemap 대조 사용)
     - 참고: 사용자 에이전트가 URI 구성 시 IDNA 처리·검증을 수행한다고 가정 → uri-host는 LDH 레이블만 포함([RFC5890] 참조) → 출처 기반 보안 정책은 사용자 에이전트가 사용하는 IDNA 알고리즘에 민감(추가 논의: 섹션 8.4)
  6. URI에 포트 구성요소가 없으면 uri-port = uri-scheme 프로토콜의 기본 포트, 있으면 uri-port = URI의 포트 구성요소
  7. 트리플 (uri-scheme, uri-host, uri-port) 반환

### 5. 출처 비교

- 두 출처가 같다 ↔ 다음 중 해당 조건 충족
  - 둘 다 스킴/호스트/포트 트리플인 경우 → 스킴·호스트·포트가 모두 같은 경우에만 같음
  - 전역적으로 고유한 식별자인 출처는 스킴/호스트/포트 트리플인 출처와 같을 수 없음
- 두 URI는 출처가 같으면 동일 출처
  - 참고: URI가 반드시 자기 자신과 동일 출처인 것은 아님 → 예: data URI[RFC2397]는 서버 기반 이름 지정 권한을 사용하지 않아 전역적으로 고유한 식별자를 출처로 가짐 → 자기 자신과도 동일 출처가 아님

### 6. 출처 직렬화

- 출처를 유니코드[Unicode6] 문자열과 ASCII[RFC20] 문자열로 직렬화하는 방법 정의

#### 6.1. 출처의 유니코드 직렬화

- 알고리즘
  1. 출처가 스킴/호스트/포트 트리플이 아닌 경우 → 문자열 `null` 반환, 단계 중단
  2. result = 출처 트리플의 스킴 부분
  3. result에 `"://"` 추가
  4. 출처 트리플의 호스트 부분의 각 구성요소를 U+002E(".")로 구분해 result에 추가
     - 구성요소가 A-레이블인 경우 → 해당 U-레이블 사용([RFC5890], [RFC5891])
     - 그 외 → 구성요소를 그대로 사용
  5. 포트 부분이 스킴의 기본 포트와 다른 경우 → `:`와 포트를 10진수로 result에 추가
  6. result 반환

#### 6.2. 출처의 ASCII 직렬화

- 알고리즘
  1. 출처가 스킴/호스트/포트 트리플이 아닌 경우 → 문자열 `null` 반환, 단계 중단
  2. result = 출처 트리플의 스킴 부분
  3. result에 `"://"` 추가
  4. 출처 트리플의 호스트 부분을 result에 추가
  5. 포트 부분이 스킴의 기본 포트와 다른 경우 → `:`와 포트를 10진수로 result에 추가
  6. result 반환

### 7. HTTP Origin 헤더 필드

#### 7.1. 구문

```
origin              = "Origin:" OWS origin-list-or-null OWS
origin-list-or-null = %x6E %x75 %x6C %x6C / origin-list
origin-list         = serialized-origin *( SP serialized-origin )
serialized-origin   = scheme "://" host [ ":" port ]
                    ; <scheme>, <host>, <port> from RFC 3986
```

#### 7.2. 의미

- HTTP 요청에 포함될 때 Origin 헤더 필드는 사용자 에이전트가 요청을 발행하게 "원인이 된" 출처를 나타냄(요청을 트리거한 API가 정의)
- 예: 출처를 대신해 스크립트를 실행하는 사용자 에이전트 → 스크립트가 요청을 발행시키면 Origin 헤더로 당시 실행 중이던 보안 컨텍스트를 서버에 알릴 수 있음(MAY)
- 여러 출처가 하나의 요청 발행에 기여하는 경우 → Origin 헤더에 모든 출처를 나열 가능(MAY)
  - 예: 요청이 한 출처에서 처음 발행된 후 다른 출처로 리다이렉트된 경우 → 두 출처 모두 관여했음을 서버에 알릴 수 있음(MAY)

#### 7.3. 사용자 에이전트 요구사항

- 모든 HTTP 요청에 Origin 헤더 필드 포함 가능(MAY)
- 어떤 HTTP 요청에도 Origin 헤더 필드를 하나 이상 포함해서는 안 됨(MUST NOT)
- "개인정보에 민감한" 컨텍스트에서 요청 발행 시 → Origin 헤더 필드 값은 "null"이어야 함(MUST)
  - 참고: 이 문서는 개인정보에 민감한 컨텍스트의 개념을 정의하지 않음 → 요청을 생성하는 애플리케이션이 컨텍스트를 지정해 사용자 에이전트의 Origin 헤더 필드 생성 방식을 제한 가능
- Origin 헤더 필드 생성 시 요구사항(MUST)
  - 문법의 serialized-origin 생성 각각은 출처의 ASCII 직렬화여야 함(MUST)
  - 연속된 두 serialized-origin 생성은 동일할 수 없음 → 연속 생성이 필요한 경우 두 번째 것은 생성해서는 안 됨(MUST NOT)

### 8. 보안 고려사항

- 동일 출처 정책은 웹 브라우저를 포함한 다수 사용자 에이전트의 보안 초석 중 하나
- 역사적으로 오염 추적·유출 방지 등 다른 보안 모델도 시도되었으나 당시 구현이 어려웠음(최근 일부 아이디어를 되살리려는 관심 존재)
- 동일 출처 정책의 보안 평가는 어려움(출처 개념 자체가 보안 환경에서 매우 중심적인 역할) → 출처는 격리 단위에 불과하며 완전하지 않음, 아래에 체계적 약점 논의

#### 8.1. DNS에 대한 의존

- 실제로 동일 출처 정책은 보안을 위해 DNS에 의존(http 등 다수 URI 스킴이 DNS 기반 이름 지정 권한 사용)
  - DNS가 부분적으로/완전히 침해되면 → 동일 출처 정책이 애플리케이션이 요구하는 보안 속성을 제공하지 못할 수 있음
- 스킴별 DNS 침해 저항성 차이
  - https: 인증서 등 다른 메커니즘으로 콘텐츠의 출처를 확인 → DNS 침해에 더 강함
  - chrome-extension([CRX] 섹션 4.3): 공개 키 기반 이름 지정 권한 사용 → DNS 침해에 완전히 안전
- 웹 출처 개념은 서로 다른 URI 스킴에서 가져온 콘텐츠를 격리 → DNS 침해의 영향을 억제하는 데 필수

#### 8.2. 상이한 격리 단위

- 시간이 지나며 다수 기술이 편리한 격리 단위로서 웹 출처 개념에 수렴했으나, 쿠키[RFC6265] 등 오늘날 사용 중인 다수 기술은 현대의 웹 출처 개념보다 앞서 있음 → 다른 격리 단위를 가져 취약점으로 이어짐
- 대안: 정규화된 도메인 이름 대신 "레지스트리 제어" 도메인만 격리 단위로 사용(예: "www.example.com" 대신 "example.com") → 여러 이유로 권장하지 않음(NOT RECOMMENDED)
  1. "레지스트리 제어" 도메인 개념은 DNS 자체의 속성이 아니라 DNS를 둘러싼 인간의 관행의 산물 → 예: 일본의 많은 지자체가 DNS 계층 구조에서 상당히 깊은 곳에서 공개 레지스트리 운영. 널리 쓰이는 "공개 접미사 목록"도 최신 상태로 유지하기 어렵고 구현 간에 다름
  2. DNS 기반 이름 지정 권한을 사용하지 않는 URI 스킴과 호환되지 않음
     - 예: 공개 키를 이름 지정 권한으로 사용하는 URI 스킴 → "레지스트리 제어" 공개 키 개념이 다소 모순적
     - 예: nntp 등은 DNS와 반대 방향으로 점 구분 위임 사용(예: alt.usenet.kooks), 일부는 DNS를 사용하되 레이블을 일반 순서의 역순으로 제시(예: com.example.www)
- 결론: "레지스트리 제어" 도메인 사용은 최선의 경우에도 URI 스킴·구현에 특화된 것이며, 최악의 경우 스킴과 구현 간 차이가 취약점으로 이어질 수 있음

#### 8.3. 환경 권한

- 동일 출처 정책 사용 시 사용자 에이전트는 콘텐츠가 지정할 수 있는 객체가 아니라 URI를 기반으로 콘텐츠에 권한을 부여 → 지정과 권한의 이러한 분리는 환경 권한의 한 예 → 취약점으로 이어질 수 있음
- 예: HTML 문서의 크로스 사이트 스크립팅
  - 공격자가 문서에 스크립트 콘텐츠를 주입 가능하면 → 해당 스크립트는 문서 출처의 권한으로 실행되어 사용자의 의료 기록 같은 민감 정보에 접근 가능
  - 스크립트의 권한이 스크립트가 지정할 수 있는 객체로 제한된다면 → 공격자가 제3자 호스팅 문서에 스크립트를 주입해도 어떤 이점도 얻지 못함

#### 8.4. IDNA 의존성 및 마이그레이션

- 동일 출처 정책의 보안 속성은 사용자 에이전트가 사용하는 IDNA 알고리즘의 세부사항에 결정적으로 의존할 수 있음
  - IDNA2003[RFC3490] vs IDNA2008[RFC5890] → 일부 국제 도메인 이름(예: U+00DF 포함)이 서로 다른 ASCII 표현으로 매핑될 수 있음
- 하나의 IDNA 알고리즘에서 다른 알고리즘으로 마이그레이션하면 여러 보안 경계가 다시 그려질 수 있음
  - 새로운 보안 경계를 세울 수도 있고, 더 나쁘게는 서로 불신하는 두 엔티티 사이의 보안 경계를 허물 수도 있음 → 서로 불신하는 두 엔티티가 동일한 출처로 결합되면 한쪽이 다른 쪽을 공격할 수 있게 되어 위험

### 9. IANA 고려사항

- 영구 메시지 헤더 필드 레지스트리([RFC3864])가 다음 등록으로 업데이트됨
  - 헤더 필드 이름: Origin
  - 적용 프로토콜: http
  - 상태: standard
  - 저자/변경 관리자: IETF
  - 명세 문서: 이 명세(섹션 7)

## RFC 6797 - HTTP Strict Transport Security (HSTS)

> 발행일: 2012년 11월
> 상태: Standards Track

### Abstract

- 목적
  - 웹사이트가 보안 연결로만 접근 가능함을 선언 가능
  - 사용자가 자신의 사용자 에이전트에 특정 사이트와 보안 연결로만 상호작용하도록 지시 가능
- 이 전체 정책의 명칭: HTTP Strict Transport Security(HSTS)
- 정책 선언 수단: Strict-Transport-Security HTTP 응답 헤더 필드, 또는 사용자 에이전트 구성 등 다른 수단

### 1. 소개

- HTTP[RFC2616]는 다양한 전송(일반적으로 TCP) 위에서 사용 가능하나, TCP는 채널 무결성 보호·기밀성·안전한 호스트 식별을 제공하지 않음
  - → SSL[RFC6101]과 후속 TLS[RFC5246]가 채널 지향 보안 제공을 위해 개발(애플리케이션 프로토콜과 TCP 사이에 계층화)
  - [RFC2818]은 HTTP를 TLS 위에 계층화하는 방법과 "https" URI 스킴을 정의(실제로는 UA가 서버와의 협상·사용자 기본 설정 조합에 따라 TLS 또는 SSL3 사용)
- UA는 로컬 보안 정책을 다양하게 적용 → 호스트와 HTTP로 통신하는지 HTTP-over-Secure-Transport로 통신하는지에 따라 달라짐
  - 예: 쿠키[RFC6265]는 Secure로 플래그 지정 가능 → UA는 Secure 쿠키를 보안 전송으로만 전송해야 함(전송에 관계없이 반환되는 non-Secure 쿠키와 대조)
- UA는 통상 보안 연결 설정 문제(인증서 신뢰 체인 검증 실패·인증서 만료·도메인 이름 불일치 등, [RFC2818] 섹션 3.1 참조)를 사용자에게 알림
  - 사용자가 문제에도 계속 상호작용을 선택할 수 있게 하는 동작 = "클릭 통과"[GoodDhamijaEtAl05][SunshineEgelmanEtAl09] → "클릭 통과 불안정"으로 설명 가능
  - 주요 취약점: 사용자 세션 관리용 쿠키 누출 → 공격자가 쿠키 획득 후 사용자를 가장해 정상 리소스와 상호작용 가능
- Jackson과 Barth[ForceHTTPS]의 제안: 웹 리소스가 UA와의 모든 상호작용이 안전하게 수행되어야 하며 보안 전송 세션 설정 관련 문제는 치명적으로(직접적인 사용자 개입 없이) 처리되어야 함을 선언 가능하게 하는 접근 방식 → 목표: 클릭 통과 불안정 방지 및 기타 잠재적 위협 해결
- 이 규격은 [ForceHTTPS] 접근 방식을 구현·개선
  - 쿠키 대신 전용 HTTP 응답 헤더 필드로 정책을 UA에 전달
  - 웹 리소스의 호스트가 정책이 호스트 이름을 루트로 하는 전체 도메인 이름 하위 트리에 적용됨을 선언 가능(HSTS가 서브도메인의 "도메인 쿠키" 보호에 적용)
  - [JacksonBarth2008]의 "전체 호스트" 기반 정책 적용 개념 통합: 발행 호스트의 모든 TCP 포트에서 HTTP(만)에 적용
- 이 규격이 정의하는 정책은 "The Web Origin Concept"[RFC6454]의 "동일 출처 정책"과 명확히 다름(차이점은 부록 B에 요약)

#### 1.1. 이 규격의 구성

- 섹션 2: HSTS 사용 사례·정책 효과·위협 모델·요구사항 개요
- 섹션 3: 적합성 요구사항
- 섹션 4: 관련 용어
- 섹션 5~15: HSTS 메커니즘 자체의 공식 명세

#### 1.2. 문서 규약

- 참고: 독자가 명시적으로 염두에 두거나 고려해야 할 사항을 표시하는 노트

### 2. 개요

- 사용 사례를 논의하고, HSTS 정책을 요약하며, 위협 모델·대응되지 않는 위협·파생 요구사항을 논의

#### 2.1. 사용 사례

- 웹 브라우저 사용자: 다양한 웹사이트(일부는 임의적, 일부는 알려진)와 안전한 방식으로 상호작용하기를 원함
- 웹사이트 배포자: 자신과 사용자의 이익을 위해 명시적으로 안전한 방식으로 사이트를 제공하기를 원함

#### 2.2. HTTP Strict Transport Security 정책 효과

- 적합 UA가 HSTS 정책을 적용하는 호스트(HSTS 호스트)와 상호작용할 때
  1. UA는 HSTS 호스트에 대한 비보안 URI 참조를 역참조하기 전에 보안 URI 참조로 변환
  2. UA는 모든 보안 전송 오류·경고에 대해 보안 전송 연결 시도를 종료

#### 2.3. 위협 모델

- 대응 대상: 수동적 네트워크 공격자·능동적 네트워크 공격자·불완전한 웹 개발자
- 명시적으로 미대응 대상: 피싱·악성 소프트웨어
- 세부사항·관련 인용: [ForceHTTPS] 섹션 2 참조

##### 2.3.1. 대응되는 위협

###### 2.3.1.1. 수동적 네트워크 공격자

- 로컬 무선 네트워크(802.11 등)에서 근처 공격자가 로컬 네트워크 자체의 보안 여부와 무관하게 암호화되지 않은 연결을 도청 가능[BeckTews09]
  - 무료 무선 스니핑 도구(예: [Aircrack-ng])는 로컬 네트워크가 안전하게 운영되더라도 수동적 도청 공격을 가능하게 함
  - 도청으로 세션 식별자·인증 쿠키를 탈취해 사용자 세션을 하이재킹 가능[ForceHTTPS]
  - 예: Firesheep(브라우저 확장)[Firesheep] 같은 널리 사용되는 도구로 다른 사용자의 세션 쿠키 획득 가능
- 완화 시도: 종단 간 보안 전송 지원("https" 스킴[RFC2818] 등)이나 강제는 아님
  - 세션 식별자가 비보안 전송 서비스와의 상호운용을 위해 non-Secure 쿠키에 저장되는 경우가 많아 실제 배포에서는 보호되지 않는 경우가 흔함("Secure 쿠키" = "Secure" 속성[RFC6265]을 포함하는 쿠키)
  - 예: 이메일 서비스의 세션 식별자가 non-Secure 쿠키에 저장된 경우, 단일 비보안 HTTP 요청만으로도 공격자가 세션을 하이재킹 가능

###### 2.3.1.2. 능동적 네트워크 공격자

- 공격 수단: DNS 서버 가장, 무선 네트워크 프레임 스푸핑, 유사 이름의 악성 쌍둥이 액세스 포인트, 기본 암호를 이용한 무선 홈 라우터 재구성 등
- 은행 등 일부 사이트는 종단 간 보안 전송으로 능동적 공격자를 방어하나, 자체 서명 인증서(CA 인증서를 사용자 브라우저에 미배포) 등으로 보안 전송을 잘못 배포한 사이트에서는 브라우저가 사용자에게 이러한 보호를 쉽게 선택 해제하게 함

###### 2.3.1.3. 웹사이트 개발 및 배포 버그

- 균일하게 보안된 사이트(모든 콘텐츠가 "https" URI로 구체화)도 단순 실수(비보안 연결로 CSS나 SWF 영화를 로딩하는 등)를 악용하는 능동적 공격자에 의해 보안이 완전히 손상 가능
  - CSS와 SWF 영화는 모두 임베딩 페이지를 스크립팅 가능, 일부 브라우저는 비보안 연결로 SWF가 임베드될 때 "혼합 콘텐츠 경고"를 발행하지 않음
  - 로그인 페이지에서 "혼합 콘텐츠"를 주의 깊게 검토해도, 사이트 전체 어디서든 단 하나의 비보안 임베딩만 있으면 공격자가 다른 비보안 페이지에 코드를 주입해 로그인 페이지를 스크립팅(제어)할 수 있어 로그인 페이지의 보안까지 손상
- 참고: 여기서의 "혼합 콘텐츠"([W3C.REC-wsc-ui-20100812] 섹션 5.3도 참조)는 이 규격의 "혼합 보안 컨텍스트" 개념을 지칭 → XML·HTML 같은 마크업 언어 컨텍스트에서 사용되는 동일 용어와 혼동 주의

##### 2.3.2. 대응되지 않는 위협

###### 2.3.2.1. 피싱

- 공격자가 실제 사이트와 다른 도메인에 가짜 사이트를 호스팅해 인증 자격 증명을 요청(이메일 링크 등으로 트래픽 유도)
- 사용자가 실제 사이트와 가짜 사이트를 구별하기 어려워 매우 효과적일 수 있음
- HSTS는 그 자체로 피싱에 대한 방어는 아님 → 세션 무결성과 장기 인증 토큰을 보호하도록 브라우저에 지시함으로써 기존 피싱 방어를 보완 [ForceHTTPS]

###### 2.3.2.2. 악성 소프트웨어 및 브라우저 취약점

- HSTS는 브라우저 보안 메커니즘으로 구현 → 세션 보호가 사용자 시스템의 신뢰성에 의존
- 사용자 시스템에서 실행되는 악성 코드는 HSTS 사용 여부와 무관하게 브라우저 세션을 손상시킬 수 있음

#### 2.4. 요구사항

- 사용 사례·위협에서 파생된 요구사항을 식별·열거 → HSTS가 해결하는 상세 핵심 요구사항, 직접 해결되지는 않는 부수적 요구사항으로 구분

##### 2.4.1. 전체 요구사항

- 웹 브라우저 사용자와 웹사이트 배포자를 위해 수동적·능동적 네트워크 공격자, 웹사이트 개발·배포 버그, 불안전한 사용자 행동에서 파생되는 위험 최소화

###### 2.4.1.1. 상세 핵심 요구사항

- 전체 요구사항에서 파생되며 이 규격이 해결하는 핵심 요구사항
  1. 웹사이트는 UA에 엄격한 보안 정책 사용 접근을 요구함을 선언 가능해야 함
  2. 웹사이트는 비보안으로 연락한 UA에 보안으로 다시 접속하도록 지시 가능해야 함
  3. UA는 엄격한 보안 정책 활성화 신호를 보낸 웹사이트에 대한 영구 데이터를 웹사이트가 선언한 시간 범위 동안 유지해야 함 + 웹사이트가 정보를 업데이트할 수 있도록 "가장 신선한" 정책 정보를 캐시해야 함
  4. UA는 정책이 활성화된 웹사이트에 대한 모든 비보안 "http" URI 로드를 "https" 보안 스킴으로 다시 작성해야 함
  5. 웹사이트 관리자는 엄격한 보안 정책이 활성화된 상위 도메인의 서브도메인에도 정책 적용을 신호할 수 있어야 하며, UA는 해당 정책을 시행해야 함
     - 예: example.com과 foo.example.com 모두 bar.foo.example.com에 대한 정책 설정 가능
  6. UA는 엄격한 보안 정책이 활성화된 도메인이 피어 도메인·상위 도메인에 대한 정책 적용을 신호하는 것을 허용해서는 안 됨
     - 예: bar.foo.example.com이나 foo.example.com 모두 example.com에 대한 정책 설정 불가, bar.foo.example.com도 foo.example.com에 대한 정책 설정 불가, foo.example.com도 sibling.example.com에 대한 정책 설정 불가
  7. UA는 사용자가 보안 경고를 "클릭 통과"하는 것을 방지해야 함(보안 전송 예외에 직면해 연결 시도를 중단하는 것은 허용). 섹션 12.1("사용자 회피 불가") 참조
     - 참고: 위 첫 번째 핵심 요구사항을 균일하게 안전하게 충족하는 수단은 이 규격이 구체적으로 다루지 않음(섹션 14.6("부트스트랩 MITM 취약점") 참조) → 향후 개정판이나 다른 규격에서 다룰 수 있음. UA 구현이 첫 번째 핵심 요구사항을 더 완전히 충족할 수 있는 수단도 있음(섹션 12("사용자 에이전트 구현 조언") 참조)

###### 2.4.1.2. 상세 부수적 요구사항

- 전체 요구사항에서 파생되나 이 규격에서 규범적으로 다루지는 않는 요구사항(UA 구현자 재량으로 충족 가능하나 복잡할 수 있음)
  1. "혼합 보안 컨텍스트" 로드 금지(섹션 2.3.1.3 참조)
  2. 사이트가 HSTS 정책을 신호하는지 여부와 무관하게, 사용자가 엄격한 보안 정책이 활성화된 웹사이트를 선언하는 것을 용이하게 함

### 3. 적합성 기준

- 이 규격은 호스트와 사용자 에이전트를 위해 작성됨
- 적합 호스트: 호스트에 적용 가능한 이 규격의 모든 요구사항 구현
- 적합 사용자 에이전트: 사용자 에이전트에 적용 가능한 이 규격의 모든 요구사항 구현
- MUST/MUST NOT/REQUIRED/SHALL/SHALL NOT/SHOULD/SHOULD NOT/RECOMMENDED/MAY/OPTIONAL → [RFC2119]에 설명된 대로 해석

### 4. 용어

- ASCII 대소문자 구분 없는 비교: 두 문자열을 코드포인트별로 정확히 비교 + U+0041~U+005A(라틴 대문자 A~Z)와 U+0061~U+007A(라틴 소문자 a~z)의 해당 문자도 일치로 간주([Unicode] 참조)
- 코드포인트: Code Point의 축약, 유니코드 코드스페이스의 모든 값(0~10FFFF 16진수의 정수 범위)[Unicode]
- 도메인 이름: "DNS 이름"으로도 지칭, [RFC1035]에서 점으로 구분된 레이블 시퀀스로 표현되도록 정의(예: "example.com", "yet.another.example.org"). [RFC3986] 부록 A의 reg-name 프로덕션, [RFC2616] 섹션 14.23 Host 헤더 필드의 host 컴포넌트에 해당
  - 참고: 실제 URI 인스턴스에 나타나는 도메인 이름은 완전한 정규화된 도메인 이름일 수도 있고 아닐 수도 있음
- 도메인 이름 레이블: 도메인 이름에서 "점 사이에" 나타나는 부분(예: "foo.example.com"의 "foo"·"example"·"com")
- 유효 요청 URI: HTTP 호스트가 수신하는 모든 요청에 대해 대상 리소스를 식별하기 위해 추론 가능한 URI(요청이 완전한 절대 URI를 포함하지 않는 경우가 많아 추론이 필요). 섹션 9("유효 요청 URI 구성") 참조
- HTTP Strict Transport Security: 이 규격이 정의하는 결합된 UA·서버 측 보안 정책의 전체 이름
- HTTP Strict Transport Security 호스트: HSTS 정책의 HTTP 서버 측면을 구현하는 적합 호스트 → 보안 전송으로 전송된 응답에 "Strict-Transport-Security" 헤더 필드 반환을 의미
- HTTP Strict Transport Security 정책: 이 규격에 정의된 동작의 결합된 UA·서버 측 패싯의 이름
- HSTS: HTTP Strict Transport Security 참조
- HSTS 호스트: HTTP Strict Transport Security 호스트 참조
- HSTS 정책: HTTP Strict Transport Security 정책 참조
- 알려진 HSTS 호스트: UA가 HSTS 정책 적용 중으로 기록한 HSTS 호스트. 섹션 8.1.1("HSTS 호스트 기록 - 저장 모델") 참조
- 로컬 정책: 배포자가 지정하는 정책 규칙(주로 구성 설정으로 나타남)
- MITM: "man in the middle"의 약어. [RFC4949]의 "man-in-the-middle attack" 참조
- 요청 URI: UA가 HTTP 요청 메시지를 발행하는 데 사용하는 URI. "유효 요청 URI"도 참조
- UA: "user agent"의 약어, 이 규격의 목적상 통상 사용자가 능동적으로 조작하는 HTTP 클라이언트 애플리케이션[RFC2616]
- 알려지지 않은 HSTS 호스트: 사용자 에이전트가 기록하지 않은 HSTS 호스트

### 5. HSTS 메커니즘 개요

- HSTS 호스트가 자신의 정책을 UA에 전달하는 메커니즘과 UA가 수신 정책을 처리하는 방법의 개요(세부사항: 섹션 6~15)

#### 5.1. HSTS 호스트 선언

- HTTP 호스트는 보안 전송(TLS 등)으로 Strict-Transport-Security 헤더 필드를 발행함으로써 자신을 HSTS 호스트로 선언
- 적합 UA가 이 헤더를 오류 없이 수신·처리하면 → 해당 호스트를 알려진 HSTS 호스트로 간주

#### 5.2. HSTS 정책

- HSTS 정책은 UA가 알려진 HSTS 호스트와 보안 전송으로만 통신하도록 지시 + 정책 유지 기간 지정
- HSTS 정책이 없었다면 UA를 비보안으로 통신하게 했을 URI 참조·사용자 입력(위치 표시줄 등)·기타 정보의 UA 처리를 명시적으로 재정의
- 선택적 지시문 includeSubDomains: 정책이 호스트의 도메인 이름의 모든 서브도메인에도 적용됨을 지정 가능

#### 5.3. 사용자 에이전트에 의한 HSTS 정책 저장 및 유지 관리

- UA는 발행 HSTS 호스트의 도메인 이름에 엄격히 기반해 HSTS 정책을 저장·인덱싱
- 주어진 HSTS 호스트의 정책은 도메인 이름이 슈퍼도메인/서브도메인인 다른 HSTS 호스트의 정책과 별도로 유지
  - 정책 업데이트·삭제는 해당 HSTS 호스트만 가능(새 max-age·서브도메인 적용 가능성 값을 담은 헤더 필드를 UA에 재전송해 달성)
  - UA는 사실상 "가장 신선한" 정책 정보를 캐시
  - max-age=0 지정 시 → UA에 해당 호스트의 HSTS 정책(주장된 includeSubDomains 지시문 포함) 삭제를 신호
  - 세부사항: 섹션 8.1("Strict-Transport-Security 응답 헤더 필드 처리"), 예시: 섹션 6.2

#### 5.4. 사용자 에이전트 HSTS 정책 시행

- 주어진 호스트에 대한 HTTP 연결 설정 시(어떻게 촉발되었든) UA는 알려진 HSTS 호스트 캐시에서 해당 호스트의 도메인 이름의 슈퍼도메인을 가진 항목이 있는지 확인
  - 발견되고 그 중 includeSubDomains 지시문이 주장된 것이 있으면 → HSTS 정책 적용
  - 그렇지 않으면 해당 호스트 자체가 UA에 HSTS 호스트로 알려진 경우에만 → HSTS 정책 적용
  - 세부사항: 섹션 8.3("URI 로딩 및 포트 매핑")

### 6. 구문

- Strict-Transport-Security HTTP 응답 헤더 필드와 지시문의 구문 정의 + 예시(섹션 7: 서버 처리 모델, 섹션 8: UA 처리 모델)

#### 6.1. Strict-Transport-Security HTTP 응답 헤더 필드

- STS 헤더 필드는 이 헤더 필드를 포함하는 응답을 발행하는 호스트에 대해 UA가 HSTS 정책을 시행해야(MUST) 함을 나타냄
- STS 헤더 필드의 ABNF 구문은 [RFC2616] 섹션 2의 Generic Grammar에 기반("암시적 선형 공백"·"암시적 *LWS" 개념 포함)

```
Strict-Transport-Security = "Strict-Transport-Security" ":"
                            [ directive ]  *( ";" [ directive ] )

directive                 = directive-name [ "=" directive-value ]
directive-name            = token
directive-value           = token | quoted-string
```

```
token          = <token, [RFC2616], 섹션 2.2에 정의됨>
quoted-string  = <quoted-string, [RFC2616], 섹션 2.2에 정의됨>
```

- 지시문에 대한 전체 요구사항
  1. 지시문 출현 순서는 중요하지 않음
  2. 모든 지시문은 STS 헤더 필드에 한 번만 나타나야(MUST) 함(정의에 따라 선택 사항이거나 필수)
  3. 지시문 이름은 대소문자를 구분하지 않음
  4. UA는 이 규격의 구문을 따르지 않는 지시문·헤더 필드 값 데이터를 포함하는 모든 STS 헤더 필드를 무시해야(MUST) 함
  5. STS 헤더 필드에 UA가 인식하지 못하는 지시문이 포함된 경우 → 인식되지 않은 지시문은 무시해야(MUST) 하며, 나머지 요구사항(1~4)을 충족하는 경우 인식된 지시문은 처리해야(MUST) 함
- STS 헤더 필드의 의미적 기능을 확장하는 추가 지시문은 다른 규격에서 정의 가능(그 경우 IETF Review[RFC5226] 정책의 IANA 레지스트리 정의 필요)
  - 참고: 그러한 미래 지시문은 이 규격만 구현하는 UA뿐 아니라 비적합 UA에도 무시됨(추가 논의: 섹션 14.2("비적합 사용자 에이전트 영향"))

##### 6.1.1. max-age 지시문

- 필수(REQUIRED) "max-age" 지시문: STS 헤더 필드 수신 후 UA가 호스트를 알려진 HSTS 호스트로 간주하는 시간(초)을 지정. 섹션 8.1.1도 참조. delta-seconds 프로덕션은 [RFC2616]에 지정

```
max-age-value = delta-seconds

delta-seconds = <1*DIGIT, [RFC2616], 섹션 3.3.2에 정의됨>
```

- 참고: max-age=0("max-age=0")은 UA에 해당 호스트를 알려진 HSTS 호스트로 간주하는 것을 중단하도록 신호(주장된 includeSubDomains 지시문 포함). 섹션 8.1도 참조

##### 6.1.2. includeSubDomains 지시문

- 선택적(OPTIONAL) "includeSubDomains" 지시문: 값이 없는 지시문
- 존재("주장")하는 경우 → HSTS 정책이 해당 HSTS 호스트뿐 아니라 호스트의 도메인 이름의 모든 서브도메인에도 적용됨을 UA에 신호

#### 6.2. 예제

- HSTS 정책이 1년(약 31536000초) 동안 유효, 발행 HSTS 호스트의 도메인에만 적용

```
Strict-Transport-Security: max-age=31536000
```

- HSTS 정책이 약 6개월 동안 유효, 발행 HSTS 호스트의 도메인과 모든 서브도메인에 적용

```
Strict-Transport-Security: max-age=15768000 ; includeSubDomains
```

- max-age 지시문 값은 선택적으로 따옴표로 묶을 수 있음

```
Strict-Transport-Security: max-age="31536000"
```

- UA가 헤더 필드를 보낸 HSTS 호스트와 연관된 전체 HSTS 정책을 삭제해야 함을 나타냄

```
Strict-Transport-Security: max-age=0
```

- max-age가 0일 때 includeSubDomains 지시문의 존재는 무시되므로 바로 위와 정확히 같은 효과

```
Strict-Transport-Security: max-age=0; includeSubDomains
```

### 7. 서버 처리 모델

- HSTS 호스트가 구현하는 처리 모델은 두 패싯으로 구성
  - 보안 전송(TLS[RFC5246] 또는 SSL[RFC6101], 섹션 14.1도 참조)으로 수신된 요청의 처리 규칙
  - TCP 등 비보안 전송으로 수신된 요청의 처리 규칙

#### 7.1. HTTP-over-Secure-Transport 요청 유형

- 보안 전송으로 전달된 요청에 응답 시, HSTS 호스트는 섹션 6.1의 문법을 충족해야(MUST) 하는 STS 헤더 필드를 응답 메시지에 포함해야(SHOULD) 함
  - 포함하는 경우 STS 헤더 필드는 하나만 포함해야(MUST) 함
- 주어진 UA 컨텍스트에서 주어진 호스트를 알려진 HSTS 호스트로 설정하는 방법
  - 최소 하나의 유효한 STS 헤더 필드를 UA에 올바르게 반환(MAY)
  - 또는 클라이언트 측 사전 로드된 알려진 HSTS 호스트 목록 등 다른 메커니즘(MAY, 섹션 12 참조)
  - 참고: "MUST"가 아니라 "SHOULD"인 이유 = 다양한 서버·네트워크 측 캐시와 로드 밸런싱 구성에서 STS 헤더 필드를 균일하게 발행하기 어려울 수 있기 때문

#### 7.2. HTTP 요청 유형

- HSTS 호스트가 비보안 전송으로 HTTP 요청을 수신하는 경우
  - 영구 리다이렉트를 나타내는 상태 코드(예: 301[RFC2616] 섹션 10.3.2)를 포함하는 응답 메시지를 보내야(SHOULD) 함
  - Location 헤더 필드 값: 원래 유효 요청 URI(섹션 9)의 스킴을 "https"로 필요에 따라 변경한 URI, 또는 "https" 스킴을 가진 로컬 정책에 따라 생성된 URI
  - 참고: 위 동작이 "MUST"가 아니라 "SHOULD"인 이유
    - 서버 측 비보안-보안 리다이렉트의 위험[OWASP-TLSGuide]
    - 사이트 배포 특성 → 예: 타사 구성요소를 통합하는 사이트는 서버 측 비보안-보안 리다이렉트 시 오동작할 수 있으나 보안 전송으로 균일하게 접근될 때는 정상 동작(이미 사이트를 알려진 HSTS 호스트로 기록한 HSTS 지원 UA의 경우가 이에 해당)
- HSTS 호스트는 비보안 전송으로 전달된 응답에 STS 헤더 필드를 포함해서는 안 됨(MUST NOT)

### 8. 사용자 에이전트 처리 모델

- UA에 대한 HSTS 처리 모델은 다음 하위 섹션에 열거된 여러 패싯으로 구성
- 가정: UA가 IDNA2008[RFC5890] 또는 IDNA2003[RFC3490]을 구현(섹션 13 참조) + 이 규격의 컨텍스트에서 조작되는 모든 도메인 이름이 이 섹션의 처리 전 섹션 10("도메인 이름 IDNA 정규화")에 설명된 대로 이미 IDNA 정규화됨
  - 참고: [RFC3490]은 가까운 미래에도 실제 배포와의 지속적 관련성으로 인해 참조됨
- 위 가정은 처리 전 도메인 이름에 대한 적절한 IDNA·유니코드 검증과 문자 목록 테스트가 IDNA 정규화와 함께 수행되었음을 구체적으로 가정함을 의미(근거·세부사항: 섹션 14.10의 IDNA 관련 보안 고려사항)

#### 8.1. Strict-Transport-Security 응답 헤더 필드 처리

- 보안 전송으로 수신된 HTTP 응답이 섹션 6.1의 문법을 따르는 STS 헤더 필드를 포함하고 기반 보안 전송 오류·경고가 없는 경우(섹션 8.4 참조) → UA는 다음 중 하나를 반드시(MUST) 수행
  - 호스트가 아직 알려진 HSTS 호스트로 기록되지 않은 경우 알려진 HSTS 호스트로 기록(섹션 8.1.1 참조)
  - 또는 max-age·includeSubDomains 값 중 하나 또는 둘 다 UA가 이미 유지하는 것과 다른 정보를 전달하는 경우 알려진 HSTS 호스트에 대한 UA의 캐시 정보 업데이트
    - max-age 값은 본질적으로 STS 헤더 필드 수신 시간에 상대적인 "수명" 값
    - max-age 값이 0인 경우 → UA는 호스트가 알려진 경우 캐시된 정책 정보(주장된 includeSubDomains 지시문 포함)를 제거해야(MUST) 하며, 아직 알려지지 않은 경우 이 호스트를 기록해서는 안 됨(MUST NOT)
    - UA가 보안 전송 응답에서 둘 이상의 STS 헤더 필드를 수신하는 경우 → 첫 번째 헤더 필드만 처리해야(MUST) 함
  - 그렇지 않으면
    - 응답이 비보안 전송으로 수신된 경우 → 존재하는 모든 STS 헤더 필드를 무시해야(MUST) 함
    - 섹션 6.1의 문법을 따르지 않는 모든 STS 헤더 필드를 무시해야(MUST) 함

##### 8.1.1. HSTS 호스트 기록 - 저장 모델

- Request-URI(호스트가 응답한 메시지의)의 host 프로덕션과 일치하는 부분 문자열이 [RFC3986] 섹션 3.2.2의 IP-literal 또는 IPv4address 프로덕션과 구문적으로 일치하는 경우 → UA는 이 호스트를 알려진 HSTS 호스트로 기록해서는 안 됨(MUST NOT)
- 그렇지 않으면, 부분 문자열이 섹션 8.2의 매칭 절차에 따라 알려진 HSTS 호스트의 도메인 이름과 합동으로 일치하지 않는 경우 → UA는 이 호스트를 알려진 HSTS 호스트로 기록해야(MUST) 함
  - 도메인 이름 캐싱 + 주어진 max-age 값에 따른 만료 시간 기록 + includeSubDomains 지시문 주장 여부 기록. 섹션 11.2("HSTS 정책 만료 시간 고려사항") 참조
- UA는 슈퍼도메인 일치된 알려진 HSTS 호스트의 만료 시간·includeSubDomains 지시문을 수정해서는 안 됨(MUST NOT)
- 알려진 HSTS 호스트는 캐시 항목의 만료 날짜가 과거인 경우 "만료"된 것 → UA는 만료된 알려진 HSTS 호스트가 캐시에 존재하면 어느 때든 모두 제거해야(MUST) 함

#### 8.2. 알려진 HSTS 호스트 도메인 이름 매칭

- 주어진 도메인 이름은 알려진 HSTS 호스트의 도메인 이름과 합동 일치·슈퍼도메인 일치 중 하나 또는 둘 다로 일치 가능, 또는 일치가 없을 수 있음
- 판정 절차: UA의 만료되지 않은 각 알려진 HSTS 호스트의 도메인 이름과 비교(가장 오른쪽 레이블부터 오른쪽에서 왼쪽으로, ASCII 대소문자 구분 없는 비교로 레이블별 비교. [RFC5890] 섹션 2.3.2.4도 참조)
  - 슈퍼도메인 일치: 전체 알려진 HSTS 호스트의 도메인 이름과 주어진 도메인 이름의 오른쪽 부분 사이 레이블별 일치가 발견되면 성립(주어진 도메인 이름에 대해 여러 개 가능)
    - 예: 주어진 도메인 이름 `qaz.bar.foo.example.com` → 슈퍼도메인 일치된 알려진 HSTS 호스트 도메인 이름: `bar.foo.example.com`, `foo.example.com`
  - 합동 일치: 알려진 HSTS 호스트의 도메인 이름과 주어진 도메인 이름 사이 레이블별 일치가 발견되면(비교할 추가 레이블 없음) 성립
    - 예: 주어진 도메인 이름 `foo.example.com` → 합동 일치된 알려진 HSTS 호스트 도메인 이름: `foo.example.com`
  - 그렇지 않으면 일치가 발견되지 않으면 → 주어진 도메인 이름은 알려진 HSTS 호스트를 나타내지 않음

#### 8.3. URI 로딩 및 포트 매핑

- UA가 모든 "http" URI[RFC3986](HTTP 리다이렉트[RFC2616] 포함)를 "로드"(역참조)하려 준비할 때마다, 먼저 도메인 이름이 URI에 주어져 있는지와 알려진 HSTS 호스트와 일치하는지 다음 단계로 결정해야(MUST) 함
  1. URI의 authority 컴포넌트의 host 컴포넌트로 설명되는 모든 부분 문자열 추출
  2. 부분 문자열이 null이면 → 알려진 HSTS 호스트와 일치하지 않음
  3. 그렇지 않고 부분 문자열이 [RFC3986] 섹션 3.2.2의 IP-literal 또는 IPv4address 프로덕션과 구문적으로 일치하면 → 알려진 HSTS 호스트와 일치하지 않음
  4. 그렇지 않으면, 부분 문자열은 주어진 도메인 이름이며 섹션 8.2의 절차로 UA의 알려진 HSTS 호스트와 매칭되어야(MUST) 함
  5. 매칭 결과가 다음 중 하나인 경우 → 로드를 진행하기 전에 아래 처리
     - 주장된 includeSubDomains 지시문을 가진 슈퍼도메인 일치가 발견됨
     - 또는 주장된 includeSubDomains 지시문을 가진 슈퍼도메인 일치가 발견되지 않았으나 합동 일치가 발견됨(주장된 includeSubDomains 지시문 유무 무관)
     - → UA는 URI 스킴을 "https"[RFC2818]로 교체해야(MUST) 함
     - → URI에 "80"의 명시적 포트 컴포넌트가 포함된 경우 → UA는 포트 컴포넌트를 "443"으로 변환해야(MUST) 함
     - → URI에 "80"과 같지 않은 명시적 포트 컴포넌트가 포함된 경우 → 포트 컴포넌트 값은 유지되어야(MUST) 함
     - → URI에 명시적 포트 컴포넌트가 포함되지 않은 경우 → UA는 추가해서는 안 됨(MUST NOT)
     - 참고: 이 단계는 HSTS 정책이 HSTS 호스트의 모든 TCP 포트에서 HTTP에 적용되도록 보장
- 참고: 명시적 포트가 제공된 경우(어느 정도는 서브도메인의 경우도) 실제로 지정된 포트에서 HTTP(비보안) 서버가 실행 중이어 HTTPS 요청이 실패할 가능성이 합리적으로 높음(부록 A("설계 결정 노트") 항목 6 참조)

#### 8.4. 보안 전송 설정 오류

- 알려진 HSTS 호스트에 연결할 때 기반 보안 전송과의 오류가 있으면("경고"·"치명적"·기타 오류 수준 무관) → UA는 연결을 종료해야(MUST) 함(섹션 12("사용자 에이전트 구현 조언")도 참조)
  - 포함 예: 인증서 유효성 검사 오류(인증서 해지 목록(CRL)[RFC5280] 또는 온라인 인증서 상태 프로토콜(OCSP)[RFC2560] 경유), TLS 서버 신원 확인[RFC6125] 오류

#### 8.5. HTTP-Equiv <Meta> 요소 속성

- UA는 수신된 콘텐츠의 `<meta>` 요소[W3C.REC-html401-19991224]에 대한 `http-equiv="Strict-Transport-Security"` 속성 설정에 주의를 기울여서는 안 됨(MUST NOT)

#### 8.6. 누락된 Strict-Transport-Security 응답 헤더 필드

- UA가 보안 채널로 알려진 HSTS 호스트로부터 HTTP 응답을 수신하나 응답에 STS 헤더 필드가 누락된 경우 → UA는 해당 알려진 HSTS 호스트에 대한 지식의 max-age 값에 도달할 때까지 호스트를 알려진 HSTS 호스트로 계속 처리해야(MUST) 함
  - max-age 값은 주어진 알려진 HSTS 호스트에 대해 효과적으로 무한할 수 있음
  - 예: 알려진 HSTS 호스트가 목록 항목이 "만료되지" 않도록 구현된 사전 구성된 목록의 일부인 경우
